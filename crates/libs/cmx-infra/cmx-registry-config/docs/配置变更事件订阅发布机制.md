# 配置变更事件订阅发布机制

> `cmx-registry-config` 模块的配置变更事件订阅/发布（Pub/Sub）机制完整说明。

---

## 一、概述

当配置中心（如 Nacos）发生配置变更时，需要将变更通知分发给应用内的多个业务模块。`cmx-registry-config` 提供了一套**两层 Pub/Sub 机制**：

| 层级 | 抽象 | 用途 |
|------|------|------|
| **传输层** | `ConfigChangeCallback`（`Fn(&str)`） | 配置中心 SDK 适配器与全局通知器之间的桥接 |
| **应用层** | `ConfigChangeListener`（trait） | 业务模块接收结构化的配置变更事件 |

这种设计将**原始字符串回调**（传输层细节）与**结构化事件**（应用层语义）解耦，既能向后兼容老的使用方式，又为新业务模块提供类型安全的事件分发能力。

---

## 二、核心组件

### 2.1 `ConfigChangeCallback` —— 原始字符串回调

```rust
pub type ConfigChangeCallback = Arc<dyn Fn(&str) + Send + Sync>;
```

最底层的回调形式，接收配置中心的原始 TOML 字符串。用于：
- 适配 `nacos-sdk` 的 `ConfigChangeListener` 接口
- 兼容已有业务代码

### 2.2 `ConfigChangeEvent` —— 结构化变更事件

```rust
pub struct ConfigChangeEvent {
    /// 变更的配置键列表
    pub changed_keys: Vec<String>,
    /// 新的配置内容（原始 TOML 字符串）
    pub raw_content: String,
}
```

提供结构化的变更信息。`changed_keys` 由 `ConfigReloader` 在解析新配置后计算得出，业务模块可基于此做**增量更新**而非全量重载。

### 2.3 `ConfigChangeListener` —— 结构化监听器 trait

```rust
pub trait ConfigChangeListener: Send + Sync {
    fn name(&self) -> &str;
    fn interested_keys(&self) -> &[String] { &[] }  // 空切片 = 监听所有
    fn on_change(&self, event: &ConfigChangeEvent);
}
```

业务模块通过实现该 trait 来订阅配置变更：

| 方法 | 必填 | 作用 |
|------|------|------|
| `name()` | 是 | 监听器标识，用于日志 |
| `interested_keys()` | 否 | 感兴趣的配置键前缀；空切片表示监听所有变更 |
| `on_change()` | 是 | 实际处理变更的回调 |

### 2.4 `ChangeNotifier` —— 通知器实例

非全局的普通通知器实例，内部维护两个并发安全的容器：

```rust
pub struct ChangeNotifier {
    handlers: RwLock<HashMap<String, ConfigChangeCallback>>,  // 原始字符串回调
    listeners: RwLock<Vec<Arc<dyn ConfigChangeListener>>>,   // 结构化监听器
}
```

每个回调在执行时被 `std::panic::catch_unwind` 包裹，**单个处理器 panic 不会影响其他处理器**。

### 2.5 `GlobalChangeNotifier` —— 全局单例门面

通过 `OnceLock<RwLock<Option<ChangeNotifier>>>` 提供线程安全的全局访问：

```rust
pub struct GlobalChangeNotifier;
```

提供以下静态方法（详细 API 见后文）：

| 方法 | 作用 |
|------|------|
| `initialize()` | 初始化全局实例（幂等） |
| `register(key, callback)` | 注册原始字符串回调 |
| `add_listener(listener)` | 注册结构化监听器 |
| `notify(content)` | 触发所有原始字符串回调 |
| `notify_listeners(event)` | 触发所有结构化监听器 |

### 2.6 `ConfigReloader` —— 配置重载器

可选的内置业务监听器，订阅配置变更并自动应用：

1. 解析新 TOML 内容
2. 与本地配置文件 + 环境变量合并
3. 调用 `ConfigManager::reload()` 原子替换全局配置
4. 计算 diff（`changed_keys`）供上层通知

## 三、API 详解

### 3.1 初始化（应用启动时调用一次）

```rust
use cmx_registry_config::GlobalChangeNotifier;

GlobalChangeNotifier::initialize();
```

幂等操作，重复调用会被忽略并打印 warning。

### 3.2 注册原始字符串回调

```rust
use std::sync::Arc;
use cmx_registry_config::GlobalChangeNotifier;

GlobalChangeNotifier::register("my-handler", Arc::new(|content: &str| {
    info!("收到配置变更，长度: {} 字节", content.len());
}));
```

**注意**：key 在内部 `HashMap` 中唯一，重复注册同名 key 会**覆盖**之前的回调。

### 3.3 注册结构化监听器

```rust
use std::sync::Arc;
use cmx_registry_config::{ConfigChangeEvent, ConfigChangeListener, GlobalChangeNotifier};

struct DatabasePoolRefresher;

impl ConfigChangeListener for DatabasePoolRefresher {
    fn name(&self) -> &str { "db_pool_refresher" }

    fn interested_keys(&self) -> &[String] {
        // 只关心 database.* 命名空间下的变更
        static KEYS: &[String] = &["database"];
        KEYS
    }

    fn on_change(&self, event: &ConfigChangeEvent) {
        info!("数据库相关配置已变更: {:?}", event.changed_keys);
        // ... 重建连接池
    }
}

GlobalChangeNotifier::add_listener(Arc::new(DatabasePoolRefresher));
```

**`interested_keys` 匹配规则**：
- 返回空切片 → 监听所有变更（无论 `changed_keys` 是否为空）
- 返回非空 → 遍历 `changed_keys`，只要有任一 key 以某个 prefix 开头即触发
- 匹配基于**字符串前缀**（例如 `"database"` 匹配 `"database.host"`、`"database.pool.size"`）

### 3.4 触发通知

#### `notify(content)` —— 原始字符串模式

```rust
GlobalChangeNotifier::notify(new_toml_content);
```

遍历所有 `handlers`，按注册顺序依次调用。用于**第一轮**接收配置中心 SDK 推送的变更。

#### `notify_listeners(event)` —— 结构化事件模式

```rust
let event = ConfigChangeEvent {
    changed_keys: vec!["server.port".to_string(), "database.host".to_string()],
    raw_content: new_content.clone(),
};
GlobalChangeNotifier::notify_listeners(&event);
```

遍历所有 `listeners`，按 `interested_keys` 过滤后依次调用。

### 3.5 移除监听器

```rust
// 原始字符串回调（通过 key 移除）
// 注：当前未在 GlobalChangeNotifier 暴露 unregister，
// ChangeNotifier 实例上可调用 unregister(key) / remove_listener(name)

// 结构化监听器（通过 name 移除）
// ChangeNotifier 实例上可调用 remove_listener(name)
```

## 四、推荐使用模式

### 4.1 在配置中心 SDK 适配器侧（传输层）

`NacosConfigCenter::listen()` 内部将 nacos-sdk 的回调转换为 `ConfigChangeCallback`，并在回调中调用 `GlobalChangeNotifier::notify()`：

```rust
let callback: ConfigChangeCallback = Arc::new(|content: &str| {
    GlobalChangeNotifier::notify(content);
});
config_center.listen(data_id, group, callback).await?;
```

### 4.2 在应用初始化侧（编排层）

`web-server::infra_init` 编排两个核心 handler：
1. **`config_reloader`** —— 解析新配置 + 调用 `ConfigManager::reload()` + 计算 diff + 调用 `notify_listeners()`
2. **`default`** —— 打印日志

```rust
GlobalChangeNotifier::initialize();

// 1. 配置重载器
let reloader = Arc::new(ConfigReloader::new(config_file_path));
GlobalChangeNotifier::register("config_reloader", Arc::new(move |content: &str| {
    let reloader = reloader.clone();
    let content = content.to_string();
    tokio::spawn(async move {
        if let Ok(changed_keys) = reloader.reload(&content).await {
            GlobalChangeNotifier::notify_listeners(&ConfigChangeEvent {
                changed_keys,
                raw_content: content,
            });
        }
    });
}));

// 2. 默认日志处理器
GlobalChangeNotifier::register("default", Arc::new(|content: &str| {
    info!("配置变更: {} 字节", content.len());
}));
```

### 4.3 在业务模块侧（订阅层）

业务模块实现 `ConfigChangeListener` 并通过 `add_listener()` 注册：

```rust
struct MyBusinessListener;

impl ConfigChangeListener for MyBusinessListener {
    fn name(&self) -> &str { "my_business" }
    fn interested_keys(&self) -> &[String] {
        static KEYS: &[String] = &["my_module"];
        KEYS
    }
    fn on_change(&self, event: &ConfigChangeEvent) {
        // 按需处理变更
    }
}

// 在模块初始化时注册
GlobalChangeNotifier::add_listener(Arc::new(MyBusinessListener));
```

## 五、调用链与防循环设计

### 5.1 完整调用链

```
Nacos Server 推送变更
  ↓
nacos-sdk ConfigChangeListener (NacosListenerAdapter)
  ↓
ConfigChangeCallback (Fn(&str))
  ↓
GlobalChangeNotifier::notify(content)        ← 第一轮：触发所有原始 handlers
  ↓
  ├─ handler "config_reloader"               → 解析 + reload + notify_listeners()
  │   ↓
  │   GlobalChangeNotifier::notify_listeners(&event)   ← 第二轮：触发所有 listeners
  │   ↓
  │   └─ listener 1 (ConfigChangeListener)
  │   └─ listener 2 (ConfigChangeListener)
  │
  └─ handler "default"                       → 打印日志
```

### 5.2 关键防循环设计

| 设计点 | 说明 |
|--------|------|
| `notify()` 与 `notify_listeners()` 分开 | 第一轮只走 `handlers`，第二轮只走 `listeners` |
| `config_reloader` 内部调用 `notify_listeners()`（非 `notify`） | 避免 `config_reloader` 被反复触发 |
| 监听器 panic 隔离 | `std::panic::catch_unwind` 包裹，单个失败不影响其他 |
| `interested_keys` 过滤 | 减少不必要的回调，提升性能 |

⚠️ **不要在自定义 handler 内部调用 `notify()` 或 `notify_listeners()`**——这会导致无限循环。如需级联通知，请通过实现 `ConfigChangeListener` 而非注册新的 handler 来完成。

## 六、线程安全与错误处理

| 维度 | 保证 |
|------|------|
| 全局单例初始化 | 线程安全（`OnceLock`），幂等 |
| 注册/移除 | 线程安全（`RwLock`） |
| 并发通知 | 多 handler/listener 串行执行（按注册顺序） |
| Panic 隔离 | `std::panic::catch_unwind` 包裹每个 handler/listener |
| 未初始化保护 | 调用未初始化时的方法会打印 warning，不 panic |
