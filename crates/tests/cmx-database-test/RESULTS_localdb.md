# sqlx vs tokio-postgres PostgreSQL 性能对比

> 表结构：50 列宽表（1 BIGINT 主键 + 15 整数 + 15 文本 + 8 NUMERIC + 5 时间 + 3 布尔 + 2 UUID + 1 JSONB）
> 数据：同一模板行重复插入，仅主键递增
> 插入行数：100000，查询规模：[100000, 500000, 1000000]
> 多轮取中位数：插入×3 查询×5 延迟×3轮合并 管道化×5

## 结论解读

1. **插入策略的影响远大于驱动选择**：逐行 ~4.5k 行/秒 → 批量 ~58k → COPY ~235k，跨越约 50 倍。选对写入方式比选驱动重要得多。
2. **COPY 两驱动基本持平**（相对 ~1.00x，CV 个位数%）：批量导入瓶颈在 PG 服务端与网络，驱动开销被摊薄。要极限写入吞吐，用 COPY，选哪个驱动都行。
3. **批量多值 INSERT：sqlx 明显更快（约 2x）**。本基准里 tokio-postgres 每批 prepare 一条“列数 = batch×50”的独特 SQL，prepare 开销更重；sqlx 语句缓存更省。坚持用多值 INSERT 则 sqlx 占优。
4. **大结果集查询（50万–100万行）两驱动持平**（均 ~44万行/秒，CV ~1%）：瓶颈是解码+内存，驱动差异被数据量摊平。流式在两驱动上都不比 fetch_all 慢，且峰值内存 O(单行) 而非 O(结果集) —— 大结果集应优先流式。
5. **点查延迟：tokio-postgres 显著更低**（P50 230µs vs 394µs，约 1.7x）。小查询里 sqlx 的抽象层与语句协议开销占比更高。延迟敏感的高频点查 tokio-postgres 更优。
6. **Pipelining 是 tokio-postgres 独门优势**：1000 个独立点查，管道化比串行快约 **18x**。sqlx 无此能力。一个请求内有多条互不依赖 SQL 时，这是 sqlx 补不回来的结构性差距。

### 一句话选型

- 批量导入：COPY，驱动无所谓。
- 大结果集：流式，驱动无所谓（省内存是关键）。
- 高频点查 / 低延迟 / 单请求多条独立 SQL：tokio-postgres。
- 要多数据库统一 + 编译期校验 + 生态：sqlx（综合工程价值，多数场景性能差距可忽略）。
