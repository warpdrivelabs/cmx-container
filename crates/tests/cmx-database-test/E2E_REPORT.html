DB → HTTP → 前端展示模型 · 10 万行 × 50 列 · 真实 PostgreSQL + 真实前端模块
测试对象：从数据库取 10 万行(50 列宽表)经 HTTP 传到浏览器、构建成前端展示模型,三种链路对比。
表结构：1 BIGINT 主键 + 15 整数 + 15 文本 + 8 NUMERIC + 5 时间戳 + 3 布尔 + 2 UUID + 1 JSONB。

三条链路的完整路径

链路 A老链路 · sqlx / DataSet → JSON

PG→sqlx 流式取行(驱动逐行拉,但…)→DataSet 全量物化 Vec<PgRow> + DataValue 枚举全量→ColumnarCodec 列式 JSON + JSON 字节→HTTP→JSON.parse→CmxDataSet.fromJSON→dataset.rows
关键:「流式」只到取行为止。DataSet 与 ColumnarCodec 在结构上必须先攒齐所有行才能编码——这是老组件的固有限制,不是实现偷懒。于是服务端峰值 = Vec<PgRow> + DataSet(DataValue 副本) + JSON 字节 三份叠加。

链路 Bsqlx / ZmcDataSet 流式 → msgpack

PG→sqlx fetch() 流式→逐行 Zmc 编码即弃 (每行编完立即 drop,不囤)→msgpack 列式包 只剩「输出 + 单行」→HTTP→decodeMsgpack→CmxDataSet.fromJSON→dataset.rows

链路 Ctokio-postgres / ZmcDataSet 流式 → msgpack

PG→tokio query_raw 流式→逐行 Zmc 编码即弃→msgpack 列式包→HTTP→decodeMsgpack→CmxDataSet.fromJSON→dataset.rows
链路 B/C 用同一套驱动无关编码器(cmx-rowsource);唯一差别是驱动取行方式。零拷贝:文本/二进制列直接借用行的底层 Bytes,不分配。

⑤ 结论(诚实版)

1. 服务端内存是最大赢面:省 66%(1318 → 453 MB)。老链路要 Vec<PgRow> + DataSet + JSON 三份叠加;Zmc 流式边取边编码即弃。并发几个 10 万行请求,老链路就是 GB 级、Zmc 是几百 MB 级——这是生产事故线上的关键差异。
2. 端到端快 2.4×,但主因不是「二进制」,是「服务端不物化」。老链路服务端取数+物化 DataSet 就花 1343ms;Zmc 流式取数仅 65~105ms(边取边编码,不等全量)。二进制本身只省传输体积(8%)。
3. 传输体积只小 8%(114→105 MB)——低于预期,这是「路线 A」的代价。为了前端 fromJSON 零改动,msgpack 里值仍字符串化(Decimal→"1130000.5000"、时间→RFC3339、bytea→"B64:")。msgpack 只省了 JSON 的引号/括号,而列式包字段名本就只出现一次。要体积大降得走路线 B(原生 int/bin/时间),但那要改前端。
4. 前端解析:msgpack(手写 JS)反而比 JSON.parse 慢 32%(431 vs 326ms)——如实说。JSON.parse 是 V8 原生 C++,极致优化;手写 JS msgpack 解码器跑在 JIT 层。前端这一环二进制是净负——体积优势(下载)在回环下看不出,解析劣势却真实存在。真实广域网下,下载省的时间才会盖过解析多花的。
5. 前端展示构建 + 内存三链路完全相同(412ms / 484MB)。都走同一个 CmxDataSet.fromJSON → 同样的 dataset.rows 行对象树——印证「组件零改动、前端成本与传输格式无关」。
6. sqlx 与 tokio-postgres 全链路几乎无差异(总用时 1737 vs 1719ms、内存完全相同)。红利来自 ZmcDataSet 的设计(流式不物化 + 不产 DataValue 副本 + msgpack),不来自换驱动。tokio-postgres 的价值在别处(pipelining、低点查延迟),与本报告的内存/吞吐维度无关。
一句话总结:这套方案的价值 90% 在服务端(内存省 66%、端到端快 2.4×,核心是「流式不物化」);前端侧(路线 A)基本打平甚至解析略亏。老代码不必为内存红利换驱动——留在 sqlx,把出口从「DataSet+JSON」换成「ZmcDataSet+msgpack(大结果集用流式)」即可拿到几乎全部收益。

教训 1:临时 String 分配不是编码瓶颈,格式机才是。第一版只做 scratch 复用、时间列用 dt.format("%Y-…") —— 每格重新解析 strftime 格式串,反而回退到 365~444ms;换预解析 items 才追平基线;最终手写 RFC3339 writer(纯整数运算直写)才拿到 −10%。malloc 很便宜,Display/格式机的每格开销才贵。
教训 2:V8 对象形态(shape)比「少拷一次」重要得多。fromJSON 批量化时顺手删掉了 {...obj} 展开(直觉:少一次拷贝更快)——结果在真实堆条件下 3 倍慢(908ms vs 283ms):逐键动态构建的对象是 dictionary mode,直接长期持有 10 万个慢形态对象;展开重整成 fast-shape 克隆后才真正快。进程内交替微基准还差点掩盖了这一点(GC/分配器状态互相污染),分进程 A/B 才看清。
教训 3:JSON.parse / TextDecoder 是 V8 原生 C++,手写 JS「快路径」打不过。ASCII 短串 fromCharCode 拼接实测更慢且堆多 200MB(+= 产生 rope/cons 字符串,碎片化)。已回退并在代码里留注释防止后人再踩。前端解析要真正快,出路是换 @msgpack/msgpack 官方库(未做,需引依赖)或路线 B 原生类型。
第二轮小结:最优路径(tokio/Zmc)端到端 1719 → 1582ms,老链路也顺带受益(fromJSON 是共享代码)。剩余最大空间仍在前端解析(448ms,需引官方 msgpack 库)与真实网络下的体积(需路线 B)——两者都有明确代价,按需取用。

1. 服务端峰值内存 453 → 192 MB(累计 −85% vs 老链路)。单缓冲的关键:msgpack array 32(0xdd+4 字节大端)是定宽编码,与元素个数无关,所以行数未知时也能先占位、编完回填。省掉了 rows_body(一份完整输出体积)+ 一次整段 memcpy。生产 query_zmc_streaming 两侧同步受益。
2. 前端解析二进制从"净亏"翻成"净赢"(450→270ms,反超 JSON.parse)。第二轮实测手写 JS 解码器比 JSON.parse 慢 32%,是二进制路线唯一的软肋;换官方 @msgpack/msgpack(内部按 V8 特性手工优化)后 −40%,现在比 JSON.parse 还快。契约零破坏:官方 decode 对字符串键 map 返回普通对象、对 bin 返回 Uint8Array,与手写解码器输出一致,两个消费方(全量 + 逐帧)零改动。
3. gzip 体积:实测 99%,但*这个数字被合成数据夸大*——诚实修正为真实场景 ~70%。基准表每行值完全相同(同一段文本/金额重复 10 万次),gzip 对高重复数据近乎全压到 0.8MB。真实业务数据(每行不同的金额/名称/时间)压缩率约 70~85%。但即便按 70% 算,gzip 仍是体积维度 ROI 最高:生产 CompressionLayer 早已配置好(且正确排除 application/octet-stream 流式端点以保 O(单行) 分帧),application/x-msgpack 非流式端点自动享压缩,前端浏览器自动解压,零代码、零精度风险。远超"改原生类型"的 −14%。
第三轮小结:三轮累计,最优路径服务端内存 1318→192MB(−85%)、端到端 3939→1411ms(2.8×)、前端解析反超 JSON.parse、传输体积真实场景可再 gzip 掉 ~70%。关键:全部零前端契约破坏、零精度风险——单缓冲是纯后端、官方 msgpack 是 API 名不变的库替换、gzip 是生产早已配好的传输层。上一轮评估里"不建议改原生类型"的结论因此更稳:gzip 用零成本拿到了远超改类型的体积收益。
* gzip 99% 为合成数据(每行相同)结果,真实业务数据约 70~85%;报告取保守 ~70% 陈述。 计数分配器统计 Rust 堆分配(含网络缓冲/驱动缓存);前端 V8 heapUsed 于 --expose-gc 强制 GC 后取值。单机回环,5 轮取中位,数值随机器/负载波动,重点看同指标的相对差。
