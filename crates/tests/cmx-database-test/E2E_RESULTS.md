## 结论解读(诚实版)

**1. 服务端内存是最大赢面:老链路峰值 1318 MB,Zmc 流式仅 453 MB(省 66%)。**
老链路服务端要 `Vec<PgRow>` + `DataSet`(DataValue 枚举全量) + JSON 字节**三份叠加**;Zmc 流式边取边编码、每行即弃,只剩「输出 + 单行」。10 万行并发几个请求,老链路就是 GB 级、Zmc 是几百 MB 级——这是生产事故线上的关键差异。

**2. 端到端总用时快 ~2.4x(3789ms → 1560ms),但主因不是"二进制",是"服务端不物化"。**
老链路服务端"取数+物化 DataSet"就花 1216ms;Zmc 流式取数仅 59~85ms(边取边编码,不等全量)。二进制本身省的是传输体积(8%)。**真正的时间大头是老链路那份 DataValue 全量物化 + JSON 序列化。**

**3. 传输体积只小 8%(114→105 MB)——低于预期,这是路线 A 的代价。**
路线 A 为了前端 `fromJSON` 零改动,msgpack 里仍是"字符串化的值"(Decimal→"1130000.5000"、timestamp→RFC3339、bytea→"B64:")。msgpack 只省了 JSON 的引号/括号/字段名重复(列式包字段名本就只出现一次,所以省得少)。**要体积大降得走路线 B(原生 int/bin/时间),但那要改前端。**

**4. 前端解析:msgpack(手写 JS)反而比 JSON.parse 略慢(381 vs 295ms)——如实说。**
`JSON.parse` 是 V8 原生 C++,极致优化;我这个手写 JS msgpack 解码器跑在解释/JIT 层,10 万行 × 50 列的解码,慢约 30%。**前端这一环二进制是净负**——体积优势(下载)在回环下看不出,解析劣势却真实存在。真实广域网下,下载省的时间才会盖过解析多花的时间。

**5. 前端展示构建 + 总堆增量三链路几乎相同(~360ms / 484MB)。**
因为都走同一个 `CmxDataSet.fromJSON`,产出同样的 `dataset.rows` 行对象树——**前端内存/展示成本与传输格式无关**(印证了之前"组件零改动"的结论)。有意思的分解:老链路"解析"占 310MB(JSON.parse 建完整对象树)、"构建"175MB;Zmc"解析"仅 173MB(msgpack 解成列式数组更紧凑)、"构建"311MB(fromJSON 摊平成行对象)——**总量一样,只是内存花在不同环节**。

### 一句话总结

> **这套方案的价值 90% 在服务端**:内存省 66%(1318→453MB)、端到端快 2.4x,核心是"流式不物化 + 不产 DataValue 副本",而非二进制传输本身。**前端侧(路线 A)基本打平甚至解析略亏**——体积只小 8%、msgpack 解码比 JSON.parse 略慢、展示构建和内存完全相同。若要前端也获益(体积大降),需走路线 B 用原生类型,代价是改前端 `fromJSON`。sqlx 与 tokio-pg 两个驱动在全链路上几乎无差异,印证"内存/吞吐红利来自 ZmcDataSet 设计,不来自换驱动"。
