## HTTP gzip 压缩(第三轮优化:传输体积)

> `?gzip=1` 开启响应 gzip;fetch 透明解压,前端解码路径不变。x-wire-bytes 头暴露真实线上体积。

| 链路 | 未压缩体积 | gzip 后体积 | 压缩率 | 服务端 gzip 耗时 |
|------|-----------|------------|--------|------------------|
| 老链路 JSON | 114.0 MB | 0.7 MB | 省 99% | 117 ms |
| sqlx/Zmc msgpack | 105.0 MB | 0.8 MB | 省 99% | 120 ms |
| tokio/Zmc msgpack | 105.0 MB | 0.8 MB | 省 99% | 119 ms |

结论:gzip 把传输体积从 ~105MB 压到 ~1MB(省 ~99%),代价仅服务端 ~119ms 压缩耗时 + 前端零改动(浏览器自动解压)。真实广域网下这是体积维度 ROI 最高的一招——远超"改原生类型"的 −14%,且零精度风险。
