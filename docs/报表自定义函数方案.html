1 · 总体架构（三态一图）

一套函数定义，三种执行语境。核心：公式串是唯一事实源（存 cr_cell_element_map.calc_formula，缺省继承 cr_data_element.calc_formula），设计态写它、计算态解释它、应用态读它算出的缓存值。

为什么双态。 后端 CALC 是权威——真查 GL/凭证做期末余额、跑勾稽、落库；批量、事务、可审计。前端 APPLY 是读缓存的镜像——applier 已按 org+period 把 cr_cell_data 取回前端，QM/QC 在前端只需从这个缓存里命中返回，用于即时预览/联动，绝不发计算请求、绝不碰 DB。两态共享同一套 DSL 文法与函数语义，保证"前端看到的 = 后端算出的"。

2 · 函数模型与注册契约

每个函数是一个五元注册：函数名 · 原型 · 后端算法 · 前端算法 · 向导定义。外加分类/返回类型/帮助/示例等元数据。

// cmx-rpt-formula::registry —— 函数注册契约（后端 inventory 收集）
pub struct RptFunction {
    pub name:        &'static str,        // "QM"（大写规范名，解析期大写化）
    pub category:    FnCategory,          // 取数Fetch/汇总Agg/引用Ref/逻辑Logic/数学Math
    pub prototype:   Prototype,           // 参数签名（见下）
    pub ret_type:    ValueType,           // amount/qty/rate/text/date/bool
    pub is_fetch:    bool,               // true=需 DataProvider IO（QM/QC）；false=纯内存（SUM/IF）
    pub compute_fn:  ComputeFn,           // 后端真算（可访问 DataProvider + scope + resolve 回调）
    pub help:        &'static str,        // 一句话帮助

    pub wizard:      WizardSpec,          // 前端向导定义（参数控件）→ 供 designer 生成向导
}

// 原型：变参签名
pub struct Prototype {

}
pub struct Param {
    pub name: &'static str,             // "期间" / "组织机构" / "取数对象"

    pub required: bool,
    pub default: Option<&'static str>,   // 期间默认 "0"（本期）

pub struct WizardSpec {

}
直接借鉴 doc/formula.rs。 它已有 enum FValue{Num,Str,Bool,Null}、Node::Call(name, Vec<Node>)、eval_call 的 match name 分发，且函数名解析期即大写化——今天写 QM(...) 就能 tokenize+parse 成 Call("QM",args)，只在 eval_call 末尾"未知函数"处失败。cmx-rpt-formula 抬起这套架构（Token/AST/eval 三段式），加上异步取数 + 单元格引用 + 参数占位符解析 + 注册表。

4 · 公式语言 DSL（借鉴 Excel）

文法沿用 doc/formula.rs / cmx-flow expr.rs 的经典分层，primary 扩三样：函数调用、单元格引用、参数占位符。

expr    := or
or      := and ( "||" and )*
and     := cmp ( "&&" cmp )*
cmp     := add ( ("=="|"!="|"<"|"<="|">"|">=") add )?
add     := mul ( ("+"|"-") mul )*
mul     := unary ( ("*"|"/") unary )*
unary   := ("!"|"-") unary | primary
primary := number | string | bool | null
         | ident "(" args ")"        ← 函数调用   QM(-1,@current,'1001')
         | cellref                   ← 单元格引用 C5 / C5:D10
         | "[" placeholder "]"       ← 参数占位符 [期间] [组织机构]
         | "(" expr ")"
args    := ( expr ( "," expr )* )?    ← 变参

一个完整单元格公式例子

# C5 = 本期货币资金 期末余额（当前组织），减上期同项，四舍五入到分
ROUND( QM(0, @current, '1001') - QM(-1, @current, '1001'), 2 )

# D8 = 流动资产合计 = 单元格区间求和
SUM(D3:D7)

# E10 = 引本表 D8 + 引「利润表」某格（跨表取数）
D8 + REF('PROFIT', 'v1', B20)

# 校验公式（check_formula）：资产 = 负债 + 权益
D30 == D45 + D60

参数占位符[期间] [组织机构]向导可读的中文占位；也接受裸值 0/-1、@current、科目码。
相对期间0 -1 -2 -120=本期，-1=上期，-2=上两期，-12=上年同期。

6 · 公式来源与优先级（元素 ↔ 单元格）

一个单元格的公式可能来自两处：单元格自己定义的，或它所引用的数据元素上定义的。规则一句话：就近覆盖——单元格自身公式优先，缺省则继承元素公式（如同 Excel 单元格样式覆盖、CSS 就近优先）。

单元格公式来源 · 优先级阶梯（自上而下，命中即止） ┌─────────────────────────────────────────────────────────────┐ │ ① 单元格自身公式 cr_cell_element_map.calc_formula │ ◀ 最高优先 │ (本报表·本版本·该格显式定义的公式) │ "自己定义的赢" └──────────────────────────┬──────────────────────────────────┘ │ 缺省(该格无 calc_formula) ┌──────────────────────────▼──────────────────────────────────┐ │ ② 元素继承公式 cr_data_element.calc_formula │ ◀ 继承 │ (该格所绑数据元素 element_id 上定义的公式) │ "定义一次·处处复用" └──────────────────────────┬──────────────────────────────────┘ │ 缺省(元素也无 calc_formula) ┌──────────────────────────▼──────────────────────────────────┐ │ ③ 无公式 手工输入值 / 元素 value_source 取数默认 │ ◀ 叶子 │ (cr_cell_data 手工值，或 element.value_source 派生) │ └─────────────────────────────────────────────────────────────┘

校验公式 check_formula 走同一阶梯（单元格级覆盖元素级）。解析成一个函数，§8 递归解析时反复调用它判断"某格到底有没有公式"：

// 解析某单元格实际生效的公式（单元格级 > 元素级 > 无）
fn resolve_cell_formula(report:&str, ver:&str, cell:&str) -> Option<Formula> {
    let m = cell_map.get(cell)?;
    if let Some(f) = &m.calc_formula { return Some(f.clone()); }  // ① 单元格级
    if let Some(el) = m.element_id {
        if let Some(f) = data_element.get(el).and_then(|e| e.calc_formula) {
            return Some(f);                                    // ② 元素级(继承)
        }
    }
    None                                                     // ③ 无公式 → 叶子(手工/取数默认)
}
单元格自身所绑元素生效公式说明
有 calc_formula有 / 无单元格级自己定义的赢，忽略元素公式。
无有 calc_formula元素级 (继承)继承元素公式——元素上定义一次，所有绑定该元素的单元格自动套用。
无无无 (叶子)手工输入值，或按元素 value_source 取默认。
元素公式 = 复用杠杆。 「货币资金」元素上定义一次 QM(0,@current,'1001')，资产负债表、现金流量表里所有绑定该元素的格全部自动继承；哪张表的哪一格要特殊算，就在那一格写自己的公式覆盖。这也直接决定 §8 递归里"某格是否有公式"的判定——继承来的公式同样算"有公式"，同样要先算完才能被 REF 取走。

★ 核心难点：取数是异步 IO，而 eval 是同步 → 两遍法

doc/formula.rs 的 eval_call 是同步 match name；但 QM/QC 要打 DB/缓存。硬把 eval 改 async 会污染整棵树。方案用两遍法（借鉴列式数据库的"先收集谓词再批量取"）：

compute_report(report, version, org, period): ┌ 载入 ────────────────────────────────────────────────┐ │ 读全部单元格生效公式 (§6 阶梯:单元格级 or 元素继承) │ │ 逐条 tokenize ▶ parse ▶ AST，建 cellRef → AST 映射 │ └───────────────────────────────────────────────────────┘ │ ┌ 排序/解析 ────────────┼───────────────────────────────┐ │ 本表 CellRef 依赖 → DAG，Kahn 拓扑序 │ │ 跨表 REF → 按需递归解析 (§8)，三色标记检测循环引用 │ │ 环上单元格 → data_status=error │ └───────────────────────────────────────────────────────┘ │ ┌ PASS 1 · 收集取数 ────┼───────────────────────────────┐ │ 遍历所有 AST 的 Call("QM"/"QC"/…) 叶子 │ │ 解析参数 ▶ (fn, 期间码, 组织码, 对象) 三元组集合 │ async │ 去重 ▶ DataProvider.batch_resolve(三元组[]) 一次批量 │ │ 结果填入 fetch_cache: (三元组) → Decimal │ └───────────────────────────────────────────────────────┘ │ ┌ PASS 2 · 纯内存求值 ──┼───────────────────────────────┐ │ 按拓扑序逐单元格 eval(AST, scope) │ sync │ · Call(QM,…) ▶ 从 fetch_cache 命中（已批量取回） │ │ · CellRef ▶ 从 scope 取已算单元格值（拓扑保证先算） │ │ · REF(他表) ▶ 递归 resolve（§8, 记忆化命中） │ │ · SUM/IF/… ▶ doc/formula.rs 同款内存运算 │ └───────────────────────────────────────────────────────┘ │ ┌ 落库 ─────────────────┼───────────────────────────────┐ │ UPSERT cr_cell_data (num_value/text_value/value_type, │ │ data_status=computed, compute_time=now) │ │ is_manual=1 的单元格：跳过（手工覆盖优先） │ └───────────────────────────────────────────────────────┘

上图是单表批量视角：QM/QC 叶子两遍法预取、本表单元格互引按拓扑序求值。而 REF 跨表取数、以及"目标格自己也有公式且未算"的按需递归解析——统一在 §8。两者本质是同一个记忆化 DFS：单表内展开即拓扑序，跨表即懒加载递归。

DataProvider trait（占位先行）

#[async_trait]
pub trait DataProvider {
    // 批量期末/期初/发生额取数（QM/QC/FS）——一次 IO 取回一批三元组
    async fn batch_balance(&self, keys: &[BalanceKey]) -> Result<HashMap<BalanceKey, Decimal>>;
    // 表间取数（REF）：装载他表某 org+period 的公式+已算值进解析会话

8 · 依赖解析与递归（REF 跨表 · 循环检测）

REF 从本表或其他表取数。关键洞察：一个单元格引用是全局可寻址的——(报表, 版本, 组织, 期间, 单元格) 五元地址；本表引用 C5 只是 report=当前表、org/period 同上下文的 REF 特例。

难点正如需求所述：REF 取的目标格自己可能也有公式（单元格级或 §6 继承来的元素级），而且可能还没算。那就得先把它算完再取；它的公式里若又有 REF/单元格引用，继续往下递归；万一绕一圈又回到正在算的那个格——循环引用，当场斩断返回。这是一个天然的按需递归解析过程，用三色标记做记忆化 + 环检测。

单元格解析 · 三色状态（一次 compute 会话内） 未算(白) ── 首次需要其值 ─▶ 在算(灰) ── 求值完成 ─▶ 已算(黑) 从未解析 压入解析栈·递归其依赖 记忆值·出栈 ▲ │ └────────── 再次被引用: memo 命中，不重算 ◀┘ ★ 递归中再遇「灰」目标 = 又回到正在算的格 = 循环引用 → 返 #REF! 斩断，从灰目标到栈顶整条链标 error

递归解析算法（记忆化 DFS + 三色环检测）

// target = 全局单元格地址 (报表,版本,组织,期间,单元格)；本表引用 = report 同当前
fn resolve(target) -> Value {
    if let Some(v) = memo.get(target) { return v; }        // 黑：已算 → 命中记忆，不重算
    if resolving.contains(target) {                          // 灰：又绕回正在算的格
        mark_cycle_chain(target ..= stack_top);            //   → 灰目标至栈顶整链记为环
        return Value::RefErr;                             //   → 直接返回 #REF!，斩断递归
    }
    resolving.push(target);                                 // 白 → 灰：压栈，标记在算

    let val = match resolve_cell_formula(target) {         // §6 优先级：单元格级 > 元素级
        None        => stored_value(target),                // 无公式 → 取已存值(手工/默认)
        Some(f)     => {
            let ast = parse(f);
            eval(ast, |dep| resolve(dep))               // 遇 REF/CellRef → 递归 resolve(依赖)
        }
    };

    memo.insert(target, val);                             // 灰 → 黑：记忆
    resolving.pop(target);                                //        出栈
    persist(target, val, if in_cycle(target) { Error } else { Computed });
    val
}

resolving 就是递归栈；命中「灰」目标 = 需求里说的「又回到本函数」——立即返回哨兵值斩断，避免无限递归。memo 保证每格只算一次（钻石依赖 A→B、A→C、B→D、C→D 里 D 不重算）。

REF 取区域 · 逐格递归

REF(报表B, 版本, C5:C10) ← 取他表一个区域 │ ▼ 对区域内每个单元格 C5..C10 逐一 resolve： ┌──────────────────────────────────────────────────────────┐ │ resolve(B, ver, org, period, Cn) │ │ ├ 该格有公式吗? (§6 阶梯: 单元格级 or 元素继承) │ │ │ ├ 有 + 未算(白) ─▶ 递归先算完 ─▶ 取算好值 │ │ │ ├ 有 + 已算(黑) ─▶ 记忆命中，直接取 │ │ │ └ 有 + 在算(灰) ─▶ 循环引用，返 #REF! 斩断 │ │ └ 无公式 ─▶ 取已存值 (cr_cell_data / 手工) │ └──────────────────────────────────────────────────────────┘ │ ▼ 组合：SUM(REF(B,ver,C5:C10)) = 对区域解析值求和

跨表循环引用示例

# 报表A!C5 与 报表B!C5 互相 REF —— 环
A!C5 = REF('B', 'v1', C5)      # A 要 B
B!C5 = REF('A', 'v1', C5)      # B 又要 A

# 解析轨迹：
resolve(A!C5)      压栈·灰A
  └ resolve(B!C5)  压栈·灰B
      └ resolve(A!C5)      # A!C5 已是灰 → 循环！返 #REF! 斩断
  ← A!C5、B!C5 均标 data_status=error，环链记入 check_result 供用户查
环 = 隔离，不 = 全盘崩。 命中循环只把环上的格标 error（值取 #REF!/0）、把环链记进错误清单给用户看；其余无关单元格照常算完。绝不因一个环让整份报表 compute 失败。环策略（返 0 vs #REF! vs 中止）见 §14。

与两遍法（§7）的关系：一个是特例，一个是全集

依赖种类解析方式说明
QM/QC/FS 取数叶子两遍法批量预取（§7 pass1）只打 GL/DataProvider，不依赖别的格 → 可提前收集三元组一次批量取。
本表单元格引用 C5递归解析（本表内 = 拓扑序）单表内 DFS 展开即拓扑序；两遍法的"拓扑排序"就是它的扁平化。
跨表 REF递归解析（懒加载他表）他表首次被 REF 命中才懒加载其公式+值进会话；无法提前拓扑（不知会引哪张表）→ 递归是唯一诚实模型。

合起来：引擎对请求报表做递归解析；任何报表内的 QM/QC 叶子仍走两遍法批量预取；REF 跨报表边界靠懒加载 + 递归 + memo + 三色环检测。memo 与 resolving 跨报表共享（一次 compute 会话一份），所以 A 表算过的格 B 表 REF 时命中记忆、不重算。

9 · 前端计算态（读缓存）

新 formula-eval.js——后端 DSL 的前端镜像（doc/formula.rs 头注就约定它有一个语义对齐的 formula-eval.js 对手）。同一文法、同一函数语义，但取数函数改读缓存：

函数类前端 eval_fn
QM/QC/FS/JE 取数从 applier 的 cr_cell_data 缓存命中：applier 「取数」已把该 org+period 的 {cellRef→值} / {elementCode→值} 取回前端。QM 前端态 = 用参数解析出目标 key → 查缓存 → 返回。命中即返、不发请求；未命中 → 标 pending 或回退向后端请求。
REF 跨表读跨报表缓存：目标表若已在前端加载（同会话打开过），命中其缓存值直接返；否则回退后端（前端不做跨表递归——递归求值是后端权威职责）。
SUM/IF/ROUND/… 内存与后端逐位一致的纯 JS 实现（同 truthy/数值语义），本地即算。

用途：① 应用态联动——用户改一格手工值，依赖它的合计格前端即时重算（不等后端）；② 设计态预览——designer 里输入公式，用样例/缓存值给个预览数，所见即所得。

前后端一致性是硬约束（§14）：两套 DSL 必须逐位等价，否则"前端预览 ≠ 后端落库"会造成信任崩塌。方案要求共享一套文法对拍测试用例（同一批 公式串 → 期望值 同时喂 Rust 与 JS，CI 双跑），把一致性钉死。REF 跨表递归求值只在后端做——前端只读缓存、不递归，从源头避免两端递归语义漂移。
