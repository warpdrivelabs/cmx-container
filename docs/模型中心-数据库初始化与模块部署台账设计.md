# 模型中心 · 数据库初始化与模块部署台账 — 设计方案

> 版本：草案 v1（2026-07-02）｜状态：**设计稿，未改任何执行代码**
> 目标：在「集群数据源浏览 → 建表工作台」里，把"当前数据库已建了哪些模块的数据字典 / 业务单据 / 初始化数据"列出来；数据库未初始化时先做**初始化（建系统表）**；系统表与各模块的字典 / 单据 / 初始数据都可**升级**，且**历史版本、当前版本、升级过程**全程可查。

---

## 0. 一句话结论

**建表/升级/种子引擎、对象级台账、多库定向（`DdlDialect`/`DbType` 抽象）、事务与分布式锁都已就绪**；缺的是①「模块 × 目标库 × 版本 × 状态」逻辑台账 + 台账自描述表；②源定义/初始数据 JSON 完整留档；③主控库跨库总览。本方案在**目标库内**新增 4 张系统表 + **主控库** 1 张汇总表，复用现有 `cmx_meta_table_define(_version)` 作对象层与升级引擎，**逐列精细对比、只改差异、绝不先删后建**，多库默认先实现 PostgreSQL。

> **第一原则（§6.0）**：对比表结构时，"库里现状"一律取自**数据库自身内省**（`information_schema`/`pg_catalog`），**绝不以台账记录为准**——台账只做记账/审计/回滚参考。现有引擎已合规，本方案沿用并扩展内省覆盖面。

## 1. 现状勘察（可复用 vs 缺口）

### 1.1 可直接复用（已就绪）

| 能力 | 位置 | 说明 |
|---|---|---|
| 建表/升级引擎 | `crates/libs/cmx-metadata/src/executor.rs` | `PgTableDefineExecutor::create_or_upgrade_table`：先建，失败则内省 `information_schema` 反查现表→`DdlDiff` 增量 ALTER。**加列/加索引，`DROP` 仅记录不执行**（`ddl/diff.rs`），天然幂等、additive-safe。 |
| 种子/初始化数据 | `crates/libs/cmx-metadata/src/seed/executor.rs` | `PgSeedDataExecutor::execute_all_seed_data`：`INSERT … ON CONFLICT` UPSERT，批量 100 + 逐行回退，错误汇总不中断。 |
| 多库定向 | `cmx-infra/cmx-database` | `execute_sql(db_id, txn_id, sql)` / `query_sql(...)`；`DbRegistry` 按 `db_id` 取池；`begin_with_guard(db_id)` → `TransactionGuard`。 |
| 分布式锁 | `cmx_buffer::LockManager` | `try_lock`（非阻塞，多实例幂等）；插件链路用 `plugin:ddl:{id}` 作 key。 |
| 对象级台账（两表） | `docs/sql/init/init_ddl.sql:756-851` | `cmx_meta_table_define`（每物理表当前态）+ `cmx_meta_table_define_version`（每版本一份 **TableDefine JSONB 快照**）。 |
| 模块身份 | 三元组 `domain_code / application_code / module_code` | 已贯穿 `cmx_plugin` / `cmx_meta_table_define(_version)`。 |
| 「应用到库」范本 | `cmx-plugin/src/service/utils.rs` + `persistence.rs` | 锁 → 事务 → 建表 → 种子 → 写台账 的完整链路样板。 |

### 1.2 必须新增的缺口

1. **无「模块 × 目标库 × 版本 × 状态」逻辑台账**：现有台账最细只到"某物理表落在哪个 `db_id`、版本几何"，答不出"GL 模块在这个库里，字典 / 单据 / 初始数据分别是什么版本、什么状态"。→ 新增 `cmx_model_module`（§3.2）。
2. **`ddl_status` 是死状态机**：仅在建行时写过 `'pending'`（`table_metadata/service.rs:100`），从不推进到 `executing/completed/failed`；`check_ddl_completed` 存在但从未被调用。要当"部署进度/结果"用必须自己推进。
3. **系统表自身无版本、无法自升级**：需要一张 meta 表描述"台账 schema 版本"，才能判定"未初始化 / 需升级系统表"。→ 新增 `cmx_model_meta`（§3.1）。
4. **源定义/初始数据 JSON 未落库**：`..._version.metadata` 只存**编译后** TableDefine，源定义原文与初始数据 JSON 未留档、无法从库内复现。→ 新增 `cmx_model_source`（§3.4，诉求 1）。
5. **无跨库总览**：无法在主控库一次看到"各数据库各装了什么"。→ 主控库新增 `cmx_model_registry`（§3.6，诉求 2）。
6. **升级对比粒度不足**：现 `diff` 未比 `db_type`/列注释/主键/分区/索引列集变更。→ 逐列精细对比增强（§6，诉求）。

### 1.3 三个必须规避的现状坑

- **坑 A — DDL 在事务外提交**：`create_plugin_tables` 里 `PgTableDefineExecutor::new(db_id, None)`、`PgSeedDataExecutor::new(db_id, None)`（`utils.rs:107/136`）传的是 `txn_id=None`，DDL/种子各自 autocommit，只有台账 DML 在事务内。⇒ 崩溃可能"表建了、台账没写"或反之。**对策**：用 `deploy_history` 的 `pending→executing→success/failed` 做**可重入对账**（不强求 DDL 进同一事务，更稳）。
- **坑 B — `ddl_status` 死状态**：本方案必须自行推进它，界面进度才真实。
- **坑 C — 迁移 runner 只跑默认库**（`cmx-database/src/migration/runner.rs` 走 `get_default_db_id()`）。⇒ 目标业务库的初始化/升级**不能**走它，只能走支持任意 `db_id` 的 `create_plugin_tables(db_id)` 那条链路。

## 2. 架构决策

### 决策 1：台账落在**目标业务库内**（DB 自描述），非集中控制库
- **理由**：契合原始诉求"初始化 = 在这个库里建系统表，这些表记录建了哪些模块"。等价 Flyway/Liquibase 的"库自带部署历史"。
- **收益**：库可移植、自解释；指向任意 `db_id` 都能问出它的部署态；不依赖控制库在线。
- **可选增强（非 MVP）**：控制库再存一份跨库汇总索引，供"所有库总览"用。

### 决策 2：字典 / 单据 / 初始数据**分 kind 独立版本**
用户明确"某些模块的字典、单据、初始数据也可能需要升级"⇒ 一个模块的三类各有独立 `version + status`，可分别升级。

### 决策 3：**追加式历史**（append-only），当前态与历史分离
`cmx_model_module` 存当前态（可更新）；`cmx_model_deploy_history` 每次操作追加一行、永不改写 ⇒ 历史版本、升级过程完整可回放/审计。

### 决策 4：分层复用
```
Meta 层    cmx_model_meta            台账自身版本（判断"是否已初始化 / 系统表要不要升级"）
Module 层  cmx_model_module          每模块当前态（工作台"已部署"数据来源）  ← 新增
History 层 cmx_model_deploy_history  追加式操作/升级历史（时间线）           ← 新增
Object 层  cmx_meta_table_define     每物理表当前态（复用，推进 ddl_status）
Snapshot   cmx_meta_table_define_version  每版本 TableDefine JSONB（复用，回滚源）
```

## 3. 系统表 DDL（初始化时建入**目标库**）

> 命名/风格对齐 `docs/sql/init/init_ddl.sql`（`cmx_` 前缀、`VARCHAR` id、审计四列、`COMMENT ON`）。落地时既可写成 `docs/sql/migrations/YYYYMMDD_NNN_model_center_ledger.up.sql`，也可由引擎用内置 `TableDefine` 建（这样"系统表升级"能复用同一条 diff 链路，**推荐后者**）。

### 3.1 `cmx_model_meta` — 台账自描述（每库 0/1 行）

```sql
DROP TABLE IF EXISTS cmx_model_meta;
CREATE TABLE cmx_model_meta
(
    id               VARCHAR(64)  NOT NULL,
    db_id            VARCHAR(100),                       -- 本库标识（自证）
    meta_version     INT4         NOT NULL DEFAULT 1,    -- 台账 schema 版本；引擎期望值 > 它 ⇒ 需升级系统表
    app_id           VARCHAR(64)  NOT NULL DEFAULT 'default',
    engine_version   VARCHAR(50),                        -- 建表引擎版本
    portal_version   VARCHAR(50),                        -- 门户构建版本
    status           VARCHAR(20)  NOT NULL DEFAULT 'ready', -- ready / upgrading / failed
    initialized_at   TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    initialized_by   VARCHAR(100),
    initialized_name VARCHAR(100),
    last_upgraded_at TIMESTAMP,
    last_upgraded_by VARCHAR(100),
    remark           VARCHAR(500),
    create_time      TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    update_time      TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
);
COMMENT ON TABLE  cmx_model_meta                IS '模型中心台账自描述（每库单例）';
COMMENT ON COLUMN cmx_model_meta.meta_version   IS '台账 schema 版本，用于判定是否需要升级系统表';
COMMENT ON COLUMN cmx_model_meta.status         IS '台账状态: ready / upgrading / failed';
COMMENT ON COLUMN cmx_model_meta.initialized_by IS '初始化创建人ID';
CREATE UNIQUE INDEX uk_model_meta_db_app ON cmx_model_meta (db_id, app_id);
```

**「未初始化」判定** = 该表不存在，或存在但无行。

### 3.2 `cmx_model_module` — 每模块当前态（工作台"已部署"来源）

```sql
DROP TABLE IF EXISTS cmx_model_module;
CREATE TABLE cmx_model_module
(
    id                   VARCHAR(64) NOT NULL,
    db_id                VARCHAR(100),
    app_id               VARCHAR(64) NOT NULL DEFAULT 'default',
    domain_code          VARCHAR(100),
    application_code     VARCHAR(100),
    module_code          VARCHAR(100),
    module_name          VARCHAR(200),
    -- 三类各自"当前已应用版本" + 状态（none/current/failed/upgrading）
    dct_version          VARCHAR(50),
    dct_status           VARCHAR(20) DEFAULT 'none',
    doc_version          VARCHAR(50),
    doc_status           VARCHAR(20) DEFAULT 'none',
    seed_version         VARCHAR(50),
    seed_status          VARCHAR(20) DEFAULT 'none',
    overall_status       VARCHAR(20) DEFAULT 'active',   -- active / partial / failed
    table_count          INT4        DEFAULT 0,          -- 该模块已建物理表数
    def_source           VARCHAR(300),                   -- 来源定义文件（如 fi/cmxfico/gl/..._dct_meta_v1.json）
    def_checksum         VARCHAR(64),                    -- 定义内容哈希，检测"定义已改但未升级"（DRIFT）
    first_deployed_at    TIMESTAMP,
    current_deployed_at  TIMESTAMP,
    deployed_by          VARCHAR(100),
    deployed_name        VARCHAR(100),
    archived             INT4        DEFAULT 0,
    create_time          TIMESTAMP   DEFAULT CURRENT_TIMESTAMP,
    update_time          TIMESTAMP   DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
);
COMMENT ON TABLE  cmx_model_module                 IS '模型中心-模块部署当前态（每模块一行）';
COMMENT ON COLUMN cmx_model_module.dct_status      IS '数据字典状态: none/current/failed/upgrading';
COMMENT ON COLUMN cmx_model_module.overall_status  IS '模块整体状态: active/partial/failed';
COMMENT ON COLUMN cmx_model_module.def_checksum    IS '来源定义内容哈希，用于检测定义漂移';
CREATE UNIQUE INDEX uk_model_module_key
    ON cmx_model_module (db_id, app_id, domain_code, application_code, module_code);
```

### 3.4 `cmx_model_source` — **源定义 / 初始数据 JSON 完整存库**（追加式，每模块×kind×版本一行）

> 诉求 1：建表和初始数据的 JSON 文件要在数据库中完整保存（DCT / DOC / 版本 / 时间戳等）。
> `cmx_meta_table_define_version.metadata` 存的是**编译后**的 TableDefine 快照；本表额外存**源定义原文**（Portal 的 DCT/DOC 定义 JSON）与**初始数据 JSON**，可复现、可审计、可离线重建。一份源 = 一行，永不改写（新版本追加新行）。

```sql
DROP TABLE IF EXISTS cmx_model_source;
CREATE TABLE cmx_model_source
(
    id               VARCHAR(64) NOT NULL,
    db_id            VARCHAR(100),
    app_id           VARCHAR(64) NOT NULL DEFAULT 'default',
    domain_code      VARCHAR(100),
    application_code VARCHAR(100),
    module_code      VARCHAR(100),
    module_name      VARCHAR(200),
    kind             VARCHAR(20),                         -- DCT / DOC / SEED
    version          VARCHAR(50),                         -- 该源的版本号
    source_file      VARCHAR(300),                        -- 原始文件名（如 cmxfico_dct_meta_v1.json）
    source_json      JSONB,                               -- ★ 源定义 / 初始数据 JSON 原文（完整保存）
    compiled_json    JSONB,                               -- 可选：编译产物（TableDefine 数组）冗余留档
    checksum         VARCHAR(64),                         -- source_json 的内容哈希（去重 / 检测漂移）
    table_count      INT4       DEFAULT 0,                -- 该源涉及的表数
    seed_row_count   INT4       DEFAULT 0,                -- SEED 时的数据行数
    is_current       INT4       DEFAULT 1,                -- 是否该模块×kind 的当前版本（1/0）
    engine_version   VARCHAR(50),                         -- 编译器版本
    imported_at      TIMESTAMP  DEFAULT CURRENT_TIMESTAMP,-- 入库时间戳
    imported_by      VARCHAR(100),
    imported_name    VARCHAR(100),
    remark           VARCHAR(500),
    create_time      TIMESTAMP  DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
);
COMMENT ON TABLE  cmx_model_source              IS '模型中心-源定义/初始数据 JSON 完整留档（每模块×kind×版本一行）';
COMMENT ON COLUMN cmx_model_source.kind         IS '源类别: DCT(数据字典)/DOC(业务单据)/SEED(初始化数据)';
COMMENT ON COLUMN cmx_model_source.source_json  IS '源定义或初始数据 JSON 原文（完整保存，可复现/审计）';
COMMENT ON COLUMN cmx_model_source.compiled_json IS '编译产物（TableDefine 数组），冗余留档';
COMMENT ON COLUMN cmx_model_source.is_current   IS '是否为该模块×kind 的当前版本';
CREATE UNIQUE INDEX uk_model_source_ver
    ON cmx_model_source (db_id, app_id, domain_code, application_code, module_code, kind, version);
CREATE INDEX idx_model_source_current
    ON cmx_model_source (db_id, domain_code, application_code, module_code, kind, is_current);
```

**写入时机**：每次建表/升级/导入初始数据，先把源 JSON UPSERT 进本表（`is_current` 翻新旧版本为 0、新版本置 1），再执行 DDL/种子。这样"这个库里到底装了哪些定义的哪个版本、原文长啥样"**完全可从库内取回**，不依赖文件系统。

### 3.5 对象层（复用现有，仅"用起来"）
- `cmx_meta_table_define`：每物理表一行；**改造点**：① 部署进目标库；② **真正推进 `ddl_status`**（`executing→completed/failed`）；③ 三元组与 `cmx_model_module` 对齐。
- `cmx_meta_table_define_version`：每版本一份**编译后** TableDefine JSONB 快照 —— **回滚源**（上一版快照即在此）。

> 三份 JSON 的分工：`cmx_model_source.source_json`＝**源定义/初始数据原文**（诉求 1）；`..._version.metadata`＝**编译后 TableDefine**（引擎回滚用）；两者互补，前者可复现门户定义、后者可复现 DDL。

### 3.6 `cmx_model_registry`（**主控库**独有）— 跨库总览 + 区分各数据库

> 诉求 2：台账放目标库，主控库也要有"用于概览"的一份，且要**区分不同的数据库**。
> 主控库（默认 `db_id`，`cmx_sys_datasource` 所在库）新增一张汇总表：每个已纳管的目标库一行（或每库×模块一行，见下），供"所有数据库总览"页读取，无需逐库连查。

**方案（推荐：每库一行 + 模块摘要 JSONB）**
```sql
DROP TABLE IF EXISTS cmx_model_registry;
CREATE TABLE cmx_model_registry
(
    id               VARCHAR(64) NOT NULL,
    db_id            VARCHAR(100) NOT NULL,               -- ★ 目标库标识（区分不同数据库）
    db_name          VARCHAR(200),                        -- 目标库显示名（冗余自 cmx_sys_datasource）
    db_type          VARCHAR(30),                         -- postgres / mysql / oracle …
    app_id           VARCHAR(64) NOT NULL DEFAULT 'default',
    initialized      INT4        DEFAULT 0,               -- 是否已初始化（1/0）
    meta_version     INT4,                                -- 目标库台账版本（镜像自 cmx_model_meta）
    module_count     INT4        DEFAULT 0,               -- 已部署模块数
    table_count      INT4        DEFAULT 0,               -- 已建物理表数
    modules_summary  JSONB,                               -- 各模块×kind 版本/状态摘要（总览直接用）
    last_deploy_at   TIMESTAMP,                           -- 最近一次部署时间
    last_sync_at     TIMESTAMP,                           -- 主控库与目标库台账最近对账时间
    health           VARCHAR(20) DEFAULT 'unknown',       -- ok / degraded / unreachable
    create_time      TIMESTAMP   DEFAULT CURRENT_TIMESTAMP,
    update_time      TIMESTAMP   DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
);
COMMENT ON TABLE  cmx_model_registry               IS '主控库-各目标数据库模型部署总览（区分不同数据库）';
COMMENT ON COLUMN cmx_model_registry.db_id         IS '目标数据库标识';
COMMENT ON COLUMN cmx_model_registry.modules_summary IS '各模块×kind 版本与状态摘要（供总览页免逐库查）';
COMMENT ON COLUMN cmx_model_registry.last_sync_at  IS '与目标库台账对账时间';
CREATE UNIQUE INDEX uk_model_registry_db ON cmx_model_registry (db_id, app_id);
```

**同步策略（主控库汇总 = 目标库台账的投影）**
- 目标库每次 `init / deploy / meta-upgrade` 成功后，**回写**主控库 `cmx_model_registry`（更新该 `db_id` 行的 `meta_version / module_count / table_count / modules_summary / last_deploy_at`）。
- 主控库为**只读投影**，事实源仍在各目标库（避免双写不一致）；提供 `POST …/registry/sync?db_id=` 手动对账兜底。
- **区分数据库**：`db_id` 唯一键；总览页按 `db_id` 分行，点进某库再走 `db-state?db_id=` 拉详情。

> 注意：主控库 = `cmx_sys_datasource` 所在的默认库；目标库可能就是主控库自身（自纳管），此时同一份台账系统表在该库内，registry 行也指向它——不冲突。

## 4. 初始化数据 JSON 结构设计（诉求 3）

> 现有引擎的种子入参是 `SeedDataConfig { table_name, file, conflict_columns, enabled }`（`cmx-core/model/meta/plugin.rs:207`）+ 数据文件（JSON 为**行对象数组** `Vec<serde_json::Value>`，`seed/loader.rs`）。
> 本方案在其上包一层「模块级初始化数据包」，把"某模块下若干张表各自的初始化数据"合并成**一个自描述 JSON**，既能整包存进 `cmx_model_source.source_json`（诉求 1），又能拆解为引擎认识的 `SeedDataConfig + rows` 执行。

### 4.1 初始化数据包结构（`*_seed_meta_v{N}.json`）

```jsonc
{
  "metaKind": "SEED",                       // 与 DCT/DOC 并列的第三类
  "moduleMeta": {
    "domain": "fi", "application": "cmxfico", "module": "gl",
    "moduleName": "GL 总账",
    "version": 1,                            // 初始化数据包版本
    "versionName": "初始基础数据",
    "isDefault": true,
    "remark": "GL 模块的字典枚举值与基础配置初始数据"
  },
  "seedTables": [                            // 一个包内含"某些表"的初始化数据
    {
      "tableName": "cf_voucher_type",        // 目标物理表
      "displayName": "凭证类型",
      "refKind": "DCT",                      // 该表来自哪类定义（DCT字典/DOC单据），便于校验表已建
      "conflictColumns": ["id"],             // → ON CONFLICT，幂等 UPSERT（对齐 SeedDataConfig）
      "enabled": true,
      "loadMode": "upsert",                  // upsert（默认）/ insert-skip / replace（受不DROP护栏约束）
      "columns": ["id", "code", "name", "sort_no", "status"],  // 可选：列顺序/白名单
      "rows": [                              // ★ 行数据（对象数组，直接喂引擎 loader）
        { "id": "1", "code": "JZ",  "name": "记账凭证", "sort_no": 1, "status": 1 },
        { "id": "2", "code": "SK",  "name": "收款凭证", "sort_no": 2, "status": 1 },
        { "id": "3", "code": "FK",  "name": "付款凭证", "sort_no": 3, "status": 1 }
      ]
    },
    {
      "tableName": "cf_gl_config",
      "displayName": "总账参数",
      "conflictColumns": ["config_key"],
      "rows": [
        { "config_key": "fiscal_year_start", "config_value": "01-01", "remark": "会计年度起始" },
        { "config_key": "multi_currency",    "config_value": "true",  "remark": "启用多币种" }
      ]
    }
  ]
}
```

**字段说明**
| 字段 | 作用 |
|---|---|
| `metaKind: "SEED"` | 与 DCT/DOC 并列，工作台把它当第三类源；存 `cmx_model_source.kind='SEED'` |
| `moduleMeta.version` | 初始化数据包版本 → 存 `cmx_model_module.seed_version`；升级即比对此版本 |
| `seedTables[].tableName` | 目标表；执行前校验该表已在库中（未建则报"请先建表"） |
| `seedTables[].conflictColumns` | 映射 `SeedDataConfig.conflict_columns` → `INSERT … ON CONFLICT`，幂等 |
| `seedTables[].rows` | 行对象数组，**原样**就是引擎 `load_seed_data` 的 JSON 格式，零转换 |
| `loadMode` | `upsert`(默认幂等) / `insert-skip`(存在跳过) / `replace`(慎用，受不DROP护栏，仅按主键覆盖) |

### 4.2 从包 → 引擎调用（无缝对接）
```
对每个 seedTables[i]:
  SeedDataConfig { table_name: tableName, file: <内存>, conflict_columns: conflictColumns, enabled }
  rows[]  →  PgSeedDataExecutor.execute_all_seed_data(定义, [config], rows)   // 已有 UPSERT 批量+逐行回退
```
> 现有引擎从**文件**读 rows；本设计把 rows **内联**在包里 → 落地时给 loader 加一条"内存 rows 直供"支路即可（或先把包内 rows 落临时文件喂现成 loader，零改引擎）。

### 4.3 与升级 / 历史的关系
- 每次导入初始数据：整包 UPSERT 进 `cmx_model_source`（`kind=SEED`, 翻新 `is_current`）→ 逐表种子 → 更新 `cmx_model_module.seed_version/seed_status` → 追加 `cmx_model_deploy_history(kind=SEED, from→to, seed_rows, ddl_summary=各表行数)`。
- **升级初始数据** = 新版本包（新增/修改行）→ 幂等 UPSERT，自然覆盖到最新；历史里 `SEED v1→v2` 一条，`seed_rows` 记增量。

## 5. 多类型数据库抽象（默认先实现 PostgreSQL）

> 诉求（后补）：实现时抽象为支持多类型数据库，默认先实现 PostgreSQL。
> **好消息**：引擎侧抽象已就绪，本方案顺其自然分层即可。

### 5.1 已有抽象（复用）
- `DdlDialect` trait（`cmx-metadata/src/ddl/mod.rs:34`）——"每种数据库实现该 trait 产出各自 DDL 语法"；现有 `PostgresDdlDialect`（`ddl/postgres.rs`）。
- `TableDefineDbExecutor` trait（`executor.rs:60`）——`create_table / upgrade_table / create_or_upgrade_table` 与具体库解耦；现有 `PgTableDefineExecutor`。
- `DbType` enum（`cmx-database/src/config/mod.rs:8`）——已含 `Postgres / MySql / Sqlite`（解析别名 postgresql/pgsql、mariadb 等）。

### 5.2 本方案的多库策略
1. **系统表 DDL 走方言层**：3+2 张台账表用 `TableDefine` 描述（而非硬编码 SQL），建表时按目标库 `db_type` 选 `DdlDialect` 实现 → **同一份台账定义可建到任意支持的库**。类型映射差异（如 PG `JSONB` vs MySQL `JSON` vs Oracle `CLOB`）在方言层收敛。
2. **`cmx_model_source.source_json` 的存储类型**：抽象为"结构化文本列"，PG=`JSONB`、MySQL=`JSON`、Oracle/其它=`CLOB/TEXT`（方言层决定）。
3. **种子 UPSERT 抽象**：现引擎生成 PG `INSERT … ON CONFLICT`；多库时改由方言层产出（MySQL `INSERT … ON DUPLICATE KEY UPDATE`、Oracle `MERGE`）。这是 SEED 跨库的主要工作量。
4. **落地节奏**：**默认只实现并测通 PostgreSQL**（现状即是）；MySQL/Oracle 留 `DdlDialect`/种子方言的空实现骨架 + `db_type` 分派点，后续按需补。目标库 `db_type` 从 `cmx_sys_datasource.db_type` 取，`registry.db_type` 冗余展示。

> 设计约束：凡是拼 SQL / 类型映射 / 冲突语法之处，一律经方言层，不在编排/台账逻辑里写死 PG 语法——保证"换库只补方言实现，不改主流程"。

## 6. 建表/升级的逐列精细对比（只改差异，绝不先删后建）

> 诉求（后补）：具体建表时先查库中是否已存在此表；若存在，**逐列对比所有信息**；若列全同，再对比**分区、索引**等；只修改与定义不同的部分，**只能改、不能先删后建**，且要**详细确认差异点**。
> 诉求（再补）：**在数据库中获取某个表的元数据，一定要用数据库本身的功能（内省），不能靠元数据表里记录的元数据。**

### 6.0 ★ 数据来源硬约束（本方案第一原则）

**对比时"现状端"的表结构，只能来自目标库的实时内省，绝不读任何台账表。**

- **现状端（old）= 数据库内省**：查目标库 `information_schema` / `pg_catalog`（`information_schema.columns` 列信息、`pg_index`/`pg_class`/`pg_namespace` 主键与索引、`pg_description`/`pg_attribute` 表与列注释、`pg_partitioned_table`/`pg_inherits` 分区），实时反查出一份 `old: TableDefine`。**这是唯一权威**。
- **目标端（new）= 定义编译产物**：Portal DCT/DOC 定义 → 编译为 `new: TableDefine`。
- **台账（`cmx_meta_table_define_version.metadata`、`cmx_model_source` 等）只做记录/审计/回滚参考，绝不作为"库里现在长啥样"的判据。**
- **理由**：台账可能与库真实结构漂移（手工改库、迁移中断、他人改动、坑 A 的 DDL/台账不一致）。只有内省不会骗人；以内省为准，diff 才能"详细确认差异点"并安全增量。
- **现状核对**：引擎已合规——`query_current_table_define`（`executor.rs:167`）正是查 `information_schema.columns` + `pg_index` + `pg_class/pg_index/pg_namespace` + `pg_description` + `pg_attribute`，**不读台账**。本方案沿用并**扩展其内省覆盖面**（补 `db_type`/列注释逐列/主键归属/索引列集/分区），台账职责始终只是"记账"。
- **多库对应**：内省 SQL 因库而异（PG=`information_schema`+`pg_catalog`；MySQL=`information_schema`+`SHOW CREATE TABLE`；Oracle=`ALL_TAB_COLUMNS`/`ALL_INDEXES`/`ALL_PART_TABLES`），统一收敛到 `DdlDialect::introspect_table(...)` 方言方法，默认先实现 PG。

### 6.1 现状（已有能力 vs 需增强）
引擎 `create_or_upgrade_table` 已是"先建、已存在则**内省反查** + diff 增量 ALTER"（`executor.rs` + `ddl/diff.rs`），且 **DROP 已被护栏抑制**（`DropTable`/`DropColumn` 只记录不生成 DDL，`diff.rs:303/329`）——与"绝不先删后建"一致，且现状端已是内省（合 §6.0）。现 `column_changed`（`diff.rs:224`）对比：`field_type / is_nullable / default_value / length / precision / scale`；索引按 `name` 增删；表 `comment`。

**需增强的对比维度**（现 diff 未覆盖或覆盖不全 —— 均需相应扩展内省 SQL 取得现状值）：
| 维度 | 现状 | 增强 |
|---|---|---|
| 列·原始 DB 类型 `db_type` | 未参与对比 | 纳入（round-trip 模式已存 `col.db_type`，避免 `VARCHAR(50)` vs `TEXT` 误判/漏判） |
| 列·comment | 未逐列对比 | 纳入列级注释差异 |
| 列·主键归属 `is_primary_key` | 未对比 | 纳入（主键增减经方言层 ALTER，不重建表） |
| 列·顺序 `ordinal` | 未对比 | 记录差异但**默认不 reorder**（PG 不支持免重建改列序；仅告警） |
| 索引·列集/唯一性 (`columns`/`kind`) | 仅按 name 增删 | 同名但**定义不同** ⇒ 判为"改"（drop old idx + create new，索引可重建，非表重建） |
| 分区 `is_partitioned/partition_*` | 未对比 | 纳入对比；**分区结构变更 PG 无法免重建 ⇒ 只检测+告警+记录，绝不自动重建表** |
| 表空间 `tablespace` / schema | 未对比 | 纳入对比，差异告警 |

### 6.2 对比算法（分层短路，输出结构化差异）
```
upgrade_table(define):
  1. 存在性检查：查目标库 information_schema.tables（内省）→ 不存在则 create（结束）
  2. ★ 反查现表 → old: TableDefine —— 只用数据库内省（information_schema/pg_catalog），绝不读台账（§6.0）
  3. 逐列对比 diff_columns(old_内省, new_定义)：
       - 按列名匹配 → 对每列比对全部属性（type/db_type/nullable/default/len/prec/scale/pk/comment）
       - new 有 old 无 → ADD COLUMN
       - old 有 new 无 → 记 DropColumn 但【不生成 DDL】（护栏），仅告警"库中多出列 X"
       - 同名属性不同 → ALTER COLUMN（逐项，只发变化的子句）
  4. 若"列全同"（无 ADD/ALTER）→ 再对比 索引（同样来自内省 pg_index/pg_indexes）：
       - 同名索引 columns/kind 不同 → DROP INDEX + CREATE INDEX（重建索引，不动表）
       - new 有 old 无 → CREATE INDEX；old 有 new 无 → DROP INDEX
  5. 索引也同 → 对比 分区/表空间/表comment（内省 pg_partitioned_table/pg_description）：
       - 分区结构不同 → 【不执行】，产出 PARTITION_MISMATCH 告警 + 记 history
       - comment 不同 → COMMENT ON …
  6. 汇总 DiffReport（见 6.3）；无差异 ⇒ no-op（幂等）
```
> 短路顺序即用户要求："列全同才比分区/索引"。但实现上索引/分区**始终对比并记录**（只是当列有变更时也一并输出），保证 DiffReport 完整。

### 6.3 差异报告结构（`DiffReport` → 存 `deploy_history.ddl_summary`，界面预览）
```jsonc
{
  "table": "cf_voucher_type",
  "exists": true,
  "verdict": "alter",               // create / alter / nochange / blocked
  "columnDiffs": [
    { "name": "name", "change": "alter",
      "fields": [ { "attr": "length", "from": 50, "to": 100 } ] },   // 逐属性列出 from→to
    { "name": "memo", "change": "add", "definition": { "type": "VARCHAR", "length": 200 } },
    { "name": "old_col", "change": "drop-detected", "action": "ignored",  // 不删，仅告警
      "note": "库中多出该列，按护栏保留" }
  ],
  "indexDiffs": [
    { "name": "idx_vt_code", "change": "recreate",
      "from": { "columns": ["code"], "unique": false },
      "to":   { "columns": ["code","status"], "unique": true } }
  ],
  "partitionDiff": { "change": "mismatch", "action": "blocked",
    "note": "分区键 from(range:created_at) → to(list:region)，PG 无法免重建，已跳过" },
  "commentDiff": { "from": "凭证类型", "to": "凭证类型(核算)" },
  "ddl": [ "ALTER TABLE cf_voucher_type ALTER COLUMN name TYPE VARCHAR(100)",
           "ALTER TABLE cf_voucher_type ADD COLUMN memo VARCHAR(200)",
           "DROP INDEX IF EXISTS idx_vt_code",
           "CREATE UNIQUE INDEX idx_vt_code ON cf_voucher_type (code, status)",
           "COMMENT ON TABLE cf_voucher_type IS '凭证类型(核算)'" ],
  "blocked": [ "partition structure change" ]   // 需人工介入的项，绝不自动重建
}
```

### 6.4 硬约束
- **现状端只用数据库内省**（§6.0 第一原则）：对比的"库里现状"一律来自 `information_schema`/`pg_catalog` 实时反查，绝不读台账元数据。
- **只发差异子句**：每处 ALTER 只针对变化的那一列/那一属性，不整表重写。
- **绝不 DROP TABLE / 先删后建**：任何"结构不兼容到无法 ALTER"的情形（如分区键变更、列类型不可安全转换）→ 判 `blocked`，产出告警 + 记 history，**交人工决策**，不自动毁表。
- **删列/删表只检测不执行**：库中多出的列/表仅告警保留（沿用现护栏）。
- **索引/注释可重建**：索引重建不动表数据，允许自动 DROP+CREATE 索引本身。
- **全程经方言层**：内省 SQL、类型可转换性判断、ALTER 语法因库而异（PG `ALTER COLUMN … TYPE … USING`、MySQL `MODIFY COLUMN`），收敛在 `DdlDialect`。
- **先看后建**：DiffReport 先经 `plan` 预览确认，再 `deploy` 执行（阶段2/3）。

## 7. 状态模型（驱动界面）

### 7.1 数据库级
| 状态 | 判定 | 界面动作 |
|---|---|---|
| `UNINITIALIZED` | 无 `cmx_model_meta` 表或无行 | 横幅「初始化数据库」，下方定义选择禁用 |
| `CURRENT` | `meta_version` == 引擎期望 | 正常显示三段 |
| `NEEDS_META_UPGRADE` | `meta_version` < 引擎期望 | 提示条「升级系统表」 |
| `FOREIGN` | 有 `cmx_` 业务表却无 `cmx_model_meta` | 冲突告警（避免误在他人库上叠加） |

### 7.2 模块级（模块 × kind）—— 即 §9.1 第二层"场景"的判定源
| 场景(scenario) | 判定（`applied` 已应用版本 vs `latest` 定义默认版本） | 动作 |
|---|---|---|
| `create` | 无 `applied`（模块无行 / 该 kind `status=none`） | 建表 |
| `current` | `applied == latest` 且 `status=current` | —（可查历史） |
| `upgrade` | `applied < latest` | 升级（显示 `v{a} → v{l}`） |
| `retry` | `status=failed` | 重试（按 failed 时目标版本） |
| `drift` | `def_checksum` 与 latest 定义不符（同版本但定义已改） | 重新应用 / 提示 |
| `downgrade` | `applied > latest`（库比定义新，罕见） | 只读告警，默认禁降级 |

> 一个模块的三 kind 可各自处于不同场景（如 字典=upgrade、单据=current、初始数据=create），界面按此组合呈现（§9）。

## 8. 三大流程

### A. 数据库初始化（目标库尚无台账）
```
锁 model:init:{db_id}
  → 按目标库 db_type 选 DdlDialect，用 TableDefineDbExecutor(db_id) 建 5 张系统表
     （cmx_model_meta / _module / _deploy_history / _source + 复用 cmx_meta_table_define(_version)）
  → INSERT cmx_model_meta(meta_version=期望值, initialized_by/at, engine_version, portal_version)
  → INSERT cmx_model_deploy_history(kind=INIT, action=create, status=success, operator=…)
  → 回写主控库 cmx_model_registry（该 db_id 行：initialized=1, meta_version, db_type…）
释放锁
```
幂等：`cmx_model_meta` 已有行 ⇒ 跳过或转「系统表升级」。

### B. 系统表升级（`meta_version` 落后）
```
锁 model:meta:{db_id}
  → 对系统表跑 create_or_upgrade_table（增量加列，绝不 DROP；经方言层）
  → UPDATE cmx_model_meta.meta_version = 期望值, last_upgraded_at/by
  → INSERT cmx_model_deploy_history(kind=META_UPGRADE, from→to, status, ddl_summary)
  → 回写主控库 cmx_model_registry.meta_version
释放锁
```

### C. 模块建表/升级（每个选中的字典/单据/初始数据）
```
前置：库已初始化（否则先强制走 A）
1. 编译：定义(默认版本) → cmx-core TableDefine（字段集展开 + 类型映射）        [编译器，阶段3]
2. 判定：查 cmx_model_module 当前 {dct/doc/seed}_version → create / upgrade / skip / retry
3. 预览：DdlDiff 生成"将建/将改"清单（先看后建，不执行；经方言层）             [阶段2]
4. 执行（锁 model:deploy:{db_id}:{module}）：
     a. history 追加 pending → 置 executing（可重入对账锚点，规避坑 A）
     b. ★ UPSERT cmx_model_source（存源定义/初始数据 JSON 原文 + checksum，翻新 is_current）   ← 诉求1
     c. create_or_upgrade_table(每表)  → 推进 cmx_meta_table_define.ddl_status（规避坑 B）
        + 写 cmx_meta_table_define_version（编译后 TableDefine 快照）
     d. SEED：按 §4 拆包 → execute_all_seed_data(种子 UPSERT)
     e. UPSERT cmx_model_module（bump {kind}_version + status=current, table_count, checksum, deployed_by/at）
     f. history 该行置 success（或 failed + error_message + finished_at/duration）
     g. 回写主控库 cmx_model_registry（module_count / table_count / modules_summary / last_deploy_at）
```
**回滚**：读 `cmx_meta_table_define_version` 上一版 JSONB 快照 → 反向 upgrade（受"不 DROP"护栏约束，回滚以"回退到旧列定义"为主，删列仅记录不执行）。源 JSON 亦可从 `cmx_model_source` 取回旧版本复现。

## 9. 工作台界面（场景由"数据库态 × 模块版本态"组合推导，非平铺）

> 现有工作台已具备：目标库确认条、定义多选（DCT/DOC + 搜索 + DAM 过滤）、选项区、生成计划。
> **本次要点**：初始化 / 创建 / 升级**不是三个并列入口**，而是由「数据库状态」×「每模块每 kind 的版本状态」**组合推导**出的场景。界面只呈现"当前真正可做的事"，把无关动作隐藏/禁用。

### 9.1 场景决策：先库级门闸，再模块级组合

**第一层门闸——数据库状态（决定整页大模式）**
| DB 态 | 页面大模式 | 允许的模块动作 |
|---|---|---|
| `UNINITIALIZED` | **初始化模式**：全屏引导「初始化数据库」；模块区**只读预览**（能看要装什么，不能装） | 无（必须先初始化） |
| `NEEDS_META_UPGRADE` | **系统表升级模式**：置顶阻断条「升级系统表 v{n}→v{m}」；模块动作**暂禁用**直到升级 | 无（先升系统表） |
| `FOREIGN` | **冲突模式**：告警"该库有 cmx_ 表但非本台账所建"，仅允许"纳管/只读"，禁写 | 无 |
| `CURRENT` | **正常模式**：进入第二层模块级组合 | 见下 |

> 即：**库没就绪时，创建/升级一律不可达**——避免"库没初始化却让用户勾字典建表"的错位。

**第二层组合——每个"模块 × kind(DCT/DOC/SEED)"独立算出一个动作**
输入两个事实（均实时取得，现状端严格走内省/台账各司其职）：
- `applied` = 该模块该 kind **已应用版本**（读 `cmx_model_module.{kind}_version` + `status`）；无记录 ⇒ 未部署。
- `latest` = 该 kind **定义默认版本**（Portal 定义分组的 default 版本）。

| 组合条件 | 场景 | 动作按钮 | 走流程 |
|---|---|---|---|
| 无 `applied`（未部署） | **创建** | 建表 | C·create |
| `applied == latest` 且 `status=current` | **已就绪** | —（可查看/查历史） | — |
| `applied < latest` | **升级** | 升级 `v{a}→v{l}` | C·upgrade |
| `status=failed` | **修复** | 重试（按 failed 时的目标版本） | C·retry |
| `def_checksum` 与 latest 不符（同版本但定义已改） | **漂移** | 重新应用 / 提示 | C·upgrade |
| `applied > latest`（库比定义新，罕见） | **降级/告警** | 只读告警，默认禁降级 | — |

> **组合而非罗列**：一个模块可能"字典=升级、单据=创建、初始数据=已就绪"三态并存；界面按模块聚合展示这三格，用户可**跨 kind 混合勾选**一次性提交（同一 batch）。

### 9.2 界面布局（正常模式下，按场景聚合而非按段罗列）

**A. 库状态条（顶部，始终显示）**
`● primary · PostgreSQL · 已初始化 · 系统表 v1 · 12 模块 / 187 表`；非 CURRENT 时此条变为阻断横幅（初始化/升级系统表/冲突）。

**B. 汇总徽标（把场景计数摆出来，一眼看全局）**
`可创建 5 · 可升级 3 · 已就绪 8 · 失败 1 · 漂移 2`（点徽标＝按该场景过滤下方列表）。

**C. 模块矩阵（主体，一模块一行，三 kind 三格，每格自带场景动作）**

| 模块 | 数据字典 | 业务单据 | 初始化数据 | 表数 | 操作 |
|---|---|---|---|---|---|
| GL 总账 | `⤴ v1→v3`〔升级〕 | `✔ v1` 已就绪 | `＋ 创建` | 35 | ☑ 〔历史〕 |
| AP 应付 | `✔ v2` 已就绪 | `⚠ 失败`〔重试〕 | `— 无定义` | 12 | ☑ 〔历史〕 |
| AR 应收 | `＋ 创建` | `＋ 创建` | `＋ 创建` | 0 | ☑ 〔历史〕 |

- 每格四态着色：`＋创建`(蓝) / `⤴v_a→v_l 升级`(琥珀) / `✔v 已就绪`(绿) / `⚠失败 重试`(红) / `— 无定义`(灰)。
- 行尾复选：勾选后**只把该行里"非已就绪"的格**纳入待执行（已就绪自动跳过）。
- 顶部「全选可创建」「全选可升级」快捷按钮，即选中所有该场景格。

**D. 执行抽屉（勾选后底部浮出）**
`将执行：创建 4 格 / 升级 3 格（约 62 表变更） → primary`，按钮**「生成计划（预览 DiffReport）」→「执行」**。计划里逐格展示 create/upgrade/blocked（§6.3 的 DiffReport），确认后统一走流程 C（同一 batch_id）。

### 9.3 场景 → 动作 → 流程 的映射（无歧义）
```
DB.UNINITIALIZED         → 流程 A（初始化）           唯一可点
DB.NEEDS_META_UPGRADE    → 流程 B（系统表升级）        唯一可点
DB.FOREIGN               → 无写动作（纳管/只读）
DB.CURRENT + 格.创建      → 流程 C·create
DB.CURRENT + 格.升级      → 流程 C·upgrade（v_a→v_l）
DB.CURRENT + 格.失败      → 流程 C·retry
DB.CURRENT + 格.漂移      → 流程 C·upgrade（重新应用）
DB.CURRENT + 格.已就绪    → 无动作（可查历史）
```
> `db-state` 接口一次性返回每模块每 kind 的 `{applied, latest, status, scenario}`，前端**只渲染 scenario 已算好的结果**，不在前端重算判定，保证与后端一致。

### 9.4 历史时间线（点〔历史〕）
侧栏读 `cmx_model_deploy_history`（按模块或整库），倒序时间线（示意）：
```
● 2026-07-01 10:22  DCT  upgrade  v1 → v2   success   张三   35 表 / 12 列变更   〔DDL 摘要〕
● 2026-06-28 15:03  INIT create   —  → v1   success   李四   5 系统表
● 2026-06-28 15:05  DOC  create   —  → v1   failed    李四   error: column type…      〔重试〕
```
点〔DDL 摘要〕展开 `ddl_summary` JSONB（建了哪些表、加了哪些列/索引）。

## 10. API 草案（`/api/portal/model/*`，落 Rust 容器）

| 方法 | 路径 | 入参 | 出参 / 作用 |
|---|---|---|---|
| GET | `…/db-state` | `db_id` | `{ initialized, meta_version, expected_meta_version, db_status, modules:[…], foreign }` |
| POST | `…/init` | `{db_id}` | 建系统表 + 写 meta + history + 回写 registry；返回新 db-state |
| POST | `…/meta-upgrade` | `{db_id}` | 升级系统表 |
| GET | `…/plan` | `db_id, defs:[{kind,domain,app,module,file}]` | 每定义 `action(create/upgrade/skip/blocked)` + **DiffReport（逐列/索引/分区差异，见 §6.3）** |
| POST | `…/deploy` | `{db_id, defs:[…], options}` | 执行建表/升级 + 存源 JSON + 台账推进 + 回写 registry（阶段3） |
| GET | `…/history` | `db_id, module?` | 时间线（读 `cmx_model_deploy_history`） |
| GET | `…/source` | `db_id, module, kind, version?` | 取回**源定义/初始数据 JSON 原文**（读 `cmx_model_source`；诉求 1） |
| GET | `…/registry` | — | **主控库跨库总览**：各 `db_id` 的初始化态/模块数/版本摘要（读 `cmx_model_registry`；诉求 2） |
| POST | `…/registry/sync` | `{db_id}` | 手动对账：从目标库台账重投影到主控库 registry |

### `db-state` 返回结构（**scenario 由后端算好**，前端只渲染）
```jsonc
{
  "db_id": "primary",
  "initialized": true,
  "meta_version": 1,
  "expected_meta_version": 1,
  "db_status": "CURRENT",           // UNINITIALIZED | CURRENT | NEEDS_META_UPGRADE | FOREIGN
  "foreign": false,
  "page_mode": "normal",            // init | meta_upgrade | conflict | normal（第一层门闸，§9.1）
  "scenario_counts": {              // 汇总徽标（§9.2-B）
    "create": 5, "upgrade": 3, "current": 8, "failed": 1, "drift": 2
  },
  "modules": [
    {
      "domain": "fi", "application": "cmxfico", "module": "gl", "module_name": "GL 总账",
      "table_count": 35,
      // 每 kind 一格：applied / latest / status / ★scenario（后端组合推导，§9.1 第二层）
      "dct": { "applied": "1", "latest": "3", "status": "current", "scenario": "upgrade" },
      "doc": { "applied": "1", "latest": "1", "status": "current", "scenario": "current" },
      "seed":{ "applied": null,"latest": "1", "status": "none",    "scenario": "create"  },
      "overall_status": "partial",
      "current_deployed_at": "2026-07-01T10:22:00Z", "deployed_name": "张三"
    }
  ]
}
```
> `scenario ∈ create | upgrade | current | retry | drift | downgrade`；前端按此值决定每格的着色与按钮，**不在前端重算**（§9.3）。`page_mode` 决定整页大模式（初始化/系统表升级/冲突/正常）。

## 11. 落地顺序（MVP 优先）

| 阶段 | 内容 | 满足的诉求 |
|---|---|---|
| **0（先做）** | 新增 5 张系统表 DDL（`cmx_model_meta/_module/_deploy_history/_source` + 主控库 `cmx_model_registry`）+ `GET db-state`（**含每模块每 kind 的 scenario + page_mode**，只读）；工作台按 §9 场景组合渲染（库门闸 + 模块矩阵 + 场景徽标） | **"列出已建哪些模块 + 是否已初始化 + 按状态组合出创建/升级/初始化场景"** |
| 1 | `init` + `meta-upgrade`（建/升系统表，经方言层）；同步回写主控库 registry | "未初始化则做初始化""系统表可升级""主控库总览" |
| 2 | `plan`（**DiffReport 逐列/索引/分区差异预览**，先看后建） | 安全确认 + "详细确认差异点" |
| 3 | `deploy`（**逐列精细 ALTER，只改差异、绝不先删后建** + 存源 JSON + 台账推进 + 接编译器） | "模块字典/单据/初始数据升级 + 源 JSON 留档 + 全程记录" |

> 编译器（Portal DCT/DOC 定义 → cmx-core TableDefine）是阶段3 唯一从零写的核心；阶段0–2 全部是读现有台账 + 建台账表，风险低。多库方言默认只实 PostgreSQL，MySQL/Oracle 留骨架。

## 12. 待你拍板的点

1. **台账位置**：本方案落在**目标业务库内**（DB 自描述，推荐）+ **主控库存 `cmx_model_registry` 汇总投影**（诉求 2，区分各 `db_id`）。已按此设计。
2. **系统表建法**：走**引擎内置 TableDefine**（能复用同一条 diff 升级链路 + 天然多库方言，推荐）还是迁移 SQL 文件（只对默认库有 runner，业务库需另走）。
3. **回滚力度**：受"绝不 DROP / 先删后建"护栏约束（§6.4），回滚只回退列定义、索引可重建、删列/删表/分区变更仅检测告警不执行。是否接受此安全边界。
4. **kind 粒度**：字典/单据/初始数据三分（本方案）是否够；是否还需把"弹性组合 FC"也纳入模块态。
5. **主控库 registry 粒度**：每库一行 + `modules_summary` JSONB（本方案，轻量）还是每库×模块一行（更细、可 SQL 聚合，行数多）。
6. **多库落地范围**：默认只实现并测通 PostgreSQL（其余留方言骨架）——确认此优先级。
