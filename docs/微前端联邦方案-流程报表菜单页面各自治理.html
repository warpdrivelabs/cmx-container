微前端联邦方案

流程 / 报表 的菜单与页面资源「各自治理、门户集中呈现」 —— 把后端「一芯双壳」范式上抬到前端层
版本 草案 v1 范围 方案设计（不动代码） 关联 cmx-portalservicecmx-flowenginecmx-report 前置 后端已微服务化（proxy 挂载已就位）

后端三个能力中心（门户 :8080 / 流程 :8091 / 报表 :8092）已各自独立成微服务，并通过 center_client.urls 的 「一芯双壳」开关在门户里内嵌↔反代自由切换。但前端仍未解耦：流程、报表的页面文件塞在门户后端目录、菜单行灌进门户库， 两者仍强依赖门户。本方案回答一个问题 —— 如何让各微服务也拥有并治理自己的菜单 / 页面 / 静态资源，同时门户仍能集中聚合、统一交互与展示。 核心思路：把后端已验证的「一芯双壳」范式，原样上抬到前端资源层。

1. 现状：前端资源为何还锁在门户

调研当前代码库，流程 / 报表的前端资源分布在门户后端的三个位置，全部由门户进程负责存储与投递：

资源今天在哪谁投递归属编码
页面（native 页） cmx-container/data/native-pages/sources/portal/flow/{design-workbench,todo-center,task-form}.js
.../portal/rpt/{designer,designer-workbench,report-applier,report-app-workbench,formula-eval}.js		 门户进程 ServeDir 静态投递（router.rs 挂 web_folder / /portal / /html） 目录名 flow / rpt（约定，非强绑定）
菜单（导航 + 工作台定义） 门户库 cmx_menu 表；由 data/sql/init_menu.sql 等 seed 灌入 门户读 cmx_menu 装配菜单树；menu_pages.rs 解析「菜单 → 页面」 行上有 domain_code/application_code/module_code（如 fi/cmxfico/gl）
静态资源 / 共享运行时 门户 web_folder 与 /portal、/html dist（组件库、图标、vendor） 门户进程 ServeDir 全局共享，无模块归属
症结：cmx_menu 行里其实已经带了 domain/application/module 归属编码，页面文件也已按 flow/、rpt/ 分目录 —— 「谁拥有什么」在数据上早已清晰，缺的只是「让拥有者自己保管、门户按归属聚合」这一层机制。今天所有权是逻辑上的，物理上仍全挤在门户。

后果：流程 / 报表团队每改一个页面或菜单，都要动门户仓、灌门户库、随门户发布 —— 微服务化在后端已完成，前端却仍是单体。

2. 目标与设计原则

要达成的

  • 各自治理：流程页面 / 菜单进 cmx-flowengine 仓，报表的进 cmx-report 仓，随各自服务发布，不再碰门户。
  • 集中呈现：用户仍在同一个门户外壳里看到统一菜单树、在同一套四区工作台里打开流程 / 报表页，URL 同源、体验无缝。
  • 一键切换：内嵌（门户自投递）↔ 联邦（微服务自投递、门户聚合）由配置切换，复用后端已有的 center_client.urls 开关。
  • 零回归：任一阶段都能回退到「门户全包」的今天，前端浏览器请求不变。

设计原则

  • 范式复用，不造新基建：后端 ReportProxyModule/FlowProxyModule + center_client 开关已验证，前端资源走同一套。
  • 所有权即归属编码：以 cmx_menu 既有的 domain/application/module 作为联邦聚合键，不发明新标识。
  • 契约先行：微服务只需对外暴露两个东西 —— 一份菜单清单（manifest） + 一个页面/资源目录，其余门户不关心其内部。
  • 外壳单一**：只有门户持有 Shell（登录、导航框架、四区工作台容器）；微服务只提供「被嵌进去的内容」，不各自造壳。

3. 三类资源的所有权重划

把「门户拥有一切」拆成「门户拥有外壳 + 聚合，微服务拥有各自内容」：

资源迁后归属门户角色微服务角色
登录 / 外壳 / 导航框架 / 四区工作台容器门户唯一持有者无
流程页面（设计器 / 待办 / 办理表单）流程微服务聚合 / 代理投递存储 + 投递源
报表页面（设计器 / 应用器 / 大盘）报表微服务聚合 / 代理投递存储 + 投递源
流程 / 报表菜单各自微服务联邦合并 + 权限过滤 + 渲染产出 menu manifest
共享运行时（组件库 / 图标 / vendor）门户（版本化契约）唯一投递，跨源可取引用门户源，不自带副本
门户自身页面 / 菜单（基础数据、系统控制…）门户不变无
关键判断：Shell 与共享运行时必须留门户单一持有（否则多壳、组件库多副本会漂移）；页面与菜单按模块下放（它们本就有归属编码，且变更频率高、最该解耦）。这条线划对了，方案就成立。

4. 核心架构：一芯双壳上抬到前端

后端每个能力已经是「一芯双壳」：同一套 handler（芯），既能内嵌进门户进程（ReportModule），又能独立跑 + 门户反代（ReportProxyModule）， 由 center_client.urls.report 配没配来切换。本方案把同一结构复制到前端资源 —— 每个微服务额外产出「菜单清单 + 页面目录」两件前端制品，门户对它们也做「内嵌镜像 ↔ 反代联邦」双模。

┌──────────────────────────────── 浏览器（单一同源门户外壳） ─────────────────────────────┐ │ 登录 · 顶栏 · 聚合菜单树 · 四区工作台容器（explorer/content/property/bottom） │ └───────────────▲───────────────────────────▲───────────────────────────▲──────────────┘ │ GET /api/menu/tree │ GET /portal/flow/*.js │ GET /portal/rpt/*.js │ （聚合后的统一菜单） │ （流程页面） │ （报表页面） ┌───────┴───────────────────────────┴───────────────────────────┴───────┐ │ 门户 cmx-portalservice :8080 —— 聚合器 / 外壳 │ │ │ │ 菜单聚合器 ── 合并 [门户本地] + [流程 manifest] + [报表 manifest] → 一棵树 │ │ 页面投递 ── 按 center_client.urls 决定： │ │ ● 空 → 内嵌镜像（ServeDir 门户本地副本，= 今天） │ │ ● 有 → 反代联邦（转发到微服务的 /ui 与 /api/menu/manifest） │ └───────────────▲───────────────────────────────────▲─────────────────────┘ proxy（可选）│ proxy（可选）│ ┌────────────────┴──────────────┐ ┌─────────────┴───────────────────┐ │ cmx-flowengine :8091 │ │ cmx-report :8092 │ │ 芯：flow handler（已有） │ │ 芯：rpt handler（已有） │ │ + web/ui/ 流程页面（新） │ │ + web/ui/ 报表页面（新） │ │ + /api/menu/manifest（新） │ │ + /api/menu/manifest（新） │ └────────────────────────────────┘ └──────────────────────────────────┘
门户：外壳 + 聚合，唯一 Shell 流程：自持页面 + 菜单清单 报表：自持页面 + 菜单清单

与后端完全同构的一句话：「配了远程地址就联邦（微服务自投递、门户聚合代理），没配就内嵌（门户本地镜像，即今天）—— 前端浏览器请求零改」。

5. 菜单联邦（Menu Federation）

今天门户读一张 cmx_menu 全表装配菜单树。联邦后：门户只保管自己的菜单，流程 / 报表菜单由各微服务产出 manifest，门户在渲染前合并。

5.1 菜单清单契约（各微服务对外暴露）

每个微服务提供一个只读端点，返回自己那棵子树。结构直接复用 cmx_menu.definition 的四区 workspace-node 语义 —— 门户已能渲染它，零新渲染逻辑：

// GET  http://cmx-flowengine:8091/api/menu/manifest
{
  "owner": { "domain":"wf", "application":"cmxflow", "module":"flow" },   // 聚合键 = 既有归属编码
  "version": "2026.08.12",                                        // 变更即失缓存
  "nodes": [
    { "code":"flow-designer", "name":"流程设计器", "icon":"flow-chart", "funCode":"WF_DESIGN",
      "definition": { /* 四区 workspace-node：explorer/content/property/bottom → views[] */
        "content": { "views":[ { "type":"native", "page":"flow/design-workbench" } ] } } },
    { "code":"flow-todo",     "name":"我的待办",   "page":"flow/todo-center", "funCode":"WF_TODO" }
  ]
}
为什么直接复用 definition？ 现在的菜单树、四区工作台、menu_pages.rs 的「菜单→页面」解析全部围绕这套 JSON。 manifest 里原样承载它，门户合并后走的还是老渲染路径 —— 联邦只改「菜单从哪来」，不改「菜单怎么画」。

5.2 门户侧聚合器

1

取

启动时（或带 TTL 缓存地）拉各微服务 /api/menu/manifest；配置里没登记的服务跳过。
2

并

把 manifest 的 nodes 按 owner 归属编码挂到菜单树对应位置（门户仍持有顶层域/应用骨架，微服务只填自己的模块子树）。
3

滤

合并后统一过门户的权限层（funCode → 用户可见性），联邦不绕过鉴权。
4

降级

某微服务不可达 → 用上次缓存的 manifest 或门户本地镜像；绝不让整棵菜单树塌掉（对齐后端「子查询失败降级 0」哲学）。

5.3 两种落地形态（可分阶段）

A. 构建期镜像（保守）B. 运行期联邦（彻底）
manifest 来源发布时把各微服务 manifest 灌进门户 cmx_menu（同今天，但源在微服务仓）门户启动/定时实时拉取，不落门户库
解耦程度仓库解耦（源码归位），运行时仍集中仓库 + 运行时全解耦
门户库 cmx_menu仍存流程/报表行（但由 seed 自动同步，非手工）只存门户自己的行
风险极低（机制不变）需处理拉取失败/缓存/版本

建议先 A 后 B：A 立即拿到「源码归各仓」的解耦收益且零风险，B 再拿「运行时不依赖门户库」的彻底收益。

6. 页面服务：内嵌镜像 ↔ 反代联邦

页面（*.js native 模块）今天由门户 ServeDir 从 web_folder 投递。联邦后同样双模，浏览器 URL 保持 /portal/flow/*.js 不变：

内嵌镜像（默认 = 今天）

center_client.urls.flow 未配 → 门户 ServeDir 投递本地副本。副本由发布流水线从 cmx-flowengine/web/ui/ 同步而来（源在微服务仓，门户只是镜像），行为与今天逐字节一致。

反代联邦（配了远程地址）

配了 → 门户把 /portal/flow/* 透明转发到 cmx-flowengine 的 /ui/*。完全复用后端 FlowProxyModule 的转发机制（同源出站、三层鉴权头 X-API-Key / X-Delegated-User-Token / X-Request-Id），只是转发的是静态资源而非 API。

6.1 微服务侧要补的能力（很小）

  • chassis 加静态目录投递：今天 cmx-web-chassis 只挂路由 + 大盘（include_str! 单页），尚无 ServeDir。补一个可选「静态目录」能力，让 flow-server / report-server 能投递自己的 web/ui/。这是加法、不改现状（大盘等仍在）。
  • 页面目录归位：data/native-pages/sources/portal/flow/* → cmx-flowengine/web/ui/；.../rpt/* → cmx-report/web/ui/。（对标本会话已做的后端 crate 物理迁移。）
转发范围问题：现有 proxy 只转 /api/*。前端联邦需要门户能把一段前缀（如 /portal/flow/）整体转发到微服务的 /ui/。这是对现有 proxy「路径映射」的一处扩展（恒等或前缀替换），机制同构、复杂度低。

7. 共享运行时与静态资源

流程 / 报表页面并非孤立文件 —— 它们 <script> / import 依赖门户提供的共享运行时（组件库 cmx-data-comp、电子表格内核、图标、UI5 runtime、vendor）。这是联邦里最需要拍板的一环。

策略做法利弊
① 门户单源（推荐）共享运行时只由门户在稳定 URL（如 /portal/vendor/…）投递并版本化；微服务页面跨源引用它零副本、零漂移、体积小微服务页面对门户 vendor URL + 版本有契约依赖；跨源需 CORS
② 各自打包每个微服务把运行时打进自己的 web/ui/页面自包含、可独立部署验证多副本、易版本漂移、体积膨胀
③ 独立 CDN运行时抽到独立 CDN，三方都引彻底中立多一个部署物 + 缓存治理
建议 ①：门户作为「共享运行时的唯一发行方」，用版本化契约（/portal/vendor/@2026.08/…）锁住兼容性。这既保留了本会话记忆里 [[cmx-megasheet-vendor-dual-bundle]] 的「三产物同步纪律」精神（避免副本漂移），又不逼各微服务重复打包重型组件库。CORS 头由门户/反代统一注入。

8. 统一外壳：门户如何集中呈现

用户视角完全不变：仍登录门户、仍在左侧看一棵菜单树、点节点在四区工作台里开 Tab。联邦只发生在幕后：

  1. 门户 Shell 请求 /api/menu/tree → 拿到聚合后的统一树（门户本地 + 流程 + 报表，已按权限过滤）。
  2. 用户点「流程设计器」→ Shell 读该节点 definition 的四区 workspace-node（同今天）。
  3. 节点 view 指向 flow/design-workbench → Shell 按老路 import() 该 native 模块，浏览器发 GET /portal/flow/design-workbench.js。
  4. 该请求命中门户：内嵌模式→本地副本；联邦模式→反代到 cmx-flowengine。Shell 与浏览器都不感知差别。
  5. 页面在四区容器内渲染，调 /api/flow/*（后端也走内嵌/反代双模）—— 前后端联邦对齐。
一句话：门户从「流程/报表页面与菜单的所有者」退位为「聚合器 + 外壳 + 共享运行时发行方」；微服务升格为各自前端资源的源。交互面 100% 不变。

9. 迁移路线（四阶段 · 每阶段零回归）

F0

契约定型（纯设计，本文档）

敲定 menu manifest 契约、页面目录约定（<svc>/web/ui/）、共享运行时策略（建议门户单源版本化）、URL 前缀（/portal/flow/、/portal/rpt/ 不变）。不动代码。
F1

源码归位（仓库解耦，运行时不变）

流程页面物理迁到 cmx-flowengine/web/ui/、报表迁到 cmx-report/web/ui/；发布流水线把它们同步镜像回门户 web_folder。菜单走「构建期镜像 A」：manifest 源在微服务仓，seed 自动灌门户库。 浏览器请求、门户投递、菜单渲染全部逐字节不变 —— 纯迁源，对标本会话后端 crate 的物理迁移。
F2

微服务自投递能力（加法）

给 cmx-web-chassis 补可选 ServeDir；flow-server / report-server 能投递自己的 web/ui/ + 暴露 /api/menu/manifest。此时两条路并存：门户镜像仍在跑，微服务自投递可独立验证（curl 微服务 /ui/…、/api/menu/manifest）。默认仍走门户镜像，零回归。
F3

联邦开关上线（运行时解耦）

门户菜单聚合器实时拉 manifest（形态 B）；页面前缀反代扩展就位。center_client.urls.{flow,report} 配了远程地址 → 切联邦（微服务自投递 + 门户聚合代理）；没配 → 回内嵌镜像。与后端 API 的一芯双壳开关同一把钥匙。任何异常配空即回退。
回退保证：F1–F3 每一阶段，把 center_client.urls 相关项配空，就回到「门户全包」的今天。开关是配置级的，不需回滚代码。

10. 配置开关一览

# portal-server.toml —— 复用后端已有的 [center_client.urls]，前后端联邦同一开关
[center_client.urls]
flow   = "http://127.0.0.1:8091"   # 配了：流程 API + 页面 + 菜单都联邦到 flow-server；空=门户内嵌镜像
report = "http://127.0.0.1:8092"   # 配了：报表 API + 页面 + 菜单都联邦到 report-server；空=门户内嵌镜像

# 可选：前端联邦的细粒度旋钮（若想 API 联邦但页面仍内嵌，用于灰度）
[federation]
menu_mode  = "manifest"   # "seed"(构建期镜像A) | "manifest"(运行期联邦B)
ui_mode    = "proxy"      # "mirror"(门户本地副本) | "proxy"(反代到微服务 /ui)
manifest_ttl_secs = 300       # manifest 缓存，拉取失败用旧值降级

沿用后端惯例：URL 配了就联邦、没配就内嵌；[federation] 段仅为灰度/回退提供更细的旋钮，缺省即「跟随 URL 开关」。

11. 收益 / 取舍 / 风险

收益

  • 流程 / 报表团队独立发布前端，不排队等门户。
  • 门户库 cmx_menu 瘦身，只管自己的行（形态 B）。
  • 前后端联邦对齐：API 与页面用同一把 center_client 钥匙，心智统一。
  • 微服务可独立演示（自投递 /ui + manifest），脱离门户也能跑通自己的界面。

取舍 / 风险

  • 共享运行时契约是命门：跨源引用 + 版本化必须治理好，否则组件库漂移（见 §7，建议门户单源）。
  • 运行期联邦（B）引入拉取失败/缓存/版本三件事 —— 用 TTL + 降级缓存 + 版本号解决，对齐后端降级哲学。
  • chassis 加 ServeDir、proxy 扩展前缀转发 —— 都是加法，但需一次性做对（路径映射、CORS、鉴权头透传）。
  • 权限过滤必须在门户聚合后统一做，联邦不能成为绕过 funCode 鉴权的后门。
