异步任务中心方案

Async Job Center · 长任务编排 · 实时进度 SSE 推送 · 暂停/停止/重启可控 · 前后端双向发起
定位：为 cmx-container 提供一套通用的长时后端任务基础设施——统一的作业生命周期、协作式暂停/停止/重启控制、按作业实时推送详细进度（SSE），前端有专门的任务中心工作台可视化监控与操控。业务方（报表计算、报表校验、凭证记账、销售汇总……）只需实现一个 trait 并注册，即可接入。
后端骨架：新增 crate 群 cmx-job-core（领域模型/状态机/JobHandler trait/JobContext）+ cmx-job-store-pg（作业与日志持久化）+ cmx-job-api（HTTP + SSE 端点，实现 ModuleRoutes）。母版对标现有 cmx-rpt / cmx-flow / cmx-doc 三分层。
SSE 母版：复用 cmx-ai::SessionRegistry 的成熟模式（按 id 广播 → 多前端订阅 → unfold 转 axum Sse → EventSource 走 query access_token + 白名单放行），抽象为通用 JobEventHub。复用模式，不耦合代码。
本文范围：仅出方案（架构 / 状态机 / 控制模型 / 通信协议 / 持久化 / 前端 / 业务接入 / 扩展路线 / 落地锚点），不动代码。

1 · 目标、范围与设计原则

1.1 要解决的问题

当前 cmx-container 内，报表计算（report_design_compute / rpt_compute）、报表校验、凭证记账、销售汇总等重处理，都是同步 async 端点：请求发起后一直阻塞到算完才返回。由此产生四个痛点：

  • 无进度——前端只能转圈，不知道算到第几张报表、还要多久、哪张失败了。
  • 不可控——一旦发起无法暂停/停止；算错了参数只能干等或杀连接（后端仍在跑）。
  • 易超时——HTTP/网关超时会截断长请求，但后端计算仍在空转，浪费且状态不明。
  • 只能前端发起——定时批量、事件触发（如「期末自动结账」）这类后端自发的长任务，没有统一的承载与监控入口。

1.2 目标

#目标说明
G1统一作业生命周期一套状态机覆盖排队→运行→完成/失败/取消，所有长任务共用。
G2实时详细进度SSE 按作业推送：总进度 + 每个明细单元（如每张报表）的状态与消息，前端毫秒级可见。
G3可控：暂停 / 恢复 / 停止 / 重启协作式控制，业务在检查点响应；停止能真正让后端停下（非仅断连）。
G4前后端双向发起前端 POST 发起，后端（定时器 / 事件总线 / 其它服务）内部 submit() 发起，走同一套监控。
G5低接入成本新业务只实现一个 JobHandler trait + 一条 inventory::submit! 注册，不碰框架。
G6可恢复 / 可审计作业状态与关键日志落库；进程重启后能看到历史作业；失败可重启（从头或断点）。
G7面向未来扩展预留优先级队列、并发编排（子作业/DAG）、多实例分布式、定时触发、可观测性接口。

1.3 设计原则

  • 复用母版，不造轮子——SSE 沿用 SessionRegistry 模式，crate 分层沿用 cmx-rpt，注册沿用 inventory，路由沿用 ModuleRoutes + merge 破环。
  • 框架与业务解耦——cmx-job-* 不依赖任何业务 crate；业务 crate 依赖 cmx-job-core 实现 trait。破环方向与 ReportModule 一致。
  • 协作式而非抢占式——Rust async 无法安全强杀 future。停止/暂停靠业务在 checkpoint() 协作。对不可中断的原子操作，只在其边界响应。
  • 快照优先——进度以「当前完整快照」为事实源，增量事件只是快照的 diff 推送。任何时刻新连接都能立即拿到全貌，天然抗刷新/抗断线。
  • 渐进落地——先单机内存态跑通（M1），再补持久化与断点（M2），再谈分布式（M3）。每步可独立上线。

3.1 状态机

状态标识含义可触达的下一状态
Pendingpending已创建入队，等待 worker 空闲。Running、Cancelled
Runningrunningworker 正在执行 handler。Paused、Cancelling、Completed、Failed
Pausedpausedhandler 在 checkpoint 挂起，占用 worker 槽但不推进。Running（resume）、Cancelling
Cancellingcancelling已发停止信号，handler 正在响应/清理（协作式，非瞬时）。Cancelled
Cancelledcancelled已停止（排队中直接停 or 运行中协作停）。终态。—（可 restart 派生新作业）
Completedcompletedhandler 正常返回，带结果摘要。终态。—
Failedfailedhandler 返回错误或 panic 被捕获，带错误摘要。终态。—（可 restart）
Cancelling 为何单列：停止不是瞬时的。发信号后 handler 可能正在一条大 SQL 中途，要到下一个 checkpoint 才能响应。Cancelling 让前端立刻看到「正在停止」，避免用户以为按钮没反应而反复点。同理，暂停也有一个短暂的「请求已发、尚未挂起」窗口，可用一个 pause_requested 标志在 UI 上表达，不必单列状态。

4 · 控制模型：暂停 / 停止 / 重启的协作式实现

4.1 为什么是协作式

Rust 的 async future 不能被安全地「强杀」——直接 drop 一个正在写库的 future 会留下不一致状态。因此本系统采用协作式控制：JobManager 通过 tokio::sync::watch 通道把最新控制意图推给正在跑的 handler，handler 在自己选定的安全点（checkpoint）响应。这与 cmx-ai 的 abort（转发上游中止）异曲同工，但更细化为四种意图。

4.2 控制信号传递

// 每个 Running 作业持有一对 watch 通道：Manager 持 Sender，Context 持 Receiver
pub enum Control { Run, Pause, Cancel }   // watch 只保留“最新意图”，天然去抖

// —— 业务 handler 侧：在循环里埋 checkpoint（唯一需要业务配合的点）——
for report in reports {
    ctx.checkpoint().await?;          // ① 若 Pause：在此挂起直到 Run/Cancel  ② 若 Cancel：返回 Err(Cancelled)  ③ 顺带心跳
    ctx.item_running(&report.code, "计算中"); // 明细行→计算中
    let r = compute_one(&report).await;
    match r {
        Ok(v)  => ctx.item_ok(&report.code, v.elapsed_ms),
        Err(e) => ctx.item_fail(&report.code, &e),   // 单张失败不必终止整个作业（策略可配）
    }
    ctx.progress_inc(1);                  // 总进度 +1，Hub 扇出 progress 事件
}
// —— checkpoint 内部（框架实现，业务无需关心）——
pub async fn checkpoint(&self) -> Result<(), JobCancelled> {
    loop {
        match *self.control.borrow() {
            Control::Cancel => return Err(JobCancelled),        // 让 handler 走 ? 优雅退出
            Control::Run    => return Ok(()),                     // 放行
            Control::Pause  => {
                self.hub.emit_state(JobStatus::Paused);        // 首次进入推 paused 状态
                self.control.changed().await.ok();          // 挂起等待下一次意图变化，零轮询
            }
        }
    }
}
关键优势：watch::changed().await 让暂停是真正的挂起（不占 CPU、不轮询），恢复是零延迟唤醒。控制意图用「最新值」语义，用户狂点暂停/恢复也只认最后一下，天然幂等。

4.3 四种控制的语义

操作端点Pending 时Running/Paused 时说明
暂停POST …/pause标记 pause_requested，取出即挂起推 Control::Pause，下个 checkpoint 挂起占用 worker 槽（见 §4.4 权衡）
恢复POST …/resume清除 pause_requested推 Control::Run，唤醒挂起点幂等
停止POST …/cancel直接置 Cancelled，出队推 Control::Cancel → Cancelling → 清理 → Cancelled协作式，非瞬时
重启POST …/restart—（无意义）仅终态可重启见 §4.5

4.4 暂停占槽的权衡

暂停中的作业仍占用一个 worker 并发槽。两种取舍：

  • M1 简单版（推荐先行）：暂停占槽。实现最简，语义清晰（handler 栈还在，恢复即原地继续）。配合「最大暂停时长」兜底，超时自动取消，防止长期占槽饿死队列。
  • M2+ 让位版：暂停超过阈值时，若 handler 支持 Suspendable（能把进度序列化为 checkpoint），则卸载出内存、释放槽，恢复时从 checkpoint 重建。成本高，仅对超长作业开启。

4.5 重启（restart）语义

只对 Failed / Cancelled 终态作业开放。两种模式，由 JobKind 声明其支持哪种：

模式行为适用前提
从头重跑
restart=fresh		用原 params 派生一个新 job_id 重新执行（原作业保留作审计）。报表计算/校验（幂等，按 org+period 覆盖写）Handler 幂等
断点续跑
restart=resume		从 cmx_job_checkpoint 读取游标，跳过已完成项，只补未完成部分。凭证记账/大批量汇总（重跑代价高）Handler 实现 Resumable，周期性存 checkpoint
幂等是重启的地基——这与库内既有实践一致：报表计算按 org+period 覆盖写 cr_cell_data、DCT/DOC 落库前有列级校验与错误码。新业务接入时，方案要求 handler 显式声明幂等级别，restart 才敢自动执行；否则退化为「仅允许人工确认后从头重跑」。

5 · 进度模型：快照 + 增量事件

5.1 双层进度

进度分两个粒度，前端可同时展示「总进度条」与「明细流」：

pub struct ProgressSnapshot {
    pub phase:        String,      // 当前阶段名："装载模板" / "求值" / "落库"
    pub phase_index:  u32,         // 第几阶段（多阶段作业）
    pub phase_total:  u32,         // 总阶段数
    pub done:         u64,         // 已完成明细数（如已算 28 张）
    pub total:        u64,         // 总明细数（42 张）→ 百分比 = done/total
    pub ok:           u64,         // 成功数
    pub failed:       u64,         // 失败数
    pub message:      String,      // 一句话人读状态
    pub eta_ms:       Option<u64>, // 预估剩余（滑动均速外推，可选）
    pub items:        Vec<ProgressItem>, // 明细行（可裁剪：仅推最近变化的，全量走详情接口）
    pub rev:          u64,         // 单调递增版本号，用于前端去重/乱序保护
}
pub struct ProgressItem {
    pub key:    String,   // 稳定业务键（报表 code），用于 upsert 寻址
    pub label:  String,   // 显示名
    pub state:  ItemState,// Queued|Running|Ok|Failed|Skipped
    pub detail: String,   // "1.2s" / "除零错误@B12"
}

5.2 快照优先，增量推送

JobManager 内每个作业持有一份权威快照。handler 上报时更新快照并把 diff 交 Hub 扇出。设计要点：

  • 新订阅先收全量——EventSource 连上，Hub 先发一个 snapshot 事件（当前完整快照），之后只发 progress 增量。刷新页面 / 多标签页 / 断线重连都能立即对齐，不丢状态。
  • rev 单调序号——每次快照更新 rev+1。前端只接受 rev 更大的事件，天然抗乱序、抗重复。
  • 推送去抖——handler 可能每毫秒更新明细；Hub 侧按 ~100–200ms 合并推送（coalesce），避免风暴。落库更狠：仅在阶段切换 / 完成 / 失败 / 固定间隔（如每 5s 或每 N 条）持久化快照，不是每次都写。
  • 明细裁剪——大作业（数千项）不把全部 items 塞进每个事件。增量只带「本次变化的行」；前端要全量时走 GET /api/jobs/{id}（含完整快照）或分页明细接口。

6.2 SSE 事件协议

事件用 SSE 的 event: 字段区分类型，data: 载 JSON。对齐 AiSseEvent{event_name, payload}。

event时机data 载荷（要点）
snapshot订阅建立时首帧完整 ProgressSnapshot + status，供前端初始化全貌
state状态机跃迁{status, rev, at}：pending→running→paused→…
progress进度推进（去抖后）diff：{done,total,ok,failed,phase,message,eta_ms,rev}
item明细行变化变化的 ProgressItem（前端按 key upsert）
log业务日志{level, text, at}：INFO/WARN/ERROR（对齐 CmxErrCode）
result成功完成结果摘要（如「42 张成功，落库 1.3 万单元格」）
error失败{code, message, violations?}：对齐 DCT/DOC 结构化 violations
done流终结（任何终态后）空；提示前端可关闭 EventSource
 
// 前端最小消费（对齐 AI 前端 EventSource 用法）
const es = new EventSource(`/api/jobs/${id}/events?access_token=${token}`)
es.addEventListener('snapshot', e => renderAll(JSON.parse(e.data)))
es.addEventListener('progress', e => updateBar(JSON.parse(e.data)))
es.addEventListener('item',     e => upsertRow(JSON.parse(e.data)))
es.addEventListener('log',      e => appendLog(JSON.parse(e.data)))
es.addEventListener('done',     () => es.close())
为什么是 SSE 而非 WebSocket：进度是单向后端→前端推送，控制走独立 HTTP POST 即可，无需双向长连。SSE 更轻、自动重连、走标准 HTTP、库内已有成熟母版与鉴权解法。WebSocket 的双向能力在此是过度设计。若未来出现「前端高频回传」需求（如交互式调参），再局部引入 WS 不迟。

6.3 断线重连

EventSource 原生自动重连。重连后 handler 端 subscribe 会重新发一帧 snapshot，前端整体对齐，无需 Last-Event-ID 复杂补偿。作业终态后仍可 GET /api/jobs/{id} 拉最终快照，SSE 只是「活跃期」的加速通道。

8.2 落库策略：省写、抗风暴

  • 状态跃迁必落——pending/running/paused/终态，每次 UPDATE status（低频、必须准）。
  • 进度快照去抖落——阶段切换、完成、失败、或每 N 秒/每 N 条才写 progress JSONB。活跃进度的高频细节交给 SSE（内存态），DB 只保留「够用来恢复展示」的粗粒度。
  • 日志异步批插——cmx_job_log 用有界 channel + 批量 flush，不阻塞 handler。溢出时优先保 ERROR/WARN，丢弃冗余 INFO（记一条「日志被截断」）。

8.3 崩溃恢复（recover_orphans）

进程重启时，DB 里可能残留 running/paused 的「孤儿作业」（内存态已随进程消失）。启动时统一处理：

原状态处理依据
running / paused / cancelling幂等作业 → 置 pending 重新入队自动续跑；非幂等 → 置 failed（error=「进程重启中断，请人工重启」）handler capabilities().idempotent
pending直接重新入队尚未开始，无副作用
这与 cmx-flow 引擎「启动期从库装载已发布定义 + 定时器 poller 找 due jobs」的恢复思路一致——状态在库、进程无状态可重建。

9 · 业务接入：以「报表计算」为样例

把现有同步的 report_design_compute 改造为一个 JobHandler。业务逻辑不变，只是包进 job 外壳并埋进度点。

// cmx-rpt 内新增 rpt_compute_job.rs（依赖 cmx-job-core）
pub struct RptComputeJob;

#[async_trait]
impl JobHandler for RptComputeJob {
    fn kind(&self) -> &'static str { "rpt.compute" }
    fn capabilities(&self) -> JobCaps { JobCaps{ pausable:true, restart:Restart::Fresh, idempotent:true } }

    fn plan(&self, p:&Value) -> Result<JobPlan> {           // 提交时预估，给进度条基数
        let codes = p["report_codes"].as_array()...;
        Ok(JobPlan{ total: codes.len(), title: format!("计算 {} · {} · {} 张报表", org, period, codes.len()), ... })
    }

    async fn run(&self, ctx:&JobContext, p:Value) -> Result<Value, JobError> {
        ctx.set_phase(1, 3, "装载模板");
        let snaps = load_snapshots(&codes).await?;         // 复用既有装载
        ctx.log(INFO, format!("装载 {} 张报表模板", snaps.len()));

        ctx.set_phase(2, 3, "求值");
        let mut results = vec![];
        for snap in snaps {
            ctx.checkpoint().await?;                     // ← 唯一的控制配合点
            ctx.item_running(&snap.code, "求值中");
            match compute_report(&snap, &provider, periods, org_parent).await {  // 复用 cmx-rpt-formula
                Ok(out) => { ctx.item_ok(&snap.code, out.elapsed); results.push(out); }
                Err(e)  => { ctx.item_fail(&snap.code, &e); /* 策略:续算 */ }
            }
            ctx.progress_inc(1);
        }

        ctx.set_phase(3, 3, "落库");
        let n = persist_cells(&results, org, period).await?;   // 复用既有 cr_cell_data 落库
        if ctx.checkpoint_dirty() { ctx.save_checkpoint(cursor).await; }
        Ok(json!({ "reports": results.len(), "cells": n }))
    }
}

11 · 两条发起路径：前端发起 / 后端发起

① 前端发起

用户点「计算」 │ POST /api/jobs │ { kind:"rpt.compute", │ params:{org,period,codes} } ▼ JobManager::submit() │ plan() 预估 → 建 Job(pending) │ 落库 + 入队 + 返回 job_id ▼ 前端拿 job_id → 打开监控器 → EventSource 订阅进度

② 后端发起

定时器 / GlobalEventBus / 其它服务 │ 例：期末自动结账、夜间批量汇总 │ cmx_job_core::manager() │ .submit(kind, params, │ Origin::Backend{trigger}) ▼ JobManager::submit() ← 同一入口 │ 建 Job(pending, origin=backend) ▼ 自动执行；无人监控也照跑 → 任何前端可事后进任务中心查看 → 失败可配置告警（见 §12）
统一入口是关键：无论谁发起，都汇聚到 JobManager::submit()，共享同一套状态机、进度、控制、持久化、监控 UI。后端发起只是 origin=Backend 且无人实时盯着——但作业照样落库、照样可被任何有权限的前端进任务中心「补看」进度与历史。对齐库内 cmx-flow 定时器 poller、GlobalEventBus 既有设施，后端触发天然可接。

12 · 扩展性与未来演进

方向预留设计落地时机
优先级调度priority 字段已在表/模型；worker 取队列时按 (priority DESC, created_at) 出队。M1 先 FIFO，切换只改出队排序。M2

定时/周期作业复用 cmx-flow 定时器母版（可注入时钟、find_due_jobs、ISO8601），到点 submit()。「每月末自动结账」即一条 cron 定义。M2

与 cmx-flow 的边界：Job 管「一个长任务的执行、进度、控制」（计算密集、单步很重）；Flow 管「多步骤的业务编排、审批、分支」（人+系统协作、状态流转）。二者正交可组合——流程节点里可以 submit 一个 job 并等其完成。不要用 job 重造 flow 的编排，也不要用 flow 承载重计算的细粒度进度。

M1 · 内存态跑通core（状态机/Manager/Context/EventHub）+ api（端点+SSE）+ 单业务 rpt.compute 接入 + monitor 页。作业状态先只在内存，进程重启即丢。暂停占槽。前端提交计算 → 实时看到 42 张逐张进度 → 暂停/恢复/停止均生效 → 完成弹结果。E2E 全绿。
M2 · 持久化+多业务+触发store-pg（落库+崩溃恢复+断点）+ 汇总 SSE 流 + center 页 + 接入 verify/rollup/post + 优先级/限流/定时触发/失败告警。进程重启后历史作业可见、running 作业按幂等策略恢复；后端定时发起的作业可在任务中心补看；记账断点续跑生效。
M3 · 分布式+编排多实例（SKIP LOCKED 抢占 + LISTEN/NOTIFY 跨节点 SSE）+ 子作业/DAG + 与 cmx-flow 互调。多 web-server 实例共享作业池不重复执行；父子作业进度聚合；流程节点可提交并等待 job。

14 · 风险、权衡与非目标

14.1 关键权衡

议题选择理由 / 代价
控制方式协作式（checkpoint）Rust async 不能安全强杀。代价：业务需埋点；不可中断的原子段有响应延迟。已用 Cancelling 中间态表达。
进度事实源内存快照为准，DB 去抖备份SSE 要实时（内存），审计要持久（DB）。代价：崩溃丢失最后几秒未落库的细粒度进度——可接受（恢复后重算/续跑）。
推送协议SSE单向推送 + 有成熟母版 + 自动重连。放弃 WS 的双向能力（当前不需要）。
暂停占槽M1 占槽 + 超时兜底实现简单、语义清晰。代价：长暂停占并发；靠最大暂停时长自动取消防饿死。M2+ 再做让位。
框架 vs 业务trait + 单向依赖 + inventory零框架改动接新业务。代价：业务要按约定埋点（换取解耦与一致监控）。

14.2 非目标（本期不做）

  • 不做通用工作流编排——多步审批/分支交给 cmx-flow，job 专注单个长任务。
  • 不做抢占式强杀——不追求「点停止瞬间线程消失」，只保证下一个安全点停下。
  • M1 不做分布式——单 web-server 实例内跑；接口按分布式预留，但不实现跨节点。
  • 不重造消息队列——不引入 Kafka/RabbitMQ；进程内队列 + PG 持久化足够当前规模，规模化时 M3 再评估。

14.3 已知风险与缓解

风险缓解
业务忘埋 checkpoint → 停不下来capabilities 声明 pausable；未声明则 UI 隐藏暂停/停止按钮，只允许「请求取消（尽力）」并提示不保证即时。lint/文档强调循环内必埋。
SSE 连接泄漏（前端不关）作业终态发 done 前端主动 close；服务端 keep-alive + 空闲超时清理；订阅数上限保护（对齐 ai 多标签页）。
进度事件风暴Hub 去抖合并（100–200ms）；明细裁剪（只推变化行）；日志有界 channel + 溢出降级。
孤儿作业（崩溃残留 running）启动 recover_orphans 按幂等策略重入队/置失败（§8.3）。
非幂等作业被误重启capabilities 强制声明幂等级别；非幂等 restart 需人工二次确认，不自动执行。
异步任务中心方案 · 仅设计不动代码 · 复用 cmx-ai SSE 母版 + cmx-rpt 分层母版 + cmx-flow 恢复/定时/子作业母版
