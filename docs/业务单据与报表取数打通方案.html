业务单据 ↔ 报表取数打通方案

Doc-to-Report Data Fetch Integration · 语义绑定 + 物理专线 · 跨库/跨服务 · 可插拔传输
要解决的问题：报表定义里的取数函数（QM/QC/FS/JE 及扩展）目前取不到业务单据的真实数据——引擎、DSL、向导、注册全就绪，唯独取数真源是占位假值。要把它接到分层单据（单头 / 分录 / 明细 / 辅助分录 / 汇总表）的真实数据上。
难点：单据的库 + 应用服务 与 报表的库 + 应用服务 大概率不在同一台服务器。取数要能跨库、跨服务、可分开部署。
核心主张：把"打通"拆成两层——语义层 单据定义声明取数暴露、报表函数绑定到它；物理层 报表侧 DataProvider 背后可插拔传输（同库直查 / 服务间 HTTP / gRPC / 物化加速），部署形态变化不动引擎。
现成地基：报表 DataProvider 取数接缝已抽象干净、单据 /api/doc/meta+DocQuery 已能按组织/期间/单据类型下推与聚合、ZmcDataSet 列式包（msgpack/JSON/流式）传输、cmx-rpc+服务鉴权三件套、[deploy] mono/micro 开关全部已落地。本方案是"接线 + 补一段取数专线"，非从零。
状态：架构方案，不动代码。落地留待方案批准后按 §14 分期实施。

取数链路的四块地基各自都已就位，唯独"报表 ↔ 单据"之间的那一段是空的。逐块盘点：

1 · 问题分解：两个"打通"

"业务单据定义和报表定义没打通"这句话里，其实压着两个独立的问题。把它们分开，方案才不会拧成一团：

语义打通 定义 ↔ 定义

报表函数 QM('1001', 本期, @current) 里的"取数对象 1001"、"本期"、"当前组织"，如何对应到单据定义里的某张表、某个度量列、某些维度列？

这是"定义之间"的映射契约——与部署在哪、跨不跨库完全无关。它决定"取什么"。

物理打通 服务 ↔ 服务 / 库 ↔ 库

把"按 1001+本期+当前组织求余额"这个聚合请求，送到单据的库/服务上执行，再把结果运回报表服务——当两者不在同一台机器时怎么走？

这是"运行时"的传输问题——与取什么无关。它决定"怎么送、怎么运回"。

关键设计决定：两层解耦，各自演进。 语义层产出一个稳定的取数请求 FetchSpec（取什么）；物理层负责把一批 FetchSpec 送达并取回结果（怎么送）。中间用报表现有的 DataProvider trait 作为唯一接合点——语义层只管把公式实参翻译成 FetchSpec，物理层只管实现一个 batch_balance。部署形态变（同库→跨库→跨服务），只换物理层传输，语义层与引擎一行不改。

2 · 语义层：取数暴露 + 取数绑定

语义打通 = 单据定义主动声明"我有哪些可取的数"（取数暴露），报表定义在函数里引用它（取数绑定）。两侧都写在各自的定义 JSON 里，不碰数据。

2.1 单据侧：取数暴露声明（Query Exposure）

在单据定义（如 cmxfico_doc_meta_v2.json）里新增一段 fetchExposure：把内部的分层表结构，翻译成对外稳定的取数语义——外部只见"度量 + 维度 + 标准余额/发生额"，不见 cv_acc_line.upper_id 这类内部细节。

// 单据定义新增段：声明"我暴露哪些可取的数"
"fetchExposure": {
  "objects": [
    {
      "key": "gl_voucher",              // 取数对象逻辑名（报表侧绑定用）
      "sourceLayer": "cv_acc_line",     // 落到哪张物理表（科目分录层）
      "dimensions": {                    // 可过滤维度 → 物理列（白名单）
        "account": "account_code",
        "org":     "comp_unit",
        "period":  "period_code",
        "aux":     "aux_value"          // 辅助核算（可选，来自 cv_aux_line）
      },
      "measures": {                      // 可取度量 → 列 + 聚合方式
        "occur_debit":  { "col":"local_dr",  "agg":"sum" },   // 本期借方发生
        "occur_credit": { "col":"local_cr",  "agg":"sum" },
        "end_balance":  { "source":"balance" }              // 余额类：见 2.3
      },
      "scope": { "docStatus": ["posted"] }   // 只取已过账，未审核不入报表
    }
  ]
}

这段声明的每一项都已有代码依据：sourceLayer=DocMetaView.layers[].table_name；dimensions/measures 的列语义来自 ColumnView.dim_type(attribute/dimension/measure) 与 ColumnView.agg（meta.rs:90，已被 /api/doc/meta 暴露）。fetchExposure 只是把这些"零散标注"收敛成"对外取数契约"。

2.2 报表侧：取数绑定（Fetch Binding）

报表的取数函数需要知道"这个 QM 取的是哪个单据对象"。两种绑定粒度，就近覆盖（复用报表现有的 §6 公式来源阶梯思路）：

层级在哪定义含义
① 数据元素级cr_data_element.fetch_binding（新列/JSON）元素"科目1001-余额"绑定 gl_voucher.end_balance，凡引用该元素的格自动继承。定义一次处处复用。
② 函数实参级公式串里直接写QM('gl_voucher:1001', [-1], @current) —— 取数对象前缀即绑定，最灵活、优先级最高。

2.3 取数键升级：BalanceKey → FetchSpec

当前 BalanceKey{kind,period,org,object}（eval.rs:96）只够"科目余额"。跨单据取数要扩成通用 FetchSpec——但向后兼容：老 QM/QC 不填 dims 时退化为纯科目取数。

pub struct FetchSpec {
    pub kind:     FetchKind,          // Balance(余额) | Occur(发生额) | Net(净额)
    pub doc_type: String,            // "gl_voucher" —— 取数对象 key（对应 fetchExposure.objects[].key）
    pub measure:  String,            // "end_balance" / "occur_debit" …
    pub dims:     BTreeMap<String,DimValue>, // {account,org,period,aux…} 已排序 → 稳定缓存键
    pub period_offset: i32,        // 相对期间（0本期/-1上期），沿用现算法
}
余额 vs 发生额，取数路径本就不同。 发生额（FS/JE）= 对单据明细一次 SUM(local_dr) GROUP BY 即得，可实时算（方案 A/C）。余额（QM/QC）需累计（期初 + Σ本期发生，或按方向滚存），从明细逐笔现算既慢又易错——宜由单据侧维护物化余额表（方案 E 的 cv_gl_balance）。所以 measure.source="balance" 走余额表、agg="sum" 走明细聚合，由单据侧按取数种类自行选路，报表侧无感。

3 · 物理层：五种连接方案

同一个 batch_balance(&[FetchSpec]) 请求，运行时怎么送到单据数据那里、结果怎么运回——五条路，各有取舍。全部藏在 DataProvider 实现背后。

A共库直查（Shared DB · in-process SQL）

报表与单据同一个 PG 库（或报表进程直接 use cmx_doc_store_pg 内存调用装载器）。报表的 DocFetchProvider 直接对 cv_* 表跑聚合 SQL。

report-service ──同进程/同库──▶ SELECT SUM(local_dr) FROM cv_acc_line WHERE … GROUP BY account_code （复用 cmx-doc-model::build_layer_select + ZmcDocLoader，零网络）

耦合 极高实时 ✓性能 ✓ 本地改造 小分开部署 ✗

优：最快、最省事，无网络无序列化。劣：要求报表懂单据表结构、共命运（单据库挂报表跟着挂）、绕过单据服务的权限与校验。不满足题目"大概率分开部署"——只适合中小一体化部署或做同库快路径。

B跨库直连（Cross-DB Direct Pool）

报表服务额外注册一个指向单据库（另一台 PG）的连接池（新增一个 db_id，db_url 填远程地址），DocFetchProvider 用这个池直接查远程 cv_* 表。

report-service ──deadpool-postgres 直连──▶ [远程 PG] cv_acc_line （复用 cmx-database-pg 多数据源）

耦合 高实时 ✓性能 ✓改造 小分开部署 △ 仅跨库安全 弱

优：几乎零新代码——new_db_pool 支持任意连接串（connection/mod.rs:482），改 dev-local.toml 的 db_url 即连远程。劣：① 报表持有单据库 DB 账号，绕过单据服务的行/列权限与业务校验，安全边界破裂；② 报表硬编码单据表结构，定义一变就漏；③ 当前仅 NoTls，跨机房裸传需补 TLS。仅建议作应急旁路，不作主路径。

C服务间 HTTP 取数（Service-to-Service HTTP）

报表 DocFetchProvider 通过 HTTP 调单据服务新增的取数端点 POST /api/doc/fetch，把一批 FetchSpec 打包发过去，单据服务内部聚合后用 ZmcDataSet 列式包（msgpack）回传。

report-service ──HTTP POST /api/doc/fetch (batch FetchSpec + 服务鉴权头)──▶ doc-service ◀── msgpack 列式包 { rows:[[account, value]…] } ──── （单据服务内做聚合 + 权限）

耦合 低实时 ✓性能 △ 可合批改造 中分开部署 ✓安全 强

优：① 经单据服务，天然继承其鉴权、行/列权限、业务口径，安全边界清晰；② 报表只认取数契约、不懂单据表结构，定义演进互不影响；③ 复用现成 ZmcDataSet msgpack + 服务鉴权三件套 + Vite/同源部署，改造集中在"一个端点 + 一个 provider"；④ 天然跨机、跨库、可独立扩缩容。劣：网络 + 序列化开销（用批量合并把一个报表的全部取数键压成一次 round-trip 化解，见 §11）；单据服务不可达时取数不可用（可降级，见 §13）。

D服务间 gRPC 取数（Service-to-Service gRPC）

同 C，但走 cmx-rpc（volo-grpc + Nacos 服务发现）而非 HTTP：为单据取数新增一个 gRPC Bundle，报表经 orchestrator_client 调用。

report-service ──gRPC (Nacos 发现 doc-service, 二进制帧, 可流式)──▶ doc-service DocFetch Bundle

耦合 低实时 ✓性能 ✓ 二进制/流式改造 大分开部署 ✓安全 强运维 重

优：性能优于 HTTP（二进制帧 + 真流式，大报表取数更省）；服务发现 + 负载均衡现成；鉴权三件套本就是为 gRPC 设计的。劣：① [rpc] 当前默认关闭，要起 gRPC server + Nacos；② 需新建 Bundle、契约用 IDL，改造与运维成本明显高于 C。作为 C 的高性能演进档——同一 DocFetchProvider 只换 transport 即可平滑切换。

E物化同步 / 取数宽表（Materialized Balance）

单据侧把余额/发生额预聚合成一张宽表 cv_gl_balance（正是报表代码注释里点名的"P4 真源"），或经 CDC/ETL 同步到报表库本地。报表取数只读这张宽表。

单据明细 cv_acc_line ──[过账触发/定时/CDC]──▶ cv_gl_balance(account,period,org,end_bal,occur_dr…) report-service ──读本地/近端宽表──▶ 命中即返回（不触单据明细，不依赖单据服务在线）

耦合 中实时 ✗ 有延迟性能 ✓✓ 宽表可用性 ✓✓ 读本地改造 大运维 重

优：① 取数极快（一张按主键组织的宽表，避免每次聚合分层明细）；② 报表可读本地副本，单据服务/库离线也能出报表，可用性最好；③ 余额类取数的天然归宿（余额本就需累计，物化最合理）。劣：① 数据有同步延迟（关账后刷新可接受，实时报表不适用）；② 需建同步管道（过账钩子/定时/CDC）+ 一致性对账。作为高频大报表的加速层与余额真源，与 C 叠加而非替代。

择优结论：不是单选，而是"一个抽象 + 主路径 + 加速层 + 快路径 + 演进档"。
主

快
A 同库直查 作同库部署的快路径——检测到单据与报表同 db_id 时，DocFetchProvider 自动退化为进程内直查，省一次网络。
进

急
B 跨库直连 仅作应急旁路（单据服务临时不可用、又必须出实时报表时），默认禁用。
这五者不是并列备选，而是同一 DataProvider 抽象下的可插拔传输策略——由部署配置与取数种类在运行时择一，切换零改引擎。

三条不变量支撑整个架构：

8 · 报表侧：DocFetchProvider

替换掉 PgProvider 的占位 batch_balance（compute.rs:194），新建 DocFetchProvider 实现同一 DataProvider trait。引擎调用点 compute_report_service（compute.rs:268）只改一行——把 &PgProvider 换成 &DocFetchProvider。

pub struct DocFetchProvider {
    transport: FetchTransport,   // Local(db_id) | Http(endpoint) | Grpc(service) | RemotePg(db_id)
    cache:     FetchCache,       // (specHash) → value，关账期可长缓存（§11）
    ctx:       CallContext,      // 委托用户 token + request-id（服务鉴权透传，§10）
}

impl DataProvider for DocFetchProvider {
    async fn batch_balance(&self, keys: &[BalanceKey]) -> Result<HashMap<..>> {
        let specs = keys.iter().map(FetchSpec::from).collect();   // ① BalanceKey→FetchSpec + 取数绑定
        let (hit, miss) = self.cache.split(specs);              // ② 缓存命中/未命中拆分
        let fetched = match &self.transport {                    // ③ 一次批量取回未命中
            Local(db)   => local_aggregate(db, &miss).await?,    // A 快路径
            Http(ep)    => http_fetch(ep, &miss, &self.ctx).await?, // C 默认
            Grpc(svc)   => grpc_fetch(svc, &miss, &self.ctx).await?,// D 演进
            RemotePg(db)=> local_aggregate(db, &miss).await?,    // B 应急（换 db_id）
        };
        self.cache.fill(&fetched);
        Ok(merge(hit, fetched))
    }
    // load_report(REF 跨表) 不变 —— 那是报表内部跨报表，仍读 cr_* 
}
为什么这样切最稳。 batch_balance 本就是批量接口，跨服务合批天然贴合。四种 transport 共用一套"BalanceKey→FetchSpec→取数→填缓存"骨架，只有中间"怎么送"一行不同。compute_report 的两遍法（先收集后批量）意味着无论传输多慢，一个报表也只付一次网络往返。

11 · 一致性 · 缓存 · 性能

合批
N+1 是跨服务取数的头号杀手，而两遍法天然免疫。 compute_report pass1 收齐一个报表全部取数键 → 去重排序 → 一次 batch_balance。几百个 QM 格 = 一次网络往返。单据端再把同对象同期间的 spec 并成少数几条 GROUP BY 大查询。
缓存
取数缓存键 = FetchSpec 指纹（dims 已排序，稳定）。关账后的历史期间余额不变→可长缓存（甚至落 cr_* 快照）；当前开放期→短 TTL 或不缓存。缓存放报表侧 DocFetchProvider，跨报表复用。
快照一致
一次 compute 的所有取数应取同一时点：单据端取数端点在单个只读事务/快照内执行整批 spec，避免报表跨行看到不一致的中间态。历史期间因已关账天然一致。
余额加速
余额类取数命中 cv_gl_balance 宽表（E）→ O(1) 主键查，避免每次扫描分层明细。发生额可直读单据自带的汇总表 summaries[]（已物化 sum）。
大报表
取数结果集大时用 ZmcDataSet chunked 帧流式（:791），峰值内存 O(单行)；报表侧边收边填缓存。

12 · 安全与权限边界

取数是"读别人家的钱"，权限边界是本方案的第一性问题。 这正是不推荐 B（跨库直连）作主路径的根因——直连绕过单据服务的一切权限。C/D 经单据服务，边界清晰。
列
取数暴露即白名单：只有 fetchExposure 声明的度量/维度可取，未声明的列（如内部备注、审批意见）取不到。维度列名经 layer.schema 二次校验。
行
行级组织权限：单据端拿 X-Delegated-User-Token 解析终端用户 → 只允许取该用户有权的组织（comp_unit）数据。报表作者能设计公式，但看报表的人只能取到自己权限内的数。
服务
服务身份 X-API-Key：只有登记的报表服务能调取数端点；取数端点纳入鉴权中间件白名单管理（mw_auth.rs:246）。
注入
零 SQL 拼接：dims 全程 $N 参数绑定 + 列名白名单（复用 DocQuery 现有防注入路径），取数对象/度量/维度都是枚举匹配而非自由字符串入 SQL。

13 · 失败与降级

故障行为
单据服务不可达 / 超时取数格标 #N/A（data_status=error），报表其余（本地 SUM/IF/REF）照算完；错误汇总进 ComputeOutcome.errors[]，前端在格上标记。不让整张报表失败（沿用现有环隔离思路：只坏取数格）。
部分 spec 失败批量取数逐 spec 结果：成功的填值，失败的标错，不整批回滚。
历史期间 + 有缓存单据服务离线时，命中缓存/物化宽表（E）仍能出历史报表——这是 E 的可用性红利。
应急旁路单据服务长时间不可用又必须出实时报表：临时启用 B（跨库直连）读单据库只读副本，事后关闭。
取数绑定缺失公式引用了未声明 fetchExposure 的对象 → 设计态即校验报错（check_formula 阶梯），不留到运行时。

1主传输定 C(HTTP) 还是直接上 D(gRPC)？先 C：改造小、复用多、够用；D 待 [rpc] 正式启用后作演进档（同 provider 换 transport）。
