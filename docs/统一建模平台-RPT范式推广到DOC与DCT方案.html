01RPT 范式拆解 what made reports work

把报表平台之所以成功的东西提炼成五个可复用要件。每一件都要问：这是通用的，还是 RPT 私有的？

② 两模式cmx-rpt-store-pg/lib.rs：load/save_layout(code+version) · query/save_data(org+period) · open_report 合流通用 最值得推广的资产

💡 两模式为什么是最强资产
「定义按 (code, version) 存、数据按 (作用域维度) 存、一个端点按是否带作用域决定要不要并数据」—— 这个分离对任何「一份模板 × 多个作用域实例」的业务都成立：报表是 org+period，单据是 org+期间/单据号， 字典其实退化成「只有定义、作用域为全局」。推广它，等于让 DOC/DCT 也获得「设计一次、多作用域复用、每作用域一份数据、幂等落库」。
⚠ 一个必须说清的现实：RPT 有两套 cr_* 表家族
勘探发现 RPT 存在两条并行血脉：活跃工作台用 cr_report_fmt/cr_cell_data（cmx-rpt-store-pg）； metaKind 部署编译出 cr_report_instance/cr_cell_value（cmx-model-deploy::compile_rpt 读 base 的 storageTables）。 两者同 cr_ 前缀但不同表、不同子系统。推广要以活跃的 store-pg 那条为范本，部署编译那条是较少走的平行支线。

02CmxMasterSlave 现状 — it already does more than you asked

用户指出前端有 CmxMasterSlave 管主从数据、与单据/字典的分层定义一致。核验后要更正一句：它不止“主从”，它是一棵任意 N 层递归树，而且层间汇总是它的一等内建能力。

🌲 任意 N 层，不是两层

_registerSchema 递归注册 schema，节点形状仅 { id, children? }，全点号路径（orders.details.taxes）。 数据树 CmxDataSet 每行挂 _children:{childId:CmxDataSet}，路径解析逐段下行、无深度上限。

packages/cmx-data-comp/src/lib/cmx-master-slave.js:89（_registerSchema，递归）

➕ 层间汇总 = 一等内建

addAggregation({from, to, toField, field, agg, scope})：把 from 层某字段按 sum/avg/min/max/count（或自定义函数） 汇总回写到 to 层的 toField。正是「父层字段 = 子层字段之和」。

cmx-master-slave.js:206（addAggregation）· :33（AGG_FUNCS）

🔗 跨多层级联上卷

_cascade：某规则写完的字段若是另一规则的 from，自动再触发—— 子明细→明细→主表 逐层传导，带成环检测与 16 层级联安全阀。

cmx-master-slave.js:836（_cascade，深度上限=级联安全，非树深）

🎛️ 定义驱动 + 命令式双可用

页面 dataFlow.{schema,aggregations,relations} 直接构造；也可 new CmxMasterSlave({...}) 命令式。 后端元数据经 cmx-doc-meta-loader 转成 N 层 schema。

init-page-models.js:711 · cmx-doc-meta-loader.js:61（buildMasterSlaveSchema）

🎁 直接后果：用户想要的「层间汇总关系」在前端已经能算了
这意味着推广的重点不在前端——前端主从树、N 层、层间与级联汇总都齐。重点在让后端也拥有同一份汇总语义： 可声明（进定义 JSON）、可校验、可持久化、可离线重算（不依赖浏览器打开）。这正是第 05 / 07 节的主题。

03DOC 映射：分层单据 业务单据

用户原话：「单据定义是分层，每层都有相应的不同的数据属性，每层的数据属性间还可以定义汇总关系。」——逐句对代码核验：

用户描述核验代码证据
单据定义是分层属实示例定义 cmxfico_doc_meta_v2.json 声明 4 层（凭证批→头→科目行→辅助行），voucherSchema.schema 嵌套数组 + relations 父子键（upper_id）。层数与表名全在定义 JSON 里，不在引擎里
每层有不同的数据属性属实每层 voucherTables[].fields[] 各自定义列；ColumnView.dim_type∈{attribute,dimension,measure}。引擎按定义读列，不认识任何具体列名
层间可定义汇总关系仅纸面voucherSchema.aggregations[] 存在但是占位："to":"上层" 是字面字符串；DocMetaView::parse 根本不读它（meta.rs 中 aggregation 引用数 = 0）
✅ 关键澄清：引擎完全通用，绝无凭证特例（已逐行核验）
「凭证批→头→科目行→辅助行」这套 4 层结构，是定义文件 cmxfico_doc_meta_v2.json 里的数据，不是引擎里的代码。逐行核验 cmx-doc-{model,store-pg,api}：
  • 0 处非注释代码出现 cv_batch/cv_header/cv_acc_line/cv_aux_line——全部 12 处 cv_* 引用都是 /// 文档注释里的举例（「如 cv_batch」），无一是可执行逻辑。
  • 装载器完全按定义驱动：loader.rs 读 layer.table_name + meta.child_layers(parent.id) + for child_layer in child_layers——走定义声明的任意层、任意深度，不知「凭证」为何物、不写死「4 层」。
  • sql_builder.rs 顶部明写「通用性铁律：本模块不认识任何具体单据（不出现 cv_batch/local_dr 等词）」；saver.rs 的父子重指向注释「与层序无关」。
  • 借贷平衡等凭证语义只存在于定义里的 validationRules（由通用 formula.rs 表达式引擎跑），不是引擎硬编码的业务规则。
换言之：DOC 引擎已经是「元数据驱动的通用分层单据引擎」——把定义换成采购订单（头→行→交货计划）或工单（工单→工序→物料），同一套引擎零改动即可跑。这正是推广得以成立的前提，也是绝不能破坏的底线。
⚠ DOC 的「层间汇总」目前是纸面声明，不落地
定义里确有两处汇总痕迹，但都不产生真实计算：
① voucherSchema.aggregations[]——"from":"...entered_dr" / "to":"上层" 全是占位串，只有一个只读 schema 可视化页 doc-base-schema.html 拿去展示，后端 parse 直接丢弃。
② voucherTables[].summaries[]——被解析成 SummaryView，但 sql_builder.rs 只生成逐层 SELECT ... WHERE upper_id=ANY($ids)，没有一处 SUM( / GROUP BY，saver.rs 从不写汇总表。列上的 agg:"sum" 注释原文说得很直白：「便于前端识别可上卷列」——是展示元数据，不是计算契约。

DOC 已具备 RPT 范式的哪半

  • 有 强类型定义投影 DocMetaView（layer_order/layers/layer_groups/relations/validation_rules/status_flow/versioning）——比 RPT 活跃层还成熟（RPT 活跃层是裸 serde_json::Value）。
  • 有 元数据驱动的通用引擎：三段式 cmx-doc-{model,store-pg,api} + ZmcDataSet 零拷贝按定义 BFS 装载 + 落库前列级校验，全程不认识任何具体单据。
  • 有 设计工作台（native-pages/demo/doc-base/* 四区：explorer/content/property）。
  • 半 两模式：定义侧成熟；数据侧有 /api/doc/data/* 装载与 /save 落库，但未按 RPT 那样把「定义 vs 作用域数据」显式二分 + 单端点合流。
  • 缺 层间汇总执行——见上。

📎 两处顺带更正（勘探所得）
① 顶层 key 是 moduleMeta（每字典表内是 dictMeta），不存在 dctMeta 顶层 key——我此前记反了。
② DCT 前端存在两种绑定风格并存：dictflat/dictcls/dictrel 是手写 fetch + setFlatData；只有 dicttree 用了声明式 CmxDCTMeta+source.apiPath（最接近 RPT 应用器范式）。统一推广时，把前三者迁到 dicttree 已示范的声明式风格即可。

DCT 的特殊性——汇总退化：字典多为查找/维度数据，「层间汇总」在多数字典无意义。但分级字典的「子节点计数 / 小计上卷」是有意义的（如成本中心树按父节点汇总下属数量或某度量）。这落进同一套汇总声明即可，只是用得少。DCT 的数据作用域也退化——多为全局（无 org+period），所以两模式在 DCT 主要体现为「定义即数据模板」，作用域维度为空。

05唯一实缺：层间汇总的后端权威引擎

把三个子系统叠在一起看，缺口收敛成一个点。这是整份方案唯一需要「造新东西」的地方，其余都是「复用 + 对齐」。

能力 前端(CmxMasterSlave) DOC 后端 DCT 后端 RPT 后端 ───────────────────────────────────────────────────────────────────────── 层间汇总·声明 ✔ aggregations 配置 △ 占位串未解析 — ✔ 公式/上卷 层间汇总·计算 ✔ addAggregation ✘ 无 ✘ 无 ✔ expand.rs(报表侧) 层间汇总·落库 ✘(前端不落库) ✘ 无 ✘ 无 ✔ cr_cell_data ▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲ 这一格就是全部缺口
🎯 缺口精确定义
一个「定义声明的、后端可执行的、结果可持久化的层间汇总引擎」，语义与前端 addAggregation 对齐（同一份 {from,to,field,toField,agg} 声明两端都读）， 使得：① 定义里写的汇总关系被后端 *MetaView::parse 真正解析；② 保存单据/字典时后端按拓扑序重算父层承接字段（不信任前端计算值，服务端为准）；③ 汇总结果随数据落库，脱离浏览器也成立（批量导入、报表取数直接读到已上卷的父层值）。

为什么这是「一处」而不是「三处」：因为 DOC/DCT/RPT 已共享 model/store-pg/api 三段式与 cmx-model 定义解析层。汇总引擎应当做成一个中立 crate（cmx-agg 或并入 cmx-model），三个 store-pg 都调它——而不是各写一份。它与前端 AGG_FUNCS 语义逐字对齐，形成「一份声明、两端执行」。

06统一架构 — one modeling platform, four kinds

推广的终局：DOC/DCT/RPT（乃至 FLX）成为同一个「层级建模平台」的四种 metaKind，共享定义层、两模式存储、双工作台外壳、三段式后端与同一套汇总引擎；差异收敛到各自的「领域内容」。

07汇总关系的声明与执行 — one declaration, both ends

汇总引擎是本方案唯一的新造件，值得把契约钉死。核心原则：定义里声明一次，前端与后端读同一份，服务端计算为权威。

① 声明（进定义 JSON，DOC/DCT 通用）

// voucherSchema.aggregations —— 把今天的占位串改成真实路径 + 声明语义
"aggregations": [
  { "from": "cv_acc_line", "to": "cv_header",
    "field": "local_dr", "toField": "total_local_dr", "agg": "sum" },
  { "from": "cv_aux_line", "to": "cv_acc_line",
    "field": "local_dr", "toField": "local_dr", "agg": "sum" }
  // 两条串联 = 辅助行→科目行→凭证头 逐层上卷（拓扑序自动推导）
]

② 后端执行（新中立 crate cmx-agg，三方共享）

// 语义与前端 AGG_FUNCS 逐字对齐；DOC/DCT/RPT 的 store-pg 都调它
pub struct AggRule { from: String, to: String, field: String, to_field: String, agg: AggFn }
pub enum AggFn { Sum, Avg, Min, Max, Count }

// 保存前：按 (from→to) 建 DAG 拓扑排序，逐层把子层聚合回写父层承接字段
pub fn rollup(tree: &mut LayerTree, rules: &[AggRule]) -> Result<()> {
    let order = topo_sort(rules)?;      // 子明细→明细→主表；成环即报错
    for rule in order {
        recompute_parent_field(tree, rule); // SUM(子层.field)→父层.to_field
    }
    Ok(())
}
⚙️ 两种执行时机，按业务选
写时上卷（推荐 DOC 凭证类）：saver 落库前对整棵变更树 rollup，父层承接字段随子层一并 UPSERT——脱离浏览器也对，报表取数直接读到已上卷值。
读时上卷（可选，省存储）：装载时按 aggregations 生成 SELECT SUM(...) ... GROUP BY upper_id 现算——不落库，适合纯展示。
两者共用同一份 AggRule 声明，只是消费点不同。DOC 六币种借贷「逐层上卷」属前者。
✅ 为什么这条路低风险
① 声明格式已存在（前端在用、DOC 定义里有占位位），只是让后端也读；② 计算语义已被前端验证（AGG_FUNCS + _cascade 跑了很久）；③ 落库通道已存在（DOC saver 的列级校验 + N 元幂等 UPSERT + 铸号），汇总值只是多几列承接字段；④ 抽成中立 crate 后三方零重复。真正的新代码只有「拓扑排序 + 逐层重算」这一小核。

09风险与取舍

  • 引擎绝不认识具体单据（已是底线，不能破）：层数、表名、列名、层间关系、汇总规则全部只存在于定义 JSON；cmx-doc 引擎逐行核验 0 处凭证特例，cmx-agg 汇总引擎同样只吃 {from,to,field,toField,agg} 声明、绝不硬编码任何 cv_*/层序。推广时任何「为某类单据加 if 分支」都是架构倒退，必须拒绝。
  • 不要过度统一：RPT 的 SpreadJS 自由画布 BLOB 是「版式即真相」，DOC/DCT 是结构化表——不要逼 DOC/DCT 也用电子表格 BLOB。共享的是「模型+两模式+汇总+三段后端+工作台外壳」，不是渲染内核。
  • 写时 vs 读时上卷要一表一议：凭证类（借贷平衡、审计留痕）走写时落库；纯展示维度走读时现算。混用同一声明但消费点不同，别一刀切。
  • 服务端计算为权威：绝不信任前端上卷值直接落库（防篡改、防浏览器缺陷）。前端 addAggregation 是即时反馈，cmx-agg 是落库前重算的最终裁判——语义对齐但后端说了算。
  • 成环与深度：汇总 DAG 必须拓扑可排（topo_sort 成环即拒），对齐前端 16 层级联安全阀；跨层汇总链过长时给出定义期告警。
  • RPT 两套 cr_* 血脉：推广以活跃 cmx-rpt-store-pg 为范本；compile_rpt 那条部署编译血脉是平行支线，别混。
  • DCT 汇总多数无意义：别为字典强行造汇总 UI；只在分级字典按需开。DCT 的两模式主要退化为「定义即模板、作用域为空」。
  • 校验/错误码已就绪可复用：落库前列级校验（type/length/precision/nullable）+ 结构化 violations + CmxErrCode 已在 DOC/DCT 共用，汇总承接字段天然纳入同一校验，无需另起。
🧭 一页纸总结
用户的设想成立且大半已就位：RPT 范式是通用模板，DOC/DCT 已复刻其后端骨架、共享定义解析、并都接到 CmxMasterSlave 递归主从树上；前端连层间/级联汇总都已内建。 推广 = 把「两模式存储」显式对齐到 DOC/DCT（低风险） + 把字典三工作台统一到声明式绑定（低风险） + 补齐唯一实缺：一个定义声明、服务端权威、可落库的层间汇总引擎 cmx-agg（三方共享，与前端语义逐字对齐）。新代码集中在一个小 crate 的「拓扑排序 + 逐层重算」，其余皆复用。
