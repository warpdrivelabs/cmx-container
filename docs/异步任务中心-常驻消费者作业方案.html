异步任务中心 · 常驻消费者作业方案

Long-Running Consumer Jobs — 消息队列消费型、循环处理、无自然终点、直至手动关闭的后端作业，如何在现有任务中心体系中运行 · 监控 · 管理。附录于《异步任务中心方案》。纯设计，不动代码。

一句话结论
这类作业与现有框架的唯一冲突是一个隐含假设：「作业有终点」。破除它只需 1 处必需的模型标记 + 4 处语义重新赋义；协作式控制、SSE 实时进度、分布式崩溃自愈这三块核心能力零改动直接可用。所以本质是一种使用模式（pattern），而非一类新作业。

1 · 问题：常驻循环作业为何"格格不入"

现有任务中心（报表计算 / 校验 / 记账 / 汇总）默认作业是有界的：提交 → 跑到底 → 落终态。而一个"消费消息队列直到手动关闭"的作业是无界的：

批处理作业（现有） 常驻消费者作业（本方案） submit submit / 系统启动自动拉起 │ │ 处理 N 条 ── 进度 done/total ┌─▶ 拉一批消息 │ = 百分比 │ 处理 · ack 完成(Completed) ✔ │ checkpoint（响应暂停/关闭） └──┘ 队列空 → 空闲等待下一批 │ ……永不自然结束…… 手动关闭 → 优雅排空 → 正常终态

五个隐含假设在这里破裂：

#现有假设常驻作业的现实
A进度 = done/total 百分比没有 total。要看的是吞吐速率、队列积压、运行时长，不是完成度
B终态 = 完成/失败/取消手动关闭是正常终态，不是错误；崩溃不该"报失败"，该自动重新拉起
C作业跑完即释放 worker 槽永久占一个槽。4 个消费者吃满 max_concurrency=4 → 批处理全饿死
D可多实例并发（分区抢占）通常必须全局单实例，否则重复消费
E明细 items 全量保留永远增长 → 内存泄漏。必须滚动窗口只留最近 N 条

2 · 契合点：什么已经现成可用（零改动）

好消息占大头——框架为"协作式长任务"设计的核心机制，恰好就是常驻消费者需要的：

现成 暂停 / 关闭 = checkpoint

消费循环每批之间调 ctx.checkpoint().await?：

  • 暂停 → 循环在此真挂起（watch::changed().await，零 CPU），停止拉取新消息、连接保持。恢复 → 零延迟继续。
  • 关闭 → checkpoint 返回 JobCancelled，handler 用 ? 跳出循环、做收尾。

这正是消费者"停拉/续拉/优雅停"所需，一行不改。

现成 实时监控 = SSE 推送

同一套 progress / log / item 事件流，按 job_id 扇出。消费者把每批的速率、积压、明细通过现有上报方法推给前端，GET /api/jobs/{id}/events 实时可见。

现成 崩溃自愈 = 心跳 + reaper

M3 分布式：属主节点每 10s 刷 heartbeat_at；节点宕机 → reaper 发现心跳超时 → 作业重置 pending → 另一节点 SKIP LOCKED 重领 → run() 再次进入消费循环。这天然就是消费者的高可用：换个节点继续消费。

现成 管理端点 + 持久化 + 历史

pause/resume/cancel/restart 端点、状态落库、关闭后归档进 cmx_job_hi 历史表——全部复用。进度采样器每 1s 落库，正是常驻作业"重启后看得到状态"的保证。

3 · 核心设计：一个标记 + 四处赋义

不新增作业类型。在现有 JobHandler / JobCaps / ProgressSnapshot 上加最小扩展：

3.1 必需·唯一模型扩展 作业种类分型：batch vs service

给 JobCaps 增一个标志（或给 JobKind 元数据加一维）：

JobCaps {
    pausable:   true,          // 已有
    restart:    Restart::Fresh,// 已有
    idempotent: true,          // 已有
    kind_class: JobClass::Service,   // 新增：Batch(默认) | Service(常驻)
    singleton:  true,             // 新增：全局单实例约束（见 §6）
}

这一个标志驱动下游全部差异化行为——进度展示、恢复策略、并发归属、UI 呈现。它是唯一必须落到模型层的改动，其余都是语义约定与 handler 侧实现。

3.2 四处语义重新赋义（零模型改动）

维度批处理原义常驻作业赋义（复用同字段）
progress.phase"求值"/"落库""消费中" / "空闲等待" / "背压暂停"
progress.done已完成明细数累计已处理消息数（单调增，u64 永不溢出）
progress.total总明细数恒 0（= 无基数，percent() 自动返回 0，不显示百分比）
progress.ok/failed成功/失败项累计消费成功 / 失败（死信）计数
progress.message一句话状态"速率 120 msg/s · 积压 340 · 运行 2h13m · 上批 15 条"
progress.eta_ms预估剩余恒 None（无终点）
progress.items全量明细行滚动窗口：只留最近 N 条处理记录（约束 E，防内存泄漏）
关键：total=0 是现成的"无进度基数"语义
现有 ProgressSnapshot::percent() 在 total==0 时已返回 0。所以常驻作业不需要改进度模型，前端只要识别 service 类作业、把"进度条"换成"吞吐仪表"即可（§7）。

4 · 运行：消费循环骨架

handler 的 run() 就是消费循环。checkpoint 埋在每批之间，兼顾暂停、关闭、心跳与背压：

async fn run(ctx, params) -> Result<Value, JobError> {
    let mq = connect_queue(¶ms).await?;        // 连接 MQ
    ctx.set_phase("消费中");
    let mut processed = 0u64;

    loop {
        ctx.checkpoint().await?;                   // ← 暂停在此挂起；关闭在此返回 JobCancelled

        let batch = mq.poll(BATCH, POLL_TIMEOUT).await?;
        if batch.is_empty() {
            ctx.phase("空闲等待"); ctx.rate(0);     // 队列空：上报空闲，继续 loop
            continue;
        }
        ctx.phase("消费中");
        for msg in batch {
            match handle(msg).await {              // 业务处理
                Ok(_)  => { ctx.ok();  mq.ack(msg).await?; }
                Err(e) => { ctx.fail(&e); mq.dead_letter(msg).await?; }  // 死信,不中断
            }
            processed += 1;
        }
        ctx.progress_add(batch.len());             // done += n → SSE progress 事件
        ctx.item_window(recent);                   // 滚动窗口明细（只留最近 N）
        ctx.rate(throughput); ctx.lag(mq.backlog());// 速率/积压 → message
    }
    // checkpoint 抛 JobCancelled 经 ? 跳出：优雅排空
}
优雅关闭 = drain（本方案关键约定）
"停止"对批处理是"尽快停"；对消费者要区分两种（§5.2）。优雅关闭：收到信号 → 停止 poll → 处理完手头这批 → ack → 关连接 → 返回 Ok(摘要)。因为 checkpoint() 在每批之间而非批中途返回错误，手头这批天然处理完，drain 语义自动成立。handler 只需在 run() 返回前（或 ? 传播路径上）做连接清理。

5 · 生命周期与状态机（复用现有状态，重新赋义）

5.1 状态映射

现有状态常驻作业含义
Running进程活着：正在消费 或 空闲等待（都算 Running，用 phase 区分）
Paused暂停拉取：连接保持、不消费。用户手动或背压触发
Completed手动正常关闭：优雅排空后 handler 返回 Ok → 携带摘要（"共处理 12345 条，正常关闭"）
Cancelled强制停止：不等排空，立即中断（连接/位点可能不干净，重启时靠 MQ 重投）
Failed不可恢复错误：连接永久失败、错误率超阈值熔断等。→ 触发告警 + 自愈重拉

5.2 两种"停止"（本方案唯一的控制语义扩展）

优雅关闭 graceful close → Completed

停止拉新 → 处理完手头批 → ack → 关连接 → 正常终态（Completed，带摘要）。日常关闭走这个。前端按钮：「关闭」。

强制停止 force cancel → Cancelled

复用现有 cancel 语义，尽快中断。用于卡死/异常场景。前端按钮：「强制停止」（次要、危险色）。

实现上：现有 Control 是 {Run, Pause, Cancel}。优雅关闭可用一个约定实现而不必扩枚举——handler 收到 Cancel 后，若是 service 作业则默认走 drain 返回 Ok（Completed）；"强制"另配一个"跳过 drain"标志（或复用一次 cancel=优雅、二次 cancel=强制）。是否扩 Control::Close 视实现口味定，语义上二者已足够表达。

6 · 单实例约束与并发预算（约束 C + D）

6.1 全局单实例锁

约束 D：一个消费者逻辑名全局只允许一个活跃实例，否则重复消费。母版现成——复用 AI 子系统的 session 级活跃锁（SessionRegistry::try_acquire_session / 409 冲突）：

  • 单机：内存 DashMap 按 kind + business_key 加锁，重复提交返回 409。
  • 分布式：DB 唯一约束 / PG advisory lock 按逻辑名加锁——保证跨节点全局仅一个活跃实例。崩溃 reaper 回收后锁释放，才允许别处重领（正好串起 §2 的自愈）。

6.2 并发预算隔离

约束 C：常驻作业永久占槽，不能和批处理抢同一个 max_concurrency 池。

心智模型转变：service 作业是"部署"，不是"排队"
批处理走 queue-drain（SKIP LOCKED 抢一个跑一个）；service 作业走 desired-state（"这个消费者应该有 1 个实例常驻"）。二者应分属独立并发预算：
  • 配置分离：max_concurrency（批处理池） + max_services（常驻池），互不挤占。
  • claim 循环对 service 作业按"期望运行集合"领取（保持单例即可），而非按队列深度抢占。

8 · 管理：启动、关闭、恢复、位点

8.1 两种发起方式

方式场景
用户启动前端任务中心"启动消费者"，POST 提交 service 作业
系统自动拉起desired-state：声明为常驻的消费者，在 init_job_subsystem 后由系统自动 submit（配合单例锁，保证只拉起一个）。这对应"服务应常驻"的心智

8.2 消费位点谁负责（关键边界）

框架只保证"作业会被重新拉起"，不保证"从哪条消息继续"
崩溃/换节点重启后，消费位点（offset / ack 状态）必须由消息队列自身或作业自持久化（可复用 cmx_job_checkpoint 表存游标），不能依赖框架的进度快照——进度快照是给人看的监控数据，不是精确位点。
  • MQ 支持消费组/手动 ack（Kafka/RabbitMQ/Pulsar）→ 位点交给 MQ，重启从上次 ack 后继续，天然 at-least-once。
  • MQ 无位点语义（如轮询库表）→ 作业用 cmx_job_checkpoint 存"处理到哪"，重启读回。

8.3 归档与历史

常驻作业只有关闭后（Completed / Cancelled）才进历史表 cmx_job_hi——正在运行的消费者不可归档（先关闭）。历史里记录本次运行的累计吞吐、起止、关闭原因，供审计。

10 · 风险与非目标

  • at-least-once 崩溃重启依赖 MQ 重投 + 手动 ack，语义是至少一次。业务处理需幂等（去重键），否则强制停止/崩溃时可能重复处理手头批。这与框架 idempotent 声明一脉相承。
  • 非目标 不做消息队列本身（连接/分区/重平衡由 MQ 客户端负责）。任务中心只做"承载消费循环 + 监控 + 生命周期管理"。
  • 非目标 不做多实例分区并行消费（本方案定位单实例常驻）。若需水平扩展，是"多个不同 business_key 的单例作业"，或交给 MQ 消费组 + 多节点各跑一个——那是部署编排，超出本附录。
  • 背压 消费跟不上时，handler 可主动 Pause 自己（phase="背压暂停"）或降速，避免拖垮下游。属 handler 策略，框架提供 checkpoint 挂起能力即可。
总结
常驻消费者作业 = 现有协作式长任务框架的自然延伸。运行靠消费循环 + checkpoint；监控靠同一套 SSE 换个吞吐仪表呈现；管理靠现有控制端点 + 单例锁 + 两态停止。真正必需的新东西只有一个 JobClass::Service 标志和一个独立并发预算——其余全是既有能力的复用与语义赋义。
