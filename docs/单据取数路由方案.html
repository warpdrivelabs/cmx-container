单据取数路由方案 · 多端点 / 多组织

Doc-Source Routing · 逻辑单据类型 → 物理端点 · 组织继承解析 · Scatter-Gather 合批 · 照搬已验证范式
本篇定位：《业务单据 ↔ 报表取数打通方案》的路由专题扩展（§17）。上一篇解决"报表怎么取单据数据"，本篇解决"当每种单据、甚至同种单据的不同部署，分散在不同服务器/库上时，取数请求该发往哪里"。
要解决的问题：① 不同类型单据在不同服务器（数据+应用），连接路径各异；② 同一类单据也可能部署在不同的应用/数据服务上（按组织、按租户、按历史分片）。取数路由必须运行时可解析，不能编译期写死。
核心结论：需要配置，但不是扁平的"类型→服务器"表——那会被"同类不同部署"击穿成条目爆炸。正解是多维路由键 (单据类型, 组织, 期间…) + 两级解耦（治理面：慢变、按组织继承；地址面：快变、服务发现动态解析）。
最大利好：这套"逻辑名 + 组织 → 物理目标"的三层解析，代码库里已有 1:1 可照搬的成品——cmx-flow 的 SubflowRouter + cmx_flow_subflow_binding 绑定表 + CRUD 管理面。外加 cmx-plugin 的 remote_importers"类别→服务名/URL"双模式解析可作跨服务落点蓝本。不是新造，是改字段平移。
状态：架构方案，不动代码。

1 · 直答：需要配置，但形态是关键

你的直觉是对的——必须有配置来指定路由，取数侧不能靠猜哪台服务器有数据。但真正的问题不是"要不要配置"，而是配置长什么样。一张朴素的"单据类型 → 服务器"映射表能应付第一个诉求（不同类型在不同服务器），却会被你提的第二个诉求击穿：

"同一类单据也可能部署在不同的应用/数据服务上"——这一句就决定了路由键不能只有"单据类型"一个维度。 一旦同类分散，扁平表就退化为"每个(类型 × 组织 × 实例)一条记录"，条目爆炸、且单据每迁移一次就要手工改配置、必然漂移。

本方案给出的形态是：多维路由键 + 组织继承 + 两级解耦 + 照搬现成范式。下面逐层展开为什么。

2 · 为什么扁平表会崩

设想最直白的配置——一张 doc_type → server 表。看它在四种现实压力下如何变形：

现实压力扁平表的下场
不同类型不同服务器✓ 能应付（这是它唯一能处理的情形）
同类型按组织分库（北京凭证在A、上海在B）✗ 退化为 (类型,组织)→server，每个组织一行；1000 个组织 = 1000 行
大部分组织走默认、少数例外✗ 无"默认+例外"表达力，要么全列举，要么写不下例外
单据服务扩容/迁移/换机房✗ 物理地址写死在表里，一迁就要改所有相关行，漂移

崩溃的根因有两个，分别对应第 3、4 节的两个设计决定：①路由键维度不足（只有类型，没有组织）；②把"归属治理"和"物理地址"焊死在一张表（治理慢变、地址快变，混在一起互相拖累）。

3 · 路由键是多维的

"同一类单据分散在不同服务器"这件事，几乎从不是随机分散的，而是沿某个业务维度分片的。把分片维度显式建进路由键，分散就被自然表达，而不是靠堆记录去枚举。

分片维度典型场景是否已有现成载体
组织（主）北京公司凭证在总部库、子公司凭证在各自库；集团多法人分库✓ cmx_org.path 物化路径 + flow 已用它做继承路由
期间当年数据在生产库、历史归档在冷库△ 单据有 period_code 列，路由需扩展
租户SaaS 多租户，每租户独立库/服务△ 需租户上下文
单据类型凭证在总账服务、费用单在费控服务✓ moduleMeta 有 doc_type / moduleCode
设计决定 ①：路由键 = (单据类型, 组织) 为主，期间/租户 为可选扩展维。 其中组织是一等维度——因为最常见的"同类分散"就是按法人/组织分库，而且组织带层级（可继承），一条默认规则能覆盖整棵子树。期间/租户按需追加，解析算法同构。

4 · 两级解耦：治理面 + 地址面

扁平表的第二个死因是把两件变化速率截然不同的事焊在一起。拆开它们：

治理面 归属决策（慢变）

"gl凭证 + 北京组织 归哪个逻辑服务/数据源管？"

这是业务/组织决策，随机构调整变化——月/季度级。用数据库绑定表存，支持组织继承，可运营（管理界面增删改）。产出的是逻辑句柄（如 db_id=fico-bj 或 service=doc-gl-bj），不是 IP。

地址面 物理定位（快变）

"逻辑服务 doc-gl-bj 此刻在哪个地址/连接串？"

这是运维/运行时关注，随扩容、迁移、故障转移变化——分钟级甚至秒级。用服务发现（Nacos）动态解析 + 配置静态兜底。治理面完全不感知地址变化。

设计决定 ②：治理面产逻辑句柄，地址面解析物理地址，两者用 db_id/service_name 作契约边界。 好处：单据服务扩容/迁移时，只有地址面变，治理绑定表一行不动；业务把某组织的凭证换个库管时，只改治理绑定，地址面无感。两个团队（业务管理员、运维）各改各的，互不踩踏。
两级解耦 · 一次取数的路由解析 FetchSpec { docType:"gl_voucher", org:"BJ-SUB-01", period:"2026-05" } │ │ ①治理面：ReportSourceRouter.resolve(docType, org) ← 慢变·可运营·组织继承 │ 精确(gl,BJ-SUB-01)? → 无 → 沿 org.path 向上找最近祖先(gl,BJ)? → 命中 ▼ 逻辑句柄 { targetKind: DbId("fico-bj") } 或 { targetKind: Service("doc-gl-bj") } │ │ ②地址面：resolve_endpoint(句柄) ← 快变·服务发现·静态兜底 │ DbId → DatabaseManager.get_db("fico-bj") → 连接池(可指向远程PG) │ Service→ Nacos discover("doc-gl-bj") → healthy实例 → http/grpc URL ▼ 物理端点 postgres://10.1.2.3:5432/fico_bj 或 http://10.1.2.7:8080

6 · 四种路由方案对比择优

把"路由配置放在哪、怎么解析"这个决定，列出四种可能，逐一权衡：

1定义文件内联（单据定义 JSON 里写 dbId）

在每个单据定义的 moduleMeta 里加 "dataSource": "fico-bj"。报表取数时读定义拿到库。

配置量 小组织维度 ✗同类不同部署 ✗可运营 ✗ 改定义要重部署

劣：定义是"逻辑设计"，物理位置写进去就把设计和部署焊死；无法表达"同一定义按组织落不同库"（一个定义只能写一个 dbId）；改路由要改定义文件+重新部署。只适合"一类单据永远在同一个库"的简单情形。

2静态配置文件映射（dev-local.toml 里 [report_source] 段）

仿 [center_client]，在配置文件里写 doc_type → service_name/db_id 映射。

配置量 中组织维度 ✗同类不同部署 ✗可运营 △ 改配置要重启

优：有现成蓝本（remote_importers 就是这么做的），实现快。劣：仍是扁平映射无组织维度；改路由要改配置文件并重启进程；不能按组织给例外。适合类型少、部署稳定、无按组织分片的场景。

3数据库绑定表 + 组织继承解析 ⭐（照搬 SubflowRouter）

治理面用一张可运营的 report_source_binding(doc_type, org_id, target, enabled) 表，三层解析（精确→沿 org 继承→兜底）；地址面 db_id/服务发现动态解析。

配置量 小（默认+例外）组织维度 ✓✓同类不同部署 ✓✓可运营 ✓✓ 热更新有现成蓝本 ✓✓

优：① 组织继承——配一条"gl默认走总账库"+ 少数例外，覆盖整棵组织树，配置量最小；② 可运营——管理界面增删改、即时生效、无需重启/重部署；③ 同类不同部署天然支持（同 doc_type 多行不同 org→不同 target）；④ 代码库已有 1:1 落地（flow 的 M5.2），连绑定表、CRUD、REST、继承 SQL 都是现成的。劣：比方案 2 多一张表 + 一个解析器（但都是照抄）。

4服务注册元数据路由（Nacos metadata 打业务标签）

单据服务注册时在 ServiceInstance.metadata 里打 doc_type/org 标签，报表侧发现时按标签过滤实例。

配置量 中组织维度 △可运营 △改造 大

劣：RegistryAwareDiscover 当前只按 service_name 发现、不按 metadata 过滤（探查确认），要改发现层；治理规则散落在各服务的自注册代码里，不可集中运营；组织×类型的绑定矩阵无法在一处审视。发现层改造收益不抵成本。但它的 metadata 可作地址面的补充标签。

择优：方案 3（数据库绑定表 + 组织继承）为主干，方案 2（静态配置）作地址面兜底，方案 4 的 metadata 作服务发现补充。
理由一句话：唯有方案 3 同时解决"同类不同部署 + 按组织分片 + 可运营 + 有现成蓝本"四件事。方案 1/2 的扁平映射在"同类分散"面前失效；方案 4 要改发现层且不可集中治理。而方案 3 几乎是把 cmx-flow 已经跑通的 M5.2 换几个字段——风险最低、契合最高。

8.2 三层解析（照搬 subflow_router.rs:58-104 的解析顺序）

async fn resolve(&self, doc_type: &str, org: Option<&str>) -> RouteResult<SourceHandle> {
  // ① 精确匹配：这个组织有专属绑定？
  if let Some(org) = org {
    // WHERE doc_type=$1 AND org_id=$2 AND enabled  ORDER BY priority DESC LIMIT 1
    if let Some(hit) = exact(doc_type, org).await? { return Ok(hit); }

    // ② 沿组织路径继承：找最近的有绑定的祖先组织（照搬 flow 的物化路径 LIKE）
    // JOIN cmx_org self ON self.id=$2
    // JOIN cmx_org anc  ON self.path LIKE anc.path || '%'   -- anc 是 self 的祖先
    // WHERE b.doc_type=$1 AND b.org_id=anc.id AND b.enabled
    // ORDER BY length(anc.path) DESC LIMIT 1   -- 最长前缀=最近祖先优先
    if let Some(hit) = inherit_along_org_path(doc_type, org).await? { return Ok(hit); }
  }
  // ③ 类型默认兜底：org_id IS NULL 的那条
  if let Some(hit) = fallback(doc_type).await? { return Ok(hit); }

  // 全无 → 明确报错，设计态即可校验（不留到运行时）
  Err(RouteError::NoBinding{ doc_type, org })
}
组织继承是配置量的胜负手。 一条 (gl_voucher, org=NULL, fico-main) 兜底 + 一条 (gl_voucher, org=BJ, fico-bj) 例外，就让北京整棵子树走 fico-bj、其余全走 fico-main——两行覆盖上千组织。这正是 flow M5.2 已验证的"总部hq/北京继承/上海branch 三结果"同款语义。

10 · Scatter-Gather：跨端点合批

上一篇"一张报表一次网络往返"的前提是"所有取数发同一个单据服务"。多端点路由打破了这个前提——必须按端点分桶再各自合批。但合批的收益依然保留：

Scatter
路由后按逻辑句柄分桶：bucket["fico-bj"]=[spec1,spec3…]、bucket["doc-fee-svc"]=[spec2…]。N 个取数键 → K 个桶（K = 涉及的端点数，通常 1~3）。
并行
K 个桶并发发出（tokio::join / futures::join_all），墙钟 = 最慢的那个端点，不是 K 个串行相加。
Gather
各桶回传的 ZmcDataSet 按 specHash 合并进统一缓存 → pass2 同步求值。一个 spec 属于哪个桶对引擎透明。
合批粒度的精确表述：从"整张报表一次"改为"每个目标端点一次、K 个端点并行"。 常态下一张报表的取数集中在 1~2 个端点（同一套账在同一库），K 很小，与上一篇几乎无差；只有跨多法人合并报表才会 K 变大，而那时并行发出仍只付"最慢端点"一次延迟。N+1 依然被消灭——被消灭的是"每个取数键一次"，不是"每个端点一次"。

治理面产出逻辑句柄后，地址面负责变成可连接的物理端点。两种句柄、两条解析路径（照搬 remote_importers 双模式）：

句柄 target_kind解析路径复用适用
db_id（数据源句柄） DatabaseManager.get_db("fico-bj") → 连接池。db_id 的 db_url 可指向任意远程 PG（改 toml 即可）。 connection/mod.rs:482 方案 A 同库 / B 跨库直连
service（服务句柄） 直连模式：查 [report_source].urls 静态 URL；发现模式：Nacos discover("doc-gl-bj") → healthy 实例 → metadata["http_port"/"grpc_port"] 拼 URL。 remote_importers/mod.rs:395-443 方案 C HTTP / D gRPC
句柄类型决定 transport，transport 决定物理形态——层层解析、各司其职。 治理绑定表只需写"逻辑上归 fico-bj 管"；至于 fico-bj 是本机库、远程库、还是一个独立单据微服务，全由地址面按 target_kind + 配置/发现决定。单据从"共库"演进到"独立微服务"，改的是绑定表里 target_kind 从 db_id 换成 service，引擎与语义层不动。

13 · 缓存 · 一致性 · 失败降级

议题处理
路由结果缓存路由解析结果 (docType,org)→handle 可缓存（治理慢变），短 TTL + 绑定变更事件失效。取数值缓存见上一篇 §11（关账长缓存）。
无绑定RouteError::NoBinding → 该取数格标 #REF!，其余照算；设计态 check_formula 时即预解析路由，无绑定当场报错，不留运行时。
某端点不可达scatter-gather 中单桶失败不拖累其他桶：该桶的取数格标 #N/A，其他端点的数据正常。降级沿用上一篇 §13。
跨端点一致性不同端点无法共享一个 DB 事务快照。策略：历史期间（已关账）天然一致；开放期跨多法人合并报表标注"取数时点"，或统一取"日终快照"。
绑定与单据实际部署漂移治理绑定表是唯一事实源；单据服务上线/迁移时同步更新绑定（或由单据服务部署钩子回写建议绑定）。定期对账：绑定指向的 db_id/service 是否仍存活。
