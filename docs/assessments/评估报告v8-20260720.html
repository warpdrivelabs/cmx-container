三、架构与模块评估

3.1 架构分层

层次代表 crate / 目录评价

API 层cmx-api、cmx-flow-api、cmx-rpt-api、cmx-doc-api、cmx-dct-api模块化程度较高，业务专属 API 逐步从总 API 中拆出，有利于避免依赖环。
领域层cmx-plugin、cmx-iam、cmx-service、cmx-flow-*、cmx-rpt-*、cmx-doc-*业务能力覆盖完整，但部分服务文件已经超过 1000 行，需要继续做职责收敛。
基础设施层cmx-database、cmx-database-pg、cmx-buffer、cmx-storage、cmx-auth、cmx-audit、cmx-rpc基础能力抽象齐全，已具备数据库、缓存、对象存储、认证、审计、RPC 的平台底座。
共享模型/工具cmx-core、cmx-utils、cmx-traits、cmx-api-types跨模块复用清晰；应持续控制共享层膨胀，避免核心包变成隐式大杂烩。

3.2 主要优势

  • 平台功能完整：插件、流程、报表、数据字典、业务单据、认证授权、审计和基础设施层能力均已落位。
  • Workspace 治理意识较强：根 Cargo.toml 集中管理成员与依赖，内部依赖注释较充分。
  • 领域拆分趋势正确：cmx-flow、cmx-rpt、cmx-doc、cmx-dct 按 model/store/api 拆层，利于隔离 HTTP、DB 与核心语义。
  • 文档资产丰富：README.md、SQL 文档、部署分析、迁移方案、API JSON 与多份专项设计文档共同构成较完整的知识库。

3.3 架构风险

  • 模块数量与依赖关系复杂：54 个 workspace 成员已接近需要自动化依赖拓扑检查的规模。
  • 大文件集中：cmx-model-center/src/lib.rs 约 3269 行，cmx-doc-store-pg/src/saver.rs 约 2075 行，cmx-api/src/handlers/portal/handler.rs 约 1933 行，建议优先拆分。
  • 历史与当前实现并存：README 与 Cargo 成员中能看到停用/注释模块、迁移说明与新老实现并行痕迹，需要以版本边界逐步清理。

六、数据库与迁移评估

项目 SQL 资产位于 docs/sql，包含 init/init_ddl.sql、init/init_dml.sql、init/init_menu.sql 与 migrations 增量文件。当前扫描结果显示：

  • migrations 中 .up.sql 28 个，.down.sql 20 个，建议确认是否存在只允许前进的迁移；如果没有，应补齐 down 文件或在迁移规范中显式标注不可逆。
  • init_ddl.sql 中建表/索引相关语句约 219 条，说明数据库初始化资产较完整。
  • 静态扫描 FOREIGN KEY 命中均为“无 FOREIGN KEY”的注释说明，未发现真实外键约束，符合项目“关联字段 + 索引替代”的数据库规范。
  • 流程相关迁移在 20260717-20260718 较集中，建议将流程引擎表结构作为重点回归对象，确保 init 与 migrations 长期一致。

七、集群部署与无状态评估

从 README 与模块命名看，项目已经具备集群化设计意识：插件运行时通过 Redis Pub/Sub 做集群同步，缓存和分布式锁放在 cmx-buffer，文件存储通过 cmx-storage 接入本地/S3，配置注册中心通过 cmx-registry-config 抽象 Nacos/Mock。

需要重点验证的点

  • 本地缓存是否只缓存可重建数据；字典、权限、插件元数据更新后是否能广播或失效全集群。
  • 流程定时任务、异步 job、插件同步 worker 是否具有幂等性和多节点竞争保护。
  • OnceCell、LazyLock、Mutex、RwLock 的 131 处静态命中应分为“基础设施只读状态”和“业务可变状态”两类治理。
  • 容器层是否已完整覆盖 /health、/ready、SIGTERM drain、连接池关闭、任务取消与滚动升级。

八、主要问题与优先级

优先级问题影响建议动作
P0关键路径中的 unwrap/panic 未分级可能在生产请求、任务、插件执行中触发进程级失败。先排除 tests/examples，再对 API、DB、插件、流程引擎模块建立清单，生产路径改为 Result 或有业务说明的 expect。
P0集群一致性缺少自动化验证矩阵多节点部署下可能出现缓存不一致、重复消费、重复同步或任务竞争。为插件发布、权限变更、流程 job、字典配置更新设计多节点集成测试。
P1SQL 迁移 up/down 不对称回滚策略不清晰，生产发布风险上升。补齐 down 或显式标记不可逆迁移；增加迁移文件命名和配对检查脚本。
P1大文件/大 handler 影响可维护性代码审查难、测试定位慢、职责边界变模糊。优先拆分超过 1000 行的 handler/service/store 文件，按 DTO、校验、SQL、事务、路由分层。
P1缺少自动依赖/许可证/安全扫描信号供应链风险和重复依赖风险难以及时发现。引入 cargo deny、cargo audit、cargo machete 或等价 CI 步骤。
P2文档丰富但容易分散新人入口和版本事实来源可能不一致。为 README、AGENTS、SQL、部署、模块方案建立“当前有效/历史归档”索引。
