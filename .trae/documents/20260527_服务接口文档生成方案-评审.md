# 服务接口文档生成方案 — 评审报告

## 一、总体评价

方案整体思路清晰，目标明确——基于编排文件和 api.json 自动生成服务接口文档，并与版本绑定存储。核心架构选择（在安装/升级时生成、存储在 `cmx_service_define_version` 表）是合理的。

以下是按维度分类的具体评审意见。

---

## 二、类型命名与实际代码不符（需修正）

方案中使用的类型名与代码库实际定义不一致，实施时会导致编译错误：

| 方案中使用 | 实际类型名 | 所在文件 |
|-----------|-----------|---------|
| `FlowNode` | `ServiceNode` | `cmx-core/src/model/service/flow.rs` |
| `FlowEdge` | `ServiceEdge` | `cmx-core/src/model/service/flow.rs` |
| `ServiceOrchestration`（声称在 orchestrator/types.rs） | `ServiceOrchestration`（实际在 `cmx-core/src/model/service/orchestration.rs`） | 位置不对 |

此外，方案中示例 JSON 的字段名（如 `sourceNodeID`）使用 camelCase，但实际 `ServiceEdge` 的字段名是 `source_node_id`（snake_case，通过 `#[serde(rename)]` 反序列化）。这虽然不影响运行时，但在方案文档中应标注清楚，避免实施者混淆。

---

## 三、入口/出口函数算法存在盲区（关键问题）

### 3.1 未考虑 `skylake-switch` 节点

方案 4.1 节的算法只查找 `skylake-func` 节点。但实际上 `skylake-switch` 节点也拥有 `nodeMeta`（pluginId、functionName），它本质上是路由函数——接收输入，判断走哪个分支。

**真实场景**：start → switch（路由判断）→ func → end

此时入口函数是 switch 节点而非 func 节点。方案算法会跳过 switch，错误地找到后面的 func 作为入口。

**建议**：入口/出口查找应同时覆盖 `skylake-func` 和 `skylake-switch` 两种节点类型，或更通用地——查找拥有 `nodeMeta` 的节点。

### 3.2 未考虑 `skylake-transaction` 节点

事务框是一种容器节点（通过 `parent` 字段关联子节点）。方案完全没有讨论事务框内的节点如何处理：

```
start → transaction_start → func_a → func_b → transaction_end → end
```

事务框内的函数可能是出口函数。方案需要明确：
- 事务框的入口/出口如何界定？
- 是否需要递归处理事务框内的子图？

### 3.3 多出口分支的语义模糊

方案 5.2 节说"取最后一个 func 节点的输出"，但没有定义"最后一个"的语义。在 DAG 中，节点的执行顺序取决于运行时路由结果，静态分析无法确定唯一出口。

**建议**：
- 对于多分支汇聚到同一个 end 的场景，应收集所有可能路径上最后一个函数节点的输出，生成"可能的输出"列表
- 或者在文档中标注"输出取决于运行时分支选择"，列出每个分支的输出结构

## 四、数据来源优先级未明确（重要问题）

方案同时引用了两个数据源来获取参数信息，但没有说明优先级和合并策略：

1. **编排文件中的 `NodeIO`**（`ServiceNode.data.inputs` / `ServiceNode.data.outputs`）—— 这些是编排设计时定义的
2. **api.json 中的 `fields`**（`functions[].input.fields` / `functions[].output.fields`）—— 这些是插件开发者定义的函数签名

**问题**：
- 两者的参数列表可能不一致（编排可能只映射了部分参数）
- 两者的类型描述格式不同（`NodeIO` 只有 key/type/description/required，api.json 的 fields 有更丰富的嵌套结构）

**建议**：
- 明确以 api.json 为权威来源（函数签名的 ground truth）
- 编排中的 `NodeIO` 作为补充/覆盖（比如描述可以以编排为准）
- 或者：入参来源取编排中入口节点的 `inputs`，类型/描述补充自 api.json

---

## 五、跨插件 API 加载的实际可行性（需细化）

### 5.1 版本确定问题

方案说"根据当前已安装的版本"查找 api.json，但实际目录结构是 `{plugin_root}/{app_id}/{plugin_id}/{version}/api/api.json`。关键问题是：**如何知道目标插件当前激活的版本号？**

方案中的 `ApiDocGenerator` 只有 `plugin_root` 和 `app_id`，没有获取其他插件版本信息的能力。

**建议**：
- 通过 `ServiceStorage` 或新增 trait 方法查询目标插件的当前版本
- 或者在 `ParsedServiceDefinition` 中提供已安装插件版本映射

### 5.2 容错策略

方案 5.1 节提到"如果找不到，使用函数名作为 fallback，在当前插件的 api.json 中模糊匹配"。

**问题**：
- "模糊匹配"语义不清，容易匹配到错误函数
- 如果跨插件引用的函数找不到，生成的文档会有缺失

**建议**：
- 找不到时不应模糊匹配，而应生成一个占位文档（标记为"未知函数"），避免错误信息比缺失信息更危险
- 在日志中 warn 记录缺失情况

## 六、数据存储方案的补充建议

### 6.1 字段设计合理

将 `api_doc` 存储在 `cmx_service_define_version` 表中是正确的设计：
- 与版本绑定，升级自动有新文档，降级自然回退到旧文档
- 无需额外清理逻辑

### 6.2 缺少 JSON 校验

方案只说 `api_doc TEXT`，建议增加：
- 在 Rust 侧确保序列化后的 JSON 是合法的
- 可考虑用 `api_doc TEXT` 配合应用层校验，而非数据库 JSON 类型（保持与现有 `config` 字段风格一致）

### 6.3 降级场景的 api_doc 处理

方案 4.3 节说"降级场景不需要生成接口文档"。这是正确的——降级时 `cmx_service_define_version` 中旧版本的记录已包含 api_doc。但需要注意：

降级时 `downgrade_persist` 会更新 `cmx_service_define` 主表的 `version` 字段，但不会修改 `cmx_service_define_version`。如果主表需要展示当前版本的 api_doc，需要 JOIN 查询：

```sql
SELECT v.api_doc FROM cmx_service_define d
JOIN cmx_service_define_version v ON d.service_key = v.service_key AND d.version = v.version
```

方案应明确 api_doc 的查询路径。

## 七、接口文档格式设计的小问题

### 7.1 `ParameterDoc.var_name` 字段

方案定义了 `var_name: Option<String>`，注释说"嵌套属性名，如 input.name"。但顶层参数不应该有 var_name，这个字段只对嵌套的 properties 有意义。

**建议**：移除顶层的 `var_name`，只在 `properties` 内部的 `ParameterDoc` 中使用，或者改为更明确的 `path` 字段（如 `"input.address.city"`）。

### 7.2 `functions` 列表的必要性

方案在输出中包含所有函数节点的文档（`functions` 数组）。这是好的设计——便于用户理解整个编排流程。但建议：
- 标注每个函数在编排中的位置（第几步）
- 标注函数之间的数据流转关系

---

## 八、实施步骤的遗漏

### 8.1 `persistence.rs` 中 `plugin_root` 的获取

方案 4.3 节修改 `install_persist` 和 `upgrade_persist` 时传递 `plugin_root`，但现有代码中 `persistence.rs` 的 `PluginPersistence` 结构体已经可以访问 `self.deps.plugin_root`（通过 `PluginManagerSettings`）。需确认这个路径是否可用。

### 8.2 `cmx-traits` 的依赖方向

方案中 `SaveServiceVersionParams` 在 `cmx-traits` 中新增字段。需要确认：
- `cmx-traits` 是否已经依赖 `serde_json`（用于 api_doc 的序列化）
- api_doc 是作为 `String` 传递还是 `Option<serde_json::Value>`

### 8.3 缺少对 `cmx-service` 的 repository 修改细节

方案只说"SQL INSERT 加入 api_doc 字段"，但实际 `save_service_version_with_txn` 使用的是纯 INSERT（不是 UPSERT），每次安装/升级都会新增记录。需要：
- 新增参数传递
- 修改 SQL
- 修改对应的查询方法（如果查询需要返回 api_doc）

---

## 九、方案优势总结

1. **版本绑定存储**：api_doc 存在 version 表中，随版本自然管理，是正确的设计
2. **在安装/升级时生成**：避免运行时计算开销，一次生成多次使用
3. **跨插件支持**：考虑了编排中引用其他插件函数的场景
4. **模块划分清晰**：新增 `api_doc_generator.rs` 独立模块，不侵入现有解析逻辑

| 优先级 | 改进项 | 说明 |
|--------|--------|------|
| **P0（必须）** | 修正入口/出口算法 | 需覆盖 switch 和 transaction 节点 |
| **P0（必须）** | 明确数据来源优先级 | NodeIO vs api.json 的合并策略 |
| **P0（必须）** | 修正类型命名 | FlowNode → ServiceNode 等 |
| **P1（重要）** | 细化跨插件版本查找 | 如何获取目标插件当前版本 |
| **P1（重要）** | 容错策略改进 | 禁止模糊匹配，改为占位+警告 |
| **P1（重要）** | 多出口分支方案细化 | 定义"可能的输出"结构 |
| **P2（建议）** | 补充查询路径 | api_doc 如何被 API 层查询和返回 |
| **P2（建议）** | 移除顶层 var_name | 简化 ParameterDoc 结构 |
| **P2（建议）** | 函数位置标注 | 在 functions 列表中标注执行顺序 |
