# cmx-iam 互斥规则重构方案

> 移除现有 SoD（权限互斥/依赖）代码，重新设计统一的互斥规则引擎，同时支持功能权限互斥与角色互斥。
>
> 版本：v2.0（重构） | 日期：2026-06-23 | 模块：cmx-iam

***

## 一、概述

### 1.1 背景

当前 cmx-iam 的规则模块存在以下问题：

* 仅支持**权限级别**的互斥/依赖，缺少**角色级别**的互斥

* 表结构 `cmx_permission_rule_item` 使用 `group_seq` 区分互斥/依赖，语义复杂

* 不支持"主对象 + 互斥对象"的灵活互斥模式（如"A 与 B 互斥、A 与 C 互斥、B 与 C 不互斥"）

* 权限依赖规则在实际业务中极少使用，增加了不必要的复杂度

### 1.2 目标

重构互斥规则系统，核心模型为\*\*「1 个主对象 + N 个互斥对象」\*\*：

* **功能互斥**（permission）：拥有主权限 A 时，不能同时拥有互斥权限 B 或 C

* **角色互斥**（role）：拥有主角色 A 时，不能同时拥有互斥角色 B 或 C

### 1.3 互斥语义

规则配置为「主对象 A + 互斥对象 \[B, C]」时：

| 用户拥有的对象集合 | 是否违反  | 原因                  |
| --------- | ----- | ------------------- |
| {A}       | 否     | 仅拥有主对象              |
| {B}       | 否     | 仅拥有互斥对象，非主对象        |
| {B, C}    | **否** | 互斥对象之间不互斥           |
| {A, B}    | **是** | 同时拥有主对象 A 和互斥对象 B   |
| {A, C}    | **是** | 同时拥有主对象 A 和互斥对象 C   |
| {A, B, C} | **是** | 同时拥有主对象 A 和互斥对象 B/C |

**校验逻辑**：仅当用户集合**同时包含主对象和任一互斥对象**时判定违反。互斥对象之间不互斥。

### 1.4 设计约束

1. **移除现有 SoD 代码**：rule/ 模块全部重写，移除权限依赖（dependency）
2. **保留临时角色功能**：`cmx_user_role_assignment` 表和相关代码不受影响
3. **RuleEnforcer 接口不变**：`check_role_permissions` / `check_user_roles` 方法签名不变
4. **统一全量校验**：移除 `SodCheckScope`，始终校验用户合并后的完整集合

### 1.5 非目标

* **权限依赖规则**：不再支持（移除 dependency 类型）

* **角色依赖规则**：不支持

* **角色层级与继承**：不引入角色树形结构

> **设计说明**：
>
> * 主对象 `primary_subject_id` 放在规则表（一对一关系，直观表达"1 主 N 互斥"模型）

#### 4.3.2 核心校验方法

```rust
/// 统一互斥校验：检查 subject_set 是否同时包含主对象和任一互斥对象
fn check_exclusion(
    rules: &[LoadedRule],
    subject_set: &HashSet<String>,
) -> Result<(), IamError> {
    for rule in rules {
        // 仅当拥有主对象时才检查互斥对象
        if !subject_set.contains(&rule.primary_subject_id) {
            continue;
        }
        // 检查是否同时拥有任一互斥对象
        for excluded_id in &rule.excluded_ids {
            if subject_set.contains(excluded_id) {
                let message = rule.violation_message.clone().unwrap_or_else(|| {
                    format!("互斥规则违反 [{}]", rule.code)
                });
                return Err(IamError::RuleViolation {
                    rule_code: rule.code.clone(),
                    message,
                });
            }
        }
    }
    Ok(())
}
```

#### 4.3.4 RuleEnforcer trait 实现

```rust
#[async_trait]
impl RuleEnforcer for RuleEnforcerImpl {
    /// 角色层校验：给角色分配权限时，检查权限组合是否包含互斥冲突
    async fn check_role_permissions(
        &self,
        permission_ids: &[String],
    ) -> Result<(), IamError> {
        if !self.config.enable_sod_check {
            return Ok(());
        }

        // 仅加载功能权限互斥规则
        let rules = self.load_active_rules(Some("permission")).await?;
        let perm_set: HashSet<String> = permission_ids.iter().cloned().collect();
        Self::check_exclusion(&rules, &perm_set)
    }

    /// 用户层校验：给用户分配角色时，检查权限互斥 + 角色互斥
    async fn check_user_roles(
        &self,
        user_id: &str,
        role_ids: &[String],
    ) -> Result<(), IamError> {
        if !self.config.enable_sod_check {
            return Ok(());
        }

        // 一次性加载全部启用规则，在内存中按 subject_type 分区（避免两次 DB 查询）
        let all_rules = self.load_active_rules(None).await?;
        let (perm_rules, role_rules): (Vec<_>, Vec<_>) = all_rules
            .into_iter()
            .partition(|r| r.subject_type == "permission");

        // === 权限级互斥校验 ===
        if !perm_rules.is_empty() {
            let existing_perms = self.get_user_permission_ids(user_id).await?;
            let new_perms = self.get_role_permission_ids(role_ids).await?;
            let mut perm_set = existing_perms;
            perm_set.extend(new_perms);
            Self::check_exclusion(&perm_rules, &perm_set)?;
        }

        // === 角色级互斥校验 ===
        if !role_rules.is_empty() {
            let existing_roles = self.get_user_role_ids(user_id).await?;
            let mut role_set = existing_roles;
            role_set.extend(role_ids.iter().cloned());
            Self::check_exclusion(&role_rules, &role_set)?;
        }

        Ok(())
    }
}
```

> **设计决策：移除 SodCheckScope**
>
> 互斥校验必须基于用户合并后的完整集合（已有 + 新增）。增量模式（仅校验新增）会漏判"新增主对象与已有互斥对象冲突"的情况。因此移除 `SodCheckScope` 配置，统一全量校验。
>
> **assign\_roles 过度校验说明**：`check_user_roles` 在 assign\_roles 调用时合并了"用户当前权限/角色 + 新分配的"。由于 assign\_roles 是全量替换永久角色，合并集合包含了即将被替换的旧永久角色权限，可能导致过度校验（误报）。这是**安全方向**的偏差——更严格不会漏判，仅可能在极端场景下阻止合法分配（用户可先移除冲突的旧角色再重试）。

## 十、自我评审记录

### 第一轮评审：设计完备性

1. **移除 SodCheckScope 是否影响现有行为？**

   * **结论**：不影响。移除后统一全量校验（相当于之前的 `SodCheckScope::All`），更安全。增量模式（Incremental）会漏判，不应保留。

2. **primary\_subject\_id 放规则表 vs 明细表？**

   * **决策**：放规则表。主对象是规则的必要属性（一对一关系），直观表达"1 主 N 互斥"模型。修改主对象需 UPDATE 规则表，操作清晰。

3. **互斥对象之间不互斥的语义如何保证？**

   * **保证**：`check_exclusion` 逻辑仅在 `subject_set.contains(primary_subject_id)` 时才检查 excluded\_ids。互斥对象之间不会互相检查。

4. **是否需要 group\_seq？**

   * **结论**：不需要。互斥对象之间不互斥，无需分组。主对象与每个互斥对象互斥，不区分组。

5. **subject\_type='role' 的规则项是否需要校验 role\_id 真实存在？**

   * **决策**：create\_rule 时**校验** primary\_subject\_id 和 excluded\_subject\_ids 在对应表（cmx\_permission 或 cmx\_role）中存在，防止配置错误。后续删除权限/角色时不级联清理规则项（校验时自然跳过已删除的对象）。

6. **validate\_rule 是否需要同时支持权限和角色输入？**

   * **决策**：是。用户可能想测试"如果给用户分配这些角色，角色对应的权限是否违反规则"。因此 validate\_rule 同时接受 `permission_ids` 和 `role_ids`，分别校验对应类型的规则。
