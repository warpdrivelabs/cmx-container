# 平台级基础设施与双协议架构重构方案

> 日期：2026-06-12 | 模块：全局架构 | 状态：方案设计中（v4 — 整合第三轮评审意见）

***

## 一、目标

为平台新增企业级基础设施模块，支持 **RESTful + gRPC 双协议**：

* 用户管理、角色管理、权限控制（RBAC）

* 认证（JWT / OAuth2）

* 菜单管理、组织机构管理

* 审计日志（通用）

***

## 二、Crate 划分

### 2.1 划分原则

| 原则           | 说明                                             |
| ------------ | ---------------------------------------------- |
| 按业务领域划分      | 每个独立领域一个 crate，不按技术层拆                          |
| 基础设施 vs 业务分离 | 无业务逻辑的放 `cmx-infra/`，业务 crate 放 `crates/libs/` |
| 零循环依赖        | 通过 `cmx-traits` 中的 trait 解耦，依赖方向严格单向           |
| 协议无关的业务层     | Service 层不依赖 axum/volo，协议适配在 handler/gRPC 层    |

### 2.2 新增 Crate

| Crate       | 位置                                 | 定位   | 职责                                                                                                                | 依赖                                                                  |
| ----------- | ---------------------------------- | ---- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `cmx-auth`  | `crates/libs/cmx-infra/cmx-auth/`  | 基础设施 | JWT 编解码、Token 生命周期、密码哈希、OAuth2、会话管理、认证策略                                                                          | cmx-core, cmx-traits, cmx-buffer, cmx-audit                         |

## 五、认证上下文传播

### 5.1 AuthContext 定义位置：cmx-core

AuthContext 作为纯数据结构，定义在 **cmx-core** 中（与 SVRContext 同级），所有 crate 都能访问：

```
cmx-core/src/model/context/
  ├── svr_context.rs      # 现有 SVRContext
  └── auth_context.rs     # 🆕 AuthContext
```

### 5.2 AuthContext 结构

```
AuthContext (cmx-core)
  ├── user_id: String
  ├── username: String
  ├── roles: Vec<String>
  ├── permissions: Vec<String>
  └── org_id: Option<String>
```

### 5.3 SVRContext 扩展与兼容性

> **评审修正（v2 3.2）**：补充 SVRContext 版本化/兼容性策略

SVRContext 新增 `auth_context` 字段：

```
SVRContext (cmx-core)
  ├── headers: HashMap<String, String>     # 现有
  ├── request_id: String                   # 现有
  ├── txn_id: Option<String>               # 现有
  ├── auth_context: Option<AuthContext>    # 🆕 认证上下文
  └── ...
```

**WASM MessagePack 兼容性策略**：

`rmp_serde` 对 `Option<T>` 字段缺失时反序列化为 `None`（serde 的 `#[serde(default)]` 行为），因此：

* **旧插件**（编译时没有 auth\_context 字段）：反序列化新 SVRContext 时，auth\_context 是未知字段，rmp\_serde 默认忽略未知字段 ✅

* **新插件**反序列化旧 SVRContext（auth\_context 缺失）：`Option<AuthContext>` 缺失时反序列化为 `None` ✅

**结论**：无需版本号字段，`Option<T>` + serde 默认行为已保证前后兼容。实施时需验证 `rmp_serde` 的 `deny_unknown_fields` 未被启用。

**传播链路**：

```
HTTP 请求 / gRPC 请求
  ↓
mw_auth 中间件 / gRPC interceptor
  ↓ 从 JWT 解析 → 构建 AuthContext
  ↓
注入 SVRContext.auth_context
  ↓
Orchestrator → WASM FunctionInput.context（自动携带 auth_context）
  ↓
插件可通过 SDK 读取调用者身份
  ↓
宿主函数可自动注入 created_by / updated_by
```

### 5.4 多租户策略：共享认证库 + 权限全局有效

**决策**：

- 用户/角色/权限/菜单/组织表放在**共享认证数据库**中，所有业务服务通过统一的 db_id 访问
- **权限全局有效**：用户对所有 db_id 的同名资源拥有相同权限
- IAM 表不需要 tenant_id 列
- 业务数据仍通过 db_id 隔离
- AuthContext 不需要 tenant_id 字段

> **声明**：本平台当前为内部管理平台，**不支持租户间数据隔离的权限控制**。如后续需支持 SaaS 多租户场景，需在角色-权限关联表增加 `scope` 字段（按 db_id 绑定权限），届时改动面较大。

### 5.5 认证库 db_id 的确定方式

> **评审修正（v3 2.1）**：补充 IAM handler 如何获取认证库 db_id

**决策**：认证库使用 `DatabaseManager` 的 **default 数据源**（即 `default_db_id`），IAM 操作固定使用它。

理由：
- 当前系统已有 default 数据源概念，启动时自动连接
- IAM 表与业务表在 default 数据源中共存（单库模式），无需额外配置独立认证库
- IAM handler 不从请求 header 获取 db_id，而是使用固定的 `default_db_id`

**实现方式**：

```rust
// 业务 handler（现有模式）— 从 header 取 db_id
let db_id = get_db_id_from_header(&headers).await;
GenericCrudService::<MC>::create(mm, &db_id, None, data).await?;

// IAM handler — 固定使用 default_db_id
let db_id = mm.get_default_db_id();
UserService::create(mm, &db_id, None, data).await?;
```

如果后续需要将认证库独立为专用数据源，只需修改 `get_default_db_id()` 的返回值，IAM handler 无需改动。

## 六、双协议适配架构

### 6.1 核心要求：RESTful 和 gRPC 返回一致的响应结果

两个协议共享同一个 Service 层，Service 返回统一的协议无关结果，协议层只负责序列化。

### 6.2 统一响应模型（泛型）

> **评审修正（v1 3.1）**：ServiceResult 改为泛型 `ServiceResult<T>`，保留类型安全

**定义位置**：`cmx-api-types`（与 `ApiResp<T>` 同级）

理由：cmx-biz、cmx-iam、cmx-auth 都需要返回 ServiceResult，但它们不依赖 cmx-biz；cmx-api-types 依赖少、位置合适，所有业务 crate 都可访问。

```
ServiceResult<T> (定义在 cmx-api-types)
  ├── data: Option<T>                    ← 强类型业务数据
  ├── error: Option<BizError>            ← 统一错误
  └── meta: Option<ResponseMeta>         ← 分页等元信息

RESTful 响应：ServiceResult<T> → ApiResp<T>（T 直接序列化为 JSON，保持类型安全）
gRPC 响应：  ServiceResult<T> → protobuf（T 序列化为 JSON 字符串填入 data 字段）
```

**设计要点**：

* RESTful 端保持类型安全和高性能（T 直接 serde\_json 序列化，无多余转换）

* gRPC 端因 protobuf 限制做降级（T → JSON 字符串 → protobuf string 字段）

* 高频接口（如 service\_call、execute\_service）后续可定义专用 protobuf message 替代 JSON 字符串

### 6.3 统一认证验证

cmx-auth 提供统一验证函数，HTTP 中间件和 gRPC interceptor 都调用它：

```
cmx-auth: validate_token(token) → AuthContext

HTTP mw_auth.rs:     Authorization: Bearer <token> → validate_token → 注入 SVRContext
gRPC interceptor.rs: metadata["authorization"]      → validate_token → 注入 context
```

gRPC interceptor 失败返回 `Status::unauthenticated` / `Status::permission_denied`，与 HTTP 401/403 语义对齐。

### 6.4 认证策略

```
AuthPolicy
  ├── Public              # 免认证（如 /api/auth/login, /api/health）
  ├── Authenticated       # 需登录
  └── Permission(String)  # 需特定权限（如 "user:create"）
```

路由注册时指定策略，而非全局白名单。现有接口默认 `Public`，后续逐步迁移到 `Authenticated`。

### 6.5 宏系统 AuthPolicy 集成

> **评审修正（v2 2.2）**：补充宏演进设计

当前 `declare_crud_handlers!` 宏不支持认证参数。演进方案：

**方案：在路由注册层注入 AuthPolicy**（而非 handler 生成层）

理由：宏生成的 CRUD handler 本身是纯逻辑（调用 BMC → 返回结果），认证应在路由层统一处理，而非每个 handler 内部。

实现方式：

```rust
// 路由注册宏新增可选 auth_policy 参数
register_crud_handlers_module! {
    module: domain_crud,
    prefix: "/api/domains",
    auth_policy: AuthPolicy::Authenticated,  // 🆕 可选，默认 Public
}

// 宏内部为每个路由添加 .layer(auth_layer(policy.clone()))
```

向后兼容：不传 `auth_policy` 时默认 `Public`，现有代码无需修改。

### 6.6 插件管理 API 认证策略

## 八、CmxAppState 子 State 分组

> **评审修正（v2 2.1）**：CmxAppState 从 5 个 Option 膨胀到 10+，拆分为子 State

### 8.1 拆分方案

```rust
pub struct CmxAppState {
    pub app_id: String,
    pub core: CoreState,       // 必须初始化，字段不用 Option
    pub storage: StorageState, // 文件存储
    pub auth: AuthState,       // 认证相关
    pub iam: IamState,         // IAM 相关
    pub audit: AuditState,     // 审计
}

pub struct CoreState {
    pub plugin_query: Arc<dyn PluginQuery>,        // 非 Option
    pub runtime_invoker: Arc<dyn RuntimeInvoker>,  // 非 Option
    pub service_query: Arc<dyn ServiceQuery>,      // 非 Option
    pub service_storage: Arc<dyn ServiceStorage>,  // 非 Option
}

pub struct StorageState {
    pub storage_service: Option<Arc<dyn StorageService>>,
}

pub struct AuthState {
    pub auth_service: Option<Arc<dyn AuthService>>,
    pub permission_checker: Option<Arc<dyn PermissionChecker>>,
}

pub struct IamState {
    pub user_service: Option<Arc<dyn UserService>>,
    pub role_service: Option<Arc<dyn RoleService>>,
    pub menu_service: Option<Arc<dyn MenuService>>,
    pub org_service: Option<Arc<dyn OrgService>>,
}

pub struct AuditState {
    pub audit_logger: Option<Arc<dyn AuditLogger>>,
}
```

**设计要点**：

* `CoreState` 字段不用 `Option`（编译时保证，启动时必须初始化）

* 其他子 State 的字段用 `Option`（运行时检查，按需启用）

* handler 按功能域只访问对应子 State，减少耦合

## 九、cmx-api 瘦身重构

### 9.1 问题根源

cmx-api 当前约 70+ 源文件，混入了大量**协议无关的代码**（Entity/BMC/Filter/Service），导致 gRPC 要复用就得重写。

### 9.2 迁移计划

#### A. Entity/BMC/Filter → 对应业务 crate

| 迁移内容                            | 原位置                                    | 目标位置                                | 目标 crate   |
| ------------------------------- | -------------------------------------- | ----------------------------------- | ---------- |
| Domain Entity/BMC/Filter        | `cmx-api/src/handlers/domain/`         | `cmx-biz/src/domain/`               | cmx-biz    |
| Application Entity/BMC/Filter   | `cmx-api/src/handlers/application/`    | `cmx-biz/src/application/`          | cmx-biz    |
| Module Entity/BMC/Filter        | `cmx-api/src/handlers/module/`         | `cmx-biz/src/module/`               | cmx-biz    |
| SysDatasource Entity/BMC/Filter | `cmx-api/src/handlers/sys_datasource/` | `cmx-biz/src/datasource/`           | cmx-biz    |
| Marketplace Entity/BMC/Filter   | `cmx-api/src/handlers/marketplace/`    | `cmx-plugin/src/marketplace/`       | cmx-plugin |
| IAM 相关 Entity/BMC/Filter        | 新建                                     | `cmx-iam/src/{user,role,menu,org}/` | cmx-iam    |

**Entity 的** **`ToSchema`** **derive**：通过 feature gate 控制：

```toml
# cmx-biz/Cargo.toml (cmx-iam 同理)
[features]
default = []
openapi = ["utoipa"]
```

#### B. Service 业务逻辑 → cmx-biz

| 迁移内容                     | 原位置                                                    | 目标位置                                          |
| ------------------------ | ------------------------------------------------------ | --------------------------------------------- |
| DomainService            | `cmx-api/src/handlers/domain/service.rs`               | `cmx-biz/src/domain/service.rs`               |
| SysDatasourceService     | `cmx-api/src/handlers/sys_datasource/service.rs`       | `cmx-biz/src/datasource/service.rs`           |
| Application/Module 自定义分页 | `cmx-api/src/handlers/{application,module}/handler.rs` | `cmx-biz/src/{application,module}/service.rs` |

#### C. 消除 HTTP/gRPC 重复逻辑 → cmx-biz

> **评审修正（v2 3.4）**：补充 function\_invoker/service\_executor 的接口签名

| 提取内容       | 当前位置                            | 目标位置                              |
| ---------- | ------------------------------- | --------------------------------- |
| 插件函数调用核心逻辑 | `cmx-api` + `cmx-rpc/server.rs` | `cmx-biz/src/function_invoker.rs` |
| 服务编排执行核心逻辑 | `cmx-api` + `cmx-rpc/server.rs` | `cmx-biz/src/service_executor.rs` |

**接口签名**（trait 对象通过函数参数传入）：

```rust
// function_invoker.rs
pub async fn invoke_function(
    runtime: &Arc<dyn RuntimeInvoker>,
    plugin_query: &Arc<dyn PluginQuery>,
    svr_ctx: &SVRContext,
    service_key: &str,
    function_name: &str,
    input: Value,
) -> Result<Value, BizError>

// service_executor.rs
pub async fn execute_service(
    runtime: &Arc<dyn RuntimeInvoker>,
    plugin_query: &Arc<dyn PluginQuery>,
    service_query: &Arc<dyn ServiceQuery>,
    service_storage: &Arc<dyn ServiceStorage>,
    svr_ctx: &SVRContext,
    default_db_id: &str,
    service_key: &str,
) -> Result<Value, BizError>
```

> **评审修正（v3 2.3）**：`execute_service` 移除 `flow` 参数（编排定义由内部通过 service_key 查询获取），补充 `default_db_id` 参数（Orchestrator 构造需要）

**调用方式**：

```rust
// cmx-api handler
let state = &state.core;
let result = invoke_function(
    &state.runtime_invoker, &state.plugin_query,
    &svr_ctx, service_key, function_name, input,
).await?;

// cmx-rpc server
let result = invoke_function(
    &runtime_invoker, &plugin_query,
    &svr_ctx, service_key, function_name, input,
).await?;
```

### 9.3 重构后 cmx-api 职责边界

**只保留**：handler 薄层 + 路由注册 + 中间件 + OpenAPI 文档

**不再包含**：Entity、BMC、Filter、Service、业务逻辑

### 9.4 效果预估

| 指标             | 重构前            | 重构后       |
| -------------- | -------------- | --------- |
| cmx-api 文件数    | \~70           | \~45      |
| cmx-api 职责     | HTTP 适配 + 业务逻辑 | 仅 HTTP 适配 |
| HTTP/gRPC 重复代码 | \~300 行        | 0 行       |
| 业务逻辑可测试性       | 需启动 HTTP 服务器   | 独立单元测试    |

## 十三、风险

| 风险                         | 缓解                                                        |
| -------------------------- | --------------------------------------------------------- |
| Service 下沉引入回归             | 保留 re-export，渐进迁移                                         |
| SVRContext 结构变更影响 WASM 序列化 | `Option<T>` + serde 默认行为保证兼容，验证 deny\_unknown\_fields 未启用 |
| 认证中间件影响现有无认证接口             | AuthPolicy 白名单机制，现有接口默认 Public                            |
| gRPC/RESTful 接口一致性         | 共享 Service 层 + 统一 validate\_token                         |
| 全局单例初始化顺序                  | 在 web-server main.rs 中按拓扑顺序显式初始化                          |
| 错误类型命名变更影响面                | 统一重命名 CrudError/OrchestrationError/BizError，全局替换          |
| 权限全局有效不适用于 SaaS 多租户        | 文档明确声明，后续需增加 scope 字段时改动面较大                               |
