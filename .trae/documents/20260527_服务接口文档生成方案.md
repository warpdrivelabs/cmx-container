# 服务接口文档生成方案

## 一、背景与目标

根据服务编排文件（`servicedata/*.json`）和函数文档（`api/api.json`），自动生成服务入参和出参的接口文档。

* **入参来源**：起点（`skylake-start`）后的第一个可执行节点（`skylake-func` 或 `skylake-switch`）的输入参数

* **出参来源**：结束节点（`skylake-end`）之前的所有可执行节点的输出参数（支持多分支场景）

* **跨插件支持**：编排中的函数可能来自其他插件，需通过 `PluginQuery` 查询目标插件版本，读取对应插件目录的 `api.json` 获取参数描述

## 二、现状分析

### 2.1 服务编排格式（servicedata/\*.json）

```json
{
  "code": "bm",
  "name": "服务编排完整测试流程",
  "flow": {
    "nodes": [
      {"id": "start_1", "type": "skylake-start"},
      {"id": "route_check", "type": "skylake-switch", "data": {"nodeMeta": {"pluginId": "...", "functionName": "..."}}},
      {"id": "branch_1_func", "type": "skylake-func", "data": {"nodeMeta": {"pluginId": "...", "functionName": "..."}}},
      {"id": "end_1", "type": "skylake-end"}
    ],
    "edges": [
      {"sourceNodeID": "start_1", "targetNodeID": "route_check"},
      {"sourceNodeID": "branch_1_func", "targetNodeID": "end_1"}
    ]
  }
}
```

> **注意**：JSON 中字段名为 camelCase（如 `sourceNodeID`），反序列化后映射为 Rust 的 snake\_case（如 `source_node_id`），通过 `#[serde(rename)]` 实现。

### 2.4 数据来源优先级

编排文件和 api.json 都提供参数信息，但详略不同：

| 来源                | 位置                                | 特点                                          |
| ----------------- | --------------------------------- | ------------------------------------------- |
| api.json `fields` | 插件安装目录 `api/api.json`             | **权威来源**，包含完整的类型、嵌套属性（properties）、描述        |
| 编排 `NodeIO`       | `ServiceNode.data.inputs/outputs` | 编排设计时的简化映射，只有 key/type/description/required |

**合并策略**：

1. **以 api.json 为权威来源**：类型、嵌套结构、必填性以 api.json 为准
2. **编排 NodeIO 作为补充**：如果 api.json 中缺少 description，使用 NodeIO 中的 description
3. **api.json 不可用时的降级**：如果找不到 api.json，使用编排中的 NodeIO 生成基础文档，并在文档中标注"参数描述不完整"

## 三、接口文档格式设计

### 3.1 生成的文档结构

```json
{
  "service": {
    "key": "bm",
    "name": "服务编排完整测试流程",
    "description": "包含分支路由、事务处理、函数调用的完整测试流程",
    "plugin_id": "example_plugin",
    "version": "1.0.2"
  },
  "input": {
    "description": "服务入参，传递给第一个可执行节点",
    "source_node_id": "route_check",
    "source_node_type": "skylake-switch",
    "parameters": [
      {
        "name": "input",
        "type": "object",
        "required": true,
        "description": "函数输入，包含 RouteInput 格式的路由参数",
        "properties": [
          {
            "name": "route",
            "type": "string",
            "required": true,
            "description": "路由标识，取值为 \"1\"、\"2\"、\"3\" 或 \"4\""
          }
        ]
      }
    ]
  },
  "output": {
    "description": "服务出参，来自最终可执行节点的输出",
    "branches": [
      {
        "branch_name": "默认输出",
        "source_node_id": "merge_result",
        "source_node_type": "skylake-func",
        "parameters": [
          {
            "name": "result",
            "type": "object",
            "description": "函数执行结果"
          }
        ]
      }
    ]
  },
  "functions": [
    {
      "node_id": "route_check",
      "node_type": "skylake-switch",
      "name": "路由判断",
      "step_index": 0,
      "plugin_id": "example_plugin",
      "function_name": "route_check",
      "summary": "路由判断函数",
      "input_parameters": [],
      "output_parameters": []
    }
  ]
}
```

### 3.2 关键设计说明

1. **`input.source_node_id`** **/** **`source_node_type`**：标注入参来源节点，便于调用方理解参数来源
2. **`output.branches`**：多出口分支场景，列出所有可能的输出结构（详见 5.2 节）
3. **`functions[].step_index`**：标注函数在编排中的拓扑顺序（从入口开始 BFS 序号），便于理解执行顺序
4. **`parameters[].properties`**：对象类型时递归展开嵌套属性，无层级限制

## 四、实现方案

### 4.1 新建模块：`cmx-plugin/src/service/api_doc_generator.rs`

**职责**：

1. 解析编排文件，找到入口/出口可执行节点
2. 通过 `PluginQuery` 查询跨插件版本，加载所有引用插件的 `api.json`
3. 合并 api.json 和编排 NodeIO 的参数信息
4. 生成接口文档 JSON

**核心结构体**：

```rust
use cmx_core::model::service::{ServiceOrchestration, ServiceNode, ServiceEdge, NodeIO};
use cmx_traits::PluginQuery;
use std::path::PathBuf;
use std::collections::HashMap;

/// 可执行节点类型集合（拥有 nodeMeta 的节点）
const EXECUTABLE_NODE_TYPES: &[&str] = &["skylake-func", "skylake-switch"];

/// 接口文档生成器
pub struct ApiDocGenerator {
    plugin_root: PathBuf,
    app_id: String,
    plugin_query: Arc<dyn PluginQuery>,
}

/// 服务接口文档
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ServiceApiDoc {
    pub service: ServiceInfo,
    pub input: InputDoc,
    pub output: OutputDoc,
    pub functions: Vec<FunctionDoc>,
}

/// 服务基本信息
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ServiceInfo {
    pub key: String,
    pub name: String,
    pub description: String,
    pub plugin_id: String,
    pub version: String,
}

/// 输入参数文档
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct InputDoc {
    pub description: String,
    pub source_node_id: String,
    pub source_node_type: String,
    pub parameters: Vec<ParameterDoc>,
}

/// 输出参数文档（支持多分支）
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct OutputDoc {
    pub description: String,
    pub branches: Vec<OutputBranch>,
}

/// 单个输出分支
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct OutputBranch {
    pub branch_name: String,
    pub source_node_id: String,
    pub source_node_type: String,
    pub parameters: Vec<ParameterDoc>,
}

/// 函数文档
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct FunctionDoc {
    pub node_id: String,
    pub node_type: String,
    pub name: String,
    pub step_index: usize,
    pub plugin_id: String,
    pub function_name: String,
    pub summary: String,
    pub input_parameters: Vec<ParameterDoc>,
    pub output_parameters: Vec<ParameterDoc>,
}

/// 参数定义
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ParameterDoc {
    pub name: String,
    pub param_type: String,     // string, integer, object, array, boolean
    #[serde(skip_serializing_if = "Option::is_none")]
    pub required: Option<bool>,
    pub description: String,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub properties: Option<Vec<ParameterDoc>>, // 对象类型时的嵌套属性
}
```

**关键算法**：

```rust
impl ApiDocGenerator {
    pub fn new(plugin_root: PathBuf, app_id: String, plugin_query: Arc<dyn PluginQuery>) -> Self {
        Self { plugin_root, app_id, plugin_query }
    }

    /// 生成服务接口文档
    pub async fn generate_api_doc(
        &self,
        orchestration: &ServiceOrchestration,
        current_plugin_id: &str,
        current_plugin_version: &str,
    ) -> PluginResult<ServiceApiDoc>;

    /// 找到入口可执行节点（起点后的第一个 func 或 switch 节点）
    ///
    /// 算法：从 skylake-start 节点出发，沿边 BFS，找到第一个类型为
    /// skylake-func 或 skylake-switch 的节点。
    /// 注意：skylake-switch 节点也拥有 nodeMeta，是路由函数，应作为入口。
    fn find_entry_node<'a>(
        &self,
        nodes: &'a [ServiceNode],
        edges: &'a [ServiceEdge],
    ) -> Option<&'a ServiceNode>;

    /// 找到出口可执行节点（终点前的所有可执行节点）
    ///
    /// 算法：找到所有指向 skylake-end 的边，反向追溯到最后一个
    /// skylake-func 或 skylake-switch 节点。
    /// 如果多个分支汇聚到 end，返回每个分支的最后一个可执行节点。
    fn find_exit_nodes<'a>(
        &self,
        nodes: &'a [ServiceNode],
        edges: &'a [ServiceEdge],
    ) -> Vec<&'a ServiceNode>;

    /// 收集编排中所有可执行节点，按拓扑顺序排列
    ///
    /// 算法：从 start 节点 BFS 遍历，收集所有 EXECUTABLE_NODE_TYPES 节点，
    /// 同时处理事务框内的子节点（parent 字段）。
    fn collect_executable_nodes<'a>(
        &self,
        nodes: &'a [ServiceNode],
        edges: &'a [ServiceEdge],
    ) -> Vec<(&'a ServiceNode, usize)>; // (node, step_index)

    /// 加载指定插件的 API 定义
    ///
    /// 查找路径：{plugin_root}/{app_id}/{plugin_id}/{version}/api/api.json
    /// 版本获取：通过 PluginQuery::get_plugin 查询当前安装版本
    async fn load_plugin_api(&self, plugin_id: &str) -> Option<PluginApiDef>;

    /// 从当前插件安装目录加载 api.json（用于同插件函数）
    fn load_current_plugin_api(&self, install_path: &Path) -> Option<PluginApiDef>;

    /// 合并参数信息：以 api.json 为权威，NodeIO 补充 description
    fn merge_parameters(
        api_fields: &[ApiField],
        node_ios: &[NodeIO],
    ) -> Vec<ParameterDoc>;
}
```

### 4.2 入口/出口节点查找算法详解

#### 4.2.1 入口节点查找

```
start → [switch/func] → ...
         ↑ 入口节点
```

1. 找到 `node_type == "skylake-start"` 的节点
2. 从该节点出发，沿 `edges` 找到 `target_node_id`
3. 如果目标节点是 `skylake-func` 或 `skylake-switch`，即为入口节点
4. 如果目标节点是 `skylake-transaction`，进入事务框内部，找到事务框内第一个可执行节点

#### 4.2.2 出口节点查找

```
... → [func/switch] → end
       ↑ 出口节点
```

1. 找到所有 `target_node_id == "skylake-end"` 的边
2. 对每条边，取 `source_node_id`
3. 如果源节点是 `skylake-func` 或 `skylake-switch`，即为出口节点
4. 如果源节点是 `skylake-transaction`，进入事务框内部，找到事务框内最后一个可执行节点
5. 收集所有出口节点，每个对应一个 `OutputBranch`

#### 4.2.3 事务框处理

事务框（`skylake-transaction`）是容器节点，其子节点通过 `parent` 字段关联：

```
transaction_node (parent=None)
  ├── func_a (parent="transaction_node")
  ├── func_b (parent="transaction_node")
  └── func_c (parent="transaction_node")
```

处理策略：

* 遇到 transaction 节点时，查找 `parent == transaction.id` 的子节点

* 在子节点中按边的连接关系确定入口/出口

* 事务框的入口 = 子节点中第一个可执行节点

* 事务框的出口 = 子节点中最后一个可执行节点

### 4.4 修改 `cmx-plugin/src/service/service_parser.rs`

在现有 `parse_and_save_services` 函数中增加 api\_doc 生成逻辑，而非新建函数。这样改动最小，且保持现有调用点不变。

```rust
pub async fn parse_and_save_services(
    install_path: &Path,
    params: &ServiceParseParams,
    service_storage: &Arc<dyn cmx_traits::ServiceStorage>,
    plugin_root: &Path,           // 新增参数
    plugin_query: &Arc<dyn cmx_traits::PluginQuery>,  // 新增参数
    txn_id: Option<&str>,
) -> PluginResult<Vec<ParsedServiceDefinition>> {
    // 1. 解析服务数据（现有逻辑不变）
    let parsed = ServiceDataParser::parse_servicedata(install_path, params)?;
    // ...

    // 2. 保存服务定义（现有逻辑不变）
    // ... save_service, save_service_version ...

    // 3. 生成接口文档（新增逻辑）
    let generator = ApiDocGenerator::new(
        plugin_root.to_path_buf(),
        params.app_id.clone(),
        plugin_query.clone(),
    );

    for svc in &parsed {
        match generator.generate_api_doc(
            &svc.orchestration,
            &params.plugin_id,
            &params.plugin_version,
        ).await {
            Ok(api_doc) => {
                let api_doc_json = serde_json::to_string(&api_doc)
                    .map_err(|e| PluginError::Plugin(format!("序列化接口文档失败: {}", e)))?;
                // 将 api_doc 写入 save_service_version
                // （通过 SaveServiceVersionParams.api_doc 字段传递）
            }
            Err(e) => {
                // 生成失败不影响主流程，仅记录警告
                tracing::warn!(
                    "生成服务 {} 的接口文档失败: {:?}",
                    svc.definition.service_key, e
                );
            }
        }
    }

    Ok(parsed)
}
```

**关键设计决策**：api\_doc 生成失败时仅 warn，不阻断安装/升级主流程。因为 api\_doc 是辅助信息，缺失不影响服务执行。

### 4.6 数据存储方案

**存储位置**：`cmx_service_define_version` 表中的 `api_doc` 字段（JSON 字符串）

**数据库字段**（由其他模块负责添加）：

```sql
ALTER TABLE cmx_service_define_version ADD COLUMN api_doc TEXT;
```

**理由**：

* 接口文档与版本绑定，版本升级时新版本会自动有新的接口文档

* 降级时因为查询的是旧版本的 `api_doc` 字段，自然就是旧版本的文档

* 无需额外的降级处理逻辑

* 与现有 `config` 字段风格一致（均为 TEXT 类型存储 JSON 字符串）

**降级场景说明**：

* 降级时 `downgrade_persist` 不生成新的 api\_doc

* 旧版本的 api\_doc 已存储在 `cmx_service_define_version` 表中

* 查询当前版本的 api\_doc 时，通过 `cmx_service_define` 主表的 `version` 字段 JOIN `cmx_service_define_version`：

  ```sql
  SELECT v.api_doc
  FROM cmx_service_define d
  JOIN cmx_service_define_version v
    ON d.service_key = v.service_key
    AND d.app_id = v.app_id
    AND d.version = v.version
  WHERE d.service_key = $1 AND d.app_id = $2
  ```

## 五、关键问题处理

### 5.1 跨插件函数引用

**场景**：编排中的函数来自插件 A，但引用了插件 B 的函数。

**解决方案**：

1. 在解析编排时，收集所有 `nodeMeta.pluginId`
2. 对于每个 pluginId，通过 `PluginQuery::get_plugin(plugin_id)` 查询目标插件的当前版本号
3. 拼接路径 `{plugin_root}/{app_id}/{plugin_id}/{version}/api/api.json` 读取 API 定义

**版本查找流程**：

```rust
async fn load_plugin_api(&self, plugin_id: &str) -> Option<PluginApiDef> {
    // 1. 查询目标插件当前版本
    let snapshot = self.plugin_query.get_plugin(plugin_id).await.ok()??;

    // 2. 拼接 api.json 路径
    let api_path = self.plugin_root
        .join(&self.app_id)
        .join(plugin_id)
        .join(&snapshot.version)
        .join("api")
        .join("api.json");

    // 3. 读取并解析
    if !api_path.exists() {
        tracing::warn!("跨插件 api.json 不存在: {:?}", api_path);
        return None;
    }
    let content = tokio::fs::read_to_string(&api_path).await.ok()?;
    serde_json::from_str(&content).ok()
}
```

**容错策略**（禁止模糊匹配）：

* 如果目标插件未安装（`get_plugin` 返回 None），生成占位文档：

  ```json
  {
    "name": "unknown",
    "param_type": "unknown",
    "description": "未找到插件 {plugin_id} 的 API 定义，参数信息不可用",
    "required": null
  }
  ```

* 在日志中 `warn!` 记录缺失情况

* **不使用模糊匹配**：避免匹配到错误函数，错误信息比缺失信息更危险

### 5.2 多出口分支

**场景**：编排有多个分支，最终汇聚到一个 end 节点。

```
start → switch → branch_1_func → end
                → branch_2_func → end
                → branch_3_func → end
```

**解决方案**：

* 收集所有指向 `skylake-end` 的路径上的最后一个可执行节点

* 每个出口节点生成一个 `OutputBranch`

* `branch_name` 使用出口节点的 `data.name`（如"分支1处理"）

* 如果所有分支的输出结构相同（同一函数或输出参数一致），合并为单个分支，`branch_name` 为"默认输出"

**示例输出**：

```json
{
  "output": {
    "description": "服务出参，输出取决于运行时分支选择",
    "branches": [
      {
        "branch_name": "分支1处理",
        "source_node_id": "branch_1_func",
        "source_node_type": "skylake-func",
        "parameters": [...]
      },
      {
        "branch_name": "分支2处理",
        "source_node_id": "branch_2_func",
        "source_node_type": "skylake-func",
        "parameters": [...]
      }
    ]
  }
}
```

### 5.3 入口函数可能无参数

**场景**：第一个可执行节点的输入来自 start 节点的固定输出。

**解决方案**：

* 标记 `input.parameters` 为空数组

* 在 `input.description` 中说明"此服务无需入参"

### 5.4 api.json 中 output 无 fields

**场景**：api.json 中函数的 `output` 只有 `encoding` 和 `type`，没有 `fields`（如实际 api.json 中大部分函数的 output）。

**解决方案**：

* `output.parameters` 为空数组

* 在 `output.description` 中标注"输出结构未在 API 文档中定义"
