## 二、唯一索引冲突处理方案（核心议题）

### 2.1 方案 A：部分唯一索引（Partial Unique Index）— 推荐

**做法**：将唯一索引改为 `WHERE archived = 0` 的部分唯一索引，仅对"未归档"记录强制唯一。

```sql
-- 改造前
CREATE UNIQUE INDEX uk_cmx_role_code ON cmx_role (code);
-- 改造后
CREATE UNIQUE INDEX uk_cmx_role_code ON cmx_role (code) WHERE archived = 0;
```

**需改造的索引清单**：

| 表                     | 原索引                                                    | 新索引                                                                     |
| --------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------- |
| `cmx_user`            | `uk_cmx_user_username ON (username)`                   | `uk_cmx_user_username ON (username) WHERE archived = 0`                 |
| `cmx_user`            | `uk_cmx_user_email ON (email) WHERE email IS NOT NULL` | `uk_cmx_user_email ON (email) WHERE email IS NOT NULL AND archived = 0` |
| `cmx_role`            | `uk_cmx_role_code ON (code)`                           | `uk_cmx_role_code ON (code) WHERE archived = 0`                         |
| `cmx_permission`      | `uk_cmx_permission_code ON (code)`                     | `uk_cmx_permission_code ON (code) WHERE archived = 0`                   |
| `cmx_menu`            | `uk_cmx_menu_code ON (code)`                           | `uk_cmx_menu_code ON (code) WHERE archived = 0`                         |
| `cmx_user_role`       | `uk_cmx_user_role ON (user_id, role_id)`               | `uk_cmx_user_role ON (user_id, role_id) WHERE archived = 0`             |
| `cmx_role_permission` | `uk_cmx_role_permission ON (role_id, permission_id)`   | `uk_cmx_role_permission ON (role_id, permission_id) WHERE archived = 0` |

**优点**：

* PostgreSQL 原生支持，零运行时开销

* 改动最小：仅 DDL 索引定义变化，业务代码零改动（查询已全部带 `archived = 0`）

* 语义清晰：同一时刻只有一个"活跃"同名记录，归档记录可无限累积

* 业界主流：Django soft-delete、Rails paranoia、Hasura 等均采用此模式

**缺点**：

* 需一次性重建索引（生产环境需停机或在线 CONCURRENTLY 重建）

* 历史归档记录同名数据会累积（可配合定期清理策略）

### 2.2 方案 B：软删除时重命名唯一键

**做法**：软删除时给唯一字段追加后缀（如 `_archived_{id}` 或 `_del_{timestamp}`），释放唯一键占用。

```sql
UPDATE cmx_role 
SET archived = 1, 
    code = code || '_archived_' || id,
    update_time = NOW() 
WHERE id = ANY($1);
```

**优点**：

* 不需要改索引 DDL

* 历史数据可追溯（通过后缀知道归档时间/原 id）

**缺点**：

* 破坏业务字段完整性（`code` 不再是原始值）

* 查询历史数据需剥离后缀，复杂度高

* 若唯一字段被外键/关联引用（如 `cmx_permission.full_code_path` 含 code），需级联改名，风险高

* 不符合"数据不可变"原则，审计时原始值已丢失

### 2.3 方案 C：历史表 + 物理删除（归档迁移）

**做法**：删除时把记录 INSERT 到 `{table}_history` 表，再从主表物理 DELETE。

```
cmx_role  --DELETE-->  cmx_role_history (保留全部历史)
```

**优点**：

* 主表保持轻量，唯一索引天然不冲突

* 历史数据与生产数据物理隔离，查询互不干扰

* 符合 GDPR"被遗忘权"（主表无残留）

**缺点**：

* 实现最复杂：每张表需维护镜像历史表 + 触发器或应用层迁移逻辑

* 查询历史需跨表 UNION，开发成本高

* 历史表 schema 需与主表同步演进（DDL 维护成本翻倍）

* 与当前 `archived` 字段设计意图冲突（要么全用历史表，要么全用 archived，不能混用）

### 2.4 方案对比与结论

| 维度                | 方案 A（部分唯一索引） | 方案 B（重命名） | 方案 C（历史表） |
| ----------------- | :----------: | :-------: | :-------: |
| 实现复杂度             |       低      |     中     |     高     |
| 业务代码改动            |       零      |  中（删改逻辑）  |  高（查询/迁移） |
| 数据完整性             |       优      |     差     |     优     |
| 查询历史成本            |    低（同表过滤）   |  中（需去后缀）  |   高（跨表）   |
| 与现有 archived 设计契合 |      完美      |     一般    |     冲突    |
| PostgreSQL 原生支持   |       ✓      |     ✗     |     ✗     |
| 业界主流度             |      主流      |     少见    |   大型系统用   |

### 结论

**采用方案 A（部分唯一索引）**。

理由：

1. 当前查询层已全部带 `archived = 0` 过滤，方案 A 与现有架构零摩擦
2. PostgreSQL 原生支持部分索引，无额外运行时开销
3. 改动集中在 DDL 层（7 个索引），业务代码零改动，落地风险最低
4. 符合 `archived` 字段的设计初衷，保持架构一致性

## 三、删除策略统一结论

### 3.1 企业级最佳实践原则

| 数据类型                                   | 推荐删除策略               | 理由                                   |
| -------------------------------------- | -------------------- | ------------------------------------ |
| **主体实体表**（user/role/permission/menu）   | **逻辑删除**（archived=1） | 需审计追溯、可恢复、保留历史关系链                    |
| **关系关联表**（user\_role/role\_permission） | **物理删除**             | 关系是"状态快照"非实体；软删除会致唯一索引冲突；重新分配时需先清旧关系 |
| **临时/缓存表**                             | **物理删除**             | 无保留价值                                |

### 3.2 当前策略修正建议

| 实体                    | 当前            | 建议                    | 调整说明                                                  |
| --------------------- | ------------- | --------------------- | ----------------------------------------------------- |
| `cmx_user`            | 物理删除（代码与注释矛盾） | **改为软删除**（恢复被注释的 SQL） | 用户数据需审计追溯；改后配合方案 A 索引                                 |
| `cmx_role`            | 软删除           | 保持软删除 ✓               | 但需补充清理 `cmx_user_role`（见 3.3）                         |
| `cmx_role_group`      | 软删除           | 保持软删除 ✓               | 已有前置校验，合理                                             |
| `cmx_permission`      | 物理删除          | **保持物理删除**            | 权限含树形路径（full\_code\_path），软删除后路径维护极复杂；且权限是配置型数据，非业务实体 |
| `cmx_menu`            | 物理删除          | **保持物理删除**            | 菜单含 code\_path/id\_path 树形结构，软删除会导致路径维护困难；菜单是配置型数据    |
| `cmx_user_role`       | 物理删除          | 保持物理删除 ✓              | 关系表                                                   |
| `cmx_role_permission` | 物理删除          | 保持物理删除 ✓              | 关系表                                                   |

> **说明**：权限和菜单虽有 archived 字段，但因树形路径字段（full\_code\_path / code\_path）的存在，软删除会导致路径维护极其复杂（需保留归档节点的路径供后代引用）。企业实践中，配置型树形数据通常用物理删除 + 历史备份（导出 JSON）而非软删除。这两张表的 archived 字段建议保留（查询层已用），但删除走物理删除。

### 3.3 删除主体时关系表处理结论

**结论：删除主体时，对应的关系关联表必须物理删除（级联清理）。**

| 删除操作 | 需清理的关系表                    |  当前是否处理  | 处理位置                                                                                                                     |
| ---- | -------------------------- | :------: | ------------------------------------------------------------------------------------------------------------------------ |
| 删除用户 | `cmx_user_role`            |   ✓ 已处理  | [crud.rs:233](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/user/service/crud.rs#L233)        |
| 删除用户 | `cmx_user_role_assignment` | ✗ **缺失** | 需在 [crud.rs:232](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/user/service/crud.rs#L232) 后补充 |
| 删除角色 | `cmx_user_role`            | ✗ **缺失** | 需在 [service.rs:373](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/role/service.rs#L373) 后补充   |
| 删除角色 | `cmx_role_permission`      |   ✓ 已处理  | [service.rs:373](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/role/service.rs#L373)          |
| 删除权限 | `cmx_role_permission`      |   ✓ 已处理  | [crud.rs:499](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/permission/service/crud.rs#L499)  |
| 删除菜单 | 无关系表                       |     —    | 菜单与权限通过 `fun_code` 弱关联，无需清理                                                                                              |

**理由**：

1. **数据一致性**：主体删除后，关系表残留指向"不存在"主体的记录，是脏数据
2. **避免误授权**：若角色软删除但 `cmx_user_role` 未清理，用户仍持有该角色 ID；若未来角色被恢复（archived 改回 0），用户会"被动"重新获得权限，违反最小权限原则
3. **关系表特性**：关系表是多对多状态记录，重新分配时本就会全量替换（`assign_roles` / `assign_permissions` 均先 DELETE 再 INSERT），软删除会导致唯一索引冲突
4. **审计需求**：关系变更的审计通过 `cmx_audit_log`（审计日志表）记录，不依赖关系表本身的软删除

### 7.2 新发现问题：ON CONFLICT 与部分唯一索引兼容性（严重）

**问题本质**：PostgreSQL 的 `ON CONFLICT (cols)` 推断唯一索引时，若目标索引是**部分唯一索引**（带 `WHERE` 谓词），则 ON CONFLICT 子句必须带上**相同的 WHERE 谓词**，否则报错 `no unique or exclusion constraint matching`。首轮迁移将 6 张表的唯一索引改为部分唯一索引后，所有引用这些索引的 `ON CONFLICT (cols)` 语句都会在运行时失败。

**受影响的 6 处 ON CONFLICT 语句**：

| # | 文件 | 行 | 表 | ON CONFLICT 子句 | 修复方式 |
|---|------|---|----|-----------------|---------|
| 1 | [role/service.rs](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/role/service.rs) | assign_permissions | `cmx_role_permission` | `ON CONFLICT (role_id, permission_id) DO NOTHING` | 加 `WHERE archived = 0` |
| 2 | [role/service.rs](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/role/service.rs) | assign_role_users | `cmx_user_role` | `ON CONFLICT (user_id, role_id) DO NOTHING` | 加 `WHERE archived = 0` |
| 3 | [user/service/roles.rs](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/user/service/roles.rs) | assign_roles | `cmx_user_role` | `ON CONFLICT (user_id, role_id) DO NOTHING` | 加 `WHERE archived = 0` |
| 4 | [user_auth_query_impl.rs](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/user_auth_query_impl.rs) | L316 | `cmx_user_role` | `ON CONFLICT (user_id, role_id) DO NOTHING` | 加 `WHERE archived = 0` |
| 5 | [user_auth_query_impl.rs](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/user_auth_query_impl.rs) | L441 | `cmx_user_role` | `ON CONFLICT (user_id, role_id) DO NOTHING` | 加 `WHERE archived = 0` |
| 6 | [permission/service/definition_importer.rs](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/permission/service/definition_importer.rs) | L58 | `cmx_permission` | `ON CONFLICT (code) DO UPDATE SET ...` | 加 `WHERE archived = 0` |

**修复示例**：
```sql
-- 改前
INSERT INTO cmx_user_role ... ON CONFLICT (user_id, role_id) DO NOTHING
-- 改后
INSERT INTO cmx_user_role ... ON CONFLICT (user_id, role_id) WHERE archived = 0 DO NOTHING
```

> 注：`cmx_metadata/seed`、`cmx_biz/module/version`、`cmx_service/repository`、`cmx_plugin/marketplace` 等其他 ON CONFLICT 语句对应的表索引未改造，不受影响。

### 7.3 新发现问题：菜单 list/page 缺失 archived 过滤注入（中）

**问题**：[menu/service.rs](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-biz/src/menu/service.rs) 的 `list` 和 `page` 方法直接调用 `GenericCrudService`，未注入 `archived = 0` 默认过滤。而 `list_by_module` 和 `get_tree` 是显式带 `archived = 0` 的。首轮方案称"查询层过滤已完备"不准确。

**对比**：角色（Role）/角色组（RoleGroup）的 list/page 均有 `with_default_archived` 注入，菜单遗漏。

**修复方式**：在 `MenuService` 上新增 `with_default_archived` 静态方法，在 `list`/`page` 中对 filters 注入默认 `archived = 0`（与 Role/RoleGroup 模式一致）。

**补充修复（Review 发现）**：原 `filters.map(|fs| ...)` 在 `filters = None`（前端未传过滤条件）时不执行，`archived = 0` 过滤完全失效，会泄露归档数据。此问题同样存在于 Role/RoleGroup 的 list/page。统一改为：

```rust
let filters = Some(match filters {
    Some(fs) => fs.into_iter().map(Self::with_default_archived).collect::<Vec<_>>(),
    None => vec![Self::with_default_archived(XxxFilter::default())],
});
```

即 `filters=None` 时构造一个仅含 `archived = 0` 的默认 filter，确保无论前端是否传 filters 都过滤归档数据。已修复全部 6 个实体共 11 个方法：

| 实体 | 方法 | 文件 |
|------|------|------|
| Menu | list / page | menu/service.rs |
| Role | list_roles / page_roles | role/service.rs |
| RoleGroup | list_role_groups / page_role_groups | role_group/service.rs |
| User | list_users / page_users | user/service/query.rs |
| Permission | list_permissions / page_permissions | permission/service/query.rs |
| ExclusionRule | page_rules（路径 A） | rule/service.rs |
