## 一、概述

### 1.1 定位与目标

`cmx-iam` 是 cmx-container 平台的**身份与访问管理**业务 crate，提供 User / Role / Permission 的完整管理能力：

- **RBAC 基础**：用户、角色、权限三实体 + 多对多关联
- **角色组（Role Group）**：支持角色树形组织
- **权限字段扩展**：domain / app / module 三维分类 + extension 扩展字段
- **权限自动注册**：编译期 inventory 收集 + 注解宏注入
- **统一检查 API**：`AuthContext` 的 `require_*` 系列方法
- **互斥规则（SoD）**：1 主对象 + N 互斥对象的职责分离校验
- **临时角色授权**：带有效期的角色分配
- **缓存与熔断**：Redis 缓存 + 熔断器降级
- **权限可视化与审计 API**：有效权限查询、差异对比、使用统计

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| **WASM 可达性** | 基础数据模型（User/Role/Permission/AuthContext/Registry）放 cmx-core，业务逻辑（BMC/Filter/Service）放 cmx-iam |
| **协议无关** | Service 层不依赖 axum，handler 为薄层适配 |
| **RBAC 标准** | User → Role → Permission，多对多关系；权限采用 `resource:action` 编码 |
| **职责分离** | handler 级宏注入检查 + 路由级 TOML 中间件，互为兜底 |
| **最小侵入** | 保留现有 5 张基础表不变，所有新能力通过新增表实现 |
| **配置开关** | 所有新功能默认关闭，通过 `IamConfig` 控制 |
| **分阶段交付** | 能力相互独立，可分迭代实施 |

### 1.3 范围声明

**本方案覆盖**：

1. RBAC 基础模型（5 张表）
2. 角色组（新增 `cmx_role_group`）
3. 权限字段扩展（4 个新字段）
4. 编译期权限自动注册（inventory + 注解宏）
5. 统一检查 API（AuthContext `require_*`）
6. 互斥规则引擎（1 主 + N 互斥）
7. 临时角色授权
8. Redis 缓存 + 熔断器
9. 权限可视化与审计 API

**非目标**：

- **DataScope 数据权限**：`IamChecker::get_data_scope` 为占位实现（返回 All），具体过滤逻辑作为后续迭代
- **角色层级与继承**：角色保持扁平（无 `parent_role_id`）
- **通配符权限匹配**：仅支持精确码匹配（如 `user:create`），不支持 `user:*`
- **依赖规则（dependency）**：互斥规则仅支持 1 主 + N 互斥，不支持"分配 A 必须同时拥有 B"等依赖关系
- **OpenAPI Security 注解**：注解宏首版不集成 Swagger security

### 4.3 树节点结构

**PermissionTreeNode** 与 **RoleGroupTreeNode** 均采用 `flatten + children` 递归模式：

```rust
pub struct PermissionTreeNode {
    #[serde(flatten)]
    pub permission: Permission,
    pub children: Vec<PermissionTreeNode>,
}

pub struct RoleGroupTreeNode {
    #[serde(flatten)]
    pub role_group: RoleGroup,
    pub children: Vec<RoleGroupTreeNode>,
}
```

> `#[serde(flatten)]` 让前端可同时访问字段（如 `id`、`name`）和子节点（`children`）。

### 4.4 错误类型（error.rs）

```rust
    All,    // 必须拥有所有角色
    Any,    // 拥有任一角色即可

impl std::fmt::Display for RoleRequirement {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self {
            Self::All => write!(f, "全部"),
            Self::Any => write!(f, "任一"),
        }
    }
}

/// 访问拒绝错误（权限检查 + 角色检查统一错误类型）
#[derive(Debug, Clone, Error)]
pub enum PermissionDeniedError {
    #[error("未认证:缺少认证上下文")]
    Unauthenticated,

    #[error("用户 {user_id} 缺少权限: {permission}")]
    Permission { user_id: String, permission: String },

    #[error("用户 {user_id} 缺少角色: {role}")]
    Role { user_id: String, role: String },

    #[error("用户 {user_id} 缺少角色(需{requirement}): {roles}")]
    Roles { user_id: String, requirement: RoleRequirement, roles: String },
}

impl PermissionDeniedError {
    pub fn is_unauthenticated(&self) -> bool {
        matches!(self, Self::Unauthenticated)
    }
}
```

## 七、权限自动注册

### 7.1 设计目标

通过 **inventory crate** 在编译期收集所有权限定义和路由处理器登记，启动期用于：

1. **漏写告警**：统计已注解 handler 数量
2. **DB 一致性校验**：代码声明权限 vs DB 存在性比对
3. **权限元数据查询**：暴露 `/api/iam/permissions/registry` 给前端管理界面

### 7.2 inventory 收集结构

见 §4.5。`RegisteredPermission` / `RegisteredRouteHandler` 在 `cmx-core` 中定义，宏生成的 `inventory::submit!` 代码在调用方 crate 展开。

### 7.3 cmx-macros proc-macro crate

**路径**：`crates/libs/cmx-macros/`

**关键约束**：

- `proc-macro = true`，仅 host target
- **不依赖任何业务 crate**（仅依赖 syn/quote/proc-macro2，workspace 已有）
- 宏生成的 `inventory::submit!` 代码使用**绝对路径** `::inventory::submit!`

#### 7.3.1 宏清单（7 个）

| 宏 | 语义 | 注册内容 |
|----|------|---------|
| `#[has_permission(key, group, display, description)]` | 单权限检查 | `RegisteredPermission` + `RegisteredRouteHandler` |
| `#[has_permissions("a", "b")]` | 多权限 AND 检查 | `RegisteredRouteHandler` |
| `#[has_any_permission("a", "b")]` | 多权限 OR 检查 | `RegisteredRouteHandler` |
| `#[has_role("admin")]` | 单角色检查 | `RegisteredRouteHandler` |
| `#[has_roles("admin", "auditor")]` | 多角色 AND 检查 | `RegisteredRouteHandler` |
| `#[has_any_role("admin", "manager")]` | 多角色 OR 检查 | `RegisteredRouteHandler` |
| `#[permit_all]` | 公开路由标记 | `RegisteredRouteHandler { is_public: true }` |

> **命名约定**：
> - `has_permission`（单数）— 唯一带元数据注册的宏
> - `has_permissions`（复数）— 多权限 AND 语义
> - 7 个宏均会注册 `RegisteredRouteHandler`，确保漏写统计完整

#### 7.3.2 通用宏注入逻辑

所有权限/角色注解宏共享相同的参数检测逻辑：

```text
5. 在函数体首行注入对应的 require_* 方法调用
```

**类型路径匹配**（非参数名匹配）：


#### 7.5.1 DB 一致性校验

文件：`crates/libs/cmx-iam/src/permission/consistency_check.rs`

```rust
pub struct ConsistencyReport {
    pub missing_in_db: Vec<String>,  // 代码有、DB 无
    pub orphan_in_db: Vec<String>,   // DB 有、代码无
}

pub async fn ensure_db_permission_consistency(
    mm: &DatabaseManager,
    db_id: &str,
) -> Result<ConsistencyReport, TraitError> {
    let code_perms: HashSet<String> = all_registered_permissions()
        .iter().map(|p| p.key.to_string()).collect();

    // 比对全部权限码（含已归档，绕过 archived 过滤）
    let db_perms_raw = list_all_permission_codes(mm, db_id).await?;
    let db_perms: HashSet<String> = db_perms_raw.into_iter().collect();

    let missing_in_db: Vec<_> = code_perms.difference(&db_perms).cloned().collect();
    let orphan_in_db: Vec<_> = db_perms.difference(&code_perms).cloned().collect();

    Ok(ConsistencyReport { missing_in_db, orphan_in_db })
}

impl ConsistencyReport {
    /// 生成待执行的 INSERT SQL（开发者可复制执行）
    pub fn to_insert_sql(&self) -> String {
        let mut sql = String::new();
        for code in &self.missing_in_db {
            if let Some(p) = all_registered_permissions().iter().find(|p| p.key == code) {
                sql.push_str(&format!(
                    "INSERT INTO cmx_permission (code, name, description, status, archived) \
                     VALUES ('{}', '{}', '{}', 1, 0);\n",
                    escape_sql(p.key), escape_sql(p.display), escape_sql(p.description)
                ));
            }
        }
        sql
    }
}
```

**校验模式**（TOML 配置）：

```toml
[iam]
permission_consistency_mode = "warn"   # panic | warn | off
```

**warn 模式输出**：

```text
WARN 权限一致性校验: 3 个代码声明的权限在 DB 中缺失
     缺失: user:create, user:read, agent:export
     建议执行的 SQL:
     INSERT INTO cmx_permission (code, name, ...) VALUES ('user:create', '创建用户', ...);
     ...
```

> `escape_sql` 转义单引号（替换为两个单引号），防止 display/description 含单引号时破坏 SQL 语法。

## 八、统一检查 API

### 8.1 设计目标

在 `AuthContext` / `SVRContext` 上提供统一的 `require_*` 方法，宏注入调用，避免散落各 handler 的手动检查代码。

### 8.2 短路规则

1. `system:all` 超级权限 → 放行
2. `admin` 角色 → 放行

```rust
    self.has_permission("system:all") || self.has_role("admin")
```

### 8.3 AuthContext 6 个方法

**权限检查（3 个）**：

```rust
    fn from(e: cmx_core::PermissionDeniedError) -> Self {
```

## 九、互斥规则引擎

### 9.1 设计目标

实现职责分离（Separation of Duties）：在权限/角色分配时进行逻辑校验，防止产生冲突或危险的权限组合。

### 9.2 互斥模型

**核心模型**：1 主对象 + N 互斥对象

- 每条规则定义 1 个**主对象**（`primary_subject_id`）和 N 个**互斥对象**（`exclusion_rule_item.subject_id`）
- 仅当用户/角色集合**同时**包含主对象和任一互斥对象时判定违反
- 互斥对象之间不互斥（仅对主对象互斥）

**校验语义示例**：

| 用户拥有的对象集合 | 是否违反 | 原因 |
|------------------|---------|------|
| {A} | 否 | 仅拥有主对象 |
| {B} | 否 | 仅拥有互斥对象，非主对象 |
| {B, C} | **否** | 互斥对象之间不互斥 |
| {A, B} | **是** | 同时拥有主对象 A 和互斥对象 B |
| {A, B, C} | **是** | 同时拥有主对象 A 和互斥对象 B/C |

### 9.3 模块结构

```
crates/libs/cmx-iam/src/rule/
├── mod.rs
├── bmc.rs            # ExclusionRuleBmc / ExclusionRuleItemBmc
├── entity.rs         # ExclusionRule / CreateExclusionRuleRequest / ValidateRuleRequest 等
└── enforcer.rs       # RuleEnforcer trait + RuleEnforcerImpl
└── service.rs        # ExclusionRuleServiceImpl
```

### 9.4 RuleEnforcer trait

定义在 `rule/enforcer.rs`（不放在 `service_traits.rs`，避免跨模块耦合）：

```rust
#[async_trait]
pub trait RuleEnforcer: Send + Sync {
    /// 校验角色权限组合本身是否违反功能权限互斥规则
    /// - 仅校验 subject_type = 'permission' 的规则
    async fn check_role_permissions(
        &self,
        permission_ids: &[String],
    ) -> Result<(), IamError>;

    /// 校验用户角色组合是否违反互斥规则
    /// - 同时校验功能权限互斥和角色互斥两类规则
    /// - 合并用户已有权限/角色 + 待分配角色权限/角色
    async fn check_user_roles(
        &self,
        user_id: &str,
        role_ids: &[String],
    ) -> Result<(), IamError>;
}
```

### 9.5 核心校验实现

```rust
struct LoadedRule {
    id: String,
    code: String,
    name: String,
    subject_type: String,           // 'permission' | 'role'
    primary_subject_id: String,
    violation_message: Option<String>,
    excluded_ids: HashSet<String>,  // 互斥对象ID集合
}

fn check_exclusion(
    rules: &[LoadedRule],
    subject_set: &HashSet<String>,
) -> Result<(), IamError> {
    for rule in rules {
        if !subject_set.contains(&rule.primary_subject_id) {
            continue;
        }
        let violated = rule.excluded_ids.iter()
            .any(|id| subject_set.contains(id));
        if violated {
            let message = rule.violation_message.clone().unwrap_or_else(|| {
                format!("互斥规则违反 [{}]", rule.code)
            });
            return Err(IamError::RuleViolation {
                rule_code: rule.code.clone(),
                message,
            });
        }
    }
    Ok(())
}
```

### 9.6 校验时机

| 操作 | 调用 | 失败处理 |
|------|------|---------|
| `RoleServiceImpl::assign_permissions` | `check_role_permissions(permission_ids)` | 事务自动回滚 |
| `UserServiceImpl::assign_roles` | `check_user_roles(user_id, role_ids)` | 事务自动回滚 |
| `UserServiceImpl::assign_temp_role` | `check_user_roles(user_id, &[role_id])` | 不写入 assignment |

> `check_user_roles` 合并集合包含永久 + 临时授权。assign_roles 是全量替换永久角色，合并集合可能包含即将被替换的旧永久角色权限，存在"安全方向偏差"（更严格不会漏判，极端场景阻止合法分配）。可接受。

### 9.7 错误映射

`RuleViolation` 映射为 `BusinessError`（HTTP 400），**非** `Forbidden`（HTTP 403）。原因：规则违反是**输入数据不合规**（权限组合冲突），而非**权限不足**。前端可区分提示：403 显示"无权限"，400 显示"权限组合违反规则 XXX"。

### 9.8 规则 Service 关键逻辑

**create_rule 校验**：

1. `subject_type` 合法性（`permission` / `role`）
2. `excluded_subject_ids` 非空
3. `primary_subject_id` 不在 `excluded_subject_ids` 中
4. `primary_subject_id` 和 `excluded_subject_ids` 在对应表中存在
5. 事务内：INSERT 规则 + 批量 INSERT 互斥对象

**add_rule_items 校验**：

1. 查询规则的 `primary_subject_id`
2. 校验新增 `subject_id` 不等于 `primary_subject_id`
3. 批量 INSERT（`ON CONFLICT DO NOTHING` 幂等）

## 十、临时角色授权

### 10.1 设计目标

支持**带有效期的角色分配**：满足最小权限原则和应急访问场景，到期自动失效。

### 10.2 数据模型

`cmx_user_role_assignment` 表（见 §3.4），关键字段：

- `effective_from` / `effective_until`：有效期窗口
- `status`：0-已撤销 / 1-生效中
- `source`：manual-手动 / approval-审批 / system-系统
- `revoked_by` / `revoked_at`：撤销审计

### 10.3 查询 SQL 改造

**永久 + 临时 UNION 查询**（`IamChecker` + `UserAuthQueryImpl` 同步改造）：

```sql
-- get_user_role_codes
SELECT DISTINCT r.code FROM cmx_role r
INNER JOIN cmx_user_role ur ON ur.role_id = r.id
WHERE ur.user_id = $1 AND ur.archived = 0 AND r.archived = 0 AND r.status = 1
UNION
SELECT DISTINCT r.code FROM cmx_role r
INNER JOIN cmx_user_role_assignment ura ON r.id = ura.role_id
WHERE ura.user_id = $1 AND ura.status = 1 AND ura.archived = 0
  AND NOW() BETWEEN ura.effective_from AND ura.effective_until
  AND r.archived = 0 AND r.status = 1;
```

`get_user_permissions` 类似（含 `INNER JOIN cmx_role_permission`）。

### 10.4 临时授权 Service

## 十一、缓存与熔断

### 11.1 设计目标

1. **缓存**：引入 Redis 缓存降低 DB 压力，权限变更时精准失效
2. **熔断**：DB/缓存故障时提供降级策略，保障系统可用性

### 11.2 技术选型

**Redis 而非本地内存缓存（moka）**：

服务采用**多节点无状态部署**，本地缓存存在严重一致性问题（节点 A 修改权限后，仅失效 A 缓存，其他节点仍是旧数据；权限是安全敏感操作，缓存不一致会导致权限撤销后仍放行）。Redis 共享缓存天然一致。

复用 `cmx-buffer` 模块的 `CacheOps` 和 `TtlOps`。

### 11.3 缓存结构

```rust
pub struct IamChecker {
    mm: Arc<DatabaseManager>,
    db_id: String,
    config: IamConfig,
    cache: Option<Arc<cmx_buffer::cache::CacheManager>>,
    circuit_breaker: Arc<CircuitBreaker>,
}
```

**Key 设计**：

| Key 格式 | 值 | TTL | 说明 |
|---------|----|-----|------|
| `iam:perm:{user_id}` | `["user:list", ...]` 或 `[]` | 300s ± 10% | 用户有效权限码 |
| `iam:role:{user_id}` | `["admin", ...]` 或 `[]` | 300s ± 10% | 用户有效角色码 |

> **防穿透**：使用空数组 `[]`（短 TTL 60s）表示无权限。**防雪崩**：TTL ± 10% 随机抖动（基于 `SystemTime` 纳秒时间戳作为伪随机源）。

### 11.4 缓存策略

**读流程**：

```text
1. 检查熔断器状态
   - 熔断器打开 → 进入降级逻辑
2. 查 Redis
   - 命中（含空数组）→ record_success，返回结果
3. 缓存未命中，查 DB
   - 成功 → record_success，回填缓存，返回结果
   - 失败 → record_failure，返回错误
```

**失效策略**：

| 触发场景 | 失效操作 |
|---------|---------|
| `assign_permissions` 后 | 查询角色关联 user_ids，`del_batch` 删除这些用户的 `iam:perm:*` + `iam:role:*` |
| `assign_roles` 后 | `del_batch([iam:perm:{uid}, iam:role:{uid}])` |
| 临时角色分配/撤销后 | `del_batch` 同上 |
| 权限/角色删除后 | 保守策略，失效全量（SCAN + DEL 批量） |

> 使用 `ops.del_batch` 批量删除（单次 RTT），避免逐个 DEL 的开销。

### 11.5 熔断与降级

**配置**：

```rust
pub enum FailureMode {
    FailOpen,   // 故障开放：仅放行 system:all 用户
    FailClose,  // 故障封闭：全部拒绝（默认）
}

pub struct IamConfig {
    pub failure_mode: FailureMode,                // 默认 FailClose
    pub circuit_breaker_threshold: u32,          // 默认 5 次连续失败
    pub circuit_breaker_reset_secs: u64,         // 默认 60 秒恢复
}
```

**熔断器实现**（`cmx-iam/src/circuit_breaker.rs`）：

```rust
pub struct CircuitBreaker {
    failure_count: AtomicU32,
    is_open: AtomicBool,
    last_failure_time: Mutex<Option<Instant>>,
    threshold: u32,
    reset_duration: Duration,
}
```

**简化版**：仅实现 closed/open 两态，通过 `reset_duration` 自动恢复（不实现 half-open）。

**降级逻辑**（`has_permission` 中）：

```rust
async fn has_permission(&self, user_id: &str, permission_code: &str) -> Result<bool, TraitError> {
    if !self.circuit_breaker.allow_request() {
        return match self.config.failure_mode {
            FailureMode::FailOpen => {
                // 仅直查 DB 验证 system:all（DB 也故障时此查询失败 → Err）
                self.check_system_all_only(user_id).await
            }
            FailureMode::FailClose => Ok(false),  // 全部拒绝
        };
    }
    // 正常流程：Redis 缓存 → DB
    // ...
}
```

> **FailOpen 实际效果**：DB/Redis 全故障时仍需查 DB 验证 system:all，查询大概率失败。FailOpen 接近"全部拒绝 + 放行已知管理员"。仅在 `system:all` 用户量极少时启用。

## 二十一、假设与决策

### 21.1 核心决策

| 决策 | 理由 |
|------|------|
| **基础数据模型放 cmx-core** | WASM 插件需感知调用者身份（User/Role/Permission），cmx-core 是 WASM 可达层；纯 Serialize/Deserialize 无 sqlx 依赖 |
| **业务逻辑放 cmx-iam** | ForCreate/ForUpdate/Filter/BMC/Service 是服务端 CRUD 关注点，WASM 不需要；cmx-iam 拥有 sqlx+modql+database 完整能力 |
| **Service trait 定义在 cmx-iam 而非 cmx-traits** | trait 方法签名引用 cmx-iam 类型，放 cmx-traits 会循环依赖；与 cmx-biz 模式一致 |
| **权限采用 `resource:action` 编码** | 企业级标准，清晰可扩展 |
| **User Entity 不包含 password_hash** | 防止 API 泄漏敏感数据 |
| **关联表 assign 使用物理删除** | 关联记录是"当前状态"而非"历史数据"，assign 操作物理删除旧关联 + 插入新关联 |
| **主表删除时级联物理删除关联** | 删除主表（cmx_user, cmx_role, cmx_permission）软删除时，同步物理删除对应关联表记录 |
| **并发安全 Last-Write-Wins** | assign_roles/assign_permissions 全量替换在事务内执行，行级锁保证原子性 |
| **system:all 短路放行** | 超级管理员无需逐一检查具体权限码 |
| **审计日志尽力而为** | 审计写入失败不阻塞业务，但通过 `warn!` 日志告警 |
| **审计日志脱敏处理** | create/update 用户审计不记录明文密码 |
| **audit_write 抽取为 AuditHelper trait** | 三个 ServiceImpl 共享默认实现消除重复（DRY 原则） |
| **权限采用 Redis 缓存而非 moka** | 多节点无状态部署需保证缓存一致性；Redis 天然支持；权限数据量小（< 100 码/用户） |
| **FailClose 作为默认故障降级** | 安全优先；FailOpen 仅在 system:all 用户量极少时使用 |
| **熔断器简化版（closed/open）** | 不实现 half-open，通过 `reset_duration` 自动恢复 |
| **interim 角色使用物理删除 + 状态字段** | 临时授权逻辑撤销（`status=0`），保留审计记录 |
| **互斥规则使用 1 主 + N 互斥模型** | 语义清晰，避免 group_seq 复杂度；不实现依赖规则 |
| **规则违反映射为 400 而非 403** | 规则违反是输入数据不合规，而非权限不足；前端可据此区分提示 |
| **handler 级 + 路由级双保险** | 宏注入 require_* + TOML 中间件，互为兜底 |
| **不做路由→权限自动映射** | 编译期无法可靠获取 route_path，职责分离（handler 注解 + 路由中间件） |
| **不自动写 DB** | 启动一致性校验仅 warn 并输出 DDL，开发者手动执行（避免误操作） |
| **register_crud_permissions! 宏** | cmx-core 中定义，4 个权限码一次性注册，复用 inventory 收集 |

### 21.2 范围决策

| 不在范围 | 理由 |
|---------|------|
| **DataScope 数据权限** | `IamChecker::get_data_scope` 占位实现（返回 All），具体过滤逻辑作为后续迭代（需先实现组织机构模块） |
| **角色层级与继承** | RBAC 模型无 `parent_role_id`，角色保持扁平；权限不通过角色层级继承 |
| **通配符权限匹配** | 不支持 `system:user:*` 通配符，仅精确码匹配 |
| **依赖规则（dependency）** | 互斥规则仅 1 主 + N 互斥，不支持"分配 A 必须同时拥有 B"等依赖关系 |
| **OpenAPI Security 注解** | 首版不集成 Swagger security 注解，作为未来扩展项 |
| **跨服务权限检查** | `auth_context` 的 `#[serde(skip)]` 导致跨进程传递时权限丢失；宏注入的检查仅在 HTTP handler 同进程内有效 |
| **i18n** | `display` / `description` 为 `&'static str`，暂不支持多语言 |
| **CMX-Server-Demo 风格动态权限注册** | WASM 插件运行时注册 `PermissionRegistry::register_runtime` 为预留接口，首版不实现 |

### 21.3 命名与术语

| 决策 | 说明 |
|------|------|
| `has_permission`（单数） | 唯一带元数据注册的宏（key/group/display/description） |
| `has_permissions`（复数） | 多权限 AND 语义（Spring Security 用 `and` 连接多个 `hasAuthority`） |
| `has_any_permission` | 多权限 OR 语义（对应 `hasAnyAuthority`） |
| `exclusion_rule` 而非 `permission_rule` | 同时管理功能权限互斥和角色互斥，旧名 `permission_rule` 语义偏窄 |
| `/iam/exclusion-rules/` 前缀 | 与表名 `cmx_exclusion_rule` 对齐 |
| 角色组不使用 `code`/`status` | 角色组为组织管理用，以 `name` 为主标识，通过 `archived` 控制归档 |
| `extension` 为 `text` 类型 | 用户可存 JSON 或任意文本，无长度限制 |

## 二十二、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| **inventory 版本兼容** | edition 2024 较新，inventory 0.3 需实测 | 实测验证，不兼容则改用 `linkme` crate |
| **宏注入参数定位** | 通过类型路径匹配 `CmxSvrContext`（非参数名） | 找不到时编译期 error；支持 `svr_ctx` / `ctx` / `context` 任意 binding |
| **DB 一致性维护** | 不自动写 DB，开发者需手动执行 DDL | 启动校验 warn + 输出 DDL；后续可提供 `cmx-cli permissions diff` |
| **跨服务权限检查** | `auth_context` 跨进程不序列化 | 宏注入检查仅在 HTTP handler 同进程内有效；跨服务调用需服务端重新注入 |
| **UNION 查询性能** | `get_user_permissions` 高频查询，UNION 引入额外索引查询 | 1. 为 `cmx_user_role_assignment` 建立 4 个索引 2. 引入 Redis 缓存 3. 测试环境验证 SQL 性能 |
| **规则校验性能** | `assign_permissions` 时需加载所有规则 | 规则数据量小（< 100），全量加载内存；`enable_sod_check=false` 时跳过 |
| **缓存一致性** | 权限变更后缓存未及时失效 | 1. 所有变更点调用 `invalidate_*` 2. 合理 TTL（300 秒）兜底 3. Redis 多节点天然一致 |
| **FailOpen 实际效果** | DB/Redis 全故障时 FailOpen 仍需查 DB | DB 也故障时返回 Err，效果接近全部拒绝 + 放行已知管理员；建议 FailClose 为主 |
| **角色组循环引用** | parent_id 自引用可能形成环 | 创建/更新时校验 parent_id 不在自身子组中 |
| **迁移文件不可变** | 旧迁移文件不应修改 | 新增功能写入新迁移文件（006 / 007） |
