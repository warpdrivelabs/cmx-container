## 一、整体架构

### 1.1 模块定位

| 模块             | 路径                                | 定位               | 核心职责                                                                                                                |
| -------------- | --------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------- |
| **cmx-auth**   | `crates/libs/cmx-infra/cmx-auth/` | 平台认证基础设施         | JWT 双令牌、密码哈希、OAuth2（自建 + 第三方）、会话管理、API Key、密钥轮换、Prometheus 指标                                    |

| **cmx-core**   | `crates/libs/cmx-core/`           | 基础数据模型层（WASM 可见） | AuthContext、User/Role/RoleGroup/Permission 基础结构体、PermissionTreeNode/RoleGroupTreeNode                          |

### 1.3 Crate 依赖关系

| Crate      | 依赖方向                                                        | 说明                                      |
| ---------- | ----------------------------------------------------------- | --------------------------------------- |
| cmx-auth   | → cmx-core, cmx-traits, cmx-buffer, cmx-audit, cmx-database | 不直接依赖 cmx-iam，通过 UserAuthQuery trait 解耦 |
| cmx-iam    | → cmx-core, cmx-traits, cmx-database, cmx-buffer（权限缓存）      | 实现 UserAuthQuery trait 供 cmx-auth 调用    |
| cmx-traits | → cmx-core                                                  | 仅定义抽象 trait，无业务逻辑                       |
| cmx-core   | 无内部依赖                                                       | WASM 可达的基础类型层                           |

**双向解耦机制**：cmx-auth ↔ cmx-iam 通过 trait 实现双向依赖而无循环 crate 依赖：

* cmx-auth 持有 `Arc<dyn UserAuthQuery>`（由 cmx-iam 实现）

* cmx-iam 持有 `Arc<dyn AuthService>`（由 cmx-auth 实现）

### 1.4 类型分层设计

## 二、技术架构

### 2.1 核心技术选型

| 领域           | 技术                        | 说明                                                                                  |
| ------------ | ------------------------- | ----------------------------------------------------------------------------------- |
| **Web 框架**   | Axum                      | 中间件链：cors → body\_limit → trace → mw\_context → mw\_auth → mw\_permission → handler |
| **JWT**      | jsonwebtoken crate        | 支持 HS256（默认）/ RS256（多服务验签），kid 密钥轮换                                                 |
| **密码哈希**     | Argon2id                  | 内存 64MB、迭代 3 次、并行度 4，目标耗时 50-200ms                                                  |
| **本地缓存**     | moka crate                | 黑名单/Session 存活检查结果缓存，TTL 30s + Pub/Sub 主动失效                                         |
| **分布式缓存**    | Redis（cmx-buffer 封装）      | 会话、Refresh Token、权限缓存、在线统计、登录锁定                                                     |
| **数据库**      | PostgreSQL                | 15 张业务表，遵循 pg-table-generator 规范                                                    |
| **Token 传递** | Authorization: Bearer     | 天然免疫 CSRF，不使用 Cookie                                                                |
| **认证策略**     | Strategy Pattern          | AuthPolicy trait：JWT / API Key / OAuth2 三策略                                         |
| **熔断降级**     | CircuitBreaker（自研）        | AtomicBool + Mutex，FailClose/FailOpen 可配                                            |
| **OAuth2**   | Authorization Code + PKCE | 支持第三方 Provider（Google/GitHub）账号关联                                                   |

#### 2.2.2 Redis（会话与缓存）

| Key 模式                              | 数据结构       | TTL            | 用途                                       |
| ----------------------------------- | ---------- | -------------- | ---------------------------------------- |
| `auth:{user_id}:refresh:{jti}`      | String     | 7 天            | Refresh Token 存活标记                       |
| `auth:{user_id}:refresh_index`      | Set        | 7 天            | 用户所有 refresh token 索引                    |
| `auth:{user_id}:session`            | Hash       | 手动管理           | 用户会话表（field=device\_type，value=会话 JSON）  |
| `auth:{session_id}:session_detail` | String     | idle\_timeout  | 会话详情独立 TTL Key（自动过期）                    |
| `auth:{jti}:blacklist`              | String     | = token 剩余 TTL | 被撤销的 access token                       |
| `auth:online:users`                 | Set        | 无              | 全局在线用户集合                                 |
| `auth:{username}:login_fail`        | String     | 15 分钟          | 登录失败计数                                    |
| `auth:{username}:locked`            | String     | lock\_duration | 账号锁定标记                                    |
| `auth:{user_id}:pwd_history`        | Hash       | 手动管理           | 密码历史（field=时间戳，value=哈希，保留最近 5 条）     |
| `auth:api_key:{key_prefix}`         | String     | 60s            | **第一层缓存**（key\_prefix → ApiKeyEntity）    |
| `auth:api_key_ctx:{key_prefix}`     | String     | 60s            | **第二层缓存**（key\_prefix → AuthContext）     |
| `auth:oauth2:csrf:{state}`          | String     | auth\_code\_ttl | 自建授权服务器 CSRF state（绑定 client\_id，一次性消费） |
| `auth:oauth2:authcode:{code}`       | String     | auth\_code\_ttl | 自建授权服务器授权码（一次性消费，Lua 原子标记防重放） |
| `auth:oauth2:authcode:{code}:used`  | String     | auth\_code\_ttl | 授权码已使用标记（防重放）                          |
| `auth:oauth2:provider:state:{state}`| String     | state\_ttl     | 第三方 OAuth2 state（绑定 provider，一次性消费）       |
| `auth:oauth2:provider:callback:{code}` | String  | callback\_code\_ttl | 一次性回调授权码（前端用此换 TokenPair）                |
| `iam:perm:{user_id}`                | JSON Array | 300s ± 10%     | 用户有效权限码（空数组防穿透）                          |
| `iam:role:{user_id}`                | JSON Array | 300s ± 10%     | 用户有效角色码                                   |

> 所有 Key 使用 `{user_id}` Hash Tag 保证 Redis Cluster 同 slot，支持 Lua 原子操作。

### 2.3 缓存策略

| 缓存层            | 位置           | 内容                             | TTL    | 失效机制                    |
| -------------- | ------------ | ------------------------------ | ------ | ----------------------- |
| **本地缓存（moka）** | cmx-auth 进程内 | 黑名单查询结果、Session 存活状态           | 30s    | Pub/Sub 广播主动失效 + TTL 兜底 |
| **Redis 缓存**   | 共享           | 用户权限/角色码、Session、Refresh Token | 5-300s | 角色/权限变更时精准 DEL + TTL 兜底 |

**缓存一致性保障**：

* 权限变更时：查询受影响用户列表，`del_batch` 批量删除 `iam:perm:{uid}` + `iam:role:{uid}`

* 撤销 Token/强制下线时：Redis 黑名单 + Pub/Sub 广播清除各实例本地缓存

* 防穿透：DB 返回空结果缓存空数组 `[]`（短 TTL 60s）

* 防雪崩：TTL 添加 ±10% 随机抖动

### 2.4 安全机制

| 威胁              | 防护措施                                                          |
| --------------- | ------------------------------------------------------------- |
| **密码泄露**        | Argon2id 哈希（不存明文）+ 密码历史校验（禁用最近 5 次）+ 密码策略（最少 8 位含大小写+数字+特殊字符） |
| **Token 重放**    | Refresh Token Rotation（Lua 原子操作）+ 重放检测（撤销所有 token）+ 授权码一次性使用  |
| **暴力破解**        | 登录失败计数（5 次锁定）+ 账号锁定（15 分钟）+ Argon2 故意慢（\~100ms）               |
| **CSRF**        | 使用 Authorization Header 传递 Token，不使用 Cookie                   |
| **OAuth2 劫持**   | PKCE 校验 + client\_id/redirect\_uri 一致性校验 + state CSRF 校验      |
| **密钥泄露**        | JWT 密钥轮换（kid 机制）+ 私钥仅在文件系统（chmod 600）+ 宽限期平滑过渡                |
| **权限绕过**        | system:all 短路 + mw\_permission 路由级校验 + AuthContext 权限快照       |
| **Token 泄露到日志** | tracing `skip(token)` + 仅记录 jti/user\_id                      |
| **分布式缓存不一致**    | Redis 共享缓存（多节点天然一致）+ 精准失效策略                                   |

### 2.5 熔断与降级

| 配置项                           | 默认值       | 说明                                                   |
| ----------------------------- | --------- | ---------------------------------------------------- |
| failure\_mode                 | FailClose | 故障降级策略：FailClose 全部拒绝（安全优先）/ FailOpen 仅放行 system:all |
| circuit\_breaker\_threshold   | 5         | 连续失败次数阈值                                             |
| circuit\_breaker\_reset\_secs | 60        | 熔断恢复时间                                               |

## 三、功能设计

### 3.1 认证功能（cmx-auth）

#### 3.1.1 JWT 双令牌机制

| 令牌            | 用途               | 有效期   | 存储位置        | 可撤销      |
| ------------- | ---------------- | ----- | ----------- | -------- |
| Access Token  | API 访问凭证，自包含权限   | 30 分钟 | 客户端内存       | 黑名单检查    |
| Refresh Token | 换取新 Access Token | 7 天   | Redis + 客户端 | Redis 删除 |

**Refresh Token Rotation 流程**：客户端用旧 refresh token 换取新 token 对，Redis 通过 Lua 原子操作删除旧 token 并写入新 token。若检测到旧 token 被重放，立即撤销该用户所有 refresh token。

#### 3.1.2 认证方式

| 方式                  | 入口                                             | 说明                                                                     |
| ------------------- | ---------------------------------------------- | ---------------------------------------------------------------------- |
| **密码认证**            | `POST /api/auth/login`                         | 用户名 + 密码（Argon2id 校验），含时序攻击防护（dummy verify）                              |
| **Token 刷新**        | `POST /api/auth/refresh`                       | Refresh Token Rotation（Lua 原子操作防重放）                               |
| **API Key**         | `X-API-Key` Header                             | 服务间调用，SHA256 校验，**两层缓存优化**（详见 3.1.6）                                  |
| **OAuth2 授权码**      | `/api/auth/oauth2/authorize` + `/oauth2/token` | 自建授权服务器，含 PKCE 校验                                                      |
| **第三方 OAuth2 登录** | `/api/auth/oauth2/{provider}/login`            | Google/GitHub 等第三方登录，Provider Registry + AccountLinker（详见 3.1.7） |

#### 3.1.3 会话管理

| 能力        | 说明                                                       |
| --------- | -------------------------------------------------------- |
| **多设备会话** | 每设备类型独立 session（Redis Hash），支持配置同设备类型互踢                  |
| **心跳续期**  | 客户端每 5 分钟调用 `/api/auth/heartbeat`，刷新 session 活跃时间        |
| **在线统计**  | `SCARD auth:online:users` O(1) 查询在线总数                    |
| **强制下线**  | 管理员撤销用户所有 token + 销毁所有 session，Pub/Sub 秒级通知各实例           |
| **定时清理**  | 每 5 分钟扫描过期 session（基于 last\_active\_at 超过 idle\_timeout） |

#### 3.1.4 Token 校验流程（中间件）

1. 白名单路由（login/refresh/health）直接放行
2. 提取 Authorization Header 的 Bearer Token
3. JwtManager 解码 + 验签 + 过期检查
4. 本地缓存（moka）查黑名单，未命中查 Redis
5. Session 存活检查（本地缓存 → Redis）
6. 注入 AuthContext 到 SVRContext

#### 3.1.5 超级管理员初始化

| 要点        | 说明                                                      |
| --------- | ------------------------------------------------------- |
| 职责分离      | cmx-auth 仅暴露 `hash_password()`；cmx-iam 负责用户 CRUD + 角色关联 |
| 启动自动创建    | `IamService::initialize()` 中执行 `ensure_super_admin()`   |
| UPSERT 模式 | 用户名存在则更新密码，不存在则创建                                       |
| 自动分配角色    | 按 `role_code = "admin"` 查询并关联（不硬编码 ID）                  |

#### 3.1.6 API Key 两层缓存（M2M 性能优化）

针对 M2M（服务间调用）高频场景，避免每次请求都查询 4 次数据库（API Key 表 + User 表 + UserRole + RolePermission），引入 Redis 两层缓存：

| 缓存层 | 缓存对象           | Key 模式                          | TTL  | 命中行为                          |
| --- | -------------- | ------------------------------- | ---- | ----------------------------- |
| L1  | `ApiKeyEntity` | `auth:api_key:{key_prefix}`     | 60s  | 跳过 `cmx_auth_api_key` 查询，仍校验 SHA256 |
| L2  | `AuthContext`  | `auth:api_key_ctx:{key_prefix}` | 60s  | 跳过 User/Role/Permission 查询     |

**失效机制**：

* API Key 增删改时通过 Pub/Sub 频道 `auth:cache:invalidate` 广播 `api_key:{key_prefix}` 消息

* 收到消息的实例同时清理两层缓存（`DEL auth:api_key:*` 和 `auth:api_key_ctx:*`）

* 关联用户/角色/权限变更时，仅失效 L2 缓存（key_prefix 仍可命中 L1）

**性能效果**：99% 的请求命中两层缓存，DB 查询从 4 次降至 0 次。

> 说明：API Key 验证不计入 `LOGIN_TOTAL` 指标（属 M2M 场景），使用专用指标 `cmx_auth_api_key_validations_total` 计数。

#### 3.1.7 第三方 OAuth2 登录

**Provider Registry**：通过 `OAuth2ProviderRegistry::initialize_global()` 注册第三方 Provider（Google、GitHub、Generic 等），支持运行时动态扩展。

| 组件                   | 职责                                                    |
| -------------------- | ----------------------------------------------------- |
| `OAuth2Provider`     | Provider 抽象 trait（authorize/exchange_code/get_user_info） |
| `AccountLinker`      | 账号关联策略：已关联→直接登录 / 邮箱匹配→自动关联 / 配置允许→自动注册新用户          |
| `OAuth2FlowService`  | 自建授权服务器的授权码流程（含 PKCE、CSRF state 校验）                     |
| `OAuth2Store`        | state / callback_code 的 Redis 存储（绑定 provider，一次性消费） |

**登录流程**：

1. 前端调 `GET /api/auth/oauth2/providers` 拉取已注册 Provider 列表
2. 前端调 `POST /api/auth/oauth2/{provider}/login` 启动：服务端生成 `state` + 存储 `provider` 绑定关系（`oauth2:state:{state}`），返回第三方授权 URL
3. 用户在第三方完成授权后回跳（携带 `code` + `state`）
4. 服务端 `handle_oauth2_callback`：
   * 原子消费 `state` 并校验 provider 一致性
   * 调第三方 `exchange_code` + `get_user_info`
   * `AccountLinker::find_or_link` 三级回退：已关联 → 邮箱匹配 → 自动注册
   * 签发本平台 TokenPair，存入一次性 callback code（`oauth2:callback:{code}`，30s TTL）
5. 前端用 callback code 调 `POST /api/auth/oauth2/callback/exchange` 换取最终 TokenPair

**账号绑定/解绑**：

* `link_oauth2_account`：已登录用户可绑定更多 Provider

* `unlink_oauth2_account`：安全约束——最后一个登录绑定（既无密码又无其他 Provider）禁止解绑

**用户名生成策略**（`AccountLinkConfig.username_strategy`）：

| 策略                | 行为                         | 适用场景 |
| ----------------- | -------------------------- | ------ |
| `provider_prefix` | `{provider}_{provider_user_id}`，如 `google_1234567890` | 默认策略，最稳定，适合公开第三方 Provider |
| `provider_user_id` | 直接使用 Provider 返回的 `provider_user_id` | 适合内部 IdP 的用户 ID 已满足本地用户名规则的场景 |
| `username`        | 直接使用 Provider 返回的 `username` 字段；字段缺失时回退为 `provider_prefix` | 适合可信企业 Provider，期望本地用户名与外部账号一致 |
| `email_prefix`    | 邮箱 `@` 前缀                   | 用户体验较好，但可能冲突；依赖 Provider 返回邮箱 |
| `display_name`    | 优先使用 Provider 显示名           | 展示友好，但冲突最多，仅建议低风险场景使用 |

冲突时追加 4 位十六进制随机后缀（如 `_a3f2`），最多 3 次重试，仍冲突则返回 `OAuth2UsernameConflict`。

### 3.2 权限功能（cmx-iam）

#### 3.2.1 RBAC 权限模型

```
角色组(cmx_role_group) ──1:N── 角色(cmx_role) ──N:N── 用户(cmx_user)
                              │                         （通过 cmx_user_role 关联）
                              │
                  角色-权限关联(cmx_role_permission)
                              │
                      权限(cmx_permission)
```

**关键设计**：

* **角色扁平化**：`cmx_role` 移除 `parent_role_id`，不继承父角色权限
* **角色组（cmx_role_group）**：纯分组树形结构（`parent_id` 自引用），仅用于组织展示，不影响权限计算
* **权限域划分**：`cmx_permission` 扩展 `domain_code` / `app_code` / `module_code` 三级分类 + `extension` JSON 扩展字段

**权限编码规范**：采用 `resource:action` 格式（如 `user:create`、`role:assign_perm`、`system:all`）。

**system:all 通配权限**：拥有此权限的用户视为超级管理员，mw\_permission 和 PermissionChecker 均短路放行。

#### 3.2.2 权限校验链路

| 阶段           | 位置                | 说明                                                       |
| ------------ | ----------------- | -------------------------------------------------------- |
| **认证阶段**     | mw\_auth          | 通过 UserAuthQuery 一次性加载 roles + permissions 到 AuthContext |
| **权限检查**     | mw\_permission    | 查 AuthContext.permissions（内存），system:all 短路              |
| **Fallback** | PermissionChecker | AuthContext 缺失/过期时查 DB（EXISTS 子查询优化）                     |
| **变更生效**     | 缓存失效              | 角色/权限变更时清除相关用户 Redis 缓存 + JWT 权限在下次 refresh 时更新          |

#### 3.2.3 用户/角色/角色组/权限 CRUD

| 模块         | 核心能力                                                  |
| ---------- | ----------------------------------------------------- |
| **用户管理**   | 创建（密码哈希）、更新、软删除+关联清理、分配角色（全量替换）、分页/列表查询             |
| **角色管理**   | 创建、更新、删除（内置角色保护）、分配权限（全量替换）、角色列表                   |
| **角色组管理** | 树形结构 CRUD、`get_role_group_tree` 递归组装、子组/关联角色检查防误删       |
| **权限管理**   | 创建、更新、删除、权限树（内存递归组装）、分页/列表查询                      |

**角色组删除前置校验**：

* 待删除组下不能存在子角色组（`SELECT FROM cmx_role_group WHERE parent_id = ANY($1) AND archived = 0`）
* 待删除组下不能存在关联角色（`SELECT FROM cmx_role WHERE role_group_id = ANY($1) AND archived = 0`）
* 任意条件命中则返回 `IamError::RoleGroupInUse`，拒绝删除

#### 3.2.4 临时角色授权（Time-bound Access）

| 能力          | 说明                                                |
| ----------- | ------------------------------------------------- |
| **分配临时角色**  | 指定 effective\_from / effective\_until，支持预约授权      |
| **自动失效**    | 后台定时任务（默认 3600s）扫描过期授权，置 status=0（详见 3.1.9）      |
| **撤销/批量撤销** | 逻辑撤销（status=0），保留审计记录                             |
| **延长有效期**   | 仅限未过期的授权                                          |
| **权限合并**    | `get_user_permissions` 改为 UNION 查询（永久角色 + 有效临时角色） |
| **审计聚合**    | 清理时按用户分组聚合，超过 `audit_batch_size` 阈值时只记录统计信息        |

#### 3.2.5 互斥规则引擎（SoD）

采用「1 主对象 + N 互斥对象」模型，仅当用户集合同时包含主对象和任一互斥对象时判定违反，互斥对象之间不互斥。

| 规则对象类型                        | 语义                                |
| --------------------------- | --------------------------------- |
| **权限互斥**（subject\_type=permission） | 主权限与互斥权限列表不能同时被同一用户拥有 |
| **角色互斥**（subject\_type=role） | 主角色与互斥角色列表不能同时分配给同一用户 |

**校验时机**：

* `assign_permissions`（角色层）：仅校验权限互斥规则（`subject_type='permission'`）
* `assign_roles` / `assign_temp_role`（用户层）：同时校验权限互斥和角色互斥（合并现有权限/角色 + 待分配角色权限）

**校验逻辑**：

1. 加载所有启用的互斥规则（`status=1 AND archived=0`），按 `priority DESC` 排序
2. 用户层校验时合并「已有权限/角色 ∪ 待分配角色权限/角色」
3. 遍历规则：若合并集合包含 `primary_subject_id`，再检查是否包含任一 `excluded_subject_id`，命中即返回 `IamError::RuleViolation`

**总开关**：`enable_sod_check: bool`（默认 false）— 关闭时所有互斥校验直接返回 `Ok(())`，不读取规则表。**生产环境建议开启**。

#### 3.2.6 权限可视化与审计 API

| API    | 功能                          |
| ------ | --------------------------- |
| 用户有效权限 | 查询用户最终有效权限（含临时授权统计）         |
| 角色权限差异 | 对比两个角色的权限差异（仅角色1有/仅角色2有/共有） |
| 权限使用统计 | 统计每个权限被多少角色/用户使用            |
| 用户角色历史 | 查询用户角色变更历史（分配/撤销/过期）        |

#### 3.2.7 熔断与降级

`CircuitBreaker`（自研，AtomicBool + Mutex）配合 `FailureMode` 配置：

| 配置项                | 默认值       | 说明                                                |

| `circuit_breaker_threshold` | 5         | 连续失败次数阈值                                          |

## 六、关键设计决策汇总

| 决策                           | 理由                                            |
| ---------------------------- | --------------------------------------------- |
| cmx-auth 不直接依赖 cmx-iam       | 通过 UserAuthQuery trait 解耦，可独立开发和测试            |
| Access Token 自包含 permissions | 高频接口避免查 Redis/DB，牺牲体积换性能                      |
| Refresh Token 存 Redis        | 支持主动撤销和 Rotation 防重放                          |
| 权限缓存使用 Redis 而非本地 moka       | 多节点无状态部署需共享缓存保证一致性                            |
| 本地缓存（moka）用于黑名单/Session 检查   | 降低 Redis 往返，Pub/Sub 保证秒级失效                    |
| 超管初始化由 cmx-iam 执行            | cmx-auth 仅暴露 hash\_password，避免越权构造 cmx-iam 实体 |
| 权限编码采用 resource:action 格式    | 企业级标准，清晰可扩展                                   |
| 关联表 assign 使用物理删除            | 关联记录是"当前状态"而非"历史数据"                           |
| 角色扁平 + 角色组分组                 | 角色不继承父角色权限（避免隐式授权），分组展示用 cmx\_role\_group 独立维护  |
| cmx\_permission 三级域划分        | domain\_code / app\_code / module\_code 支持多应用权限隔离 |
| 第三方 OAuth2 用一次性 callback code | 避免 Token 暴露在 URL/浏览器历史，支持多端跳转                  |
| 第三方账号解绑需保留最后登录方式            | 既无密码又无其他 Provider 时禁止解绑，避免账号锁死                |
| API Key 两层缓存                | L1 缓存 ApiKeyEntity，L2 缓存 AuthContext，TTL 60s 双层命中  |
| 互斥规则 1+N 模型                  | 1 主对象 + N 互斥对象，仅当集合同时包含主对象和任一互斥对象时违反，支持权限/角色两类互斥 |
| 临时授权清理走审计聚合                 | 过期清理按用户分组写审计，超过 batch\_size 阈值仅记统计              |
| 审计日志脱敏处理                     | create/update 用户时不记录明文密码                      |
| 本次不实现数据权限（DataScope）         | 预留字段和接口，待组织机构模块就绪后实现                          |
