# 服务编排执行 API 使用说明

## 一、接口概述

服务编排执行接口用于执行预定义的服务编排流程（Flow JSON），支持线性流程、事务框、多分支路由等复杂编排场景。

### 接口地址

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/service/execute` | 执行服务编排（请求体包含 service_key） |
| POST | `/api/service/execute/{service-key}` | 执行服务编排（URL 路径包含 service_key） |

---

## 二、请求参数

### 2.1 请求体（ServiceExecuteRequest）

```json
{
    "service_key": "user-service",
    "input": {
        "user_id": "12345",
        "action": "query"
    },
    "include_steps": true
}
```

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `service_key` | String | ✅ | - | 服务唯一标识，对应服务定义 JSON 中的 `code` 字段 |
| `input` | JSON Value | ✅ | - | 初始输入数据，传递给第一个函数节点。支持 JSON 对象或字符串 |
| `include_steps` | Boolean | ❌ | `false` | 是否返回步骤数据。详见下方说明 |

### 2.2 include_steps 参数说明

| 值 | 场景 | 返回 steps |
|----|------|-----------|
| `false`（默认） | 生产环境调用 | 空数组 `[]`，减少数据传输 |
| `true` | 调试/前端调试 | 完整步骤数据 |
| 任意值 | 执行失败 | **始终返回**完整步骤数据（用于排错） |

**核心原则**：
- 成功时按需返回：`include_steps=false` 时不返回步骤数据
- 失败时始终返回：无论设置如何，失败时都返回完整步骤数据

### 2.3 HTTP 请求头

请求头会自动传递给 WASM 函数的 `context.headers`，可用于传递认证信息、追踪ID等：

```
Authorization: Bearer xxx
X-Request-Id: trace-123
X-Tenant-Id: tenant-001
```

## 四、响应字段详解

### 4.1 ServiceExecuteResponse

| 字段 | 类型 | 说明 |
|------|------|------|
| `success` | Boolean | 是否执行成功。所有节点都成功执行则为 `true` |
| `output` | String \| null | 最终输出结果（最后一个节点的输出）。失败时为 `null` |
| `steps` | Array | 各步骤执行记录，按执行顺序排列 |
| `total_elapsed_us` | Number | 总执行耗时（微秒） |
| `error` | Object \| null | 结构化错误信息。成功时为 `null` |

### 4.2 ServiceExecutionStep（步骤记录）

| 字段 | 类型 | 说明 |
|------|------|------|
| `node_id` | String | 节点ID，对应 Flow JSON 中的 `node.id` |
| `node_name` | String | 节点名称，对应 Flow JSON 中的 `node.data.name` |
| `node_type` | String | 节点类型（`skylake-func`、`skylake-switch` 等） |
| `status` | String | 步骤状态：`Success` / `Failed` / `Skipped` |
| `output` | String \| null | 步骤输出（函数执行结果）。失败时可能为 `null` |
| `elapsed_us` | Number | 执行耗时（微秒） |
| `error` | String \| null | 步骤级错误信息。成功时为 `null` |

### 4.3 ServiceOrchestrationError（错误详情）

| 字段 | 类型 | 说明 |
|------|------|------|
| `failed_step` | Object \| null | 失败步骤的详细信息 |
| `message` | String | 错误摘要信息 |

### 4.4 ServiceFailedStepInfo（失败步骤详情）

| 字段 | 类型 | 说明 |
|------|------|------|
| `node_id` | String | 失败的节点ID |
| `node_name` | String | 失败的节点名称 |
| `node_type` | String | 失败的节点类型 |
| `step_index` | Number | 失败步骤的序号（从 0 开始） |
| `error` | String | 具体错误信息 |
| `previous_output` | String \| null | 上一步的输出（失败前的数据，便于排查问题） |

## 五、调用示例

### 5.1 cURL 示例

```bash
# 基本调用（不返回步骤数据）
curl -X POST http://localhost:3000/api/service/execute \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer your-token" \
  -d '{
    "service_key": "user-service",
    "input": {"user_id": "12345"}
  }'

# 调试模式（返回步骤数据）
curl -X POST http://localhost:3000/api/service/execute \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer your-token" \
  -d '{
    "service_key": "user-service",
    "input": {"user_id": "12345"},
    "include_steps": true
  }'

# 路径参数版本
curl -X POST http://localhost:3000/api/service/execute/user-service \
  -H "Content-Type: application/json" \
  -d '{"input": {"user_id": "12345"}}'
```

### 5.2 JavaScript/TypeScript 示例

```typescript
interface ServiceExecuteRequest {
    service_key: string;
    input: any;
    include_steps?: boolean;
}

interface ServiceExecuteResponse {
    success: boolean;
    output: string | null;
    steps: ExecutionStep[];
    total_elapsed_us: number;
    error: OrchestrationError | null;
}

async function executeService(
    serviceKey: string,
    input: any,
    includeSteps: boolean = false
): Promise<ServiceExecuteResponse> {
    const response = await fetch('/api/service/execute', {
        method: 'POST',
        headers: {
            'Content-Type': 'application/json',
            'Authorization': `Bearer ${getToken()}`,
        },
        body: JSON.stringify({
            service_key: serviceKey,
            input,
            include_steps: includeSteps,
        } as ServiceExecuteRequest),
    });

    const result = await response.json();
    return result.data;
}

// 使用示例
const result = await executeService('user-service', { user_id: '12345' });

if (result.success) {
    console.log('执行成功:', result.output);
} else {
    console.error('执行失败:', result.error?.message);
    console.error('失败步骤:', result.error?.failed_step);
}
```

### 5.3 错误处理示例

```typescript
async function executeWithErrorHandling() {
    const result = await executeService('order-service', { order_id: '123' });

    if (!result.success) {
        // 获取失败步骤信息
        const failedStep = result.error?.failed_step;

        if (failedStep) {
            console.error(`步骤 [${failedStep.node_name}] 执行失败`);
            console.error(`节点ID: ${failedStep.node_id}`);
            console.error(`步骤序号: ${failedStep.step_index}`);
            console.error(`错误信息: ${failedStep.error}`);

            // 查看上一步输出（用于排错）
            if (failedStep.previous_output) {
                console.log('上一步输出:', failedStep.previous_output);
            }
        }

        // 查看所有步骤执行情况
        result.steps.forEach((step, index) => {
            console.log(`步骤 ${index}: ${step.node_name} - ${step.status}`);
        });
    }
}
```

## 六、最佳实践

### 6.1 include_steps 使用建议

| 场景 | 建议值 | 原因 |
|------|--------|------|
| 生产环境调用 | `false`（默认） | 减少数据传输，提升性能 |
| 前端调试 | `true` | 便于查看每个步骤的执行情况 |
| 后台任务 | `false` | 不需要步骤详情 |
| 错误排查 | 任意值 | 失败时始终返回步骤数据 |

### 6.2 错误处理建议

1. **检查 `success` 字段**：首先判断整体执行是否成功
2. **使用 `error.message`**：获取错误摘要，适合展示给用户
3. **使用 `error.failed_step`**：获取详细错误信息，适合记录日志
4. **使用 `previous_output`**：查看失败前的数据，便于定位问题

### 6.3 性能优化建议

1. 生产环境使用 `include_steps: false` 减少响应数据量
2. 利用 HTTP 请求头传递认证信息，避免在 input 中重复传递
3. 对于复杂编排，关注 `total_elapsed_us` 监控执行性能
