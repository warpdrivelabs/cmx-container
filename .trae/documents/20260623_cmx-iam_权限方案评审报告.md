## 一、新发现问题

### 1.1 【P0】角色宏和多权限宏未注册 RegisteredRouteHandler

**问题**: 方案 §3.1.2 的三个角色注解宏(`#[require_role]`/`#[require_roles]`/`#[require_any_role]`)和 §3.1.1 的两个多权限宏(`#[require_permissions]`/`#[require_any_permission]`)的伪代码中,**均未提及** `::inventory::submit! { RegisteredRouteHandler { ... } }` 注册。

只有 `#[permission]`(§3.1.1 第一个宏)明确提到会注册 `RegisteredRouteHandler`。

**影响**: §3.7.2 的 `warn_handler_annotation_status()` 统计 `all_registered_handlers()` 数量时,使用角色宏或多权限宏保护的 handler **不会被计入**,导致:
- 漏写统计数字偏低,与实际路由数差异更大,误报增多
- 无法通过 inventory 了解到哪些 handler 已被角色宏保护

**建议**: 所有 6 个保护类注解宏(`#[permission]`/`#[require_permissions]`/`#[require_any_permission]`/`#[require_role]`/`#[require_roles]`/`#[require_any_role]`)都应注册 `RegisteredRouteHandler { is_public: false, ... }`。只有 `#[public]` 注册 `is_public: true`。在 §3.1.2 的角色宏伪代码中补充 inventory::submit 说明。

### 1.2 【P0】to_insert_sql() 存在 SQL 注入/转义缺陷

**问题**: §3.7.1 的 `to_insert_sql()` 使用 `format!()` 直接拼接 SQL:

```rust
sql.push_str(&format!(
    "INSERT INTO cmx_permission (code, name, description, status, archived) \
     VALUES ('{}', '{}', '{}', 1, 0);\n",
    p.key, p.display, p.description
));
```

如果 `display` 或 `description` 含有单引号(如 `"用户's 管理"`),生成的 SQL 会语法错误。虽然这些值来自代码编译期常量(`&'static str`),安全性高于用户输入,但企业级框架不应示范不安全的 SQL 拼接模式。

**建议**:
- 对字符串值进行 SQL 转义(单引号替换为两个单引号 `''`)
- 或使用 `pg_escape_string` 等工具函数
- 或生成参数化 SQL 模板(如 `INSERT ... VALUES ($1, $2, $3)`)配合单独的参数列表

```rust
// 建议实现
fn escape_sql(s: &str) -> String {
    s.replace('\'', "''")
}
sql.push_str(&format!(
    "INSERT INTO cmx_permission (code, name, description, status, archived) \
     VALUES ('{}', '{}', '{}', 1, 0);\n",
    escape_sql(p.key), escape_sql(p.display), escape_sql(p.description)
));
```

### 1.3 【P1】ensure_db_permission_consistency 签名与实际 trait 不匹配

**问题**: §3.7.1 的 `ensure_db_permission_consistency()` 伪代码:

```rust
pub async fn ensure_db_permission_consistency(
    permission_service: &dyn cmx_iam::service_traits::PermissionService,
) -> ConsistencyReport {
    let db_perms_raw = permission_service.list_permissions(/* filter */).await;
    let db_perms: HashSet<String> = db_perms_raw.iter().map(|p| p.code.clone()).collect();
```

但实际 [PermissionService trait](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/permission/service.rs) 的 `list_permissions` 签名是:

```rust
async fn list_permissions(&self, filter: PermissionFilter) -> Result<Vec<Permission>, TraitError>
```

存在三处不匹配:
1. **filter 参数**: 需要传入 `PermissionFilter`(不能省略),且 `PermissionServiceImpl::with_default_archived` 会默认追加 `archived = 0`,但一致性校验应该比对**所有**权限(包括已归档的),否则已归档权限会被误报为 orphan
2. **返回值是 Result**: 需要处理 `TraitError`,不能直接 `.iter()`
3. **返回类型**: 函数签名应返回 `Result<ConsistencyReport, TraitError>`,而非裸 `ConsistencyReport`

**建议**:
- 明确 filter 传入空 `PermissionFilter::default()` 并**绕过** `with_default_archived`(或直接执行 SQL `SELECT code FROM cmx_permission` 查全部)
- 补充 `?` 错误传播和返回 `Result`
- 在方案伪代码中标注"示意,实际需处理错误"

## 二、细节改进建议

### 2.1 PermissionDeniedError::Roles 的 required 字段用字符串魔法值

**问题**: §3.3.1 的 `Roles` 变体:

```rust
Roles {
    required: &'static str,  // "all" 或 "any"
    roles: String,
}
```

用字符串 `"all"`/`"any"` 区分语义,是字符串魔法值。如果拼写错误(如 `"All"`)不会有编译期检查。

**建议**(可选): 改为枚举字段:

```rust
pub enum RoleRequirement {
    All,
    Any,
}

Roles {
    user_id: String,
    requirement: RoleRequirement,
    roles: String,
}
```

### 2.2 require_all_roles 只报第一个缺失角色

**问题**: §3.3.2 的 `require_all_roles` 遇到第一个缺失角色即返回,只报一个角色名:

```rust
for role in roles {
    if !self.has_role(role) {
        return Err(PermissionDeniedError::Roles {
            roles: role.to_string(),  // 只报第一个缺失的
            ...
        });
    }
}
```

用户缺少 `admin` 和 `auditor` 两个角色时,只报 `admin`,补齐后再次请求才发现还缺 `auditor`。

**建议**(可选): 先收集所有缺失角色再返回,一次性告知:

```rust
let missing: Vec<_> = roles.iter().filter(|r| !self.has_role(r)).collect();
if !missing.is_empty() {
    return Err(PermissionDeniedError::Roles {
        roles: missing.iter().map(|s| s.to_string()).collect::<Vec<_>>().join(", "),
        ...
    });
}
```

`require_all_permissions` 同理(当前也只报第一个缺失权限)。
