# API Key 物理删除 + 权限物理删除（路径化层级字段+前置校验+级联）方案

## 一、背景与目标

两处删除逻辑当前为软删除，且权限删除缺少安全校验。本方案：
1. **API Key 删除**改为物理删除。
2. **cmx_permission 表新增层级字段**（`is_leaf`/`parent_code`/`full_code_path`/`level`），删除子权限改用 `full_code_path LIKE` 查询（替代低性能的递归 CTE）。
3. **权限删除**改为物理删除 + 前置校验（被角色使用则整体拒绝并返回角色 code+name）+ 级联物理删除所有后代。
4. **权限创建/更新/导入**时自动生成并维护层级字段；父节点变更时级联重算后代路径与层级。

## 二、设计决策（已与用户确认）

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 被使用时处理 | 整体拒绝 + 返回详情 | 任一权限（含后代）被角色使用则整个请求拒绝，返回 `blocked_permissions`（含角色 code+name） |
| 子权限校验 | 同样阻止 | 后代任一被角色使用即阻止整个删除 |
| 子权限查询方式 | **`full_code_path LIKE` 前缀匹配** | 性能优于递归 CTE；PG btree 索引支持 `LIKE 'prefix/%'` |
| 层级字段 | 新增 `is_leaf`/`parent_code`/`full_code_path`/`level` | 路径化字段一次写入，查询 O(索引扫描) |
| `level` 字段 | 新增（根=1，子=父+1） | 便于前端按层级展示/排序/查询；计算简单 |
| 存量数据 | **提供 migration 脚本回填** | 确保现有权限字段完整可用 |
| 返回机制 | service 返回 `DeletePermissionOutcome` 枚举（Deleted/Blocked） | 不改动公共 `Error` 体系 |
| API Key 静态导入复活 | 方案中说明，不代码拦截 | 配置管理范畴 |

## 三、cmx_permission 表字段设计与 full_code_path 规则

### 3.1 新增字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `parent_code` | VARCHAR(200) | 父权限 code（冗余，根为 NULL） |
| `full_code_path` | VARCHAR(1000) NOT NULL | code 全路径，格式见 3.2 |
| `is_leaf` | INT4 DEFAULT 1 | 1=叶子（无子节点），0=非叶子 |
| `level` | INT4 DEFAULT 1 | 层级深度，根=1，子=父+1 |

### 3.2 full_code_path 格式约定（关键）

- **格式**：`/rootcode/childcode/grandcode`（前导 `/`，节点间 `/` 分隔，**无尾 `/`**）。
- 根节点示例：`/user:list`
- 子节点示例：`/user:list/user:delete`
- 孙节点示例：`/user:list/user:delete/user:force`
- **分隔符安全性**：权限 code 规范为 `{module}:action`（不含 `/`），用 `/` 作路径分隔符无歧义。
- **查询规则**：
  - 查节点 P（code=`user:list`）的**所有后代**（不含自身）：
    `WHERE full_code_path LIKE '/user:list/%'`
  - 查节点 P 及所有后代（含自身）：
    `WHERE full_code_path = '/user:list' OR full_code_path LIKE '/user:list/%'`

### 3.3 字段生成规则（写入时计算）

创建/更新权限 N 时，已知父 F（parent_id 或 parent_code 解析）：
- `parent_code` = F.code（无父则 NULL）
- `full_code_path` = `F.full_code_path` + `/` + `N.code`（无父则 `/` + N.code）
- `level` = `F.level + 1`（无父则 1）
- `is_leaf` = 1（新建默认叶子；若 N 作为某节点的父，则 N 创建后其父 is_leaf 置 0）

### 3.4 is_leaf 维护场景汇总（完整性保证）

凡是改变父子关系的写操作，都必须同步维护相关节点的 `is_leaf`。完整场景清单：

| # | 场景 | 触发位置 | is_leaf 操作 |
|---|------|---------|--------------|
| 1 | **新建权限（有 parent_id）** | `create_permission` | 父节点 `is_leaf = 0` |
| 2 | **移动节点（update 改 parent_id）** | `update_permission` | 新父 `is_leaf = 0`；旧父重算（无子则 `is_leaf = 1`） |
| 3 | **删除权限** | `delete_permission` | 被删节点的父节点重算（无子则 `is_leaf = 1`） |
| 4 | **批量导入** | `import_permissions` | **整个作用域完整重算**（先全置 1，再有子的置 0），避免旧父残留 0 |

**场景 4 的完整重算 SQL**（import 提交后执行）：
```sql
-- 4.1 先将该作用域下所有权限置为叶子
UPDATE cmx_permission SET is_leaf = 1
WHERE domain_code = $1 AND app_code = $2 AND module_code = $3;
-- 4.2 再将"有子节点"的父置为非叶子
UPDATE cmx_permission SET is_leaf = 0
WHERE id IN (
    SELECT DISTINCT parent_id FROM cmx_permission
    WHERE parent_id IS NOT NULL AND domain_code = $1 AND app_code = $2 AND module_code = $3
);
```

> **关键**：import 场景必须用"先 1 后 0"完整重算，不能仅"有子的置 0"。因为 import 可能改变既有权限的 parent_code（A→B），导致旧父 A 失去子节点但残留 `is_leaf=0`。

**单条 is_leaf 重算辅助方法**（供 create/update/delete 复用）：
```rust
/// 重算给定 parent_id 的 is_leaf：若无子节点则置 1，否则保持 0。
/// 用于 create（父置0的逆操作不适用，但 delete/update 旧父需要）。
async fn recompute_parent_is_leaf(&self, parent_id: &str) {
    let sql = "UPDATE cmx_permission SET is_leaf = 0 WHERE id = $1 \
               AND EXISTS (SELECT 1 FROM cmx_permission c WHERE c.parent_id = $1)";
    // 反向：若无子则置 1
    let sql2 = "UPDATE cmx_permission SET is_leaf = 1 WHERE id = $1 \
                AND NOT EXISTS (SELECT 1 FROM cmx_permission c WHERE c.parent_id = $1)";
}
```

### 3.5 父节点变更的级联重算（update/import 改变 parent_id 时）

设节点 N 的 parent 从 A 改为 B：
1. 记录 N 的旧 `full_code_path`(old_path)、旧 `level`(old_level)。
2. 计算 N 的新 `full_code_path`(new_path = B.path + '/' + N.code)、新 `level`(new_level = B.level + 1)。
3. **批量更新 N 及所有后代**（一条 SQL，利用 LIKE + 字符串函数）：
   ```sql
   UPDATE cmx_permission SET
     full_code_path = $2 || SUBSTRING(full_code_path FROM $3),  -- $2=new_path, $3=old_path长度+1
     level = level + ($4 - $5)                                   -- $4=new_level, $5=old_level
   WHERE full_code_path = $1 OR full_code_path LIKE $1 || '/%'  -- $1=old_path
   ```
   > 说明：`SUBSTRING(full_code_path FROM LENGTH(old_path)+1)` 取出 `/childcode/...` 后缀，拼到 new_path 之后，得到 `/B_path/N_code/childcode`。level 按差值整体平移。
4. 旧父 A：删除/变更后，若 A 已无其他子节点，`is_leaf=1`。
5. 新父 B：`is_leaf=0`。

  WITH RECURSIVE perm_path AS (
      SELECT id, code, parent_id, code::varchar AS path, 1 AS lvl
      FROM cmx_permission WHERE parent_id IS NULL
      UNION ALL
      SELECT c.id, c.code, c.parent_id, p.path || '/' || c.code, p.lvl + 1
      FROM cmx_permission c JOIN perm_path p ON c.parent_id = p.id
  )
  UPDATE cmx_permission x SET
      full_code_path = pp.path,
      level = pp.lvl,
      parent_code = (SELECT code FROM cmx_permission WHERE id = x.parent_id)
  FROM perm_path pp WHERE x.id = pp.id;
  -- 回填 is_leaf：有子节点的置 0
  UPDATE cmx_permission SET is_leaf = 0 WHERE id IN (SELECT DISTINCT parent_id FROM cmx_permission WHERE parent_id IS NOT NULL);
  -- 补 NOT NULL（回填后强制）
  ALTER TABLE cmx_permission ALTER COLUMN full_code_path SET NOT NULL;
  CREATE INDEX IF NOT EXISTS idx_cmx_permission_full_path ON cmx_permission (full_code_path);
  CREATE INDEX IF NOT EXISTS idx_cmx_permission_parent_code ON cmx_permission (parent_code);

## 六、假设与边界

- **full_code_path 长度**：VARCHAR(1000)，假设单条路径不超限（权限层级通常 ≤5 层，code ≤200）。
- **code 不可改**：现有约定，故 update 不涉及节点自身路径段变更，仅父变更时级联。
- **is_leaf 一致性**：删除/移动后对父节点做"无子则置 1"的修正，容忍短暂时窗（非强一致，业务可接受）。
- **LIKE 前缀索引**：PG btree 支持 `LIKE 'prefix/%'`，`idx_cmx_permission_full_path` 有效；`full_code_path` 不以尾 `/` 结尾，`LIKE '/user:list/%'` 精确匹配后代。
- **import 第一阶段占位**：非根权限先写 `/code`，第二阶段覆盖；若中途失败事务回滚，无脏数据。
- **migration 一次性**：递归 CTE 回填为一次性脚本，存量数据量可控。
- **API Key 静态导入复活风险**：物理删除后若配置仍含该 key，重启会重新 INSERT，需运维同步清理配置。

## 七、验证步骤

1. `cargo check -p cmx-iam -p cmx-api -p cmx-core` 编译通过。
2. `cargo clippy -p cmx-iam -p cmx-api` 无新增警告。
3. 执行 migration 脚本，确认存量权限 full_code_path/level/is_leaf/parent_code 正确回填（抽检根/子/叶节点）。
4. API Key 删除：删除后 list 查不到、认证失败、缓存失效。
5. 权限创建：创建带 parent_id 的子权限，确认 full_code_path/level 正确，父 is_leaf=0。
6. 权限更新（改父）：parent_id 变更后，该节点及所有后代 full_code_path/level 正确级联更新；旧父/新父 is_leaf 正确。
7. 权限删除-被阻止：被角色使用的权限（或其后代被使用），删除返回 blocked_permissions 含角色 code+name，记录未删。
8. 权限删除-级联：删父权限 P，确认 P 及所有后代物理删除、角色关联清理、P 的父 is_leaf 正确重算。
9. import_permissions：导入带 parent_code 的权限集，确认 4 字段正确填充。
