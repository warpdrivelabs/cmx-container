>
> 版本：v1.0 | 日期：2026-06-17 | 模块：cmx-iam

## 一、概述

### 1.1 背景

当前 cmx-iam 权限系统采用 RBAC（基于角色的访问控制）模型，通过 `cmx_user` → `cmx_user_role` → `cmx_role` → `cmx_role_permission` → `cmx_permission` 五表关联实现权限校验。系统已支持基础 CRUD、权限码精确匹配、`system:all` 超级权限短路等能力，但在企业级场景下存在以下不足：

- 权限分配无逻辑约束（SoD 职责分离、依赖校验缺失）
- 角色/权限授予无有效期管理（临时授权需手动撤销）
- 缺少权限可视化与审计能力（无法快速排查用户有效权限）
- 权限检查无缓存、无熔断降级（高频查询直击数据库）

### 1.2 目标

1. **权限互斥与依赖规则**：支持动态配置 SoD 规则，在权限分配时进行逻辑校验
2. **临时角色/权限授予**：支持 Time-bound Access，自动失效过期授权
3. **权限可视化与审计 API**：提供有效权限查询、权限差异对比、使用统计等管理接口
4. **缓存与熔断策略**：引入 Redis 缓存降低 DB 压力，提供故障降级策略保障系统可用性

### 1.3 范围

**本次方案覆盖**：上述 4 项增强点。

**非目标（明确排除）**：

- **DataScope 数据权限实现**：`IamChecker::get_data_scope`（[iam\_checker.rs:200-202](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/iam_checker.rs#L200-L202)）当前为占位实现，本次不实现 BMC/Service 层的 WHERE 条件注入，作为独立后续迭代
- **角色层级与继承**：不支持角色树形层级结构和权限继承
- **通配符权限匹配**：不支持 `system:user:*` 这类通配符，仅支持精确码匹配

### 1.4 设计原则

1. **最小侵入**：以新增表为主，保留现有表结构不变，确保向下兼容
2. **配置开关**：所有新功能默认关闭，通过 `IamConfig` 控制，避免阻塞现有业务
3. **分阶段交付**：4 项增强相互独立，可分迭代实施
4. **性能优先**：高频查询路径必须有索引和 Redis 缓存策略，保证多节点一致性

## 三、方案设计

### 3.1 权限互斥与依赖规则（SoD & Dependencies）

#### 3.1.1 设计目标

在权限分配时进行逻辑校验，防止产生冲突或危险的权限组合：

- **互斥规则**：拥有 `accounting:audit` 的用户不能同时拥有 `accounting:entry`（职责分离）
- **依赖规则**：分配 `user:delete` 时必须同时拥有 `user:list`（先能看到才能删除）

#### 3.1.2 表结构优化

**原方案问题**：`cmx_permission_rule_group` 表名语义模糊，`group_seq` 字段无法清晰表达互斥/依赖语义，缺少错误消息字段。

**优化方案**：

**表 1：`cmx_permission_rule`（权限规则表）**

```sql
CREATE TABLE cmx_permission_rule (
    id varchar(64) NOT NULL,
    code varchar(100) NOT NULL,
    name varchar(200) NOT NULL,
    rule_type varchar(20) NOT NULL,
    violation_message varchar(500),
    priority int4 DEFAULT 0,
    description varchar(500),
    status int4 DEFAULT 1,
    archived int4 DEFAULT 0,
    create_time timestamp DEFAULT CURRENT_TIMESTAMP,
    update_time timestamp DEFAULT CURRENT_TIMESTAMP,
    create_by varchar(100),
    create_name varchar(100),
    update_by varchar(100),
    update_name varchar(100),
    CONSTRAINT pk_cmx_permission_rule PRIMARY KEY (id),
    CONSTRAINT uk_cmx_permission_rule_code UNIQUE (code)
);

COMMENT ON TABLE cmx_permission_rule IS '权限规则表（互斥/依赖）';
COMMENT ON COLUMN cmx_permission_rule.id IS '主键ID';
COMMENT ON COLUMN cmx_permission_rule.code IS '规则编码（唯一，如 sod_finance）';
COMMENT ON COLUMN cmx_permission_rule.name IS '规则名称';
COMMENT ON COLUMN cmx_permission_rule.rule_type IS '规则类型：mutual_exclusion-互斥，dependency-依赖（使用 rule_type 而非 type，避免 PostgreSQL 保留字）';
COMMENT ON COLUMN cmx_permission_rule.violation_message IS '违反规则时的错误消息（为空时使用默认消息）';
COMMENT ON COLUMN cmx_permission_rule.priority IS '优先级（数字越大越先校验，默认0）';
COMMENT ON COLUMN cmx_permission_rule.description IS '描述';
COMMENT ON COLUMN cmx_permission_rule.status IS '状态：0-禁用，1-启用';
COMMENT ON COLUMN cmx_permission_rule.archived IS '是否归档：0-否，1-是';
```

**表 2：`cmx_permission_rule_item`（规则权限项表）**

> 原方案表名 `cmx_permission_rule_group` → 优化为 `cmx_permission_rule_item`，语义更清晰。

```sql
CREATE TABLE cmx_permission_rule_item (
    id varchar(64) NOT NULL,
    rule_id varchar(64) NOT NULL,
    group_seq int4 NOT NULL,
    permission_id varchar(64) NOT NULL,
    CONSTRAINT pk_cmx_permission_rule_item PRIMARY KEY (id),
    CONSTRAINT uk_cmx_permission_rule_item UNIQUE (rule_id, group_seq, permission_id)
);

CREATE INDEX idx_cmx_permission_rule_item_rule ON cmx_permission_rule_item (rule_id);
CREATE INDEX idx_cmx_permission_rule_item_perm ON cmx_permission_rule_item (permission_id);

COMMENT ON TABLE cmx_permission_rule_item IS '规则权限项表';
COMMENT ON COLUMN cmx_permission_rule_item.id IS '主键ID';
COMMENT ON COLUMN cmx_permission_rule_item.rule_id IS '关联规则ID';
COMMENT ON COLUMN cmx_permission_rule_item.group_seq IS '组序号：互斥规则下所有项两两互斥；依赖规则中 group_seq=1 为前置权限，group_seq=2 为依赖权限';
COMMENT ON COLUMN cmx_permission_rule_item.permission_id IS '关联权限ID';
```

**语义明确化**：

- **互斥规则**（`rule_type='mutual_exclusion'`）：同一 `rule_id` 下所有 `permission_id` 两两互斥（不区分 `group_seq`，校验时检查用户是否同时拥有任意两个）
- **依赖规则**（`rule_type='dependency'`）：`group_seq=1` 的权限是 `group_seq=2` 的前置条件（用户拥有 `group_seq=2` 的权限时，必须同时拥有至少一个 `group_seq=1` 的权限）

**`RuleEnforcer`** **trait 设计**：

> **关键决策**：区分"角色权限校验"与"用户权限校验"两个维度。
>
> - `assign_permissions` 是角色维度操作，仅校验**角色权限组合本身**是否违反互斥规则（不展开到用户，避免性能问题）
> - `assign_roles` 是用户维度操作，需校验**用户合并后的权限集合**（现有权限 + 新角色权限）

```rust
#[async_trait]
pub trait RuleEnforcer: Send + Sync {
    /// 校验角色权限组合本身是否违反互斥规则
    /// - `permission_ids`：待分配给角色的权限ID列表
    /// - 仅校验互斥规则（依赖规则针对用户场景，角色层不校验）
    async fn check_role_permissions(
        &self,
        permission_ids: &[String],
    ) -> Result<(), IamError>;

    /// 校验用户权限组合是否违反规则（合并现有权限 + 待分配角色权限）
    /// - `user_id`：目标用户ID（用于查询已有权限）
    /// - `role_ids`：待分配的角色ID列表（展开到权限后与现有权限合并）
    async fn check_user_roles(
        &self,
        user_id: &str,
        role_ids: &[String],
    ) -> Result<(), IamError>;
}
```

**校验逻辑**：

**`check_role_permissions`（角色层校验）**：

1. 加载所有 `rule_type='mutual_exclusion' AND status=1 AND archived=0` 的规则
2. 检查 `permission_ids` 是否包含同一互斥规则下的任意两个权限
3. 违反时返回 `IamError::RuleViolation`

**`check_user_roles`（用户层校验）**：

1. 查询用户当前已有的权限集合（合并永久 + 临时授权）
2. 展开待分配 `role_ids` 到权限集合（查询角色关联的权限）
3. 合并后得到**用户最终权限集合**，按规则类型校验：
   - **互斥**：检查合并后集合是否包含同一规则下的任意两个权限
   - **依赖**：遍历**所有依赖规则**，对于规则中每个 `group_seq=2` 的权限（无论是否在本次新增），检查用户权限集合中是否至少有一个 `group_seq=1` 的权限
4. 违反规则时返回 `IamError::RuleViolation { rule_code, message }`

> **依赖规则校验范围说明**：依赖规则不仅校验本次新增的权限，还会校验用户**已有的** group\_seq=2 权限是否满足前置条件。这样可以发现"历史遗留的不合规状态"（例如规则后加，已有权限不满足）。若希望仅校验新增权限，可在 `IamConfig` 增加 `sod_check_scope` 配置（默认 `All`，可选 `Incremental`）。

**校验时机**：

- `RoleServiceImpl::assign_permissions`（[role/service.rs:426-485](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/role/service.rs#L426-L485)）：在事务开启后、DELETE 之前调用 `check_role_permissions`，失败时事务自动回滚

- 临时角色分配 `assign_temp_role`：同样调用 `check_user_roles`

#### 3.1.4 错误类型扩展

在 [error.rs](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-iam/src/error.rs) 新增：

```rust
#[derive(Debug, Error)]
pub enum IamError {
    // ... 现有变体 ...

    #[error("权限规则违反: 规则={rule_code}, 原因={message}")]
    RuleViolation {
        rule_code: String,
        message: String,
    },
}
```

并在 `From<IamError> for cmx_api_types::Error` 和 `From<IamError> for TraitError` 中增加映射：

```rust
// 在 From<IamError> for cmx_api_types::Error 的 match 中增加：
IamError::RuleViolation { rule_code, message } => {
    cmx_api_types::Error::BusinessError(format!("[{}] {}", rule_code, message))
}

// 在 From<IamError> for TraitError 的 match 中增加：
IamError::RuleViolation { rule_code, message } => {
    cmx_traits::error::TraitError::Business(format!("[{}] {}", rule_code, message))
}
```

> **映射决策**：`RuleViolation` 映射为 `BusinessError`/`Business`（HTTP 400），而非 `Forbidden`（HTTP 403）。原因是规则违反是**输入数据不合规**（用户提交的权限组合冲突），而非**权限不足**（用户没有操作权限）。前端可据此区分提示：403 显示"无权限"，400 显示"权限组合违反规则 XXX"。

### 3.2 临时角色/权限授予（Time-bound Access）

#### 3.2.1 设计目标

支持给用户分配带有效期的角色，到期自动失效，实现最小权限原则。

#### 3.2.2 表结构优化

**原方案问题**：缺少撤销审计字段、授权来源字段，索引设计不完整。

### 3.4 缓存与熔断策略

#### 3.4.1 设计目标

1. **缓存**：引入 Redis 缓存降低 DB 压力，权限变更时精准失效，保证多节点一致性
2. **熔断**：DB/缓存故障时提供降级策略，保障系统可用性

> **架构决策：选择 Redis 而非本地内存缓存（moka）**
>
> 服务采用**多节点无状态部署**，本地缓存存在严重的一致性问题：
>
> - 节点 A 修改权限后，仅失效节点 A 的缓存，节点 B/C/D 仍是旧数据
> - 权限检查是安全敏感操作，缓存不一致会导致权限撤销后仍放行（安全漏洞）
> - 本地缓存要解决一致性需引入 Pub/Sub 广播失效，增加复杂度，违背无状态原则
>
> Redis 缓存的优势：
>
> - 多节点共享，一处失效全局生效，天然一致
> - 符合无状态部署原则
> - 项目已有 `cmx-buffer` 模块封装 Redis 操作，可直接复用
> - 权限数据量小（每用户权限码 < 100），Redis 存储开销低

#### 3.4.2 缓存设计

**技术选型**：复用项目现有 `cmx-buffer` 模块的 `CacheOps`（[cache/ops.rs](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-infra/cmx-buffer/src/cache/ops.rs)）和 `TtlOps`（[cache/ttl.rs](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-infra/cmx-buffer/src/cache/ttl.rs)）

**缓存结构**：

**Key 设计**：

| Key 格式               | 值（JSON）                                       | TTL                                           | 说明                      |
| -------------------- | --------------------------------------------- | --------------------------------------------- | ----------------------- |
| `iam:perm:{user_id}` | `["user:list","user:create",...]` 或 `[]`（空数组） | `permission_cache_ttl_secs`（默认 300s ± 10% 抖动） | 用户有效权限码列表（空数组表示无权限，防穿透） |
| `iam:role:{user_id}` | `["admin","user",...]` 或 `[]`（空数组）            | `permission_cache_ttl_secs`（默认 300s ± 10% 抖动） | 用户有效角色码列表               |

> **注**：
>
> - Key 前缀 `iam:` 由 `RedisClient::build_key` 自动添加项目全局前缀（如 `cmx:iam:perm:{user_id}`）
> - **防穿透方案**：使用空数组 `[]` 而非单独的空标记 key，避免 key 命名冲突，且语义统一（无权限即空数组）

**缓存策略**：

- **读流程**：先查 Redis，命中则反序列化返回（含空数组）；未命中查 DB 并回填 Redis（带 TTL）
- **写流程**：DB 查询失败时不回填缓存，触发熔断逻辑
- **缓存穿透对策**：DB 返回空结果时缓存空数组 `[]`（短 TTL 60 秒），与正常结果用 TTL 长短区分，避免 key 冲突
- **缓存雪崩对策**：TTL 添加随机抖动（±10%），防止大量 key 同时过期
- **序列化**：优先使用 `CacheOps::set_serialized` / `get_deserialized`（内部已封装 serde\_json）

**失效策略**（精准失效，多节点天然一致）：

| 触发场景                                    | 失效操作                                                               | 说明         |
| --------------------------------------- | ------------------------------------------------------------------ | ---------- |
| `RoleServiceImpl::assign_permissions` 后 | 查询该角色关联的所有 user\_id，逐个 `DEL iam:perm:{uid}` + `DEL iam:role:{uid}` | 失效角色关联用户缓存 |
| `UserServiceImpl::assign_roles` 后       | `DEL iam:perm:{user_id}` + `DEL iam:role:{user_id}`                | 失效该用户缓存    |
| 临时角色分配/撤销后                              | `DEL iam:perm:{user_id}` + `DEL iam:role:{user_id}`                | 失效该用户缓存    |
| 权限/角色删除后                                | `DEL iam:perm:*` + `DEL iam:role:*`（SCAN + DEL 批量）                 | 保守策略，失效全量  |

**新增方法**：

    pub async fn invalidate_user_cache(&self, user_id: &str) -> Result<(), TraitError> {
        let ops = self.cache.ops();
        let perm_key = format!("iam:perm:{}", user_id);
        let role_key = format!("iam:role:{}", user_id);
        // 使用 del_batch 批量删除（单次 RTT）
        let _ = ops.del_batch(&[&perm_key, &role_key]).await; // 失败不阻塞，TTL 兜底
        Ok(())
    }

    /// 带缓存的权限查询
    async fn get_user_permissions_cached(&self, user_id: &str) -> Result<Vec<String>, TraitError> {
        let ops = self.cache.ops();
        let key = format!("iam:perm:{}", user_id);

        // 1. 查 Redis（优先使用 get_deserialized）
        if let Ok(Some(perms)) = ops.get_deserialized::<Vec<String>>(&key).await {
            return Ok(perms); // 命中（含空数组）
        }

        // 2. 未命中，查 DB
        let perms = self.query_permissions_from_db(user_id).await?;

        // 3. 回填 Redis（使用 set_ex 带 TTL，空结果用短 TTL 防穿透）
        let ttl = if perms.is_empty() {
            Duration::from_secs(60) // 空结果短 TTL
        } else {
            self.calc_ttl_with_jitter()
        };
        let _ = ops.set_ex(&key, &serde_json::to_string(&perms).unwrap_or_default(), ttl).await;

        Ok(perms)
    }

    /// 计算带随机抖动的 TTL（防雪崩）
    fn calc_ttl_with_jitter(&self) -> Duration {
        let base = self.config.permission_cache_ttl_secs;
        // ±10% 随机抖动，使用简单的纳秒时间戳作为伪随机源（避免引入 rand 依赖）
        let now_nanos = std::time::SystemTime::now()
            .duration_since(std::time::UNIX_EPOCH)
            .map(|d| d.subsec_nanos() as u64)
            .unwrap_or(0);
        let jitter = (base as f64 * 0.1) as u64;
        let offset = now_nanos % (jitter * 2 + 1);
        let ttl = base + offset - jitter;
        Duration::from_secs(ttl.max(60))
    }
}

**降级逻辑**（在 `has_permission` 中）：

> **FailOpen 性能说明**：熔断器打开时，FailOpen 模式需查询 DB 检查 `system:all`。由于此时 DB/Redis 可能已故障，此查询大概率也会失败，FailOpen 实际效果接近"全部拒绝 + 放行已知管理员"。建议仅在 `system:all` 用户量极少时启用 FailOpen，否则 FailClose 更合适。

```rust
async fn has_permission(&self, user_id: &str, permission_code: &str) -> Result<bool, TraitError> {
    // 1. 检查熔断器状态
    if !self.circuit_breaker.allow_request().await {
        // 熔断器打开，执行降级策略
        return match self.config.failure_mode {
            FailureMode::FailOpen => {
                // 故障开放：仅放行 system:all 用户（直接查 DB 单条权限）
                // 注意：DB 也故障时此查询会失败，实际返回 Err
                self.check_system_all_only(user_id).await
            }
            FailureMode::FailClose => {
                // 故障封闭：全部拒绝（不查 DB，保护系统）
                Ok(false)
            }
        };
    }

    // 2. 正常流程：Redis 缓存 → DB
    match self.has_permission_with_cache(user_id, permission_code).await {
        Ok(result) => {
            self.circuit_breaker.record_success();
            Ok(result)
        }
        Err(e) => {
            self.circuit_breaker.record_failure().await;
            Err(e)
        }
    }
}

/// 带缓存的权限检查
async fn has_permission_with_cache(
    &self,
    user_id: &str,
    permission_code: &str,
) -> Result<bool, TraitError> {
    // 1. 从缓存获取用户权限列表
    let perms = self.get_user_permissions_cached(user_id).await?;

    // 2. 内存中检查（含 system:all 短路）
    if perms.iter().any(|p| p == "system:all" || p == permission_code) {
        return Ok(true);
    }
    Ok(false)
}
```

### 6.4 API 设计原则

1. **权限隔离**：规则管理需 `system:all`，临时授权管理需 `user:assign_role`
