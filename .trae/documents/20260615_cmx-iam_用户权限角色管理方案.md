## 一、目标

基于 `20260612_平台级基础设施与双协议架构重构方案.md` 的 crate 划分，详细设计 **cmx-iam** 中用户、角色、权限三个核心模块的：

1. **数据库表结构**（DDL，遵循 pg-table-generator 规范）
2. **Entity / BMC / Filter 定义**（遵循 cmx-biz 模式）
3. **Service 层业务逻辑**
4. **cmx-traits / cmx-iam Trait 定义**（跨 crate 抽象 trait + cmx-iam 内部 Service trait，含数据权限扩展预留接口）
5. **API handler / route 规划**

### 设计原则

| 原则 | 说明 |
|------|------|
| 标准 RBAC 模型 | User → Role → Permission，多对多关系 |
| 企业级粒度 | 权限采用 `resource:action` 编码（如 `user:create`） |
| 数据权限预留 | 角色 data_scope 字段 + PermissionChecker trait 扩展方法，本次不实现具体数据过滤逻辑 |
| 遵循现有模式 | Entity/BMC/Filter/Service 四文件结构，GenericCrudService 复用 |
| 协议无关 | Service 层不依赖 axum，handler 为薄层适配 |
| **WASM 可达性** | **基础数据结构体放 cmx-core，业务逻辑（BMC/Filter/Service）放 cmx-iam** |

### 类型分层设计

> cmx-core 已有 `DomainEntity`、`TableDefine` 等纯数据结构先例，且 WASM SDK 直接 re-export cmx-core 类型。

| 层级 | 位置 | 包含内容 | WASM 可见 |
|------|------|----------|----------|
| **基础数据模型** | `cmx-core/src/model/iam/` | `User`、`Role`、`Permission`、`PermissionTreeNode`（纯 Serialize/Deserialize，无 sqlx 依赖）；`AuthContext` 已存在于 `cmx-core/src/model/service/context.rs`，不在 iam/ 中重复定义 | ✅ 是 |
| **业务操作层** | `cmx-iam/src/{user,role,permission}/` | `UserForCreate`、`UserForInsert`、`UserForUpdate`、`UserForUpdateInsert`、`UserBmc`、`UserFilter`、`UserService`、`AssignRolesRequest`；`RoleForCreate`、`RoleForUpdate`、`RoleBmc`、`RoleFilter`、`RoleService`；`PermissionForCreate`、`PermissionForUpdate`、`PermissionBmc`、`PermissionFilter`、`PermissionService` | ❌ 否（服务端专用） |

**分层理由**：
- WASM 插件需要感知调用者身份（User/Role）和权限信息（Permission），这些类型必须在 cmx-core 中
- WASM 插件不需要 ForCreate/ForInsert/ForUpdate/Filter/BMC（这些是服务端 CRUD 关注点）
- cmx-core 无 sqlx 依赖，基础结构体为纯 `Serialize/Deserialize`；cmx-iam 拥有 sqlx + modql + database 等完整能力

## 二、RBAC 权限模型设计

### 2.1 模型关系图

```
┌──────────┐     ┌──────────────┐     ┌──────────┐
│  cmx_user │─────│ cmx_user_role│─────│ cmx_role │
│  用户表   │  N:N│  用户角色关联 │  N:N│  角色表   │
└──────────┘     └──────────────┘     └────┬─────┘
                                            │
                                    ┌───────┴────────┐
                                    │cmx_role_permission│
                                    │  角色权限关联     │
                                    └───────┬────────┘
                                            │
                                    ┌───────┴─────┐
                                    │cmx_permission│
                                    │  权限表      │
                                    └─────────────┘
```

### 2.2 权限编码规范

权限 `code` 采用 `resource:action` 格式：

| 资源 | 操作 | 权限码 | 说明 |
|------|------|--------|------|
| user | create / read / update / delete | `user:create` 等 | 用户管理 |
| role | create / read / update / delete | `role:create` 等 | 角色管理 |
| permission | read / assign | `permission:read` 等 | 权限管理 |
| menu | create / read / update / delete | `menu:create` 等 | 菜单管理 |
| org | create / read / update / delete | `org:create` 等 | 组织管理 |
| system | config / all | `system:all` | 系统管理 |

> **通配权限 `system:all`**：拥有 `system:all` 权限的用户视为超级管理员，mw_permission 和 PermissionChecker 均短路放行，无需逐一检查具体权限码。

### 2.3 数据权限扩展设计（预留，本次不实现）

**DataScope 枚举**（定义在 cmx-traits，供 PermissionChecker 使用）：

```rust
/// 数据权限范围 — 本次仅定义枚举和接口，不实现过滤逻辑
#[derive(Debug, Clone, Serialize, Deserialize, Default)]
pub enum DataScope {
    #[default]
    All,                  // 全部数据
    Custom(Vec<String>),  // 自定义部门范围（部门ID列表）
    Dept,                 // 本部门
    DeptAndSub,           // 本部门及子部门
    SelfData,             // 仅本人数据
}
```

**预留机制**：
- `cmx_role` 表包含 `data_scope` 字段（int4，默认 1=All）
- `PermissionChecker` trait 包含 `get_data_scope()` 方法（带默认实现返回 `All`）
- 未来实现数据权限时，只需：① 实现 `get_data_scope` 具体逻辑 ② 在 BMC/Service 层注入数据过滤条件

```sql
-- admin 角色拥有全部权限（使用 CTE + ROW_NUMBER 生成关联 ID）
WITH perms AS (
    SELECT id, ROW_NUMBER() OVER () AS rn FROM cmx_permission
)
INSERT INTO cmx_role_permission (id, role_id, permission_id)
SELECT CONCAT('1898765432100003', LPAD(rn::TEXT, 4, '0')),
       '1898765432100001001',
       id
FROM perms
ON CONFLICT DO NOTHING;
```

> **种子数据 vs 实际 SQL 差异**：实际 SQL 仅包含 admin 角色 + system:all 权限 + 一条关联，较为精简。建议按本方案补充完整权限种子数据，使 admin 角色拥有所有权限。关联数据插入使用 CTE + ROW_NUMBER 方式生成唯一 ID，避免依赖权限行的物理顺序。

```rust
// crates/libs/cmx-traits/src/iam/data_scope.rs

use serde::{Deserialize, Serialize};

/// 数据权限范围 — 本次仅定义枚举，不实现过滤逻辑
///
/// 未来实现数据权限时，BMC/Service 层根据此枚举注入 WHERE 条件
#[derive(Debug, Clone, Serialize, Deserialize, Default, PartialEq)]
pub enum DataScope {
    /// 全部数据（默认）
    #[default]
    All,
    /// 自定义数据范围（部门ID列表）
    Custom(Vec<String>),
    /// 本部门数据
    Dept,
    /// 本部门及子部门数据
    DeptAndSub,
    /// 仅本人数据
    SelfData,
}

/// 从 int4 数据库值转换（cmx_role.data_scope 字段）
impl From<i64> for DataScope {
    fn from(v: i64) -> Self {
        match v {
            2 => DataScope::Custom(vec![]),
            3 => DataScope::Dept,
            4 => DataScope::DeptAndSub,
            5 => DataScope::SelfData,
            _ => DataScope::All,
        }
    }
}

impl From<&DataScope> for i64 {
    fn from(ds: &DataScope) -> Self {
        match ds {
            DataScope::All => 1,
            DataScope::Custom(_) => 2,
            DataScope::Dept => 3,
            DataScope::DeptAndSub => 4,
            DataScope::SelfData => 5,
        }
    }
}
```

### 4.3 PermissionChecker Trait（核心 — 含数据权限扩展点）

> trait 方法不含 `db_id` 参数，由 impl 持有状态。

```rust
use async_trait::async_trait;
use crate::error::TraitError;
use crate::iam::data_scope::DataScope;

/// 权限校验器 — 功能权限 + 数据权限扩展点
///
/// 功能权限（本次实现）：has_permission（EXISTS 子查询优化）/ has_role / get_user_permissions
/// 数据权限（本次预留）：get_data_scope 默认返回 All，未来实现具体逻辑
#[async_trait]
pub trait PermissionChecker: Send + Sync {
    /// 检查用户是否拥有指定权限码（如 "user:create"）
    ///
    /// 优化：先通过 EXISTS 子查询检查 system:all（轻量，不加载全部权限），再精确检查目标权限
    async fn has_permission(
        &self,
        user_id: &str,
        permission_code: &str,
    ) -> Result<bool, TraitError>;

    /// 检查用户是否拥有指定角色码（如 "admin"）
    async fn has_role(
        &self,
        user_id: &str,
        role_code: &str,
    ) -> Result<bool, TraitError>;

    /// 获取用户的所有权限码列表（聚合所有角色的权限）
    async fn get_user_permissions(
        &self,
        user_id: &str,
    ) -> Result<Vec<String>, TraitError>;

    /// 获取用户的所有角色码列表
    async fn get_user_role_codes(
        &self,
        user_id: &str,
    ) -> Result<Vec<String>, TraitError>;

    // ===== 数据权限扩展点（本次仅定义，不实现具体逻辑）=====

    /// 获取用户的数据权限范围
    ///
    /// 实现策略（未来）：
    /// 1. 查询用户的所有角色
    /// 2. 取角色中 data_scope 最严格的范围（优先级：SelfData > Dept > DeptAndSub > Custom > All）
    /// 3. 如果是 Custom，查询 cmx_role_data_scope 关联表获取部门列表
    ///
    /// 默认实现返回 DataScope::All（无限制），后续实现时覆盖
    async fn get_data_scope(
        &self,
        _user_id: &str,
    ) -> Result<DataScope, TraitError> {
        Ok(DataScope::All)
    }
}
```

> **设计决策**：Service impl 持有 `mm: Arc<DatabaseManager>`、`db_id: String`（优先 config.auth_db_id，fallback default_db_id）、`config: IamConfig`、`audit: Option<Arc<dyn AuditLogger>>` 等状态字段，trait 方法不含 `db_id` 参数。

#### AuditHelper trait（审计辅助 trait — 消除重复代码）

> `audit_write` 方法在三个 ServiceImpl 中完全一致，抽取为 AuditHelper trait，通过默认实现消除重复。

```rust
// crates/libs/cmx-iam/src/audit_helper.rs

use std::sync::Arc;
use serde::Serialize;
use cmx_audit::{AuditLogger, AuditRecord, AuditDomain, OperationResult};
use cmx_core::model::service::SVRContext;

/// 审计辅助 trait — 三个 ServiceImpl 共享 audit_write 默认实现
pub trait AuditHelper {
    fn audit_logger(&self) -> Option<&Arc<dyn AuditLogger>>;

    /// 记录审计日志（尽力而为，失败不阻塞业务，通过 warn! 告警）
    async fn audit_write<T: Serialize>(
        &self,
        svr_ctx: &SVRContext,
        action: &str,
        target_type: &str,
        target_id: &str,
        detail: &T,
    ) {
        if let Some(audit) = self.audit_logger() {
            let record = AuditRecord::new(AuditDomain::Iam, action, OperationResult::Success)
                .with_actor(
                    svr_ctx.auth_context.as_ref().map(|ac| ac.user_id.as_str()).unwrap_or("unknown"),
                    svr_ctx.auth_context.as_ref().and_then(|ac| ac.username.as_ref().map(|s| s.as_str())),
                )
                .with_target(target_type, target_id)
                .with_details(serde_json::to_value(detail).unwrap_or_default());
            if let Err(e) = audit.log(record).await {
                tracing::warn!("审计日志写入失败: {e}");
            }
        }
    }
}
```

```rust
        // 3. 构造 UserForInsert（password → password_hash）

            email: data.email,

        ).await?;

            .map_err(|e| IamError::Business(format!("数据转换失败: {e}")))?;
        // 6. 审计日志 — 脱敏处理，不记录明文密码
        let audit_detail = serde_json::json!({
            "username": &data.username,
            "email": &data.email,
            "password_changed": true,
        });
        self.audit_write(svr_ctx, "create_user", "user", &user.id, &audit_detail).await;
        Ok(user)
    }
```

### 5.10 AuthStorageQuery trait 定义（从 UserAuthQuery 拆分）

> cmx-traits 中的 UserAuthQuery trait 需在实施时移除上述 4 个 Auth 表方法，改由 AuthStorageQuery 承载。cmx-auth 的 AuthServiceImpl 需同时实现 UserAuthQuery（IAM 表查询）和 AuthStorageQuery（Auth 表操作）。

```rust
// crates/libs/cmx-traits/src/auth_storage_query.rs

/// Auth 表存储查询 — 由 cmx-auth 自行实现
///
/// 从 UserAuthQuery 拆分出的 Auth 专属方法，操作 cmx_auth_* 表
#[async_trait]
pub trait AuthStorageQuery: Send + Sync {
    /// 新增或更新 API Key
    async fn upsert_api_key(
        &self,
        key_prefix: &str,
        key_hash: &str,
        user_id: Option<&str>,
        service_name: Option<&str>,
        scopes: &[String],
        description: Option<&str>,
    ) -> Result<(), TraitError>;

    /// 按 prefix 查询 API Key
    async fn get_api_key_by_prefix(&self, key_prefix: &str) -> Result<Option<ApiKeyData>, TraitError>;

    /// 记录 Token 事件
    async fn record_token_event(
        &self,
        event_type: &str,
        user_id: &str,
        jti: &str,
        detail: &str,
    ) -> Result<(), TraitError>;

    /// 查询 OAuth2 客户端配置
    async fn get_oauth2_client(&self, client_id: &str) -> Result<Option<OAuth2ClientData>, TraitError>;
}
```

> **重要说明**：
> - `UserAuthQuery` 不含 `db_id` 参数，由 impl 持有 `db_id: String` 字段（优先 config.auth_db_id，fallback default_db_id）
> - **Auth 表职责划分**：cmx_auth_api_key / cmx_auth_token_event / cmx_auth_client 等 Auth 表由 cmx-auth 自行管理（使用自己的 DbBmc），UserAuthQueryImpl 不再操作这些表
> - **AuthStorageQuery 拆分**：cmx-traits 中的 `UserAuthQuery` trait 已移除 Auth 表方法（upsert_api_key、get_api_key_by_prefix、record_token_event、get_oauth2_client），改由独立的 `AuthStorageQuery` trait 承载。cmx-auth 的 AuthServiceImpl 需同时实现 UserAuthQuery（IAM 表查询）和 AuthStorageQuery（Auth 表操作）
> - UserAuthQuery 新增 `update_last_login(user_id, ip)` 方法，供 cmx-auth 登录流程更新 last_login_at/last_login_ip
> - UserAuthQuery 实现是 cmx-auth 能正常运行的前提，应在 IAM 开发中优先实现

## 六、权限 Enforcement 设计

### 6.1 mw_auth 中间件

> mw_auth 已存在于 `crates/libs/cmx-api/src/middleware/mw_auth.rs`，属于 cmx-auth 范围。

mw_auth 的职责：
1. 提取请求中的 Bearer Token 或 X-API-Key
2. 调用 `AuthService::validate_token()` 或 `validate_api_key()` 进行认证
3. 认证成功后，将 `AuthContext` 注入到请求扩展（request extensions）中
4. 后续 handler 通过 `SVRContext.auth_context` 获取认证信息

> IAM 方案声明 mw_auth 属于 cmx-auth 范围，已在 cmx-auth 开发时完成。SVRContext.auth_context 由 mw_auth 填充。

### 6.2 mw_permission 中间件

在 mw_auth 之后添加 mw_permission 中间件，实现基于权限码的访问控制：

1. 从请求扩展获取 AuthContext
2. 查询路由→权限码映射表（配置驱动）
3. 检查 AuthContext.permissions 是否包含所需权限码
4. **`system:all` 权限短路放行**（超级管理员无需逐一检查）
5. 无权限返回 403

**路由→权限码映射配置示例（TOML）**：

```toml
[iam_permissions]
"/api/iam/user/create" = "user:create"
"/api/iam/user/update" = "user:update"
"/api/iam/user/delete" = "user:delete"
"/api/iam/role/assign-permissions" = "role:assign_perm"
```

### 6.3 权限缓存策略

- **认证阶段**（mw_auth）：通过 `UserAuthQuery::get_user_permissions()` 一次性加载权限到 AuthContext
- **权限检查阶段**（mw_permission）：直接查 `svr_ctx.auth_context.permissions`（内存），**不查数据库**
- **PermissionChecker 作为 fallback**：AuthContext 缺失/过期时使用
- **权限变更实时生效**：角色/权限变更时，清除相关用户的 Redis 会话缓存，触发 re-auth（JWT 中的 permissions 在签发时固定，变更后在下次 token refresh 或强制 re-auth 时生效）

### 7.2 Handler 文件结构

> 遵循 `20260612_平台级基础设施与双协议架构重构方案.md` 的架构规划：cmx-api 为**薄层 HTTP 适配**，IAM handler 模块**仅包含 `handler.rs + mod.rs`**，不单独定义 request.rs/response.rs。Entity/Filter 类型直接从 cmx-iam 导入。

```
cmx-api/src/rest/handlers/iam/
  ├── mod.rs                       # 路由聚合 + 汇总导出
  │
  ├── user/                        # 用户管理
  │   ├── mod.rs                   # 模块导出 + routes() 注册
  │   └── handler.rs               # 自定义 handler（create/update 含密码哈希，assign_roles / get_roles）
  │                                 #   导入 cmx_iam::user::{UserBmc, UserForCreate, UserFilter, ...}
  │
  ├── role/                        # 角色管理
  │   ├── mod.rs
  │   └── handler.rs               # 自定义 handler（assign_permissions / get_permissions）
  │                                 #   导入 cmx_iam::role::{RoleBmc, RoleForCreate, RoleFilter, ...}
  │
  └── permission/                  # 权限管理
      ├── mod.rs
      └── handler.rs               # 自定义 handler（get_permission_tree）
                                      #   导入 cmx_iam::permission::{PermissionBmc, PermissionFilter, ...}
```

**关键区别（vs 旧模式）**：
- **不建 request.rs**：`AssignRolesRequest` / `AssignPermissionsRequest` 等 IAM 专用请求体定义在 **cmx-iam 的 entity.rs** 中
- **不建 response.rs**：直接使用 cmx-iam 的 Entity（如 `User`、`Role`）作为响应类型
- handler.rs 仅做：请求解析 → 调用 `cmx_state.iam()` 中的 trait 方法 → 包装 `ApiResp` 返回

### 9.1 axum-handler-generator 技能更新内容

在技能 SKILL.md 的「九、Handler 文件组织结构」之后新增章节，描述**新架构（cmx-iam 等业务 crate）的薄层 handler 模式**：

```markdown
## 十一、新架构薄层 Handler 模式（cmx-iam / cmx-auth 等）

> 适用于遵循 `20260612_平台级基础设施与双协议架构重构方案.md` 架构的业务 crate。

### 11.1 与旧模式的区别

| 维度 | 旧模式（如 plugin handler） | 新架构薄层模式（如 iam handler） |
|------|---------------------------|-------------------------------|
| 文件结构 | mod.rs + handler.rs + request.rs + response.rs | **仅 mod.rs + handler.rs** |
| Entity/Filter 定义位置 | cmx-api handler 模块内 | **业务 crate（如 cmx-iam）** |
| 请求/响应类型 | request.rs / response.rs 独立定义 | **直接复用业务 crate 的 Entity** |
| handler 职责 | 请求解析 + 业务逻辑 + 响应构造 | **仅请求解析 → 调用 trait → 包装 ApiResp** |

### 11.2 薄层 Handler 文件结构

handlers/iam/
  ├── mod.rs                 # 汇总导出 + 路由聚合
  ├── user/
  │   ├── mod.rs             # 路由注册 + 从 cmx-iam 导入类型
  │   └── handler.rs         # 自定义 handler（导入 cmx_iam::{UserBmc, UserForCreate, ...}）
  ├── role/
  │   ├── mod.rs
  │   └── handler.rs
  └── permission/
      ├── mod.rs
      └── handler.rs

### 11.3 导入规范

薄层 handler 从业务 crate 直接导入 Entity/Filter/请求体类型：

use cmx_iam::user::{UserBmc, UserForCreate, UserForUpdate, UserFilter, AssignRolesRequest};
use cmx_iam::role::{RoleBmc, RoleForCreate, RoleFilter, Role};
use cmx_iam::permission::{PermissionBmc, PermissionForCreate, PermissionFilter, Permission};

不使用 super::request::* 或 super::response::*。

### 11.4 自定义 Handler 场景

当 ForCreate/ForUpdate 不 derive Fields（含非 DB 列如 password）时，必须使用自定义 handler：
- 用户 create/update：UserForCreate/UserForUpdate 不 derive Fields，需自定义 handler 调用 Service 层转换
- 角色/权限 CRUD：ForCreate/ForUpdate derive Fields，可使用通用 GenericCrudService handler
```

## 十一、假设与决策

| 决策 | 理由 |
|------|------|
| 权限采用 `resource:action` 编码 | 企业级标准，清晰可扩展 |
| User Entity 不包含 password_hash | 防止 API 泄漏敏感数据 |
| 角色-权限为全量替换模式 | 简化前端操作，避免增量同步复杂性 |
| DataScope 定义在 cmx-traits 而非 cmx-iam | 未来 BMC 层（cmx-database）也需要感知 |
| PermissionChecker 有默认实现 | 按需启用，不影响现有无认证接口 |
| 本次不建 cmx_role_data_scope 表 | 避免过度设计，待组织机构模块就绪后再建 |
| 用户表无 dept_id 字段 | 组织机构在 Phase 6 实现，届时通过 cmx_user_org 关联表处理 |
| **用户表含 org_id 字段** | cmx-auth JWT Claims 中已有 org_id，实际 SQL 已包含此字段，用于标识用户所属组织（当前作为多租户标识，未来 SaaS 场景可能新增独立 tenant_id） |
| **基础数据模型放 cmx-core** | WASM 插件需感知调用者身份（User/Role/Permission），cmx-core 是 WASM 可达的共享类型层。cmx-core 已有 DomainEntity 等纯数据结构先例，无 sqlx 依赖 |
| **ForCreate/ForUpdate/BMC/Filter 放 cmx-iam** | 这些是服务端 CRUD 关注点，WASM 不需要，cmx-iam 拥有 sqlx+modql+database 完整能力 |
| **cmx-core 结构体无 Fields/FromRow derive** | cmx-core 不依赖 sqlx，基础模型为纯 Serialize/Deserialize；Fields/FromRow 在 cmx-iam 的 ForCreate/ForUpdate 上 |
| **AuthContext 不在 model/iam/ 重复定义** | cmx-auth 开发时已在 `model/service/context.rs` 创建 AuthContext（含 session_id/device_type/auth_method 等扩展字段），IAM 直接复用 |
| **UserAuthQuery 由 cmx-iam 实现** | cmx-auth 不直接依赖 cmx-iam，通过 trait 解耦。UserAuthQueryImpl 仅操作 IAM 表（cmx_user/cmx_role/cmx_permission 及关联表） |
| **Auth 表由 cmx-auth 自行管理** | cmx_auth_api_key/cmx_auth_token_event/cmx_auth_client 等 Auth 表属于 cmx-auth 职责，通过独立 AuthStorageQuery trait 访问，不应由 cmx-iam 的 UserAuthQueryImpl 操作 |
| **权限表用 resource_type 而非 type** | `type` 是 Rust 关键字，需 `r#type` 转义；`resource_type` 语义更清晰，且与 PermissionFilter 的 `resource_type` 字段一致 |
| **关联表需 UNIQUE 约束** | 防止重复关联（如同一用户被分配同一角色多次），实际 SQL 缺少此约束需补充 |
| **trait 方法不含 db_id 参数** | IAM 操作优先使用 config.auth_db_id，fallback 到 default_db_id，由 Service impl 持有 db_id 字段，简化 trait 调用签名 |
| **UserForCreate 不 derive Fields** | 含明文 password（非 DB 列），不能直接用于 GenericCrudService，需 Service 层转换为 UserForInsert |
| **内置角色保护通过 IamConfig** | 不在 DB 中加 is_builtin 字段，通过配置 `builtin_role_codes: Vec<String>` 实现，灵活且避免 schema 变更 |
| **关联表 assign 使用物理删除** | 关联记录（cmx_user_role, cmx_role_permission）是"当前状态"而非"历史数据"，assign 操作物理删除旧关联 + 插入新关联 |
| **主表删除时级联物理删除关联** | 删除主表（cmx_user, cmx_role）软删除时，同步物理删除对应关联表记录 |
| **并发安全 Last-Write-Wins** | assign_roles/assign_permissions 全量替换在事务内执行，通过行级锁保证原子性。并发操作同一用户角色分配时，后执行请求覆盖先前结果（Last-Write-Wins），企业级场景建议前端提交时重新加载最新数据 |
| **last_login_at 由 cmx-auth 更新** | last_login_at 和 last_login_ip 由 cmx-auth 登录流程更新，通过 UserAuthQuery.update_last_login(user_id, ip) 方法 |
| **权限变更实时生效机制** | 角色/权限变更时清除相关用户 Redis 会话缓存触发 re-auth。JWT 含签发时权限快照，变更在下次 token refresh 或强制 re-auth 时生效 |
| **system:all 短路放行** | mw_permission 和 PermissionChecker.has_permission 均先检查 system:all，超级管理员无需逐一检查具体权限码 |
| **org_id 作为当前租户标识** | 当前使用 org_id 标识多租户，未来 SaaS 场景可能新增独立 tenant_id 字段 |
| **UserForUpdate 不含 username/org_id** | username 修改影响登录凭证，org_id 修改影响组织归属，均需通过专门的管理员 API 操作，不通过普通用户更新接口 |
| **本次不支持角色继承与层级** | RBAC 模型无 `parent_role_id`，角色保持扁平，不支持树形结构和权限继承，当前业务场景无需求，后续按需扩展 |
| **审计日志尽力而为** | 审计写入失败不阻塞业务，但通过 `warn!` 日志告警。审计在事务提交成功后记录，保证审计与业务状态一致 |
| **API 路由暂不加版本前缀** | IAM 路由 `/api/iam/...` 不含版本号，与现有 `/api/auth/...` 一致。版本化属全局路由层职责，后续全局统一添加 `/api/v1/` 前缀 |
| **org_id 组织调动需管理员 API** | UserForUpdate 不含 org_id，普通用户不能自行修改组织归属。未来可通过专门的管理员 API（如 `transfer_org`）实现组织调动，当前预留 |
| **审计日志脱敏处理** | create/update 用户审计日志不序列化含 password 的完整结构体，仅记录 username/email/password_changed: bool，防止明文密码泄漏 |
| **audit_write 抽取为 AuditHelper trait** | 三个 ServiceImpl 中 audit_write 方法完全一致，通过 AuditHelper trait + 默认实现消除重复（DRY 原则），各 ServiceImpl 仅需实现 audit_logger() |
| **Service trait 定义在 cmx-iam 而非 cmx-traits** | UserService/RoleService/PermissionService 的方法签名引用 cmx-iam 类型（ForCreate/Filter），放 cmx-traits 会循环依赖。与 cmx-biz 模式一致：业务 trait 在业务 crate |
