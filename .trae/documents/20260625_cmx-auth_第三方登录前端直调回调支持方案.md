# 第三方 OAuth2 登录前端直调回调支持方案

> 模块：`cmx-auth` / `cmx-api`
> 日期：2026-06-25
> 目标：在保持现有"后端回调 + 一次性码换 Token"流程完全兼容的前提下，让现有 `exchange` 接口同时支持"Provider 直接回调前端页面"的场景，前端无感知差异。

***

## 一、背景与现状分析

### 1.1 现有流程（后端回调模式）

当前 `cmx-auth` 的第三方 OAuth2 登录流程（见 [USAGE.md](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-infra/cmx-auth/USAGE.md#L1025-L1043)）：

1. 前端 `GET /api/auth/oauth2/provider/{provider}/authorize` → 后端 302 到 Provider 授权页
2. Provider 授权后 302 回调到**后端** `GET /api/auth/oauth2/{provider}/callback?code=XXX&state=YYY`
3. 后端 [oauth2\_provider\_callback](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-api/src/handlers/auth/oauth2_provider_handler.rs#L83-L115) 调用 [handle\_oauth2\_callback](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-infra/cmx-auth/src/auth_service_impl.rs#L1697-L1778)：

   * 原子消费 `state`（防重放）

   * 用 `code` 向 Provider 换 `access_token`

   * 获取用户信息 → 关联/注册用户 → 签发本平台 TokenPair

   * **签发一次性回调授权码**（30s TTL，存 Redis，key: `auth:oauth2:provider:callback:{code}`）
4. 后端 302 跳转到 `{frontend_callback_url}?code={one_time_code}&state={state}`
5. 前端 `POST /api/auth/oauth2/provider/exchange {code, state}` → 后端 [exchange\_oauth2\_callback\_code](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-infra/cmx-auth/src/auth_service_impl.rs#L1797-L1818) 原子消费回调码，返回 TokenPair

### 1.2 关键发现

* 现有 `exchange` 接口接收的 `code` 是**后端签发的一次性回调授权码**，**不是** Provider 返回的原始授权码。

* 现有 `callback` 接口是后端接收 Provider 回调、处理后再 302 给前端。

* **目前没有**任何接口能直接接收 Provider 的原始 `code`/`state` 并返回 TokenPair。

### 1.3 用户需求

1. 支持 Provider 配置的 `redirect_uri` 直接指向前端页面（而非后端接口）的场景：Provider 授权后直接 302 到前端页面，前端拿到 Provider 的原始 `code` 和 `state`。
2. **前端无感知**：前端不应感知"后端回调模式"与"前端直调模式"的差异，应始终调用同一个接口换 Token。
3. 要求**最小修改**，不破坏现有流程。

### 1.4 可行性结论

完全可行。关键洞察：**两种模式的** **`code`** **存储位置不同，可据此自动判断**。

* 后端回调模式：`code` 是后端签发的一次性回调码，存储在 Redis key `auth:oauth2:provider:callback:{code}`

* 前端直调模式：`code` 是 Provider 原始授权码，**不在** Redis 中；但其 `state` 存储在 Redis key `auth:oauth2:provider:state:{state}`

因此可以让现有 `exchange` 接口先尝试消费 callback\_code，失败后再尝试消费 state 走前端直调流程，前端始终调用同一个 `POST /api/auth/oauth2/provider/exchange {code, state}`，后端自动路由到正确模式。

***

## 二、方案设计

### 2.1 核心思路：统一 exchange 接口，后端自动判断模式

**前端始终调用同一个接口**：`POST /api/auth/oauth2/provider/exchange {code, state}`

**后端判断逻辑**（在 Service 层）：

```
1. 尝试消费 callback_code（Redis: auth:oauth2:provider:callback:{code}）
   ├─ 成功 → 后端回调模式：反序列化 CallbackCodeData，返回存储的 TokenPair
   └─ 失败（key 不存在）→ 步骤 2

2. 尝试消费 state（Redis: auth:oauth2:provider:state:{state}）
   ├─ 成功 → 前端直调模式：获取 provider，执行核心流程（换 token、获取用户信息、
   │         关联用户、签发 TokenPair），返回 TokenPair
   └─ 失败（key 不存在）→ 返回错误"授权码或 state 无效或已过期"
```

### 2.2 为什么能让前端无感知

| 维度          | 后端回调模式                                    | 前端直调模式                                    | 前端感知          |
| ----------- | ----------------------------------------- | ----------------------------------------- | ------------- |
| 前端拿到的 code  | 后端签发的一次性回调码                               | Provider 原始授权码                            | 都是 `code` 字符串 |
| 前端拿到的 state | authorize 阶段生成的 state                     | authorize 阶段生成的 state                     | 完全一致          |
| 前端调用的接口     | `POST /api/auth/oauth2/provider/exchange` | `POST /api/auth/oauth2/provider/exchange` | 完全一致          |
| 请求体         | `{code, state}`                           | `{code, state}`                           | 完全一致          |
| 响应体         | `ExchangeCodeResponse`                    | `ExchangeCodeResponse`                    | 完全一致          |

前端代码**完全不需要修改**，只需在 Provider 配置中调整 `redirect_uri` 即可切换模式。

### 2.3 安全机制（全部复用现有实现）

* **state 原子消费**：复用 [consume\_provider\_state](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-infra/cmx-auth/src/oauth2/store.rs) 的 Lua 脚本（GET+DEL），防 CSRF 重放

* **callback\_code 原子消费**：复用 [consume\_callback\_code](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-infra/cmx-auth/src/oauth2/store.rs) 的 Lua 脚本（GET+DEL），防重放

* **state 中 provider 校验**：前端直调模式下，校验 state 中存储的 provider 与请求一致

* **redirect\_uri 服务端固定**：复用 `provider_impl.redirect_uri()`，前端不可覆盖，防 Open Redirect

* **state 二次校验**：Handler 层校验请求体 `state` 与结果中 `state` 一致（与现有 exchange 接口一致）

* **审计日志**：复用现有 `audit_log("oauth2_login", ...)`

### 2.4 两种模式的配置差异

| 模式         | `redirect_uri` 配置                                 | Provider 回调到  | 前端行为                     |
| ---------- | ------------------------------------------------- | ------------- | ------------------------ |
| 后端回调模式（现有） | 后端接口 URL `/api/auth/oauth2/{provider}/callback`   | 后端 → 302 → 前端 | 从 302 URL 取 code/state   |
| 前端直调模式（新增） | 前端页面 URL `https://your-domain.com/login/callback` | 前端页面          | 从 URL query 取 code/state |

两种模式可共存（不同 Provider 配置不同 `redirect_uri`），前端 exchange 接口统一处理。

## 三、具体修改清单

### 3.1 `cmx-auth`：重构 Service 层逻辑

**文件**：[crates/libs/cmx-infra/cmx-auth/src/auth\_service\_impl.rs](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-infra/cmx-auth/src/auth_service_impl.rs)

#### 3.1.1 抽取内部方法 `process_provider_code_after_state`

将 [handle\_oauth2\_callback](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-infra/cmx-auth/src/auth_service_impl.rs#L1697-L1778) 中**消费 state 之后**的逻辑（步骤 2-7：获取 Provider → 换 token → 获取用户信息 → 关联用户 → 签发 TokenPair → 审计）抽取为私有方法，**不含 state 消费**：

```rust
/// 处理 Provider 授权码的核心逻辑（不含 state 消费）。
///
/// 前置条件：state 已由调用方消费，并校验 provider 一致性。
///
/// 供 `handle_oauth2_callback`（后端回调模式）和 `exchange_oauth2_callback_code`
/// （统一 exchange，前端直调分支）复用。
async fn process_provider_code_after_state(
    &self,
    provider: &str,
    code: &str,
    device_info: Option<DeviceInfo>,
) -> Result<(cmx_traits::auth::TokenPair, bool, String), AuthError> {
    // 1. 获取 Provider
    let registry = crate::oauth2::OAuth2ProviderRegistry::get_global()
        .ok_or(AuthError::Internal("OAuth2 Provider 注册表未初始化".to_string()))?;
    let provider_impl = registry.get_provider(provider)?;

    // 2. 获取 redirect_uri（从 Provider 配置中获取）
    let redirect_uri = provider_impl.redirect_uri().to_string();

    // 3. 交换 Token
    let token_response = provider_impl.exchange_code(code, &redirect_uri).await?;
    tracing::info!(provider = %provider, "Token 交换成功");

    // 4. 获取用户信息
    let user_info = provider_impl.get_user_info(&token_response).await?;
    tracing::info!(provider = %provider, provider_user_id = %user_info.provider_user_id, "用户信息获取成功");

    // 5. 关联/注册用户
    let link_result = self.account_linker.find_or_link(provider, &user_info.provider_user_id, &user_info).await?;
    let (user_id, is_new) = match link_result {
        crate::oauth2::provider::LinkResult::Linked { user_id, is_new } => (user_id, is_new),
        crate::oauth2::provider::LinkResult::BindingRequired { .. } => {
            return Err(AuthError::OAuth2("账号未注册，请联系管理员开通".to_string()));
        }
    };

    // 6. 签发本平台 Token
    let token_pair = self.authenticate(
        Credentials::ThirdPartyOAuth2 {
            provider: provider.to_string(),
            provider_user_id: user_info.provider_user_id,
            user_id: user_id.clone(),
        },
        device_info,
    ).await?;

    // 7. 审计日志：第三方 OAuth2 登录
    self.audit_log("oauth2_login", cmx_audit::OperationResult::Success, &user_id, Some("user"), Some(&user_id), Some(serde_json::json!({
        "provider": provider,
        "is_new": is_new,
    }))).await;

    Ok((token_pair, is_new, user_id))
}
```

#### 3.1.2 重构 `handle_oauth2_callback`

将原方法体替换为：消费 state → 调用 `process_provider_code_after_state` → 签发一次性回调码：

```rust
async fn handle_oauth2_callback(
    &self,
    provider: &str,
    code: &str,
    state: &str,
    device_info: Option<DeviceInfo>,
) -> std::result::Result<OAuth2CallbackResult, AuthError> {
    // 1. 原子消费 state，获取 provider 名称
    let stored_provider = self.oauth2_store.consume_provider_state(state).await
        .map_err(|e| AuthError::Internal(e.to_string()))?
        .ok_or(AuthError::OAuth2("OAuth2 Provider state 无效或已过期".to_string()))?;
    if stored_provider != provider {
        return Err(AuthError::OAuth2("State 中的 provider 与请求不匹配".to_string()));
    }

    // 2. 执行核心流程（换 token、获取用户信息、关联用户、签发 TokenPair）
    let (token_pair, is_new, _user_id) = self.process_provider_code_after_state(provider, code, device_info).await?;

    // 3. 签发一次性回调授权码（存储 TokenPair + is_new + provider）
    let callback_code = uuid::Uuid::new_v4().to_string();
    let callback_data = CallbackCodeData {
        access_token: token_pair.access_token,
        refresh_token: token_pair.refresh_token,
        token_type: token_pair.token_type,
        access_expires_at: token_pair.access_expires_at,
        refresh_expires_at: token_pair.refresh_expires_at,
        is_new,
        provider: provider.to_string(),
        state: state.to_string(),
    };
    let callback_data_json = serde_json::to_string(&callback_data)
        .map_err(|e| AuthError::Internal(e.to_string()))?;
    self.oauth2_store.store_callback_code(&callback_code, &callback_data_json).await
        .map_err(|e| AuthError::Internal(e.to_string()))?;

    Ok(cmx_traits::auth::OAuth2CallbackResult {
        callback_code,
        state: state.to_string(),
        is_new,
        provider: provider.to_string(),
    })
}
```

#### 3.1.3 改造 `exchange_oauth2_callback_code`（核心：统一两种模式）

将现有 [exchange\_oauth2\_callback\_code](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-infra/cmx-auth/src/auth_service_impl.rs#L1797-L1818) 改造为统一接口，新增 `device_info` 参数：

```rust
async fn exchange_oauth2_callback_code(
    &self,
    code: &str,
    state: &str,
    device_info: Option<DeviceInfo>,
) -> std::result::Result<OAuth2CallbackExchangeResult, AuthError> {
    // 模式 1：后端回调模式 —— 尝试消费一次性回调码
    if let Some(json) = self.oauth2_store.consume_callback_code(code).await
        .map_err(|e| AuthError::Internal(e.to_string()))? {
        let callback_data: CallbackCodeData = serde_json::from_str(&json)
            .map_err(|e| AuthError::Internal(format!("回调数据反序列化失败: {}", e)))?;

        // 校验 state 一致性（防 CSRF）
        if !state.is_empty() && state != callback_data.state {
            return Err(AuthError::OAuth2("state 不匹配".to_string()));
        }

        return Ok(OAuth2CallbackExchangeResult {
            access_token: callback_data.access_token,
            refresh_token: callback_data.refresh_token,
            token_type: callback_data.token_type,
            access_expires_at: callback_data.access_expires_at,
            refresh_expires_at: callback_data.refresh_expires_at,
            is_new: callback_data.is_new,
            provider: callback_data.provider,
            state: callback_data.state,
        });
    }

    // 模式 2：前端直调模式 —— 尝试消费 state，获取 provider
    let provider = self.oauth2_store.consume_provider_state(state).await
        .map_err(|e| AuthError::Internal(e.to_string()))?
        .ok_or(AuthError::OAuth2CallbackCodeInvalid)?;

    // 执行核心流程（换 token、获取用户信息、关联用户、签发 TokenPair）
    let (token_pair, is_new, _user_id) = self.process_provider_code_after_state(&provider, code, device_info).await?;

    Ok(OAuth2CallbackExchangeResult {
        access_token: token_pair.access_token,
        refresh_token: token_pair.refresh_token,
        token_type: token_pair.token_type,
        access_expires_at: token_pair.access_expires_at,
        refresh_expires_at: token_pair.refresh_expires_at,
        is_new,
        provider: provider,
        state: state.to_string(),
    })
}
```

> **注意**：模式 1 失败后才会走模式 2。由于 `consume_callback_code` 是原子消费（GET+DEL），即使 key 不存在也不会有副作用，安全可重试。

///
/// **后端回调模式**：`code` 为 `handle_oauth2_callback` 签发的一次性回调码，

/// # Errors

### 3.3 `cmx-api`：改造 Handler 传递 device\_info

**文件**：[crates/libs/cmx-api/src/handlers/auth/oauth2\_provider\_handler.rs](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-api/src/handlers/auth/oauth2_provider_handler.rs#L152-L188)

改造 [oauth2\_provider\_exchange](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-api/src/handlers/auth/oauth2_provider_handler.rs#L152-L188) handler，提取 device\_info 并传递给 service：

```rust
/// 用授权码换 TokenPair（统一接口，后端自动判断模式）
pub async fn oauth2_provider_exchange(
    State(state): State<CmxAppState>,
    headers: HeaderMap,
    Json(req): Json<ExchangeCodeRequest>,
) -> Result<Json<ApiResp<ExchangeCodeResponse>>> {
    let auth_service = state.auth_service().ok_or_else(|| {
        Error::InternalError("认证服务未初始化".to_string())
    })?;

    // 提取设备信息（前端直调模式签发 TokenPair 时使用）
    let device_info = extract_device_info(&headers);

    let exchange_result = auth_service.exchange_oauth2_callback_code(&req.code, &req.state, device_info).await.map_err(|e| {
        error!(error = %e, "授权码换 Token 失败");
        match e {
            cmx_traits::auth::AuthError::OAuth2CallbackCodeInvalid => {
                Error::Unauthorized("授权码或 state 无效或已过期".to_string())
            }
            cmx_traits::auth::AuthError::OAuth2(msg) => {
                Error::BadRequest(msg)
            }
            cmx_traits::auth::AuthError::OAuth2ProviderNotFound(_) => {
                Error::BadRequest("Provider 不存在".to_string())
            }
            cmx_traits::auth::AuthError::OAuth2ProviderUnavailable(_) => {
                Error::BadRequest("Provider 服务不可用".to_string())
            }
            cmx_traits::auth::AuthError::OAuth2ProviderTokenError(_) => {
                Error::BadRequest("Provider 授权失败".to_string())
            }
            cmx_traits::auth::AuthError::OAuth2ProviderUserInfoError(_) => {
                Error::BadRequest("Provider 用户信息获取失败".to_string())
            }
            other => Error::InternalError(other.to_string()),
        }
    })?;

    // 校验 state 一致性（防 CSRF，Service 层已校验，Handler 层二次防护）
    if !req.state.is_empty() && req.state != exchange_result.state {
        return Err(Error::Unauthorized("state 不匹配".to_string()));
    }

    let response = ExchangeCodeResponse {
        access_token: exchange_result.access_token,
        refresh_token: exchange_result.refresh_token,
        token_type: exchange_result.token_type,
        access_expires_at: exchange_result.access_expires_at,
        refresh_expires_at: exchange_result.refresh_expires_at,
        is_new: exchange_result.is_new,
        provider: exchange_result.provider,
        state: exchange_result.state,
    };

    Ok(Json(ApiResp::ok(response)))
}
```

**关键变更**：

1. 新增 `headers: HeaderMap` 参数
2. 调用 `extract_device_info(&headers)` 提取设备信息
3. 调用 `auth_service.exchange_oauth2_callback_code(&req.code, &req.state, device_info)` 传递 state 和 device\_info
4. 错误处理增强：区分 `OAuth2CallbackCodeInvalid`（统一错误信息）和 `OAuth2`（具体业务错误）
5. 移除原 Handler 层的 state 校验（已移到 Service 层），但保留作为二次防护

## 四、配置与使用说明

### 4.1 配置示例

#### 后端回调模式（现有，保持不变）

```toml
[auth.oauth2]
frontend_callback_url = "https://your-domain.com/login/callback"

[[auth.oauth2.providers]]
name = "google"
# redirect_uri 指向后端接口
redirect_uri = "https://api.your-domain.com/api/auth/oauth2/google/callback"
enabled = true
```

#### 前端直调模式（新增）

```toml
[auth.oauth2]
frontend_callback_url = "https://your-domain.com/login/callback"

[[auth.oauth2.providers]]
name = "google"
# 关键：redirect_uri 指向前端页面
redirect_uri = "https://your-domain.com/login/callback"

```

### 4.2 前端使用流程（统一，前端无感知）

无论哪种模式，前端流程完全一致：

1. 前端 `GET /api/auth/oauth2/providers` 获取 Provider 列表
2. 前端跳转浏览器到 `GET /api/auth/oauth2/provider/{provider}/authorize`（后端 302 到 Provider 授权页）
3. 用户在 Provider 授权
4. **Provider 302 回调**（回调地址由 `redirect_uri` 配置决定）：

   * 后端回调模式：回调到后端 → 后端处理 → 302 到前端 `{frontend_callback_url}?code={one_time_code}&state={state}`

   * 前端直调模式：回调到前端页面 `https://your-domain.com/login/callback?code={provider_code}&state={state}`
5. 前端在回调页面提取 `code` 和 `state`，调用 **`POST /api/auth/oauth2/provider/exchange`**（body: `{code, state}`）
6. 后端自动判断模式，返回 `ExchangeCodeResponse`（含 Access + Refresh Token）
7. 前端存储 Token，完成登录

**前端代码完全不需要修改**，模式切换仅靠后端 `redirect_uri` 配置完成。

### 4.3 两种模式对比

| 步骤            | 后端回调模式                             | 前端直调模式                         |
| ------------- | ---------------------------------- | ------------------------------ |
| Provider 回调到  | 后端接口                               | 前端页面                           |
| 前端拿到的 code    | 后端签发的一次性回调码                        | Provider 原始授权码                 |
| 中间跳转次数        | 2 次 302（Provider→后端→前端）            | 1 次 302（Provider→前端）           |
| exchange 接口行为 | 消费 callback\_code，返回已签发的 TokenPair | 消费 state，执行完整流程签发 TokenPair    |
| **前端调用方式**    | `POST /exchange {code, state}`     | `POST /exchange {code, state}` |

## 五、假设与决策

### 5.1 假设

1. `OAuth2ProviderConfig.redirect_uri` 配置为前端页面 URL 时，Provider 接受该 URL 并在授权后直接回调前端（符合 OAuth2 规范）。
2. 前端页面能正确从 URL query 中提取 `code` 和 `state`。
3. Provider 的 `code` 有效期（通常 10 分钟）足够前端发起 `exchange` 请求。
4. `consume_callback_code` 在 key 不存在时返回 `Ok(None)`，无副作用（基于现有 Lua 脚本实现确认）。

### 5.2 决策

1. **统一到现有** **`exchange`** **接口**：不新增路由，前端无感知模式差异。用户反馈明确要求"让前端无感知"，这是最优解。
2. **后端通过 code 存储位置自动判断模式**：先查 callback\_code（后端回调模式），再查 state（前端直调模式）。判断逻辑清晰，无歧义。
3. **抽取** **`process_provider_code_after_state`** **私有方法**：避免 `handle_oauth2_callback` 和 `exchange_oauth2_callback_code` 的前端直调分支逻辑重复，保证三条路径行为一致。
4. **复用** **`ExchangeCodeRequest`** **/** **`ExchangeCodeResponse`** **/** **`OAuth2CallbackExchangeResult`**：不新增数据结构，前端无需适配新格式。
5. **trait 方法签名变更（新增 state + device\_info 参数）**：这是必要的 breaking change，因为前端直调模式需要 state 来消费获取 provider，需要 device\_info 来签发 TokenPair。由于该方法属于 OAuth2 内部流程，调用点有限。
6. **state 校验移到 Service 层**：后端回调模式下，Service 层校验请求 state 与 CallbackCodeData.state 一致；前端直调模式下，state 已被消费，返回时携带原 state。Handler 层保留二次校验作为防护。
7. **错误信息统一**：`OAuth2CallbackCodeInvalid` 的错误信息从"授权码无效或已过期"改为"授权码或 state 无效或已过期"，覆盖两种模式的失败场景。

## 六、验证步骤

### 6.1 编译验证

```bash
rtk cargo check -p cmx-traits -p cmx-auth -p cmx-api
```

确认 trait 签名变更、impl 实现、handler 改造全部编译通过。需特别注意是否有 `AuthService` 的其他 mock 实现。

### 6.2 功能验证 - 后端回调模式（回归）

1. 配置 Provider，`redirect_uri` 指向后端接口
2. 走完整 `authorize` → `callback` → `exchange` 流程
3. 确认 exchange 接口返回 TokenPair，功能正常
4. 确认现有流程未受重构影响

### 6.3 功能验证 - 前端直调模式（新增）

1. 配置 Provider，`redirect_uri` 指向前端页面 URL
2. 调用 `GET /api/auth/oauth2/provider/{provider}/authorize`，确认 302 到 Provider 时 `redirect_uri` 为前端 URL
3. 模拟 Provider 回调到前端页面，前端拿到 `code`/`state`
4. 调用 `POST /api/auth/oauth2/provider/exchange`（body: `{code, state}`），确认返回 TokenPair
5. 重复调用同一 `code`/`state`，确认返回"授权码或 state 无效或已过期"错误（防重放）
6. 篡改 `state`，确认返回"state 不匹配"错误（防 CSRF）

### 6.4 错误场景验证

1. 传入不存在的 code 和 state → 返回"授权码或 state 无效或已过期"
2. 后端回调模式下篡改 state → 返回"state 不匹配"
3. 前端直调模式下 state 中 provider 与请求不一致 → 返回"State 中的 provider 与请求不匹配"
