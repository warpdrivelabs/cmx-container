# 请求追踪中间件性能优化重构方案

## 一、背景与问题分析

### 1.1 当前问题

现有 [mw\_trace.rs](file:///media/yqs/工作/rustspace/cmx/cmx-container/crates/libs/cmx-api/src/middleware/mw_trace.rs) 存在严重性能瓶颈：

| 问题            | 影响                                                 |
| ------------- | -------------------------------------------------- |
| **无条件读取请求体**  | 每个请求都将 body 读入内存（上限 10MB），即使日志级别为 INFO 也会执行        |
| **无条件读取响应体**  | 每个响应都将 body 消费并重建（上限 5MB），JSON 反序列化 + 递归脱敏开销大      |
| **JSON 解析开销** | 对请求体和响应体都做 `serde_json::from_slice` 解析，CPU 密集      |
| **字符串分配**     | `sanitize_json_value` 递归重建整个 JSON 树，大量 `String` 分配 |
| **无级别感知**     | 不管 RUST\_LOG 是 info 还是 debug，都执行全部昂贵的操作            |

### 1.2 性能影响量化

在生产环境（`RUST_LOG=info`）下，每个 HTTP 请求的 trace 中间件额外开销：

* 1 次 `body->bytes` 转换（请求体，最大 10MB）

* 1 次 `body->bytes` 转换（响应体，最大 5MB）

* 1-2 次 JSON 反序列化 + 序列化

* 大量字符串分配和拷贝

这些操作在生产环境完全不需要，但当前代码无条件执行。

***

## 二、设计目标

1. **INFO 级别（生产环境）**：零开销，仅记录方法、路径、查询参数、状态码、耗时
2. **DEBUG 级别（开发调试）**：完整请求/响应追踪，包含请求头、请求体、响应体（脱敏）
3. **文件上传下载排除**：multipart 上传和二进制下载不读取 body
4. **企业级架构**：模块化、可配置、可扩展、安全脱敏

***

## 三、架构设计

### 3.1 目录结构

在 `crates/libs/cmx-api/src/middleware/` 下新建 `trace/` 目录：

```
crates/libs/cmx-api/src/middleware/trace/
├── mod.rs           # 模块入口，公共 API 导出
├── config.rs        # TraceConfig 配置结构
├── layer.rs         # 核心中间件实现
├── sanitizer.rs     # 请求体/响应体脱敏工具
└── detector.rs      # 内容类型检测（multipart、二进制、文件下载）
```

### 3.2 模块职责

| 模块             | 职责              | 关键类型/函数                                                            |
| -------------- | --------------- | ------------------------------------------------------------------ |
| `mod.rs`       | 模块入口，统一导出公共 API | `pub mod`, `pub use`                                               |
| `config.rs`    | 追踪配置定义          | `TraceConfig`, `TraceMode`                                         |
| `layer.rs`     | 中间件核心逻辑         | `trace_layer()`                                                    |

| `detector.rs`  | 内容类型判断          | `is_multipart()`, `is_binary_response()`, `is_file_download()`     |

### 3.3 核心设计：运行时日志级别感知

**关键机制**：通过 `tracing::dispatcher::get_default` 获取当前 subscriber 的 `max_level_hint()`，在中间件入口判断 DEBUG 是否启用。

```rust
fn is_debug_enabled() -> bool {
    tracing::dispatcher::get_default(|dispatch| {
        dispatch.max_level_hint()
            .map_or(false, |filter| filter >= tracing::Level::DEBUG)
    })
}
```

**原理**：

* `tracing` 的 dispatcher 维护了当前全局 subscriber

* `max_level_hint()` 返回 subscriber 允许的最大日志级别

* 此调用仅读取 thread-local，开销极低（纳秒级）

* 与 `EnvFilter` 和 `RUST_LOG` 环境变量完全一致

### 3.4 双模式执行路径

```
                    ┌─────────────────────┐
                    │   trace_layer()     │
                    │   入口中间件         │
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
                    │ is_debug_enabled()? │
                    └─────┬────────┬──────┘
                          │        │
                ┌─────────▼──┐  ┌──▼─────────────┐
                │  YES       │  │  NO             │
                │  DEBUG模式  │  │  INFO模式       │
                └─────────┬──┘  └──┬─────────────┘
                          │        │
            ┌─────────────▼──┐  ┌──▼──────────────────┐
            │ 读取请求体      │  │ 仅记录:              │
            │ 脱敏处理        │  │  - method + path     │
            │ 透传给 handler  │  │  - query params      │
            │ 读取响应体      │  │  - status code       │
            │ 脱敏 + 重建响应  │  │  - duration          │
            │ 详细日志输出     │  │ 不读取 body           │
            └────────────────┘  │ info!() 输出          │
                                └──────────────────────┘
```

## 四、详细设计

### 4.1 config.rs — 配置结构

```rust
/// 追踪模式
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum TraceMode {
    /// 轻量模式：仅记录方法、路径、查询参数、状态码、耗时
    Lightweight,
    /// 详细模式：记录完整请求头、请求体、响应体（脱敏）
    Verbose,
}

/// 追踪配置
#[derive(Clone, Debug)]
pub struct TraceConfig {
    /// 追踪模式（由日志级别决定）
    pub mode: TraceMode,
    /// 请求体最大读取字节数（仅 Verbose 模式生效）
    pub max_request_body_size: usize,
    /// 响应体最大读取字节数（仅 Verbose 模式生效）
    pub max_response_body_size: usize,
    /// 响应体预览截断长度（仅 Verbose 模式生效）
    pub max_preview_length: usize,
}

impl Default for TraceConfig {
    fn default() -> Self {
        Self {
            mode: TraceMode::Lightweight,
            max_request_body_size: 10 * 1024 * 1024,  // 10MB
            max_response_body_size: 5 * 1024 * 1024,   // 5MB
            max_preview_length: 2000,
        }
    }
}
```

### 4.2 detector.rs — 内容类型检测

```rust
/// 检测是否为 multipart/form-data 请求（文件上传）
pub fn is_multipart_request(headers: &HeaderMap) -> bool { ... }

/// 检测是否为文件下载响应
/// 判断依据：Content-Disposition: attachment 或非文本 Content-Type
pub fn is_file_download_response(headers: &HeaderMap) -> bool { ... }

/// 检测响应是否为 JSON
pub fn is_json_response(headers: &HeaderMap) -> bool { ... }
```

文件下载检测逻辑：

* `Content-Disposition` 包含 `attachment`

* Content-Type 为二进制类型：`application/octet-stream`、`application/zip`、`application/pdf`、`image/*`、`video/*`、`audio/*`

### 4.3 sanitizer.rs — 脱敏工具

从现有 `mw_trace.rs` 迁移并优化：

* `collect_headers()` — 收集并过滤敏感请求头

* `sanitize_body()` — 清理请求体

* `sanitize_json_value()` — 递归清理 JSON 敏感字段

* `sanitize_field_value()` — 单字段值脱敏

* `is_sensitive_field()` — 敏感字段名判断

这些函数逻辑不变，仅搬迁到独立模块。

### 4.4 layer.rs — 核心中间件

#### 4.4.1 入口函数

```rust
pub async fn trace_layer(req: Request<Body>, next: Next) -> Response {
    let start = Instant::now();
    let method = req.method().clone();
    let uri = req.uri().clone();
    let path = uri.path().to_string();
    let query = uri.query().map(|s| s.to_string());

    let debug_enabled = is_debug_enabled();

    if debug_enabled {
        trace_verbose(req, next, start, method, path, query).await
    } else {
        trace_lightweight(req, next, start, method, path, query).await
    }
}
```

#### 4.4.2 轻量模式（INFO 级别）

```rust
async fn trace_lightweight(
    req: Request<Body>,
    next: Next,
    start: Instant,
    method: Method,
    path: String,
    query: Option<String>,
) -> Response {
    let mut response = next.run(req).await;
    let duration = start.elapsed();
    let status = response.status();

    info!(
        target: "req_trace",
        method = %method,
        path = %path,
        query = ?query,
        status = status.as_u16(),
        duration_ms = duration.as_millis() as u64,
        "{} {} -> {} ({:?})",
        method, path, status.as_u16(), duration
    );

    if status.as_u16() >= 500 {
        warn!(
            target: "req_trace",
            "SERVER ERROR: {} {} - {}", method, path, status.as_u16()
        );
    }

    response
}
```

**性能保证**：

* ✅ 不读取请求体

* ✅ 不读取响应体

* ✅ 不做 JSON 解析

* ✅ 不做字符串分配（除格式化日志本身）

* ✅ 仅 `Instant::now()` + `elapsed()` 计时

#### 4.4.3 详细模式（DEBUG 级别）

```rust
async fn trace_verbose(
    req: Request<Body>,
    start: Instant,
    method: Method,
    path: String,
    query: Option<String>,
    next: Next,
) -> Response {
    let headers = collect_headers(req.headers());

    // 检测 multipart（文件上传）— 不读取 body
    if is_multipart_request(req.headers()) {
        let mut response = next.run(req).await;
        let duration = start.elapsed();
        let status = response.status();

        debug!(
            target: "req_trace",
            "REQUEST [MULTIPART - BODY SKIPPED] {} {}\n\
             query: {:?}\n\
             headers: {:?}\n\
             RESPONSE: {} ({:?})",
            method, path, query, headers, status.as_u16(), duration
        );
        return response;
    }

    // 读取并脱敏请求体
    let (parts, body) = req.into_parts();
    let body_bytes = axum::body::to_bytes(body, 10 * 1024 * 1024)
        .await
        .map(|b| b.to_vec())
        .unwrap_or_default();
    let req_body_preview = sanitize_body(&body_bytes);

    let new_req = Request::from_parts(parts, Body::from(body_bytes.clone()));
    let mut response = next.run(new_req).await;
    let duration = start.elapsed();
    let status = response.status();

    // 检测文件下载 — 不读取响应体
    if is_file_download_response(response.headers()) {
        debug!(
            target: "req_trace",
            "REQUEST {} {}\n\
             query: {:?}\n\
             headers: {:?}\n\
             body: {}\n\
             RESPONSE: {} [FILE DOWNLOAD - BODY SKIPPED] ({:?})",
            method, path, query, headers, req_body_preview,
            status.as_u16(), duration
        );
        return response;
    }

    // 读取并脱敏响应体（仅 JSON）
    let resp_body_preview = extract_response_body(&mut response).await;

    debug!(
        target: "req_trace",
        "REQUEST {} {}\n\
         query: {:?}\n\
         headers: {:?}\n\
         body: {}\n\
         RESPONSE: {} body: {} ({:?})",
        method, path, query, headers, req_body_preview,
        status.as_u16(), resp_body_preview, duration
    );

    if status.as_u16() >= 500 {
        warn!(
            target: "req_trace",
            "SERVER ERROR: {} {} - {}", method, path, status.as_u16()
        );
    }

    response
}
```

## 六、性能对比

### 6.1 INFO 模式（生产环境，RUST\_LOG=info 或 warn）

| 操作      | 旧 mw\_trace | 新 trace\_layer |
| ------- | ----------- | -------------- |
| 读取请求体   | ✅ 最大 10MB   | ❌ 不读取          |
| 读取响应体   | ✅ 最大 5MB    | ❌ 不读取          |
| JSON 解析 | ✅ 1-2 次     | ❌ 不执行          |
| 字符串分配   | ✅ 大量        | ❌ 仅日志格式化       |
| 计时      | ✅           | ✅              |
| 状态码检查   | ✅           | ✅              |

**INFO 模式零额外开销**：不读取 body、不解析 JSON、不分配脱敏字符串。

### 6.2 DEBUG 模式（开发调试，RUST\_LOG=debug）

| 操作      | 旧 mw\_trace | 新 trace\_layer |
| ------- | ----------- | -------------- |
| 读取请求体   | ✅           | ✅              |
| 读取响应体   | ✅           | ✅（仅 JSON）      |
| 文件下载排除  | ❌           | ✅              |
| JSON 解析 | ✅           | ✅              |
| 脱敏处理    | ✅           | ✅（复用逻辑）        |

DEBUG 模式功能与旧版一致，新增了文件下载排除能力。

## 八、注意事项

1. **不修改 mw\_trace.rs**：旧文件完整保留，仅停止使用
2. **日志 target 保持一致**：继续使用 `"req_trace"` 作为 target，兼容现有日志过滤配置
3. **tracing-log 桥接**：web-server 已启用 `tracing-log` feature，确保 `log` crate 日志也被 tracing 捕获
4. **`tracing::dispatcher::get_default`** **线程安全**：该函数读取 thread-local，在 tokio 异步环境中安全使用
5. **环境变量兼容**：所有现有 `RUST_LOG` 配置（docker-compose、Dockerfile、K8s）无需修改
