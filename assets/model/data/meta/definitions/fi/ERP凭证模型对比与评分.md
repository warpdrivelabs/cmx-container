> 对象：`fi/` 目录下四套主流 ERP 的会计凭证元数据（DCT 数据字典 + DOC 单据），外加自研 `fi/gl` 一套作参照。

## 二、核心差异：多维核算怎么实现

这是凭证模型的灵魂，四套走了三条路：

| 模型 | 方式 | 特点 | 比喻 |
|---|---|---|---|
| **SAP FI** | **固定专用字段**：利润中心/段/业务范围/功能范围/订单/WBS 各占一个独立列 | 维度语义明确、独立可查；但维度写死，加新维度需改结构 | 每个维度一个专用插槽，插槽固定 |
| **Oracle EBS** | **弹性域(Flexfield) + 代码组合(CCID)**：科目本身是多段组合，段可配置 | 加维度=加一个段，不改表结构；但多维藏在 CCID 里，单独分析需解析 | 维度"长在科目里" |
| **用友 / 金蝶** | **辅助核算 / 核算维度**：科目挂载维度，分录按需录入 | 加维度=加数据(辅助核算项)，不改结构；概念比弹性域简单 | 科目"按需挂维度" |

末层（行/分录）维度字段：
- **SAP**：16 个专列 —— `gl_account / posting_key / profit_center / cost_center / segment / business_area / functional_area / trading_partner / internal_order / wbs_element / partner / special_gl_ind / tax_code …`
- **Oracle EBS**：10 个 —— `code_combination(CCID) + company/cost_center/account/product/intercompany 五个段展开 + supplier/customer/tax_rate`
- **用友**：14 个 —— `account_subject + direction + 7 个辅助核算(部门/个人/客户/供应商/项目/存货/自定义) + cashflow_item / settlement_method / currency / tax_rate`
- **金蝶**：14 个 —— `account + direction + 7 个核算项目(部门/职员/客户/供应商/物料/项目/自定义) + cashflow_item / settlement_method / currency / tax_rate`

## 三、逐套评价

### ① SAP FI —— 工业级标准，重而全
**优势**
- 维度最丰富且语义明确（行项目 16 专列），每个维度独立可查，无需解析。
- 并行会计最强：分类账(0L/L1/L2) + 7 个多币种度量(本位币/集团币/第二三本位币)，天生支持 IFRS/CAS/税务并行出表。
- 凭证拆分：可按利润中心/段强制平衡，颗粒度细。
- 字典最全(31)，含记账码、特别总账标识、字段状态组等精细控制。

**劣势**
- 固定字段 = 不灵活：加全新分析维度需扩展数据结构，业务不能自助。
- 配置重（公司代码/控制范围/科目表层层分配），中小企业用不满。

### ② Oracle EBS —— 弹性域优雅，但科目即组合
**优势**
- 弹性域最优雅：段数与含义实施时定义，扩展维度只加一个段，不改表结构 —— 比 SAP 固定字段灵活。
- CCID 设计精巧：合法段值组合预校验，凭证行只引一个 CCID，组合合法 + 存储压缩。
- 三层凭证（批→头→行）：批量过账、按来源冻结控制最强，适合大批量自动化。
- 多币种度量 10 个（输入币/本币/集团币借贷分列），并行评估强。

**劣势**
- 多维藏在 CCID 内：行项目直接维度仅 10 个，按某段单独分析要先解析 CCID，不如 SAP 专列直观。
- 弹性域配置门槛高（值集/段/CCID 三层概念实施重）。

### ③ 用友 —— 辅助核算务实，本土最佳实践
**优势**
- 辅助核算最贴合中国会计实务：科目挂部门/个人/客户/供应商/项目/存货/自定义，加维度不改表结构，灵活度接近 EBS 弹性域但概念更简单。
- 凭证字号 + 四签字（制单/审核/记账/出纳）：还原中国凭证完整内控流程，SAP/EBS 没有。
- 现金流量项目内建，直接支持现金流量表。

**劣势**
- 多币种最弱：仅 6 个多币种度量；并行会计（多准则分类账）支持弱 —— 与 SAP/EBS 的代差。
- 维度语义不如 SAP 专列：7 个辅助核算字段都叫 aux_*，靠类型区分，分析多一层映射。
- 缺记账码、字段状态组这类精细控制。

### ④ 金蝶 —— 与用友同源，云星空更进一步
**优势**
- 核算维度可配置（云星空弹性域）：本质同用友辅助核算，但做成可配置弹性域，扩展性略优于用友。
- 同样有凭证字、四签字、现金流量项目，本土内控完整。
- 物料作为独立核算维度，制造业场景略强于用友。

**劣势**
- 结构上与用友几乎同构（2 层 + 14 维度 + 6 多币种度量），未拉开本质差距。
- 多币种/并行会计同样弱于 SAP/EBS。
- "核算维度"与用友"辅助核算"换名而已，实施概念雷同。

## 四、综合打分（10 分制）

| 评价维度 | 权重 | SAP FI | Oracle EBS | 用友 | 金蝶 |
|---|---|---|---|---|---|
| 维度丰富度 / 分析力 | 20% | 9.5 | 8.5 | 7.5 | 7.5 |
| 扩展灵活性（加新维度） | 20% | 6.0 | 9.0 | 8.5 | 8.5 |
| 多币种 / 并行会计 | 15% | 9.5 | 9.0 | 6.0 | 6.0 |
| 本土合规 / 内控（签字/现金流） | 15% | 6.5 | 6.0 | 9.0 | 9.0 |
| 架构精巧度 | 20% | 8.5 | 9.0 | 7.5 | 7.5 |
| 易用 / 实施成本（越易越高） | 10% | 5.5 | 5.5 | 8.0 | 8.0 |
| **加权综合** | | **8.0** | **8.1** | **7.6** | **7.6** |

### 排名
```
🥇 Oracle EBS  8.1   架构最优雅：弹性域扩展性 + 三层批控制 + 多币种均衡领先，短板最少
🥈 SAP FI      8.0   维度与并行会计最强，但固定字段灵活性短板，实施最重
🥉 用友        7.6   本土实务最佳，辅助核算务实，多币种/并行是代差
🥉 金蝶        7.6   与用友同源，云星空弹性域略优，本质差距不大
```

> EBS 综合略胜 SAP，是因为它用弹性域在"扩展灵活性"上兼顾了 SAP 的分析力和用友的灵活性，且三层结构 + 多币种均不弱，**短板最少**。SAP 单项天花板更高（分析力、并行会计），但固定字段灵活性和实施成本拖了综合分。

## 五、选型建议

| 场景 | 推荐 | 理由 |
|---|---|---|
| 跨国集团、多准则并行出表、强分析 | **SAP FI** | 维度专列 + 分类账并行 + 凭证拆分无对手 |
| 大型集团、灵活扩维 + 大批量自动化 | **Oracle EBS** | 弹性域可配置 + 三层批过账 |
| 中国企业、重内控合规、性价比 | **用友 / 金蝶** | 辅助核算贴合实务，签字流程合规，实施轻 |
| 制造业、存货维度多 | **金蝶**（略优用友） | 物料核算维度 + 云星空弹性域 |

**核心权衡**：SAP/EBS 是"强但重"（分析力与并行会计天花板高，实施成本高）；用友/金蝶是"轻但浅"（本土合规与易用性好，多币种/并行会计有代差）。

## 六、对自研模型（fi/gl）的启示

自研 `fi/gl`（3 层：头→分录→明细，13/4/2 字典）的设计取舍可参考：
1. **多维载体选型**：若面向中国客户为主，走用友/金蝶的"辅助核算/核算维度"模式（科目挂载、加维度不改结构）实施最轻；若要对标 SAP 的强分析，再补利润中心/段等专列。
2. **并行会计是分水岭**：要支持多准则（IFRS/CAS/税务）出表，必须像 SAP/EBS 那样引入分类账维度 + 多币种度量列；这是用友/金蝶的明显短板，自研可据目标客户决定是否补齐。
3. **本土内控别丢**：凭证字 + 四签字 + 现金流量项目是中国财务刚需，用友/金蝶都有，自研应保留。
4. **CCID/弹性域慎用**：EBS 的 CCID 优雅但实施重、分析需解析，除非客户需要高度自定义维度组合，否则"专列 + 辅助核算"组合的性价比更高。

## 七、真实对齐度优化（2026-06-16，按 codex 偏差反馈从高到中处理）

四套模型经偏差核对后做了如下结构性/命名性对齐（保留"统一语义分析模型"可对比性的前提下，提升与真实 ERP 物理表的吻合度）：

### 高优先级
1. **动态维度 → 真实结构**
   - **用友**：分录上 7 个固定 `aux_*` 列删除，改为 **L3 辅助核算明细子表 `yy_gl_voucher_entry_aux`（分录 1:N）**，每个辅助项一行 `{aux_type 辅助类型, aux_value 取值}` —— 还原 NC `gl_freevalue`/U8 辅助核算的动态多辅助。
   - **金蝶**：分录上 7 个固定 `acc_*` 列删除，改为 **L3 核算项目明细子表 `kd_gl_voucher_entry_item`（分录 1:N）**，`{acc_type 核算维度, acc_value 取值}` —— 还原 K/3 t_VoucherGroup / 云星空可配置弹性域。
   - **EBS**：凭证行上 5 个 `*_segment` 列删除，行只留 `code_combination_id(CCID)` —— 真实段在 `GL_CODE_COMBINATIONS`，段数由 Accounting Flexfield 配置决定，按段分析 JOIN `code_combination` 字典。
2. **physicalField 真实技术字段名映射**：四套字段补 `physicalField`（语义 id 不变，集成按此对接）。SAP `BUKRS/HKONT/DMBTR/SHKZG…`；EBS `LEDGER_ID/CODE_COMBINATION_ID/ACCOUNTED_DR…`；用友 `pk_accasoa/debitamount/creditamount…`；金蝶 `FAccountID/FDebit/FCredit/FDC…`。

### 中优先级
3. **SAP 拆分 + 归位**：item `tableAlias` 改为纯 `BSEG`（remark 注明 S/4 对应 ACDOCA 通用日记账，非同一物理表）；`ledger_id` 从凭证头下沉到行项目（S/4 ledger 语义在 ACDOCA 行层）；新增 `document_no(BELNR)`，remark 声明真实复合主键 `BUKRS+BELNR+GJAHR`（BELNR 来自 FI number range）。
4. **借贷金额去冗余**：SAP 删 `debit_amount/credit_amount`（真实是金额 WRBTR/DMBTR + 借贷标志 SHKZG）；EBS 删额外 `debit_amount/credit_amount`，上卷改用真实 `accounted_dr/accounted_cr`（+ 补 `gl_sl_link_table` 子分类账关联键）；用友/金蝶 `direction` 标 `derived`（真实由借/贷列定方向）。
5. **汇总金额与状态机贴近真实**：四套凭证头 `total_*` 标 `derived`（SAP 真实 BKPF 无此列）；EBS `running_total_*` 标 `systemMaintained`（Oracle 系统维护，真实存在）；状态机补真实状态码 —— SAP 加 `held` + BSTAT；EBS STATUS 补 `processing(I)`/`error(E)` 单字符码、注明 GL_JE_ACTION_LOG 动作日志、SLA(XLA_AE_HEADERS/LINES)/GL_IMPORT_REFERENCES 来源链路。

### 优化后结构变化
| 模型 | 优化前层级 | 优化后层级 | 关键变化 |
|---|---|---|---|
| SAP | 2 (头→行) | 2 (头→行) | item 纯 BSEG、ledger 下沉、加 BELNR、删借贷冗余列 |
| EBS | 3 (批→头→行) | 3 (批→头→行) | 行删 5 段列(回收进 CCID)、删借贷冗余、STATUS 真实码 |
| **用友** | 2 (头→分录) | **3 (头→分录→辅助明细)** | 辅助核算改 1:N 子表 |
| **金蝶** | 2 (头→分录) | **3 (头→分录→核算项目明细)** | 核算项目改 1:N 子表 |

### 仍未做（codex 提的"中"项，工作量大，仅 remark 注明未建表）
- EBS 完整 SLA 链路（XLA_AE_HEADERS/XLA_AE_LINES、GL_IMPORT_REFERENCES）与 GL_JE_ACTION_LOG 实体表 —— 偏子分类账，本轮在 remark 注明，未单独建表。
- DCT 字典层的 physicalField（主数据物理表名如 SKA1/T001）—— 本轮重点在 DOC 凭证字段，DCT 仅 tableName 承载。
