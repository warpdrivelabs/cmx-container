1 头号发现：加固成果全部未提交，HEAD 未动

v5 把 .env 出库、CI 门禁、工具链锁定、IAM store 下沉都记为「闭环」。逐项核对 git 状态：这些改动没有一个进入版本库。

🔴 仓库当前 HEAD = b6729ee8（DCT/DOC 重构），与 v4 评估时同一提交。v5 描述的全部加固都在工作区悬空。
v5 记为「闭环」的成果实际 git 状态后果
.env 含 NACOS 凭据出库 仅暂存 D .env 已 staged 但未 commit；git ls-tree HEAD 仍列出 .env 凭据仍在 HEAD 树内与历史中，泄露面未收窄
CI 门禁 .gitlab-ci.yml 未追踪 ?? GitLab 按提交里的 CI 文件跑流水线——文件不在提交里，门禁跑在虚空
工具链锁定 rust-toolchain.toml 未追踪 ?? 他人检出仍用各自本地工具链，锁定不生效
.env.example 模板 未追踪 ?? 新人无占位符模板参照
IAM store 下沉 api_key/ oauth_client/ 未追踪 ??（整目录新增，未 add） 见下方「编译一致性」——这是最危险的一条
handler 去 SQL、README、四处文档化标注等 已改未暂存 共 19 个 M 文件 改动真实存在，但未纳入版本，随时可能被覆盖/丢失
🔴 编译一致性缺口（本轮最实质的技术风险）

被改的 api_key_handler.rs 第 15 行已经 use cmx_iam::api_key::store;，但 HEAD 版本的 cmx-iam/src/lib.rs 并未声明 pub mod api_key。当前工作区之所以能 cargo check ✓，完全依赖两个未被 git 追踪的新目录（api_key/、oauth_client/）+ 工作区版 lib.rs 的模块声明。

这意味着：① 任何人干净检出 HEAD 得到的是「.env 仍在、无 CI」的旧仓库；② 若这两个未追踪目录被 git clean 或误删，工作区立刻编译失败，而 git 无法恢复它们（从未纳入版本）。成果的正确性正悬挂在未追踪文件上。

✅ 好消息：这一切一次提交即可闭环

工作区里的东西是对的、也通过了构建校验。要做的只是把它真正提交进仓库（git add -A 覆盖新目录 → commit）。提交后，v5 描述的「战略债闭环」才名副其实，安全/工程化两项立刻回到 88/91 区间。这是本报告第一优先级、也是唯一的紧急项。
